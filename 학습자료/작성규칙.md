# 작성규칙

교재 원고, 노트북의 설명 셀, 실습 재료의 문장에 모두 적용한다.
상태: 2판(2026-11-26, 개념 중심 교재). 1장 시범 검토 후 확정한다. 1판(일자별 복습 교재)에서 바뀐 규칙은 4절과 7절에 있다.

## 1. 기준

1. 생성형 AI의 용어와 원리가 잘 설명되어야 한다. 원본 강의안은 다룰 주제의 목록으로만 쓴다.
2. 원본의 절 순서, 예제, 실습, 재료를 옮기지 않는다. 원본의 설명이 틀렸으면 고쳐서 쓴다.
3. 확신할 수 없는 사실은 공식 문서로 확인한다. 확인하지 못하면 쓰지 않는다.
4. 실행 결과는 실제로 실행해 얻은 것만 싣는다.

## 2. 개념을 설명하는 순서

새 개념은 다음 순서로 쓴다. 짧은 개념은 한 문단에 다 담아도 된다.

1. **정의**: 한 문장으로 무엇인지 말한다.
2. **필요성**: 왜 알아야 하는지, 모르면 어떤 문제가 생기는지 쓴다.
3. **원리**: 어떻게 동작하는지 쓴다. 필요하면 도식이나 표를 쓴다. 동작을 말하는 데서 멈추지 않고 그렇게 동작하는 메커니즘까지 쓴다. 예: "한국어는 토큰이 더 듭니다"에서 멈추지 않고, BPE가 학습 데이터에 자주 나온 글자 조합을 묶기 때문이라는 것을 작은 예로 보여 준다. 수식은 softmax와 temperature처럼 꼭 필요한 곳에만 숫자 예로 쓴다.
4. **예**: 짧은 코드나 숫자로 보여 준다.
5. **주의**: 흔한 오해, 헷갈리기 쉬운 다른 개념과의 차이를 쓴다.

앞에서 설명하지 않은 용어를 쓰지 않는다. 뒤에서 설명할 용어를 먼저 써야 하면 "(3절에서 설명합니다)"처럼 위치를 알린다.

이 규칙은 정규식으로 검사할 수 없다. 장을 다 쓴 뒤 처음부터 읽으면서 다음을 확인한다.

- 용어집에 있는 용어가 장에서 처음 나오는 곳에 정의가 있거나, 설명하는 위치를 알리는 말이 있다. 표, 목록, 그림 설명에 처음 나오는 경우도 같다. 예: thinking, 최대 출력 토큰, 모델 등급.
- 예제 코드에 처음 나오는 인자와 값은 그 예제보다 앞에서 설명한다. 공통 호출 함수(`llm.py`)가 바꿔서 돌려주는 값은 API의 어떤 값에 해당하는지도 적는다. 예: `max_tokens=8000`, 종료 이유 `end`(Anthropic의 `end_turn`, OpenAI 호환의 `stop`).
- 프롬프트, 재료, 코드 주석에만 있는 낱말을 본문에서 쓰면 처음 쓸 때 뜻을 한 문장으로 적는다. 예: 프롬프트의 "칸", 재료 이름의 "받아쓰기".
- 줄여 부르는 말은 처음 쓸 때 무엇을 줄인 말인지 적는다. 예: 체인의 첫째 단계를 "1단"으로 부른다.
- 학계나 공식 문서에서 쓰는 이름이 따로 있는 개념은 그 이름을 함께 적는다. 독자가 다른 자료에서 찾아볼 때 쓰는 이름이다. 예: instruction tuning, RLHF.

## 3. 문장

- 합니다체로 쓴다. 독자를 가리킬 때는 주어를 생략하거나 "여러분"을 쓴다.
- 한 문장에는 한 가지 내용만 담는다. 길어지면 나눈다.
- 주어와 서술어를 갖춘 문장으로 쓴다. 슬라이드식 명사 나열("요청 → 응답 → 검사")은 표나 목록에만 쓴다.
- 능동문을 쓴다. "~되어집니다", "~하게 됩니다"를 피한다.
- 수치에는 단위와 조건을 붙인다. "입력 148토큰(시스템 프롬프트 포함)".
- 강조는 꼭 필요한 곳에만 굵게 쓴다. 한 문단에 한 번을 넘기지 않는다.

| 요청을 보내는 주체로 씀 | 요청 여러 개가 다시 보내면 | 요청 여러 개를 다시 보내면 | `요청[^.]{0,8}(개|들)[이가] [^.]{0,20}보내면` |
| 정의 없는 지어낸 말 "서비스 모델" | API로 서비스 모델을 호출합니다 | API로 모델을 호출합니다, API로 제공되는 모델 | `서비스 모델` |
| 등급 이름과 겹치는 "기본 모델" | Anthropic 기본 모델 | `llm.py`가 쓰는 Anthropic 모델 | `Anthropic 기본 모델|API의 기본 모델` |
| 상한이 "채워진다" | 상한은 조금씩 채워지므로 | 남은 허용량이 조금씩 다시 채워지므로 | `상한[은는이가]? [^.]{0,30}채워` |
| 내용 없이 앞 장을 가리킴 3 | 1장의 반복대로 | 무엇을 반복하는지 쓰고 끝에 "(1장)" | `의 반복대로` |
| 없는 제품 이름 | OpenAI 호환 SDK | OpenAI SDK(OpenAI 호환 API에 연결) | `OpenAI 호환 SDK` |
| 가명을 "토큰"이라고 부름 | `<사번_2>` 같은 토큰, 토큰과 원래 값의 짝 | 가명, 가명과 원래 값의 짝. 토큰은 LLM의 토큰만 가리킨다 | `토큰과 원래 값|같은 토큰으로 바꿔|응답의 토큰을|토큰만 (있|회사)|토큰 형식의 글|같은 값은 토큰` |
| 주어가 맞지 않는 "권한이 유출" | 권한이 유출되기 쉬운 곳 | 권한 밖의 내용이 새어 나가기 쉬운 곳 | `권한이 [^.]{0,20}유출` |
| 내용 없이 앞을 가리킴 4 | 1장에서 본 대로, 3장에서 설명한 대로 | 내용을 쓰고 끝에 "(1장)"처럼 위치만 적는다 | `(장|절)에서 (본|설명한) 대로` |
| 사물을 사람처럼 씀 3 | 요청에 함께 갑니다, 요청이 로그를 읽고 | 요청에 들어갑니다, 별도 요청에 로그를 넣고 | `함께 (갑니다|가고|가는|갔)|요청이 [^.]{0,8}읽고` |
| 피동 "~게 되면" | 또 입력하게 되면 | 또 입력해야 하면 | `(?<!어떻)게 되면` |
| 비유 "이기다" | deny가 늘 이기고 | deny가 늘 우선하고 | `이기고|이깁니다|이긴다` |
| 시점이 두 뜻으로 읽히는 "뒤에서" | 분류 모델이 뒤에서 검사합니다 | 실행 전에 검사합니다 | `뒤에서 (검사|확인)` |
| 방향으로 빗댄 분류 | 같은 쪽의 현상 | 긴 컨텍스트에서 정보를 덜 정확히 쓰는 현상 | `같은 쪽의` |

"달라집니다."로 끝나는 문장은 무엇이 어떻게 달라지는지를 같은 문장이나 바로 다음 문장에 써야 한다. 검사는 문단의 마지막 문장이 "달라집니다."로 끝나는 경우만 잡는다.

## 4. 구조와 그림

독자에는 생성형 AI를 처음 배우는 사람이 있다. 그래서 이유를 설명하는 문장은 줄이지 않는다. 분량은 문장을 조각내서가 아니라 구조로 줄인다.

- 절 첫머리에 `:::요점` 상자로 그 절의 결론을 한두 문장 적는다. 요점은 본문의 문장을 그대로 옮기지 않고 절 전체를 줄여 쓴다. 요점과 거의 같은 문장이 본문에 또 나오면 본문 쪽을 고친다(테스트가 검사한다).
- 장은 제목, "강의 N일차 파트 M에 해당" 한 줄, `## 학습 목표`로 시작한다. 목표는 이 장을 마치면 할 수 있는 것으로 3~5개 쓰고, "~할 수 있습니다"로 끝낸다. 독자가 실제로 가질 법한 궁금증을 목표 문장에 넣는다. 예: "같은 질문에 응답이 매번 다른 이유를 확률 분포와 샘플링으로 설명할 수 있습니다." 본문은 이 목표의 순서대로 쓴다. 자가점검에는 목표마다 문제를 하나 이상 둔다.
- 장의 끝에는 개념 확인 실습 안내와 자가점검을 둔다. 핵심 정리는 두지 않는다. 절마다 있는 요점과 겹치기 때문이다(2026-11-27 결정).
- 한 가지 사실은 한 곳에서 설명한다. 요점은 절의 결론, 본문은 이유와 원리, 그림은 과정과 구조를 맡고, 서로 같은 문장을 되풀이하지 않는다. 그림 설명(figcaption)은 한 문장으로 쓴다.
- 그림으로 보여 줄 수 있는 과정, 구조, 비교, 분포는 그림으로 그린다. 그림이 보여 주는 내용을 본문에서 다시 풀어 쓰지 않는다.
- 실행 결과가 PC, 라이브러리 버전, 실행할 때마다 다를 수 있다는 단서는 장 첫머리의 예제 안내에 한 번만 쓴다.
- 예제 코드의 인자 설명은 코드 주석으로 쓴다. 예제 상자의 글에는 무엇을 보는지만 쓴다.
- 검토 지적을 반영할 때는 문장을 더하지 않고 기존 문장을 바꿔 쓴다. 반영한 뒤 그 절이 길어졌으면 다른 문장을 줄인다.
- 본문에 원본 쪽수(`{원본 p.xx}`), 원본 대응표, 변경 기록을 두지 않는다. 원본과의 대응은 `작업/원본_대응표.md`에 적는다.
- 장 하나에 예제는 2~4개를 넘기지 않는다. 원리 설명이 본문의 중심이고, 예제는 설명을 확인하는 데 쓴다.
- 한 절은 한 가지 주제만 다룬다. 본문이 1,500자를 넘으면 소절로 나눈다.
- 나란히 놓이는 항목이 셋 이상이면 문단으로 쓰지 않고 목록이나 표로 쓴다. 목록의 각 항목도 문장으로 쓴다.
- 표는 여러 항목을 같은 기준으로 가로로 비교할 때만 쓴다. 다음에 해당하면 표로 쓰지 않고 목록으로 쓴다: 조건에 따라 하나를 고르는 내용, 칸에 설명 문장이 길게 들어가는 내용, 열 이름을 "하는 일", "쓰는 경우"처럼 지어내야 하는 내용. 항목이 둘뿐이어도 두 가지 이상의 기준으로 맞대어 비교하면 표로 쓴다(예: 컨텍스트 윈도우와 최대 출력 토큰). 파일 목록, 코드와 뜻, 오류 문구와 조치처럼 찾아보는 용도의 표는 그대로 쓴다.
- 조건에 따라 고르는 내용은 "~이면 ~합니다"처럼 조건을 문장 앞에 두고, 조건은 한 문장에 하나만 쓴다. "A는 없고 B가 있으면"처럼 조건 두 개를 이어 붙이지 않는다.
- 버전과 확인 날짜는 문장 중간에 끼우지 않는다. 문장 끝이나 절 끝의 보충 상자에 모아 적는다.

그림은 글로 쓰면 독자가 머릿속에서 직접 그려야 하는 내용에 쓴다.

| 그림으로 그린다 | 글로 쓴다 |
| --- | --- |
| 시간 순서(재시도, 대화가 쌓이는 과정) | 정의 |
| 포함 관계(전체와 부분, 상한) | 이유와 근거 |
| 갈림(조건에 따라 다르게 처리) | 주의점과 예외 |
| 여러 단계를 지나는 흐름 | 수치의 해석 |

- 그림에는 실제 예제의 숫자를 쓴다.
- 그림만 보고도 알 수 있게 `aria-label`과 그림 설명(`figcaption`)을 문장으로 적는다. 그림에만 있고 본문에 없는 내용은 두지 않는다.
- 색은 교재의 색 변수(`var(--teal)` 등)를 써서 어두운 화면에서도 보이게 한다. 원본 강의안의 이미지는 넣지 않는다.

## 5. 삭제하는 것

- 강의 진행 안내: 일정, 제출 방법, 키 배부와 회수, 화면 조작 순서 중 교재 독자에게 필요 없는 것.
- 내용 없는 연결 문장: "이제 ~를 알아보겠습니다", "앞에서 본 것처럼".
- 같은 내용의 반복: 슬라이드 머리말·꼬리말, "(계속)" 장마다 되풀이되는 문구.
- 근거 없는 수식어: "매우 중요한", "강력한", "쉽게".
- 코드 주석 중 코드가 이미 말하는 것을 되풀이하는 것.

## 6. 용어와 표기

- 용어는 `용어집.md`의 채택 표기만 쓴다. 새 용어가 필요하면 용어집에 먼저 넣는다.

### 용어를 고르는 기준

독자는 소프트웨어 엔지니어와 공학 엔지니어다. 엔지니어가 문서와 대화에서 일반적으로 쓰는 용어를 쓴다.

- 우리말로 풀어 새로 만든 말을 쓰지 않는다. 공식 문서와 현업에서 쓰는 말을 쓴다. 예: "시간 제한"이 아니라 "타임아웃", "가짜 호출"이 아니라 "mock 호출".
- 한글로 굳어진 표기가 없으면 원어를 그대로 쓴다. 예: thinking, temperature, mock.
- 다른 뜻으로 이미 쓰이는 말을 번역어로 쓰지 않는다. 예: thinking을 "추론"으로 옮기지 않는다. 엔지니어에게 추론은 inference다.
- 표준 용어가 처음 접하는 사람에게 낯설면 용어를 바꾸지 않고, 처음 나올 때 한 문장으로 뜻을 설명한다.
- 한 낱말이 두 가지로 읽히면 다른 낱말을 쓴다. 예: 코드를 "쓴다"는 작성한다는 뜻인지 사용한다는 뜻인지 알 수 없다. 작성은 "작성하다", 사용은 "쓰다"로 구분한다.
- 구어체 낱말 대신 기술 문서에서 쓰는 낱말을 쓴다. 예: 재다 → 측정하다, 거르다 → 필터링하다, 다시 보내다 → 재시도하다(실패한 요청의 경우).
- 사용자가 유지하기로 정한 말: 대화 이력, 입력 검사, 응답 검사, 표본.

- 영어에서 온 용어는 처음 나올 때 한글(영문)로 쓰고 이후에는 한글만 쓴다. 예: 컨텍스트 윈도우(context window). 채택 표기가 이미 원어(Skill, thinking)이면 괄호를 붙이지 않는다(2026-11-27 사용자 지적).
- 약어는 장에서 처음 나오는 곳에 "약어(원어)"로 쓰고, 그 약어를 정의하는 절에서도 한 번 더 "약어(원어)"로 쓴다. 그 밖의 곳에서는 약어만 쓴다. 예: SFT(supervised fine-tuning). 학습 목표와 요점도 "처음"에 들어간다. 장마다 따로 읽는 독자가 있으므로 장마다 다시 적용한다. 다른 장을 이름으로 가리키는 곳(5장 "LLM API")은 세지 않는다. `tests/test_style.py`가 용어집의 약어로 검사한다(2026-11-27 사용자 지적).
- API가 돌려주는 값이나 요청에 넣는 값을 말할 때는 우리말 풀이만 쓰지 않고 원문 값을 함께 적는다. 예: "종료 이유가 `max_tokens`(OpenAI 호환은 `length`)로 나옵니다". 독자가 코드와 로그에서 실제로 보는 것은 원문 값이다.
- 그림에서 "이 선", "여기"처럼 가리키는 말을 쓰지 않는다. 색이나 모양, 이름으로 무엇인지 적는다. 예: "주황색 점선(max_tokens 한도)".
- 그림의 글자는 상자 안쪽에 좌우 12px 이상 여백이 남게 한다. 용어를 바꿔 글자가 길어지면 상자도 넓힌다.
- 코드에 실제로 쓰는 이름은 코드 서식으로 쓴다. 예: `max_tokens`, `stop_reason`. 조사는 붙여 쓴다. 예: `messages`에 넣습니다.
- 한글과 영문, 숫자 사이에 불필요한 공백을 넣지 않는다. 원본의 "API 를", "1-1 에서"는 "API를", "1-1에서"로 쓴다. 코드의 주석, docstring, 출력 문구, 예외 메시지에도 적용한다. 단위도 붙여 쓴다: `print(n, '건')`은 "8 건"으로 출력되므로 `print(f'{n:,}건')`으로 쓴다. 변수 뒤에는 받침에 따라 달라지는 조사(`{name}가`)를 고정하지 않고, 조사가 필요 없는 말로 쓴다(`{name}의 합계`). 검사는 `tests/test_style.py`의 `spaced()`가 한다. 프롬프트와 재료 안의 표기는 모델 입력이므로 바꾸지 않는다.
- 숫자는 아라비아 숫자로 쓰고 천 단위에 쉼표를 넣는다. 단위는 붙여 쓴다. 예: 1,024토큰, 30초, 120건.
- 낫표(「」)와 가운뎃점 나열(A · B · C)은 쓰지 않는다. 인용은 큰따옴표, 나열은 쉼표를 쓴다. 예제 코드의 출력 문구, 주석, 예외 메시지에도 적용한다(`tests/test_style.py`의 코드 검사). 재료와 프롬프트에 든 가운뎃점은 모델 입력이므로 바꾸지 않는다.
- 모델 이름, 요금, API 파라미터처럼 바뀌는 사실에는 확인한 날짜를 적는다.

## 7. 코드

- 예제의 코드는 원고의 `:::예제` 상자 안에 실행 가능한 전체 코드로 쓴다. 이 코드가 장 노트북의 코드 셀이 된다. 줄여 쓰지 않는다.
- 예제와 실습 상자 안에는 코드 앞에 한두 문장으로 무엇을 보여 주는지, 무엇을 눈여겨볼지 쓴다. 이 글이 장 노트북의 안내 셀이 된다. 노트북에는 본문이 없으므로 이 글만 읽고도 무엇을 실행하는지 알 수 있어야 한다.
- 실습의 빈칸 코드는 `:::실습` 상자에, 풀이 코드는 그 안의 `:::풀이` 상자에 쓴다. 풀이는 HTML에만 접혀 실린다.
- 실행 결과는 원고에 적지 않는다. 빌드가 풀이 노트북을 실행한 사본에서 가져온다.
- 예제 하나는 한 가지만 보여 준다.
- 변수와 함수 이름은 뜻이 드러나는 영어로 쓴다. 한 글자 이름(`r`, `x`, `c`)은 쓰지 않는다.
- 주석과 출력 문구는 한국어로 쓴다. 주석은 "왜"를 적는다.
- 예제는 직접 실행해야 납득되는 현상만 보여 준다. 예: 같은 프롬프트에 응답이 매번 다른 것, 토큰 수, 유사도 숫자. 글로 설명해도 충분한 내용은 예제로 만들지 않는다.
- 예제 하나는 코드 15줄 안팎의 셀 하나로 쓴다. 한 예제에 세부 셀을 여러 개 잇지 않는다.
- 예제 코드는 공통 호출 함수(`llm.py`)로만 작성한다. Anthropic SDK와 OpenAI 호환 SDK를 직접 호출하는 코드는 5장 "LLM API"에서 한 번만 나란히 싣는다. 한쪽에만 있는 기능은 그렇게 표시한다.
- 재시도, 배치 처리, 저장처럼 LLM을 시스템에 붙이는 구현 코드는 본문 예제에 두지 않고 실습에 둔다. 본문에는 LLM을 쓰면 왜 그 문제가 생기는지만 쓴다.
- 키, 사내 주소, 사내 모델 이름은 코드에 적지 않는다. 환경 변수에서 읽는다.

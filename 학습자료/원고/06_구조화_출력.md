# 6장 구조화 출력

강의 2일차 파트 2에 해당합니다.

모델의 응답을 사람이 읽을 때는 문장이면 충분합니다. 응답에서 값을 꺼내 조건문에 쓰거나 결과 테이블에 저장하려면, 모델이 정해진 구조의 데이터로 응답하게 하고 코드가 그 데이터를 파싱해야 합니다. 이 장은 JSON(JavaScript Object Notation) 스키마로 구조를 정하는 방법, 구조화 출력이 그 구조를 보장하는 원리, 구조화 출력이 보장하지 않는 것, 그리고 여러 건의 결과를 다시 실행해도 같은 문의가 두 번 저장되지 않게 하는 방법을 설명합니다.

## 학습 목표

1. 프롬프트로만 형식을 요구하면 어떤 파싱 오류가 생기는지 설명하고, 응답을 구조화된 데이터로 받아야 하는 이유를 설명할 수 있습니다.
2. JSON 스키마로 필드의 이름, 자료형, 허용값(enum), 필수 여부를 정의할 수 있습니다.
3. 구조화 출력이 형식을 보장하는 원리(제약 디코딩)를 1장의 다음 토큰 확률 분포로 설명할 수 있습니다.
4. 구조화 출력이 보장하지 않는 것(내용의 정확성, 잘림과 거절)을 들고, 스키마 검증, 업무 규칙, 정답 라벨 비교로 확인하는 방법을 설명할 수 있습니다.
5. 분류 결과를 저장할 때 실패한 건만 다시 보내도 같은 문의의 행이 두 개 생기지 않게 저장하는 방법과, 결과와 함께 남길 값을 설명할 수 있습니다.

예제 6-1과 6-3은 API(application programming interface)로 모델을 호출하고, 예제 6-2는 1장의 공개 LLM(large language model)을 PC에서 실행합니다. 모델의 응답과 확률은 실행할 때마다 교재와 다를 수 있습니다.

## 응답을 데이터로 받기

:::요점
프로그램이 응답을 쓰려면 응답 텍스트를 파싱해 파이썬의 dict 같은 자료 구조로 바꿔야 합니다. 프롬프트로 "JSON으로 답하라"고만 하면 모델이 대부분 따르지만, 설명 문장이나 코드 블록 표시가 붙거나 목록 밖의 값이 나오는 응답이 섞입니다.
:::

[[JSON]](JavaScript Object Notation)은 이름과 값의 쌍을 중괄호로 묶어 적는 텍스트 형식입니다. 이름과 값 한 쌍을 [[필드]](field)라고 합니다. 문의 하나를 분류한 결과는 `{"label": "안전", "urgent": true}`처럼 적을 수 있습니다. 응답은 언제나 문자열이므로, 프로그램은 이 문자열을 `json.loads()`로 [[파싱]](parsing)해 dict로 바꾼 뒤 값을 꺼냅니다.

프롬프트로만 형식을 요구하면 모델은 학습한 대로 그럴듯한 글을 이어 쓸 뿐입니다(1장). 프롬프트에는 형식을 강제하는 장치가 없습니다. 그래서 다음과 같은 응답이 섞이고, 대부분 [[파싱 오류]](parsing error)가 납니다.

- JSON 앞뒤에 "분류 결과입니다" 같은 설명 문장이 붙습니다.
- JSON을 코드 블록 표시(백틱 세 개와 json)로 감쌉니다.
- 라벨 목록에 없는 값("설비 이상/안전")이나 다른 이름의 필드가 나옵니다. 파싱은 되지만, 다른 이름의 필드는 값을 꺼낼 때 `KeyError`가 나고, 목록 밖의 라벨은 오류 없이 저장되어 집계에서 빠집니다(5장의 조용한 실패).
- 최대 출력 토큰에 닿아 닫는 괄호 전에 끊깁니다.

## JSON 스키마

:::요점
JSON 스키마는 응답이 가져야 할 필드의 이름, 자료형, 허용값, 필수 여부를 적은 명세입니다. 같은 스키마를 모델에 주는 데도, 받은 데이터를 검사하는 데도 씁니다.
:::

[[JSON 스키마]](JSON Schema)는 JSON 데이터의 구조를 JSON으로 적은 명세입니다. 문의 분류 결과의 스키마는 다음과 같습니다.

```json
{
  "type": "object",
  "properties": {
    "label": {"type": "string", "enum": ["설비 이상", "품질", "안전", "문서와 데이터 요청"]},
    "urgent": {"type": "boolean"},
    "equipment_id": {"type": ["string", "null"]}
  },
  "required": ["label", "urgent", "equipment_id"],
  "additionalProperties": false
}
```

| 키워드 | 뜻 |
| --- | --- |
| `type` | 자료형. `object`, `array`, `string`, `integer`, `number`, `boolean`, `null` |
| `properties` | 객체의 필드마다 다시 스키마를 적습니다 |
| `enum` | 필드가 가질 수 있는 값의 목록 |
| `required` | 빠지면 안 되는 필드 |
| `additionalProperties` | `false`이면 `properties`에 없는 필드를 허용하지 않습니다 |

[[불리언]](boolean)은 참과 거짓 두 값만 갖는 자료형이고, JSON에서는 `true`와 `false`로 적습니다. [[enum]]은 고를 값이 정해진 필드에 씁니다. 라벨을 자유 문자열로 두면 "안전 문제", "안전(긴급)"처럼 같은 뜻의 다른 문자열이 나와 집계가 어려워집니다. 값이 없을 수 있는 필드는 자료형에 `null`을 함께 넣습니다. [[null]]은 JSON에서 값이 없음을 나타내는 값입니다. `null`을 허용하지 않으면 문의에 설비 번호가 없어도 모델은 문자열 하나를 채워야 하므로, 근거 없는 번호를 지어낼 수 있습니다(4장의 형식이 빈칸을 채우는 현상).

필드 이름은 결과 테이블의 열 이름으로 그대로 쓰므로 짧은 영문으로 짓습니다. 스키마는 프롬프트보다 먼저 작성합니다. 결과 테이블에 어떤 열이 필요한지 정하고, 그 열을 채울 수 있게 프롬프트를 작성합니다.

## 구조화 출력

:::요점
구조화 출력은 요청에 JSON 스키마를 넣어, 정상 종료한 응답이 그 스키마에 맞는 JSON이 되게 하는 API 기능입니다(예외는 "잘림과 거절"에서 설명합니다). Anthropic API와 OpenAI 호환 API 모두 지원하지만, 사내 서버가 지원하는지는 확인해야 합니다.
:::

[[구조화 출력]](structured output)은 요청에 스키마를 함께 보내면 서버가 스키마에 맞는 JSON만 생성하는 기능입니다. 요청하는 방법은 API마다 다릅니다.

| API | 요청에 넣는 값 |
| --- | --- |
| Anthropic | `output_config={'format': {'type': 'json_schema', 'schema': 스키마}}` |
| OpenAI 호환 | `response_format={'type': 'json_schema', 'json_schema': {'name': ..., 'schema': 스키마, 'strict': True}}` |

`llm.send()`와 `llm.ask()`에 `schema=`로 스키마를 주면 이 값을 넣어 보냅니다. 두 API 모두 객체마다 `additionalProperties: false`를 요구하고, OpenAI는 스키마의 최상위가 객체여야 합니다. 그래서 예제 6-3은 배열을 `items` 필드 하나를 가진 객체로 감쌉니다. Anthropic API는 숫자의 범위(`minimum`, `maximum`)나 문자열 길이(`minLength`) 같은 키워드는 지원하지 않습니다. 지원하지 않는 키워드를 넣으면 400 오류가 납니다(2026-11 확인). 이런 조건은 받은 뒤 코드로 검사합니다.

OpenAI 호환 서버 가운데는 `json_schema` 방식을 지원하는 서버도 있고, `json_object`만 지원하는 서버도 있습니다. 환경 변수 `LLM_STRUCTURED`로 방식을 고릅니다.

| `LLM_STRUCTURED` | 서버가 보장하는 것 | 스키마를 보내는 곳 | 코드가 할 일 |
| --- | --- | --- | --- |
| `json_schema`(기본) | 스키마에 맞는 JSON | 요청의 형식 지정 값 | 종료 이유 확인 |
| `json_object` | JSON 형식만 | 프롬프트 | 종료 이유 확인, 스키마 검증 |
| `prompt` | 없음 | 프롬프트 | 종료 이유 확인, 파싱 오류 처리, 스키마 검증 |

[[스키마 검증]](schema validation)은 받은 데이터가 스키마에 맞는지 코드로 확인하는 것입니다. 요청에 넣은 스키마를 그대로 써서 `jsonschema` 패키지의 `jsonschema.validate(data, SCHEMA)`로 검사하면, 맞지 않을 때 `ValidationError`가 발생합니다.

:::예제 6-1 프롬프트로만 요구할 때와 구조화 출력
판단하기 어려운 문의 5건을 같은 프롬프트로 두 번씩 보냅니다. `parsed()`는 준비 셀의 함수로, `json.loads()`에 실패하면 "파싱 오류"와 응답 앞부분을 돌려줍니다. 한 번은 프롬프트에 형식만 적고, 한 번은 `schema=`로 구조화 출력을 요청합니다. 두 응답을 각각 `json.loads()`로 파싱해 보고, 어느 쪽에서 파싱 오류나 목록 밖의 라벨이 나오는지 봅니다. 이 셀은 API를 10번 호출합니다.

```python
SCHEMA = {'type': 'object',
          'properties': {'label': {'type': 'string', 'enum': LABELS}, 'urgent': {'type': 'boolean'}},
          'required': ['label', 'urgent'], 'additionalProperties': False}
ask_format = ('이 문의를 분류하고 판단 이유를 짧게 설명한 뒤, {"label": 라벨, "urgent": 긴급 여부} 형식의 JSON으로 답하세요. '
              f'라벨은 {", ".join(LABELS)} 중 하나입니다.\n문의: ')
for item in inquiries[40:45]:                       # Q41~Q45
    prompt_only = llm.ask(ask_format + item['문의'], model='소형', max_tokens=2000)
    structured = llm.ask(ask_format + item['문의'], model='소형', max_tokens=2000, schema=SCHEMA)
    print(f"{item['번호']} 정답 {item['라벨']}")
    print(f'  프롬프트로만: {parsed(prompt_only.text)}')
    print(f'  구조화 출력: {parsed(structured.text)}')
```
:::

교재의 실행에서 프롬프트로만 형식을 요구한 응답은 5건 모두 파싱 오류였습니다. 프롬프트가 판단 이유를 먼저 설명하라고 했으므로 응답이 설명 문장으로 시작했고, `json.loads()`는 첫 글자부터 JSON이 아니면 실패합니다. 구조화 출력은 5건 모두 파싱됐고 라벨도 목록 안에 있었습니다. 스키마에 이유를 적을 필드가 없으므로 이유는 빠졌습니다. 이유가 필요하면 스키마에 `reason` 같은 짧은 문자열 필드를 둡니다. 그런데 구조화 출력의 라벨도 Q42와 Q43은 정답과 달랐습니다. 이 차이는 "구조화 출력이 보장하지 않는 것" 절에서 설명합니다.

## 형식을 보장하는 원리

:::요점
구조화 출력은 모델이 다음 토큰을 고를 때마다 스키마에 어긋나는 토큰의 확률을 0으로 만들고 남은 토큰 중에서 고르게 합니다. 이 방식을 제약 디코딩이라고 합니다. 모델은 그대로이고 토큰을 뽑는 단계만 제한하므로, 형식은 보장되지만 어느 값을 고를지는 여전히 모델의 확률이 정합니다.
:::

모델은 다음 토큰마다 어휘 전체에 확률을 매기고, 그중 하나를 샘플링해 붙이는 일을 되풀이합니다(1장). [[제약 디코딩]](constrained decoding)은 이 반복 사이에 단계 하나를 더합니다. 지금까지 생성한 글을 보고 스키마상 다음에 올 수 있는 토큰을 계산한 뒤, 그 밖의 토큰은 확률을 0으로 만들고 남은 확률을 합이 1이 되게 다시 나눕니다. 예를 들어 `{"label": "`까지 생성했다면 다음에는 enum 값의 첫 토큰만 올 수 있고, 라벨 문자열이 끝나면 닫는 따옴표만 올 수 있습니다.

:::예제 6-2 다음 토큰 후보 제한하기
1장의 공개 LLM에 문의 하나를 분류하라고 하고, 응답이 `{"label": "`까지 생성됐다고 가정합니다. 제약 없이 본 다음 토큰의 상위 5개와, 네 라벨의 첫 토큰만 남기고 다시 계산한 확률을 비교합니다. 상위 후보에 라벨이 아닌 토큰이 있는지, 제약 뒤에 어느 라벨이 1위인지 봅니다. API를 호출하지 않습니다.

```python
import torch
tokenizer, model = load_local_model()               # 1장의 Qwen2.5-0.5B-Instruct
inquiry = inquiries[42]                             # Q43 냉각수 누수(정답 라벨: 안전)
messages = [{'role': 'user', 'content': f'문의를 {", ".join(LABELS)} 중 하나로 분류해 JSON으로 답하세요.\n문의: {inquiry["문의"]}'}]
prefix = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True) + '{"label": "'
with torch.no_grad():
    logits = model(**tokenizer(prefix, return_tensors='pt')).logits[0, -1]
probs, top = torch.softmax(logits, dim=-1).topk(5)
print('제약 없음:', ', '.join(f'{tokenizer.decode(token)!r} {prob:.1%}' for prob, token in zip(probs, top)))
allowed = {tokenizer.encode(label)[0]: label for label in LABELS}   # 라벨마다 첫 토큰만 허용합니다
masked = torch.full_like(logits, float('-inf'))
masked[list(allowed)] = logits[list(allowed)]                        # 나머지 토큰의 확률은 0이 됩니다
for token, prob in zip(allowed, torch.softmax(masked, dim=-1)[list(allowed)]):
    print(f'제약 뒤: {tokenizer.decode(token)!r}({allowed[token]}) {prob:.1%}')
```

교재의 실행에서 제약 없이 본 상위 5개 가운데 '질', '물', '비'는 어느 라벨의 첫 토큰도 아니었고, 이런 토큰이 뽑히면 목록 밖의 라벨이 나옵니다. 네 라벨의 첫 토큰만 남기자 '문'(문서와 데이터 요청)이 56.6%로 1위가 되었습니다. 정답 라벨인 안전의 첫 토큰 '안'은 2.7%였습니다. 제약 디코딩은 허용 범위만 좁히므로, 모델이 틀린 라벨에 높은 확률을 주면 틀린 라벨이 형식에 맞게 나옵니다. 이 예제는 첫 토큰 하나만 제한했습니다. '문'의 16.2%에는 "문의"처럼 라벨이 아닌 말을 시작하려던 확률도 들어 있습니다. 제약 디코딩은 이 확률을 그대로 문서와 데이터 요청 쪽으로 넘기므로, 56.6%를 모델이 이 라벨을 고른 확률로 읽으면 안 됩니다. 실제 구현은 '문' 다음에는 '서'만 허용하는 식으로 라벨 문자열을 끝까지 따라가며 토큰마다 허용 범위를 다시 계산합니다.

### 잘림과 거절

구조화 출력의 보장은 정상 종료한 응답에만 적용됩니다. 최대 출력 토큰에 닿아 `max_tokens`(OpenAI 호환은 `length`)로 끝나면 JSON이 중간에 끊깁니다. Anthropic API에서 안전 기준에 따라 `refusal`로 끝나면 거절 문장이 스키마보다 우선합니다. OpenAI 호환 API는 거절 문장을 응답의 `refusal` 필드에 담고, `llm.py`는 두 경우 모두 `refusal`로 돌려줍니다. 두 경우 모두 [[상태 코드]]는 200이고 생성한 토큰에 요금이 붙습니다(2026-11 확인). 그래서 파싱하기 전에 종료 이유부터 확인합니다(5장). thinking 토큰도 최대 출력 토큰 안에 들어가므로 `max_tokens`는 JSON 길이보다 넉넉하게 둡니다.

Anthropic API 문서에는 예외가 두 가지 더 있습니다. enum 값의 대소문자는 보장하지 않아, 영문 값이면 띄어 쓴 단어의 첫 글자가 대문자로 바뀌어 나올 수 있습니다. 필드는 스키마에 적은 순서로 나오지만, 필수 필드가 선택 필드보다 앞에 옵니다(2026-11 확인).

### 형식은 맞지만 틀린 내용

스키마는 `label`이 네 라벨 중 하나라는 것만 정할 뿐, 어느 라벨이 맞는지는 정하지 않습니다. 형식이 맞는 데이터 안에서 다음 두 가지를 따로 확인합니다.

- [[업무 규칙]](business rule)은 형식과 별개로 업무에서 값이 지켜야 하는 조건입니다. 예를 들어 "라벨이 안전인데 `urgent`가 false이면 사람이 확인한다"처럼 필드 사이의 조합을 검사합니다. 규칙에 걸린 건은 버리지 않고 [[사람 확인]](human review)으로 보냅니다.
- [[정확도]](accuracy)는 [[정답 라벨]](4장, 사람이 미리 정해 둔 정답)과 결과가 일치한 건의 비율입니다. 모든 건의 정답을 알 수는 없으므로, 표본에 사람이 정답 라벨을 붙여 비교합니다. 표본이 15건이면 한 건이 약 7%p를 차지하므로, 모델이나 프롬프트를 정할 때는 표본을 늘립니다(5장).

같은 문의를 다시 보내도 결과가 같은지도 확인합니다. 구조화 출력은 샘플링을 없애지 않으므로, 확률이 비슷한 라벨 사이에서는 실행마다 다른 라벨이 나올 수 있습니다(1장). 다시 실행했을 때 같은 결과가 나오는 정도를 [[재현성]](reproducibility)이라고 합니다. 두 번 실행해 결과가 다른 건은 판단이 어려운 문의이므로 사람 확인으로 보냅니다.

:::예제 6-3 형식은 맞지만 틀린 라벨
판단하기 어려운 문의 15건(Q41~Q55)을 배열 스키마의 구조화 출력으로 한 요청에 보내고, 같은 요청을 한 번 더 보냅니다. 돌려받은 건수, 정답 라벨과 비교한 정확도, 업무 규칙(안전인데 긴급 아님)에 걸린 건, 두 실행에서 라벨이 다른 건을 봅니다. 이 셀은 API를 2번 호출합니다.

```python
hard = inquiries[40:55]
ITEMS = {'type': 'object', 'additionalProperties': False, 'required': ['items'], 'properties': {'items': {'type': 'array', 'items': {
    'type': 'object', 'additionalProperties': False, 'required': ['id', 'label', 'urgent'],
    'properties': {'id': {'type': 'string'}, 'label': {'type': 'string', 'enum': LABELS}, 'urgent': {'type': 'boolean'}}}}}}
prompt = '각 문의를 분류하고 긴급 여부를 판단하세요.\n' + '\n'.join(f"{item['번호']}: {item['문의']}" for item in hard)
runs = []
for run in range(2):
    reply = llm.ask(prompt, model='소형', max_tokens=8000, schema=ITEMS)
    if reply.stop_reason != 'end':                                               # 잘렸거나 거절했으면 파싱하지 않습니다
        print(f'{run + 1}회차: 종료 이유 {reply.stop_reason}'); runs.append({}); continue
    runs.append({row['id']: row for row in json.loads(reply.text)['items']})
    rows = runs[-1]
    correct = sum(rows.get(item['번호'], {}).get('label') == item['라벨'] for item in hard)
    rule = [key for key, row in rows.items() if row['label'] == '안전' and not row['urgent']]
    print(f'{run + 1}회차: 종료 이유 {reply.stop_reason}, 돌려받은 건 {len(rows)}/{len(hard)}, '
          f'정확도 {correct}/{len(hard)}, 업무 규칙에 걸린 건 {rule}')
changed = [key for key in runs[0] if runs[0][key]['label'] != runs[1].get(key, {}).get('label')]
print('두 실행에서 라벨이 다른 건:', changed)
```
:::

교재의 실행에서 두 실행 모두 15건을 돌려받았고, 정확도는 두 번 모두 15건 가운데 11건이었습니다. 이번 프롬프트에는 예제 5-2와 달리 판정 기준을 넣지 않았습니다. 업무 규칙에 걸린 건은 없었고, Q42와 Q43은 두 실행의 라벨이 달랐습니다. 형식 검사와 업무 규칙만으로는 틀린 4건을 하나도 찾지 못합니다. 틀린 건은 정답 라벨과 비교해야 드러나고, 두 실행의 라벨이 다른 건은 다시 실행해 비교해야 드러납니다. 어느 건의 라벨이 바뀌는지는 실행마다 다릅니다.

## 결과를 저장하기

:::요점
분류 결과는 한 건을 받을 때마다 문의 번호를 기본 키로 삼아 upsert로 저장하고, 실제 모델 이름과 실행 번호를 함께 남깁니다. 그러면 중간에 멈춰도 받은 결과가 남고, 실패한 건만 다시 보내도 같은 문의의 행이 두 개 생기지 않으며, 어느 조건에서 나온 결과인지 알 수 있습니다.
:::

여러 건을 처리한 결과는 파일이나 DB(database)에 저장해 집계하고 사람에게 넘깁니다. LLM의 결과를 저장할 때는 두 가지를 고려합니다. 첫째, 수백 건을 보내면 일부는 재시도 끝에 실패하므로(5장) 다시 실행해야 합니다. 이때 전체를 다시 보내면 이미 성공한 건의 요금을 또 내고, 샘플링 때문에 그 건의 라벨이 바뀔 수도 있습니다. 둘째, 같은 문의라도 모델, 프롬프트, 스키마를 바꾸면 라벨이 바뀌는데, 라벨만 저장하면 어느 조건에서 나온 라벨인지 알 수 없습니다.

### 실패한 건만 다시 보내기

결과는 모든 건을 마친 뒤가 아니라 한 건을 받을 때마다 바로 저장합니다. 그래야 300건째에서 멈춰도 그때까지의 결과가 남습니다. 다시 실행할 때는 저장된 결과를 먼저 읽고, 결과가 없거나 재시도 끝에 실패한 건만 보냅니다. 잘림과 거절은 같은 요청을 다시 보내도 대부분 되풀이되므로, 잘린 건은 `max_tokens`를 늘리고 거절된 건은 사람 확인으로 보냅니다.

같은 작업을 여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질을 [[멱등성]](idempotency)이라고 합니다. 저장을 멱등으로 만든다는 것은 같은 문의를 몇 번 저장해도 그 문의의 행이 하나로 유지된다는 뜻입니다. 다시 보낸 건의 라벨까지 같아지지는 않습니다. 결과를 행으로 덧붙이기만 하면 다시 실행할 때마다 같은 문의의 행이 늘어 건수가 실제보다 크게 나옵니다.

문의 번호처럼 행 하나를 유일하게 가리키는 열을 [[기본 키]](primary key)라고 합니다. 같은 기본 키의 행이 없으면 넣고 있으면 고치는 저장 방식을 [[upsert]]라고 합니다. 결과는 문의 번호를 기본 키로 두고 upsert로 저장합니다. SQLite는 파이썬에 `sqlite3` 모듈로 들어 있는, 파일 하나로 된 DB입니다. SQLite에서는 `INSERT INTO 결과 (번호, 라벨) VALUES (?, ?) ON CONFLICT(번호) DO UPDATE SET 라벨 = excluded.라벨`처럼 작성합니다. `excluded.라벨`은 새로 넣으려던 값이고, 번호 열이 기본 키여야 이 SQL 문이 동작합니다.

### 결과와 함께 남길 값

다음 값을 라벨과 함께 저장해야, 저장된 결과가 어느 모델과 프롬프트로 만든 것인지 알 수 있습니다.

- 응답에 적힌 실제 모델 이름(`Reply.model`)을 남깁니다. 별칭(`'소형'`)이 가리키는 모델은 환경 변수와 `llm.py`의 설정에 따라 바뀌기 때문입니다.
- 프롬프트와 스키마의 버전을 남깁니다. 프롬프트를 고친 뒤의 결과와 구분하기 위해서입니다.
- 배치를 시작할 때 정한 실행 번호(예: 시작 시각)를 남깁니다. 같은 실행에서 재시도한 건은 실행 번호가 같습니다.
- 처리 상태(자동 처리, 사람 확인, 실패)와 사유, 입력 토큰, 출력 토큰, 요금을 남깁니다. 실패한 건을 고르고 요금을 집계하는 데 씁니다.

upsert는 같은 문의의 이전 결과를 고쳐 씁니다. 예제 6-3처럼 두 실행의 라벨을 비교하려면 두 결과가 모두 남아야 하므로, (번호, 실행 번호)를 함께 기본 키로 둡니다. 이때 건수를 셀 때는 문의마다 가장 최근 실행의 행만 셉니다. 사람 확인으로 보낸 건은 담당자가 열어 볼 수 있게 엑셀 파일로 따로 내보냅니다(pandas의 `to_excel()`).

## 관통 프로젝트 2단계

1단계의 `answer()`는 답을 문장으로 돌려줬습니다. 2단계에서는 답과 함께 문의의 분류, 긴급 여부, 사내 문서가 필요한지를 구조화된 데이터로 받습니다. 사내 문서가 필요한지(`needs_document`)는 8장에서 문서를 검색할지 정하는 데 씁니다.

:::실습 P2 답을 구조화된 데이터로 받기
`ANSWER_SCHEMA`에 네 필드(`category`: 라벨 네 개 중 하나, `urgent`: 불리언, `needs_document`: 불리언, `answer`: 문자열)를 모두 필수로 적습니다. 업무 규칙은 두 가지입니다. 분류가 "문서와 데이터 요청"이면 `needs_document`가 참이어야 하고, 분류가 "안전"인데 `urgent`가 거짓이면 사람이 확인합니다. `answer_structured()`는 1단계의 `answer()`를 호출하되, `send` 인자에 스키마를 넣은 `llm.send`를 넘깁니다. 상태가 "완료"인 응답만 파싱하고, `check()`로 업무 규칙 두 가지를 검사합니다. 규칙에 걸리면 "사람 확인", 걸리지 않으면 "자동 처리", 1단계에서 실패했거나 확인이 필요했으면 "실패"입니다. 문의 6건의 처리 상태와 사유가 출력되면 끝납니다. 이 셀은 API를 6번 호출합니다.

완료 기준

- 6건의 처리 상태가 출력되고, 규칙에 걸린 건에는 사유가 나옵니다.
- 출력에 1단계에서 계산한 요금이 그대로 나옵니다.

:::힌트
 `functools.partial(llm.send, schema=ANSWER_SCHEMA)`는 `schema`를 미리 채운 `llm.send`입니다. 이것을 `answer(question, send=...)`로 넘기면 재시도와 종료 이유 확인을 1단계 코드 그대로 씁니다.
:::

1단계의 결과 dict에 파싱한 데이터를 더하고, 상태만 다시 정합니다.

```python
import functools

ANSWER_SCHEMA = {'type': 'object', 'additionalProperties': False,
                 'required': ['category', 'urgent', 'needs_document', 'answer'],
                 'properties': {'category': {'type': 'string', 'enum': LABELS}, 'urgent': {'type': 'boolean'},
                                'needs_document': {'type': 'boolean'}, 'answer': {'type': 'string'}}}


def check(data):
    """업무 규칙 검사. 문제가 없으면 None, 있으면 사유 문자열을 돌려줍니다"""
    if data['category'] == '문서와 데이터 요청' and not data['needs_document']:
        return '문서 요청인데 사내 문서가 필요하지 않다고 답함'
    if data['category'] == '안전' and not data['urgent']:
        return '안전 문의인데 긴급이 아니라고 답함'
    return None


def answer_structured(question):
    """1단계의 answer()에 구조화 출력을 더합니다. 결과 dict에 data(파싱한 dict)와 status, reason을 넣습니다"""
    result = answer(question, send=functools.partial(llm.send, schema=ANSWER_SCHEMA))
    result['data'] = None
    if result['status'] != '완료':                   # 잘림과 거절은 스키마에 맞지 않을 수 있으므로 파싱하지 않습니다
        result['status'] = '실패'
        return result
    result['data'] = json.loads(result['answer'])
    problem = check(result['data'])
    result['status'], result['reason'] = ('사람 확인', problem) if problem else ('자동 처리', '')
    return result


for item in [item for item in inquiries if item['번호'] in ('Q21', 'Q24', 'Q31', 'Q43', 'Q49', 'Q56')]:
    result = answer_structured(item['문의'])
    print(f"[{result['status']}] {item['번호']} {item['문의']}\n  → {result['data']}, 사유: {result['reason']}, 요금 {result['cost']:.5f}달러")
```

## 자가점검

**1.** 프롬프트에 "JSON으로만 답하세요"라고 적었는데도 `json.loads()`가 가끔 실패합니다. 왜 그렇습니까? 어떤 응답이 섞입니까?

:::정답
프롬프트는 모델이 JSON을 이어 쓸 확률을 높일 뿐, JSON이 아닌 토큰을 고르지 못하게 막지는 않습니다. 그래서 JSON 앞뒤에 설명 문장이 붙거나, 코드 블록 표시로 감싸거나, 최대 출력 토큰에 닿아 닫는 괄호 전에 끊긴 응답이 섞입니다.
:::

**2.** 문의에서 담당 부서와 설비 번호를 뽑는 스키마를 작성하려 합니다. 담당 부서는 다섯 부서 중 하나이고, 설비 번호는 문의에 없을 수도 있습니다. 두 필드의 스키마를 어떻게 적습니까? 설비 번호에 `null`을 허용하지 않으면 어떤 일이 생길 수 있습니까?

:::정답
담당 부서는 `{"type": "string", "enum": [다섯 부서]}`, 설비 번호는 `{"type": ["string", "null"]}`로 적고 둘 다 `required`에 넣습니다. 설비 번호에 `null`을 허용하지 않으면 번호가 없는 문의에도 모델이 문자열을 채워야 하므로, 문의에 없는 번호를 지어낼 수 있습니다.
:::

**3.** 구조화 출력은 모델을 다시 학습시키지 않고 어떻게 스키마에 맞는 JSON만 나오게 합니까? 다음 토큰의 확률 분포로 설명해 보세요.

:::정답
모델은 평소처럼 어휘 전체에 확률을 매깁니다. 서버는 지금까지 생성한 글과 스키마를 보고 다음에 올 수 있는 토큰을 계산해, 그 밖의 토큰의 확률을 0으로 만들고 남은 토큰의 확률을 다시 나눈 뒤 그 안에서 뽑습니다(제약 디코딩). 모든 단계에서 스키마에 맞는 토큰만 뽑히므로 정상 종료한 응답은 스키마에 맞습니다. 영문 enum 값의 대소문자만 예외입니다.
:::

**4.** 구조화 출력으로 받은 분류 결과가 모두 스키마에 맞았습니다. 이 결과를 그대로 현업에 넘겨도 됩니까? 무엇을 더 확인합니까?

:::정답
아닙니다. 형식이 맞다는 것은 값이 정해진 목록 안에 있다는 뜻일 뿐, 맞는 라벨이라는 뜻이 아닙니다. 종료 이유가 정상 종료인지 확인하고, 업무 규칙(예: 안전인데 긴급 아님)에 걸린 건은 사람 확인으로 보내고, 표본에 정답 라벨을 붙여 정확도를 측정합니다. 두 번 실행해 결과가 다른 건도 사람이 확인합니다.
:::

**5.** 사내 API가 `json_schema` 방식을 지원하지 않아 `LLM_STRUCTURED=prompt`로 설정했습니다. 응답을 처리하는 코드에서 무엇이 달라져야 합니까?

:::정답
서버가 아무것도 보장하지 않으므로 제약 디코딩의 보장이 없습니다. 파싱 오류를 예외로 잡아 실패 목록에 남기고, 파싱한 데이터는 스키마 검증(필드, 자료형, enum)을 코드로 거친 뒤에 씁니다.
:::

**6.** 문의 500건을 분류하는 배치가 300건째에서 멈췄습니다. 다시 실행해도 요금이 두 번 들지 않고 결과 테이블에 같은 문의의 행이 두 개 생기지 않으려면 저장하고 다시 보내는 코드를 어떻게 작성해야 합니까?

:::정답
결과를 받을 때마다 한 건씩, 문의 번호를 기본 키로 두고 upsert로 저장합니다. 그래야 300건째에서 멈춰도 299건의 결과가 남습니다. 다시 실행할 때는 저장된 결과를 먼저 읽어, 결과가 없거나 재시도 끝에 실패한 건만 보냅니다. 이미 성공한 건은 다시 보내지 않으므로 요금이 들지 않고, 실패한 건을 다시 저장해도 같은 번호의 행을 고쳐 쓰므로 행이 늘지 않습니다. 결과와 함께 실제 모델 이름과 실행 번호를 남겨, 다시 보낸 건이 어느 실행의 결과인지 알 수 있게 합니다.
:::

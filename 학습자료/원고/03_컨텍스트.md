# 3장 컨텍스트

강의 1일차 파트 1과 파트 2, 2일차 파트 1, 6일차 파트 1에 해당합니다.

모델은 요청 하나를 받을 때마다 그 안에 든 글만 보고 응답합니다. 이 장은 그 "요청 하나에 든 글", 곧 컨텍스트가 무엇으로 채워지고 어디까지 들어가는지를 설명합니다. 대화가 이어지는 것처럼 보이는 이유, 대화가 길어질수록 비용이 늘어나는 이유도 이 장에서 설명합니다.

## 학습 목표

1. 컨텍스트 윈도우가 무엇으로 채워지는지(시스템 프롬프트, 대화 이력, 넣은 문서, 질문, 출력) 설명하고, 상한을 넘으면 어떤 일이 생기는지 설명할 수 있습니다.
2. 시스템 프롬프트와 역할(system, user, assistant)이 채팅 템플릿을 거쳐 하나의 토큰 열이 되는 과정을 설명할 수 있습니다.
3. 모델이 대화를 기억하지 않는다(무상태)는 것과, 대화를 이어 가려면 이력 전체를 매번 다시 보내야 해서 입력 토큰이 쌓인다는 것을 계산으로 보일 수 있습니다.
4. 긴 문서를 한 번에 넣을 때와 나눠 넣을 때 각각 무엇을 얻고 잃는지 설명할 수 있습니다.

예제 3-1과 실습 3-1은 1장의 토크나이저만 PC에서 씁니다. 예제 3-2와 3-3은 API(application programming interface)로 모델을 호출합니다. 모델의 응답, 토큰 수, 걸린 시간은 실행할 때마다 교재와 다를 수 있습니다.

## 컨텍스트 윈도우

:::요점
모델이 요청 하나에서 다룰 수 있는 토큰 수에는 상한이 있고, 입력과 출력이 이 상한을 나눠 씁니다. 입력에는 이번 질문뿐 아니라 시스템 프롬프트, 대화 이력, 넣은 문서가 모두 들어갑니다.
:::

[[컨텍스트 윈도우]](context window)는 모델이 요청 한 번에 다룰 수 있는 토큰 수의 상한입니다. 모델은 다음 토큰을 정할 때마다 입력과 지금까지 생성한 토큰 전체를 다시 보므로(1장), 상한은 입력과 출력을 합친 길이에 걸립니다.

현행 Claude 모델의 컨텍스트 윈도우는 100만 토큰이고, 1장과 2장에서 PC로 실행한 Qwen2.5-0.5B-Instruct는 32,768토큰입니다. 입력만으로 윈도우를 넘으면 API가 요청을 오류(400, `prompt is too long`)로 거절합니다. 생성 중에 윈도우가 차면 응답이 끊기고, Claude 4.5 이후 모델은 종료 이유 `model_context_window_exceeded`를 돌려줍니다(`llm.py`는 `max_tokens`로 바꿔 줍니다). 채팅 서비스는 대화가 아주 길어지면 앞부분을 빼고 보내기도 하므로, 긴 대화의 앞부분은 응답에 반영되지 않을 수 있습니다(2026-11 확인).

## 역할과 채팅 템플릿

:::요점
요청에 담은 시스템 프롬프트와 메시지들은 모델에 따로따로 전달되지 않습니다. 채팅 템플릿이 역할 표시 토큰으로 감싸 글 한 덩어리로 이어 붙이고, 모델은 그 끝에 이어질 토큰을 생성할 뿐입니다.
:::

API로 요청할 때는 [[메시지]](message)의 목록을 보냅니다. 메시지마다 누가 말했는지를 나타내는 [[역할]](role)이 붙습니다. user는 사용자, assistant는 모델이고, system은 대화 전체에 적용할 지시로 이 글을 [[시스템 프롬프트]](system prompt)라고 합니다. OpenAI 호환 API는 system 역할의 메시지로, Anthropic API는 `system` 파라미터로 받습니다. 무엇을 적을지는 4장 "프롬프트 설계"에서 다룹니다.

그런데 1장에서 본 모델의 입력은 토큰 ID의 나열 하나뿐입니다. 메시지 목록은 [[채팅 템플릿]](chat template)이라는 규칙을 거쳐 글 한 덩어리가 됩니다. 채팅 템플릿은 메시지마다 역할을 나타내는 표시 토큰을 앞뒤에 붙이고, 마지막에 모델의 답 차례를 여는 표시를 붙입니다. 2장의 SFT(supervised fine-tuning)에서 모델은 바로 이 형식의 글로 학습했으므로, 답 차례가 열리면 답을 이어 씁니다.

:::예제 3-1 채팅 템플릿 보기
시스템 프롬프트, 질문, 이전 답, 새 질문으로 된 메시지 네 개를 1장의 토크나이저로 채팅 템플릿에 넣고, 만들어진 글과 그 토큰 수를 봅니다. 역할 이름 앞뒤에 어떤 표시 토큰이 붙는지, 마지막 줄이 무엇인지 봅니다.

```python
messages = [
    {'role': 'system', 'content': '너는 반도체 후공정 라인의 문의에 답하는 도우미다.'},
    {'role': 'user', 'content': '다이싱이 무엇인가요?'},
    {'role': 'assistant', 'content': '웨이퍼를 개별 칩으로 자르는 공정입니다.'},
    {'role': 'user', 'content': '그다음 공정은요?'},
]
# add_generation_prompt=True: 마지막에 모델의 답 차례를 여는 표시를 붙입니다
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
print(text)
print(f'메시지 {len(messages)}개 → 글 한 덩어리, {len(tokenizer.encode(text))}토큰')
```
:::

시스템 프롬프트도 별도 입력이 아니라 이 글의 맨 앞부분입니다. 모델이 시스템 프롬프트를 잘 따르는 것은 SFT와 RLHF(reinforcement learning from human feedback)에서 system 표시 토큰 안의 지시를 따르도록 학습했기 때문입니다. 표시 토큰의 형태는 모델마다 다르고, API로 제공되는 모델의 템플릿은 공개되지 않은 경우가 많습니다. 그래도 API에 보낸 메시지가 한 덩어리의 글로 바뀌어 모델에 들어간다는 점은 같습니다.

## 모델은 대화를 기억하지 않는다

:::요점
모델과 이 교재가 쓰는 API(Anthropic Messages, OpenAI 호환 Chat Completions)는 이전 요청을 기억하지 않습니다. 대화를 이어 가려면 앞의 질문과 답을 매번 다시 보내야 하므로, 대화가 길어질수록 요청 하나의 입력 토큰과 전체 비용이 함께 늘어납니다.
:::

모델은 요청에 든 글만 보고 응답하며, 요청이 끝나면 그 내용을 다음 요청으로 이어 주지 않습니다. 이처럼 이전 요청을 기억하지 않는 성질을 [[무상태]](stateless)라고 합니다. 채팅 화면에서 대화가 이어지는 것처럼 보이는 것은, 화면 쪽 프로그램이 지금까지 주고받은 메시지인 [[대화 이력]](conversation history)을 요청마다 함께 보내기 때문입니다. API를 직접 쓸 때는 이 일을 우리 코드가 합니다.

```python
print(f'[이력 없이] 입력 토큰 {alone.input_tokens}개: {alone.text.strip()}\n')

for question in ['제 이름이 뭐였죠?', '제가 처음에 한 말을 그대로 적어 주세요.']:
    reply = llm.ask(question, history=history, model='소형', max_tokens=500)   # 이력을 함께 보냄
    print(f'[이력 {len(history)}개와 함께] 입력 토큰 {reply.input_tokens}개: {reply.text.strip()}\n')
    history += [{'role': 'user', 'content': question}, {'role': 'assistant', 'content': reply.text}]
```

:::

:::예제 3-3 긴 문서의 중간

n번째 요청의 입력은 앞 대화 쌍(최대 `keep_last`쌍)에 500토큰씩, 새 질문 200토큰을 더한 값입니다.

```python
def total_input_tokens(turns, question_tokens=200, answer_tokens=300, keep_last=None):
    """요청마다 보낸 입력 토큰(이력 + 새 질문)을 모두 더합니다. keep_last가 있으면 이력을 최근 keep_last쌍만 보냅니다"""
    total = 0
    for turn in range(1, turns + 1):
        pairs = turn - 1 if keep_last is None else min(turn - 1, keep_last)  # 이번 요청에 함께 보내는 앞 대화 쌍
        total += pairs * (question_tokens + answer_tokens) + question_tokens
    return total


my_guess = {'전체 이력': 50000, '최근 3쌍만': 30000}
print(f'전체 이력: {total_input_tokens(20):,}토큰 (예측 {my_guess["전체 이력"]})')
print(f'최근 3쌍만: {total_input_tokens(20, keep_last=3):,}토큰 (예측 {my_guess["최근 3쌍만"]})')
```

입력과 출력이 같은 윈도우를 나눠 쓰므로 출력에 남은 토큰은 약 2만입니다. Claude 4.5 이후 모델은 요청을 받고 응답이 약 2만 토큰에 이르면 `model_context_window_exceeded`로 끊고, 그 이전 모델은 요청을 오류로 거절합니다. 문서를 줄이거나 나누거나 필요한 부분만 찾아 넣습니다.
:::

**2.** 채팅 화면에서는 모델이 앞의 대화를 기억하는 것처럼 보입니다. 실제로는 어떻게 이루어지는 일입니까?

:::정답
모델과 서버는 이전 요청을 기억하지 않습니다(무상태). 화면 쪽 프로그램이 지금까지의 대화 이력을 요청마다 함께 보내므로, 모델은 매번 대화 전체를 처음 읽고 이어서 답합니다.
:::

**3.** 대화가 길어질수록 같은 길이의 질문을 보내도 요금이 늘어나는 이유를 설명해 보세요.

:::정답
이력 전체가 요청마다 입력으로 다시 들어가므로, 질문 길이가 같아도 요청 하나의 입력 토큰은 앞 대화만큼 늘어납니다. 입력 토큰에도 요금이 붙으므로 요청마다 요금이 커지고, 대화 전체의 누적 요금은 요청 수의 제곱에 가깝게 늘어납니다.
:::

**4.** 시스템 프롬프트는 모델에 어떤 형태로 전달됩니까? 모델이 시스템 프롬프트의 지시를 따르는 이유는 무엇입니까?

:::정답
채팅 템플릿이 시스템 프롬프트를 system 표시 토큰으로 감싸 글의 맨 앞에 두고, 뒤에 user와 assistant 메시지를 이어 붙여 글 한 덩어리를 만듭니다. 모델은 SFT와 RLHF에서 이 형식의 글로 학습하며 system 표시 토큰 안의 지시를 따르도록 배웠기 때문에 그 지시를 따릅니다.
:::

**5.** 400쪽짜리 안전 매뉴얼에서 특정 설비의 점검 주기를 찾으려 합니다. 한 번에 넣기, 분할 처리, 필요한 부분만 찾아 넣기의 장단점을 비교해 보세요.

:::정답
한 번에 넣으면 문서 전체를 근거로 판단하지만 입력 토큰이 많아 비용과 시간이 크고, 중간 내용을 놓칠 수 있습니다. 분할 처리는 윈도우 문제를 풀지만 구간마다 따로 판단하므로 결과를 합쳐 검산해야 합니다. 필요한 부분만 찾아 넣으면 짧고 저렴하지만, 검색이 해당 부분을 찾지 못하면 답도 틀립니다. 특정 사실 하나를 찾는 질문이라면 찾아 넣는 방법이 알맞습니다(8장).
:::

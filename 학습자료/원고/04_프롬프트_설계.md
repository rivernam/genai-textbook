# 4장 프롬프트 설계

강의 1일차 파트 2에 해당합니다.

프롬프트는 LLM(large language model)에 입력하는 지시와 재료입니다. 모델은 입력에 이어질 그럴듯한 토큰을 고를 뿐이므로(1장), 같은 모델이라도 무엇을 입력하느냐에 따라 응답이 크게 달라집니다. 이 장은 프롬프트의 어떤 부분이 응답을 어떻게 바꾸는지를 원리와 실험으로 설명합니다.

## 학습 목표

1. 프롬프트의 요소(목적, 맥락, 입력 재료, 출력 형식, 제약)를 더할수록 응답이 왜 일정해지는지 1장의 확률 분포로 설명할 수 있습니다.
2. few-shot 예시가 응답을 바꾸는 원리를 설명하고, 예시를 고를 때 주의할 점(라벨 치우침, 순서)을 들 수 있습니다.
3. 형식이 빈칸을 요구할 때 모델이 칸을 무엇으로 채우는지 보이고, 제약으로 채울 값을 정하는 방법을 설명할 수 있습니다.
4. CoT(chain of thought), 프롬프트 체인, 자기 검증과 루브릭이 각각 무엇을 해결하고 무엇을 해결하지 못하는지 설명할 수 있습니다.

예제와 실습은 가상 후공정 회사의 현장 문의 60건(`data/문의.csv`)을 씁니다. 문의마다 정답 라벨(설비 이상, 품질, 안전, 문서와 데이터 요청)과 긴급 여부가 붙어 있고, 두 라벨에 걸쳐 헷갈리는 문의 15건과 정보가 빠진 문의 5건이 섞여 있습니다. 모든 예제와 실습은 API(application programming interface)로 소형 모델을 호출하며, 응답은 실행할 때마다 교재와 다를 수 있습니다. 준비 셀에는 세 함수가 있습니다.

- `numbered()`: 문의를 "번호: 문의" 줄로 잇습니다.
- `parse_labels()`: 응답에서 "번호: 라벨" 줄(표라면 첫 칸)을 읽습니다.
- `accuracy()`: 정답 라벨과 맞는 비율을 계산합니다.

## 프롬프트가 응답을 바꾸는 원리

:::요점
모델은 프롬프트에 이어질 그럴듯한 글을 만듭니다. 지시가 모호하면 그럴듯한 응답이 여러 가지여서 실행마다 달라지고, 지시가 구체적일수록 후보가 좁아져 응답이 일정해집니다.
:::

[[프롬프트]](prompt)는 모델에 입력하는 지시와 재료 전체입니다. "이 문의들을 분류해 주세요"라는 지시 뒤에는 표, 문단, 제각각의 라벨 이름 등 그럴듯한 이어짐이 아주 많습니다. 1장의 말로 하면 첫 토큰부터 확률이 여러 후보에 퍼져 있고, 샘플링할 때마다 다른 이어짐이 뽑힙니다. 라벨 목록과 출력 형식을 정해 주면 그 밖의 이어짐은 그럴듯하지 않게 되어 후보가 좁아집니다.

:::예제 4-1 모호한 지시와 구체적 지시
문의 10건을 "분류해 주세요"만으로 두 번, 라벨 목록과 "번호: 라벨" 형식을 정해 두 번 보냅니다. 응답의 길이, 읽어 낸 라벨의 종류, 응답 앞부분이 실행마다 어떻게 다른지 봅니다. 이 셀은 API를 4번 호출합니다.

```python
sample = [inquiries[i] for i in [0, 10, 20, 30, 40, 42, 44, 49, 11, 31]]   # 라벨이 섞이게 고른 10건
vague = '다음 문의들을 분류해 주세요.\n\n' + numbered(sample)
specific = ('다음 문의를 [설비 이상, 품질, 안전, 문서와 데이터 요청] 중 하나로 분류하세요.\n'
            '한 줄에 한 건씩 "번호: 라벨" 형식으로만 답하세요.\n\n' + numbered(sample))
for name, prompt in [('모호한 지시', vague), ('구체적 지시', specific)]:
    for attempt in range(1, 3):
        reply = llm.ask(prompt, model='소형', max_tokens=2000)
        labels = parse_labels(reply.text)                        # "Q01: 라벨" 줄만 읽습니다
        valid = sum(label in LABELS for label in labels.values())   # 네 라벨 가운데 하나로 읽힌 건수
        print(f'[{name} {attempt}회] 응답 {len(reply.text):,}자, 네 라벨로 읽힌 건 {valid}/10')
        print('   앞부분:', reply.text.strip()[:80].replace('\n', ' / '))
```
:::

모호한 지시에는 두 번 모두 마크다운 표로 답했고, 열 구성(세부 유형, 우선순위, 담당 추천, 요약 등)이 실행마다 달랐습니다. 분류 이름도 모델이 그때그때 지어서, 네 라벨로 읽힌 건이 0건이었습니다. 이런 응답은 사람이 읽을 수는 있어도 프로그램이 라벨을 파싱할 수 없습니다. 구체적 지시에는 두 번 모두 네 라벨만 쓴 열 줄로 답했습니다. 다만 Q41(정답 설비 이상)은 두 번 모두 품질로, Q43(정답 안전)은 한 번은 안전, 한 번은 설비 이상으로 분류했습니다. 형식을 정해도 판정은 틀리거나 실행마다 바뀔 수 있으며, 판정은 few-shot 절의 예시와 실습 4-1의 판정 기준이 다룹니다.

- **목적**: 무엇을 하라는 것인지 한 문장으로 적습니다. 목적이 없으면 모델은 요약, 분류, 설명 가운데 그럴듯한 것을 고릅니다.
- **[[맥락]](context)**: 결과를 누가 어디에 쓰는지 적습니다. 무엇을 앞에 두고 무엇을 뺄지 판단하는 기준이 됩니다.
- **입력 재료**: 처리할 글입니다. 지시와 재료가 섞이지 않게 `<문의>` 같은 태그로 감싸 구분하는 것을 Anthropic의 프롬프트 안내가 권합니다(2026-11 확인). 이 장의 예제는 문의가 한 줄씩이라 "번호: 문의" 줄로 구분합니다.
- **출력 형식**: 응답의 구조를 정합니다. 프로그램이 응답을 읽어야 한다면, 형식이 어긋날 때 파싱 오류가 납니다. 형식을 강제로 지키게 하는 방법은 6장 "구조화 출력"에서 다룹니다.
- **[[제약]](constraint)**: 지킬 조건과 하지 말 일입니다. 특히 근거가 없을 때 무엇을 쓸지 정해 둡니다(이 장의 "형식과 제약").

"너는 장비팀 파트장이다"처럼 모델의 입장을 정하는 [[역할 지정]](role prompting)은 말투와 관점을 맞추는 데 쓰이며, Anthropic은 이를 시스템 프롬프트에 두기를 권합니다. 다만 역할 지정만으로 모델이 모르는 지식이 생기지는 않습니다. 매번 같은 역할, 규칙, 형식은 시스템 프롬프트(3장)에, 요청마다 바뀌는 재료는 사용자 메시지에 둡니다.

## few-shot

:::요점
프롬프트에 입력과 정답의 예시를 몇 개 넣으면, 모델은 예시가 보여 준 형식과 판정 방식으로 새 입력 뒤를 이어 씁니다. 예시도 입력의 일부이므로 예시의 라벨이 치우치면 응답도 치우칠 수 있습니다.
:::

[[few-shot]](few-shot prompting)은 프롬프트에 입력과 정답의 예시 몇 개를 넣는 방법이고, 예시가 없으면 zero-shot이라고 합니다. 모델의 파라미터는 바뀌지 않습니다. 예시가 입력에 들어가 다음 토큰의 확률 분포를 바꿀 뿐이며, 이를 in-context learning이라고 부릅니다(Brown 외, 2020).

Zhao 외(2021)는 GPT-3에서 예시에 많이 나온 라벨과 끝 쪽에 놓인 예시의 라벨이 더 자주 예측되는 치우침을 보고했습니다. 예시는 라벨마다 같은 수로, 헷갈리는 엣지 케이스를 중심으로 뽑습니다. Anthropic의 안내는 예시를 3~5개 넣기를 권합니다(2026-11 확인).

:::예제 4-2 few-shot의 효과와 치우침
헷갈리거나 정보가 빠진 문의 16건(Q45~Q60)을 예시 없이, 라벨이 서로 다른 예시 3개로, 모두 "안전"인 예시 3개로 분류하고 정확도와 라벨별 건수를 비교합니다. 이 셀은 API를 3번 호출합니다.

```python
evaluation = inquiries[44:60]                    # Q45~Q60: 헷갈리는 11건과 정보가 빠진 5건
instruction = ('다음 문의를 [설비 이상, 품질, 안전, 문서와 데이터 요청] 중 하나로 분류하세요.\n'
               '한 줄에 한 건씩 "번호: 라벨" 형식으로만 답하세요.\n')


def with_examples(numbers):
    """예시로 쓸 문의(0부터 센 위치)를 "예시) 문의 → 라벨" 줄로 붙입니다"""
    return instruction + '\n'.join(f"예시) {inquiries[n]['문의']} → {inquiries[n]['라벨']}" for n in numbers) + '\n'


conditions = {'예시 없음': instruction,
              '예시 3개(라벨 세 종류)': with_examples([40, 41, 42]),     # Q41 설비 이상, Q42 문서와 데이터 요청, Q43 안전
              '예시 3개(모두 안전)': with_examples([20, 21, 22])}      # Q21~Q23 모두 안전
for name, prompt in conditions.items():
    predicted = parse_labels(llm.ask(prompt + '\n' + numbered(evaluation), model='소형', max_tokens=2000).text)
    counts = {label: list(predicted.values()).count(label) for label in LABELS}
    print(f'[{name}] 읽은 라벨 {len(predicted)}건, 정확도 {accuracy(predicted, evaluation):.0%}, 라벨별 건수 {counts}')
```
:::

교재의 실행에서 16건 가운데 맞힌 건수는 예시 없음 14건(88%), 라벨이 서로 다른 예시 15건(94%), 모두 안전인 예시 15건(94%)이었습니다. 1건 차이는 다시 실행하면 바뀔 수 있는 크기이고, 모두 안전인 예시를 넣어도 "안전"으로 분류한 건수는 3건으로 같았습니다. 이 실행에 쓴 소형 모델은 라벨 이름만으로도 이 문의들을 대부분 맞혔고, 예시 3개의 효과는 작았습니다. few-shot의 효과는 모델과 과제에 따라 크게 다르므로, 넣기 전과 후의 정확도를 측정해 확인합니다. 헷갈리는 문의는 예시보다 판정 기준을 글로 적는 편이 효과가 클 수 있습니다(실습 4-1).

## 형식과 제약

:::요점
형식은 응답의 칸을 정하고, 모델은 칸을 채우려 합니다. 근거가 없는 칸에 무엇을 쓸지 제약으로 정하지 않으면 그럴듯한 값을 지어낼 수 있습니다.
:::

모델은 그럴듯한 이어짐을 고르므로, "담당자" 칸이 있는 표를 요구받으면 칸을 비우는 것보다 이름을 적는 쪽이 그럴듯할 수 있습니다. 2장의 환각이 형식 때문에 생길 수 있습니다. 이를 막으려면 근거가 없을 때 쓸 값("확인 필요")을 제약으로 정하고, 응답을 받은 뒤 그 값이 실제로 원문에 있는지 검사합니다.

:::예제 4-3 빈칸을 채우는 모델
설비 번호, 담당자, 시각이 빠진 문의 5건(Q56~Q60)으로 "번호 | 설비 번호 | 담당자 | 발생 시각 | 요청 내용" 표를 요구합니다. 제약 없이 한 번, "없는 값은 확인 필요"라는 제약 한 줄을 더해 한 번 보내고, 문의에 없는 값이 표에 생기는지 봅니다. 이 셀은 API를 2번 호출합니다.

```python
missing = inquiries[55:60]                       # Q56~Q60: 설비 번호, 담당자, 시각이 빠진 문의
table = ('다음 문의마다 "번호 | 설비 번호 | 담당자 | 발생 시각 | 요청 내용" 표의 한 행을 만드세요.\n\n'
         + numbered(missing))
guarded = table.replace('만드세요.', '만드세요. 문의에 없는 값은 지어내지 말고 "확인 필요"로 적으세요.')
for name, prompt in [('제약 없음', table), ('제약 한 줄 추가', guarded)]:
    reply = llm.ask(prompt, model='소형', max_tokens=2000)
    print(f'[{name}]\n{reply.text.strip()}\n')
```
:::

교재의 실행에서 모델은 이름이나 번호를 지어내지 않고, 빈칸을 "미확인"으로 채웠습니다. 같은 예제를 여러 번 실행해 보면 "미기재", "미지정", "해당 없음"처럼 실행마다, 열마다 다른 말이 나오기도 했습니다. 제약 한 줄을 더하면 빈칸이 우리가 정한 "확인 필요"로 통일됩니다. 이 실행에 쓴 소형 모델은 이 정도 문의에서 값을 지어내지 않았지만, 빈칸에 쓸 값이 하나로 정해져 있어야 코드가 그 칸을 찾아 사람에게 넘길 수 있습니다.

## CoT와 thinking

:::요점
중간 단계를 먼저 적게 하면 복잡한 문제의 정확도가 오를 수 있고, 무엇보다 중간 값을 검산할 수 있습니다. thinking 모델은 이 일을 스스로 하므로, 지시의 쓸모는 중간 값을 응답에 남기는 쪽으로 옮겨 갔습니다.
:::

[[CoT]](chain of thought)는 답에 이르는 중간 단계를 먼저 적게 하는 방법입니다. Wei 외(2022)는 중간 풀이가 든 예시를 몇 개 넣으면 큰 모델의 산술 문제와 상식 판단 문제의 정확도가 크게 오른다고 보고했습니다. 2장의 원리로 보면, 중간 단계의 토큰도 입력 끝에 붙으므로 답 토큰이 그 중간 결과를 보고 계산됩니다.

현행 Claude 모델(예: 이 교재의 소형 모델)은 요청에 thinking 설정이 없어도 thinking을 하므로(2장), "단계별로 생각하라"는 지시의 효과는 작아졌습니다. 대신 답의 근거나 계산에 쓴 중간 값을 짧게 적게 하면 사람이나 코드가 검산할 수 있습니다. thinking을 그대로 응답에 옮기라는 지시는 거절(`refusal`)될 수 있습니다(2026-11 확인).

## 프롬프트 체인

:::요점
여러 일을 한 번에 시키지 않고 단계로 나누면, 단계 사이에서 결과를 검사하고 잘못된 결과를 다음 단계로 넘기지 않을 수 있습니다. 대신 앞 단계의 오류는 뒤 단계로 그대로 전해집니다.
:::

[[프롬프트 체인]](prompt chaining)은 한 작업을 여러 단계로 나누고, 앞 단계의 출력을 다음 단계의 입력으로 넘기는 방법입니다. 단계마다 프롬프트가 짧고 목적이 하나라서 응답이 일정하고, 단계 사이에서 코드로 결과를 검사할 수 있습니다.

## 자기 검증과 루브릭

:::요점
모델에게 자기 응답을 점검하게 하면 확인할 곳을 표시하는 데는 도움이 되지만, 모델이 모르는 사실을 찾아내지는 못합니다. 응답을 비교하려면 항목별 기준(루브릭)을 정하고, 모델에게 채점을 맡길 때는 순서 편향을 확인합니다.
:::

[[자기 검증]](self-verification)은 모델에게 자기 응답을 "알려진 사실, 문서로 확인할 것, 추측"으로 나누게 하는 단계입니다. 같은 모델이 같은 지식으로 점검하므로, 모르는 사실이 틀렸어도 알아차리지 못합니다. 자기 검증의 결과는 사람이 원문과 대조할 곳의 목록으로 씁니다.

두 프롬프트의 결과 가운데 어느 쪽이 나은지 비교할 때는 "좋아 보인다" 대신 [[루브릭]](rubric)을 씁니다. 결과를 몇 개 항목(예: 원문에 없는 내용이 없는가, 요구한 형식을 지켰는가)으로 나누고 항목마다 점수의 기준을 적은 평가표입니다. 모델에게 루브릭으로 채점하게 하는 [[LLM-as-a-judge]]는 사람보다 빠릅니다. 다만 Zheng 외(2023)는 두 응답의 순서를 바꾸면 판정이 바뀌는 [[position bias]]를 보고했습니다. 두 순서로 모두 채점해 판정이 같은지 확인합니다. 정량 평가는 9장에서 다룹니다.

검사는 라벨이 허용 목록에 있는지만 봅니다. 2단계 프롬프트는 긴급의 뜻과 함께, 문의 옆에 1단계 라벨을 붙여 줍니다.

```python
hard = inquiries[40:60]
URGENT = '긴급은 지금 조치하지 않으면 사람이 다치거나, 생산이 멈추거나, 불량이 출하될 수 있는 문의입니다.\n'


def invalid_labels(predicted):
    """허용 목록(LABELS)에 없는 라벨이 붙은 번호의 목록"""
    return [number for number, label in predicted.items() if label not in LABELS]


def step2_prompt(labels):
    """문의와 1단계 라벨을 함께 주고, 긴급 여부만 "번호: 예" 또는 "번호: 아니오"로 묻는 프롬프트"""
    lines = '\n'.join(f"{item['번호']}: {item['문의']} (라벨: {labels.get(item['번호'])})" for item in hard)
    return URGENT + '각 문의가 긴급인지 판단하세요. 한 줄에 한 건씩 "번호: 예" 또는 "번호: 아니오"로만 답하세요.\n\n' + lines


assert step2_prompt({'Q41': '설비 이상'}), 'step2_prompt()를 먼저 작성합니다'   # 빈칸이면 API를 부르기 전에 멈춥니다
# 한 번에: 라벨과 긴급 여부를 함께(분류 기준은 실습 4-1의 my_prompt)
once = llm.ask(my_prompt + URGENT + '"번호: 라벨 / 예 또는 아니오"로 답하세요.\n\n' + numbered(hard),
               model='소형', max_tokens=3000).text
# 체인 1단계: 라벨만, 단계 사이에서 검사
step1 = parse_labels(llm.ask(my_prompt + '\n' + numbered(hard), model='소형', max_tokens=2000).text)
print('1단계 검사에 걸린 번호:', invalid_labels(step1))
# 체인 2단계: 긴급 여부만
step2 = parse_labels(llm.ask(step2_prompt(step1), model='소형', max_tokens=2000).text)

pairs = {number: value.split('/') for number, value in parse_labels(once).items()}

once_urgent = {number: parts[-1].strip() for number, parts in pairs.items()}
urgent_score = lambda answers: sum(answers.get(item['번호']) == item['긴급'] for item in hard) / len(hard)
print('한 번에 응답 앞부분:', once.strip()[:60].replace('\n', ' / '))
print(f'한 번에: 라벨 {accuracy(once_labels, hard):.0%}, 긴급 {urgent_score(once_urgent):.0%}')
print(f'체인:   라벨 {accuracy(step1, hard):.0%}, 긴급 {urgent_score(step2):.0%}')
```

교재의 실행에서 라벨 정확도는 두 방식 모두 100%였고, 긴급 판단은 한 번에 물었을 때 70%, 체인으로 따로 물었을 때 90%였습니다. 두 방식 모두 같은 긴급의 뜻(`URGENT`)을 받았으므로, 차이는 한 요청에 두 판단을 섞었는지에서 나왔다고 볼 수 있습니다. 다만 20건 중 4건 차이이므로 다시 실행해 확인합니다. 체인은 요청이 하나 늘어나는 대신 단계마다 한 가지만 묻고, 1단계 결과를 검사한 뒤 다음 단계로 넘길 수 있습니다. 1단계 라벨이 틀린 문의는 2단계에서도 틀린 라벨을 참고하므로, 앞 단계의 오류가 전해질 수 있다는 점도 함께 기억합니다.

## 자가점검

**1.** "이 회의록 정리해 줘"로 받은 응답이 매번 형식과 길이가 다릅니다. 1장의 확률 분포로 이유를 설명하고, 고칠 방법을 두 가지 들어 보세요.

:::정답
지시가 모호하면 그럴듯한 이어짐이 많아 확률이 여러 후보에 퍼지고, 샘플링할 때마다 다른 이어짐이 뽑힙니다. 목적(무엇을 하라는지), 맥락(누가 어디에 쓰는지), 출력 형식(예: 결정 사항 표와 할 일 목록) 가운데 빠진 것을 적어 후보를 좁힙니다.
:::

**2.** few-shot 예시는 모델의 파라미터를 바꿉니까? 예시 다섯 개가 모두 같은 라벨이면 어떤 일이 생길 수 있습니까?

:::정답
파라미터는 바뀌지 않습니다. 예시는 입력의 일부로 들어가 다음 토큰의 확률 분포를 바꿀 뿐입니다. 예시의 라벨이 한쪽에 치우치면 그 라벨이 더 자주 예측될 수 있으므로, 예시는 라벨마다 같은 수로 뽑습니다.
:::

**3.** 정보가 빠진 문의로 "담당자" 칸이 있는 표를 요청했더니 문의에 없는 이름이 적혔습니다. 원인과 막는 방법은 무엇입니까?

:::정답
형식이 칸을 요구하면 칸을 채우는 이어짐의 확률이 높아 근거 없는 값이 생성될 수 있습니다. "문의에 없는 값은 확인 필요로 적는다"는 제약을 넣고, 응답의 값이 원문에 실제로 있는지 검사합니다.
:::

**4.** thinking 모델에 "단계별로 생각해서 답하라"고 지시할 필요가 있습니까? 그래도 중간 과정을 적게 하는 이유는 무엇입니까?

:::정답
thinking 모델은 지시하지 않아도 답 전에 thinking을 하므로 정확도를 위한 지시의 효과는 작습니다. 그래도 근거와 중간 값을 응답에 짧게 적게 하면, 보이지 않는 thinking과 달리 사람이나 코드가 검산할 수 있습니다.
:::

**5.** 프롬프트 체인의 장점과 단점을 하나씩 들어 보세요.

:::정답
장점: 단계마다 목적이 하나라 응답이 일정하고, 단계 사이에서 코드로 결과를 검사할 수 있습니다. 단점: 앞 단계의 오류가 뒤 단계로 그대로 전해지고, 요청 수가 늘어 시간과 비용이 듭니다.
:::

**6.** 두 요약 A, B를 모델에게 루브릭으로 비교하게 했더니 A가 낫다고 했습니다. 이 판정을 믿기 전에 무엇을 해야 합니까?

:::정답
A와 B의 순서를 바꿔 다시 채점하게 합니다. 순서에 따라 판정이 바뀌면(position bias) 그 판정은 믿을 수 없습니다. 또 모델이 원문에 없는 내용을 알아차리지 못할 수 있으므로, 사실 여부는 원문과 대조합니다.
:::

파트 1. 벡터 DB와 RAG의 구조

2일차 파트 3에서는 문서 253건의 임베딩을 만들어 질문과 가까운 문서를 찾았습니다. 그 벡터 인덱스는 프로그램을 끝내면 사라지고, 문서가 바뀌면 처음부터 다시 만들어야 했습니다. 실제 사내 문서는 매주 개정되고, 새로 올라오고, 폐기됩니다. 이 파트에서는 인덱스를 파일로 저장하고 바뀐 문서의 행만 고치는 코드를 작성합니다. 그리고 RAG 전체에서 이 인덱스가 어느 단계에 해당하는지 정리합니다. 임베딩 모델을 고르는 기준과, 과제가 RAG에 맞는지 판단하는 기준도 다룹니다.

이 파트를 마치면 다음을 할 수 있습니다.

  1. RAG를 인덱싱, 검색, 생성의 세 단계로 나누고, 각 단계가 언제 실행되는지와 응답이 틀렸을 때 어느 단계부터 확인하는지 설명합니다.
  2. 벡터 인덱스를 파일로 저장하고 불러오며, 문서 번호와 임베딩 모델의 이름을 함께 저장하는 이유를 설명합니다.
  3. 문서의 개정, 추가, 폐기를 바뀐 행만 고쳐 반영하고, 벡터와 문서 번호의 순서가 어긋나면 어떤 일이 생기는지 설명합니다.
  4. 임베딩 모델을 고르는 기준(언어, 최대 입력 길이, 차원, 실행 위치)을 말하고, 후보 모델을 같은 질문 세트로 측정해 비교합니다.
  5. 임베딩 모델을 바꾸면 인덱스 전체를 다시 만들어야 하는 이유를 실행 결과로 설명합니다.
  6. 과제가 RAG에 맞는지 문서의 분량, 문서가 바뀌는 빈도, 출처의 필요 여부로 판단합니다.

예제의 실행 결과는 2026-11-26에 실행한 값이고, 학습 노트북을 실행한 출력을 그대로 실었습니다. 검색 점수와 순위는 같은 임베딩 모델을 쓰면 거의 같은 값이 나옵니다. 이 파트의 예제는 생성 모델 API를 호출하지 않고 임베딩 모델만 PC에서 실행합니다. 노트북의 "준비 (2)" 셀 끝에 있는 연결 확인만 API를 한 번 부릅니다. API를 설정하지 않아 이 확인이 실패해도 앞에서 만든 이름은 그대로 쓸 수 있으므로 예제를 계속 실행해도 됩니다.

RAG의 세 단계 원본 p.22–30, 70

RAG는 인덱싱, 검색, 생성의 세 단계입니다. 인덱싱은 문서가 바뀔 때만 실행하고, 검색과 생성은 질문이 올 때마다 실행합니다. 응답이 틀리면 검색 결과부터 확인합니다.

2일차에서 RAG를 검색과 생성의 두 단계로 설명했습니다. 이 두 단계는 질문이 올 때마다 실행됩니다. 질문이 오기 전에 문서를 검색할 수 있게 준비해 두는 일이 하나 더 있고, 이를 인덱싱이라고 합니다. 인덱싱은 문서를 처리해 임베딩으로 바꾸고 벡터 인덱스에 넣는 일입니다. 문서 처리는 원본 문서에서 글을 뽑아 검색 단위로 자르는 일이며 파트 2에서 다룹니다. 인덱싱은 문서가 바뀔 때만 다시 실행합니다.

검색은 질문의 임베딩과 가까운 문서를 점수 순으로 찾습니다. 검색 결과에서 점수가 높은 k건을 top-k라고 합니다. k는 정수이고, RAG에서는 프롬프트에 넣을 문서의 건수입니다. 아래 그림과 표의 "상위 k건"이 top-k입니다.

세 단계를 비교하면 다음과 같습니다.

단계 실행 시점 받는 것 내보내는 것
인덱싱 문서가 바뀔 때 원본 문서 벡터 인덱스(문서의 임베딩)
검색 질문마다 질문 한 건 점수가 높은 순으로 정렬한 상위 k건
생성 질문마다 질문과 검색 결과 응답과 출처 문서 번호

RAG를 세 단계로 나누는 이유는 틀린 응답을 고칠 곳을 찾기 위해서입니다. 응답 하나만 보면 어느 단계가 틀렸는지 알 수 없습니다. 단계를 나누면 다음과 같이 고칠 곳을 정할 수 있습니다.

  • 문서가 바뀌었는데 응답이 옛 내용이면 인덱싱을 확인합니다.
  • 검색 결과에 질문과 관계없는 문서가 있으면 검색을 고칩니다.
  • 검색 결과는 맞는데 응답이 그 내용과 다르거나 형식이 틀리면 생성(프롬프트)을 고칩니다.

검색이 가져오지 못한 내용은 모델이 답할 수 없으므로, 응답이 이상하면 검색 결과부터 확인합니다.

이 교재는 검색을 먼저 만들고 문서 처리를 나중에 다룹니다. 실제 파이프라인에서는 문서 처리가 가장 앞입니다. 검색을 먼저 만들어 보면 문서를 어떻게 다듬어야 하는지가 검색 결과로 드러납니다.

벡터 DB와 벡터 인덱스 원본 p.35–38, 45–46, 51

벡터 인덱스를 파일로 저장해 두면 문서를 다시 임베딩하지 않아도 됩니다. 인덱스에는 벡터와 함께 문서 번호와 임베딩 모델의 이름을 저장합니다.

벡터 DB는 벡터 인덱스를 저장하고, 바뀐 문서의 행을 고치고, 질문과 가까운 벡터를 찾아 주는 시스템입니다. 서버로 운영하는 제품도 있고, 프로그램 안에서 쓰는 라이브러리도 있습니다. 이 교재에서는 numpy 배열 하나와 문서 번호 목록으로 같은 기능을 직접 구현합니다. 저장, 행 단위 갱신, 유사도 검색이라는 기능은 제품과 같고, 코드가 짧아서 안에서 무슨 일이 일어나는지 볼 수 있습니다. 다만 많은 제품은 검색을 빠르게 하려고 근사 검색(이 절의 끝에서 설명합니다)을 씁니다.

검색만 빠르게 해 주는 라이브러리도 있습니다. FAISS(C++로 작성했고 Python 바인딩을 제공합니다)는 모든 벡터와 비교하는 정확한 검색과 가까운 후보만 찾는 근사 검색을 모두 지원합니다. hnswlib는 HNSW(Hierarchical Navigable Small World)라는 그래프 기반 근사 검색 알고리즘을 구현했습니다. 근사 검색은 가장 가까운 벡터를 가끔 놓치는 대신, 모든 벡터와 비교하는 검색보다 빠릅니다. 어느 쪽을 쓰든 인덱싱, 검색, 생성의 단계 구분은 같습니다.

문서가 바뀔 때 원본 p.47–50

문서가 개정되면 그 행의 벡터를 다시 계산해 교체하고, 새 문서는 행을 추가하고, 폐기한 문서는 행을 삭제합니다. 벡터와 문서 번호를 따로 고치면 어긋나므로 한 객체에 묶어 함께 고칩니다.

문서가 바뀌었다고 인덱스 전체를 다시 만들지는 않습니다. 바뀐 문서의 행만 고칩니다.

  • 개정: 그 문서의 본문으로 벡터를 다시 계산해 같은 행을 교체합니다.
  • 신규: 벡터를 계산해 맨 아래에 행을 추가합니다.
  • 폐기: 그 문서의 행을 삭제합니다.

이때 조심할 점이 있습니다. 벡터 배열과 문서 번호 목록은 같은 순서여야 하는데, 둘을 따로 고치면 한쪽만 고치고 끝내는 실수가 생깁니다. 코퍼스에는 SOP-ETCH-012의 구판(v1.2)과 개정판(v2.0)이 모두 있습니다. 구판 문서의 벡터만 지우고 문서 번호 목록은 그대로 두면 어떻게 되는지 봅니다.

# 예제 1-2 (VectorIndex 클래스)
class VectorIndex:
    """벡터, 문서 번호, 본문을 한 객체에 두고 항상 같은 순서로 고칩니다."""

    def __init__(self, names, docs, vectors, model):
        if not len(names) == len(docs) == len(vectors):
            raise ValueError(f'개수가 다릅니다: 문서 번호 {len(names)}, 본문 {len(docs)}, 벡터 {len(vectors)}')
        self.names, self.docs, self.model = list(names), list(docs), model
        self.vectors = np.array(vectors)

    def __len__(self):
        return len(self.names)

    def search(self, query_vector, k=3):
        """질문 벡터와 가까운 상위 k건의 (문서 번호, 점수)를 돌려줍니다."""
        scores = self.vectors @ query_vector
        order = np.argsort(-scores, kind='stable')[:k]
        return [(self.names[row], round(float(scores[row]), 3)) for row in order]

    def rank_of(self, query_vector, gold):
        """정답 문서 gold가 몇 위인지 돌려줍니다. 1위가 1입니다."""
        order = list(np.argsort(-(self.vectors @ query_vector), kind='stable'))
        return order.index(self.names.index(gold)) + 1

    def replace(self, name, doc, vector):
        """개정: 같은 행의 본문과 벡터를 바꿉니다."""
        row = self.names.index(name)
        self.docs[row], self.vectors[row] = doc, vector

    def add(self, name, doc, vector):
        """신규: 맨 아래에 행을 추가합니다."""
        if name in self.names:
            raise ValueError(f'{name}은 이미 있습니다. 고치려면 replace()를 호출합니다')
        self.names.append(name)
        self.docs.append(doc)
        self.vectors = np.vstack([self.vectors, vector])

    def remove(self, name):
        """폐기: 그 문서의 행을 지웁니다."""
        row = self.names.index(name)
        del self.names[row], self.docs[row]
        self.vectors = np.delete(self.vectors, row, axis=0)

    def save(self, folder):
        np.save(f'{folder}/index.npy', self.vectors)
        with open(f'{folder}/index.json', 'w', encoding='utf-8') as file:
            json.dump({'model': self.model, 'names': self.names, 'docs': self.docs}, file, ensure_ascii=False)

    @classmethod
    def load(cls, folder, model=None):
        """저장한 인덱스를 불러옵니다. model을 주면 저장된 모델 이름과 같은지 확인하고, 다르면 ValueError를 냅니다."""
        with open(f'{folder}/index.json', encoding='utf-8') as file:
            saved = json.load(file)
        if model is not None and saved['model'] != model:
            raise ValueError(f'이 인덱스는 {saved["model"]}로 만들었는데 지금 모델은 {model}입니다')
        return cls(saved['names'], saved['docs'], np.load(f'{folder}/index.npy'), saved['model'])

임베딩 모델을 고르는 기준 원본 p.52–59

임베딩 모델은 한 번 정하면 바꾸기 비쌉니다. 한국어로 학습했는지, 최대 입력 길이, 차원, 실행 위치를 보고 후보를 고른 뒤 사내 질문 세트로 측정해 정합니다. 모델을 바꾸면 인덱스 전체를 다시 만들어야 합니다.

임베딩 모델은 글을 입력받아 벡터를 출력하고, 글을 생성하지 않습니다(2일차 파트 3). 그래서 고르는 기준도 생성 모델과 다릅니다. 응답의 품질이 아니라 의미가 비슷한 글을 가까운 벡터로 바꾸는지를 봅니다.

고르는 기준은 네 가지입니다.

  • 학습한 언어: 한국어 문장으로 학습한 모델이어야 합니다. 여러 언어로 학습한 모델(multilingual)이나 한국어 전용 모델이 해당합니다. 영어만으로 학습한 모델이 한국어 문서를 얼마나 찾는지는 예제 1-3에서 측정합니다.
  • 최대 입력 길이: 한 번에 읽을 수 있는 토큰 수의 상한입니다(최대 입력 길이). 이보다 긴 글은 뒷부분이 잘려서 벡터에 반영되지 않습니다. 생성 모델의 컨텍스트 윈도우와 별개로 임베딩 모델마다 정해져 있습니다. 문서를 청크로 나누는 이유가 여기에 있고, 파트 2에서 확인합니다.
  • 차원: 벡터의 숫자 개수입니다. 차원이 클수록 벡터 인덱스의 저장 크기와 검색 계산량이 늘어납니다. 이 교재의 모델은 384차원입니다.
  • 실행 위치: 모델을 PC에서 실행하는지, API로 호출하는지입니다. 회사 밖의 서버에 있는 API로 호출하면 문서의 글이 그 서버로 갑니다. 사내 문서를 밖으로 보낼 수 없다면 PC에서 실행하는 모델이나 사내 서버의 모델을 고릅니다. 이 교재의 임베딩 모델은 PC에서 실행하므로 문서가 PC 밖으로 나가지 않습니다. 생성 모델의 API에는 검색 결과로 고른 문서만 보냅니다.

공개 순위표는 후보를 고르는 데 씁니다. MTEB(Massive Text Embedding Benchmark)가 대표적이고, 임베딩 모델을 여러 언어와 과제에서 평가한 점수를 보여 줍니다. 이 점수는 공개 데이터셋에서 측정한 값입니다. 사내 문서에서 현장 말투, 약어, 문서 번호가 섞인 질문을 얼마나 찾는지는 알려 주지 않습니다. 후보 두세 개를 정한 뒤 사내 문서와 질문 세트로 recall@k를 측정해 최종으로 고릅니다.

MTEB가 임베딩 모델을 여러 언어와 과제에서 평가하는 벤치마크라는 설명은 MTEB 저장소의 README에서 확인했습니다(2026-11-24 확인).

한국어로 학습한 모델과 영어 전용 모델을 같은 질문 세트로 비교합니다. 영어 전용 모델로는 sentence-transformers/all-MiniLM-L6-v2를 씁니다. 이 모델도 384차원이어서, 차원을 같게 두고 학습한 언어의 효과를 비교할 수 있습니다. 비교 대상인 이 교재의 모델은 intfloat/multilingual-e5-small이고 여러 언어로 학습했습니다. 이 모델을 다국어 모델이라고 부릅니다. 영어 전용 모델을 내려받지 못하면 예제는 "건너뜁니다"를 출력하고 끝납니다.

RAG가 맞는 과제 원본 p.68–79

문서가 자주 바뀌고 답마다 출처가 필요한 지식은 RAG로 다룹니다. 문서가 한두 건이고 한 번 쓰고 끝나는 일은 프롬프트에 넣으면 됩니다. 데이터에서 계산해야 하는 질문은 RAG로 답할 수 없습니다.

RAG를 만드는 데는 인덱싱, 검색, 생성을 모두 운영하는 비용이 듭니다. 과제를 받으면 RAG를 만들기 전에 다음 네 가지를 순서대로 묻습니다.

  1. 답이 문서에 적혀 있습니까? 아니면 RAG가 아닙니다. 답이 공정 데이터나 센서 기록에 있고 계산이 필요한 질문은 문서를 검색해도 답이 나오지 않습니다. 데이터 분석 과제입니다.
  2. 문서 전체가 컨텍스트 윈도우에 들어갑니까? 들어가지 않으면 문서를 프롬프트에 모두 넣을 수 없으므로 RAG를 씁니다.
  3. 문서가 자주 바뀌거나 답마다 출처를 밝혀야 합니까? 그렇다면 RAG를 씁니다. 문서가 개정되면 해당 행만 갱신하고, 응답에 문서 번호를 붙일 수 있습니다.
  4. 문서가 한두 건이고 개정과 출처가 필요 없습니까? 그렇다면 문서를 프롬프트에 넣으면 됩니다. 인덱스를 만들 이유가 없습니다.

3번과 4번 어느 쪽도 아니면(예: 문서가 컨텍스트 윈도우에 들어가지만 수백 건이고, 개정이 드물며 출처도 필요 없을 때) 문서 분량과 질문 수로 요금을 비교해 정합니다.

문서가 많다는 것이 RAG를 쓰는 이유의 전부는 아닙니다. 2일차에서 문서 253건(70,937자)을 모두 프롬프트에 넣어도 모델이 답했습니다. 문서가 많아도 컨텍스트 윈도우에 들어가는 분량이면 모두 넣을 수 있습니다. 그래도 RAG를 쓰는 이유는 다음과 같습니다.

  • 문서를 모두 넣으면 질문마다 문서 전체의 입력 토큰 요금이 듭니다.
  • 문서가 개정될 때마다 프롬프트에 넣을 문서를 사람이 고르고 바꿔야 합니다. RAG는 인덱스에서 바뀐 행만 고칩니다.
  • 검색 결과 몇 건만 넣으면 응답의 근거가 될 수 있는 문서가 몇 건으로 줄어, 사람이 응답과 원문을 대조하기 쉽습니다.

핵심 정리

  • RAG는 인덱싱, 검색, 생성의 세 단계입니다. 인덱싱은 문서가 바뀔 때만, 검색과 생성은 질문마다 실행합니다. 응답이 틀리면 검색 결과부터 확인합니다.
  • 벡터 인덱스는 파일로 저장해 다시 씁니다. 벡터와 함께 문서 번호와 임베딩 모델의 이름을 저장합니다.
  • 문서가 바뀌면 바뀐 행만 고칩니다. 개정은 교체, 신규는 추가, 폐기는 삭제입니다. 벡터와 문서 번호를 한 객체에 두고 함께 고쳐 어긋남을 막습니다.
  • 갱신이 반영됐는지는 개정에서 새로 들어간 낱말을 넣은 질문의 순위로 확인합니다. 행 수만으로는 알 수 없고, 값이 맞는지는 본문을 열어 확인합니다.
  • 임베딩 모델은 한국어로 학습했는지, 최대 입력 길이, 차원, 실행 위치를 보고 후보를 정하고, 사내 질문 세트로 측정해 고릅니다. 모델을 바꾸면 인덱스 전체를 다시 만듭니다.
  • 문서가 컨텍스트 윈도우에 들어가지 않거나, 자주 바뀌고 출처가 필요하면 RAG를, 문서가 한두 건이고 한 번 쓰고 끝나면 프롬프트에 넣기를 씁니다. 답이 데이터에 있는 질문은 RAG로 답할 수 없습니다.

파트 2. 문서 처리 파이프라인

파트 1에서는 문서 253건의 벡터 인덱스를 만들고 고치는 방법을 다뤘습니다. 그 문서는 이미 정리된 Markdown 파일이었습니다. 실제 사내 문서는 PDF, 워드, 엑셀로 옵니다. 머리말과 쪽번호가 본문에 섞여 있고, 표는 칸마다 줄이 바뀌고, 엑셀에는 열 이름 위에 장식 줄이 있습니다. 이 파트에서는 그런 원본 문서에서 검색할 수 있는 청크를 만드는 일을 다룹니다.

이 파트를 마치면 다음을 할 수 있습니다.

  1. 문서 처리를 파싱, 정리, 청킹, 메타데이터 붙이기의 네 단계로 나누고, 각 단계에서 검색이 나빠지는 원인을 말합니다.
  2. PDF, DOCX, XLSX를 알맞은 도구로 열고, 형식마다 생기는 문제(PDF의 머리말과 표, XLSX의 장식 줄)를 실행해서 확인합니다.
  3. 여러 문서에 반복되는 줄을 찾아 지우는 규칙을 만들고, 이 방법이 틀리는 경우를 설명합니다.
  4. 표를 통째로 임베딩하면 최대 입력 길이를 넘는 뒷부분이 벡터에 반영되지 않는 것을 확인하고, 행을 한 문장으로 풀어 해결합니다.
  5. 문서를 글자 수, 문장, 문서 구조로 자르고 중첩을 주어 청크 수가 어떻게 변하는지 확인하며, 청크 크기를 질문 세트로 측정해 고릅니다. 질문이 적으면 결론이 뒤집힐 수 있다는 점을 설명합니다.
  6. 청크에 메타데이터를 붙여 검색 범위를 줄이고, 열리지 않는 파일을 실패 목록에 남기는 파이프라인 함수를 작성합니다.

예제의 실행 결과는 2026-11-26에 실행한 값이고, 학습 노트북을 실행한 출력을 그대로 실었습니다. 이 파트의 예제는 생성 모델 API를 호출하지 않고 임베딩 모델만 PC에서 실행합니다. 노트북의 "준비 (2)" 셀 끝에 있는 연결 확인만 API를 한 번 부릅니다. 검색 점수와 순위는 같은 임베딩 모델과 같은 라이브러리 버전에서 거의 같은 값이 나옵니다. PDF의 글자 수와 줄 수는 PDF를 여는 도구에 따라 다릅니다.

문서 처리는 파싱, 정리, 청킹, 메타데이터 붙이기의 네 단계입니다. 임베딩 모델은 이 단계가 만든 글만 보므로, 여기서 검색의 품질이 먼저 정해집니다.

임베딩 모델은 원본 파일을 보지 못하고 청크의 글만 받습니다. 청크에 머리말이 섞여 있거나 표의 뒷부분이 빠져 있으면 모델은 그 상태로 벡터를 만듭니다. 검색 결과가 이상할 때 모델이나 k를 먼저 바꾸기 쉽지만, 원인이 이 단계에 있을 수 있습니다. 이 파트에서 원인이 될 만한 것을 하나씩 실행해 확인합니다.

문서 처리는 네 단계로 이루어집니다.

청크(chunk)는 문서를 검색 단위로 자른 조각이고, 벡터 인덱스의 행 하나가 청크 하나입니다. 문서를 청크로 자르는 일이 청킹(chunking)입니다. 파트 1의 인덱스는 문서 한 건이 청크 하나였습니다.

그림처럼 형식마다 파서를 따로 두고 결과는 같은 청크 목록으로 모으면, 새 형식이 생겨도 파서 하나만 더하면 됩니다. 문서는 계속 개정되고 추가되므로 이 일은 한 번 하고 끝나지 않습니다. 사람이 파일을 손으로 정리하면 다음 달에 다시 해야 합니다. 정리 규칙을 코드로 만들어 두면 문서 묶음이 바뀔 때마다 같은 코드를 다시 실행합니다.

열리지 않은 파일을 알려 주는 것은 처리 보고뿐입니다. 처리 보고는 "파이프라인으로 묶기" 절에서 만듭니다.

PDF는 글자의 위치만 있고 제목과 본문의 구분이 없습니다. DOCX는 문단마다 스타일이 있어 제목을 알 수 있고, XLSX는 열 이름 위에 장식 줄이 붙어 있습니다. 형식마다 도구와 읽는 방법이 다릅니다.

파싱은 원본 파일에서 글을 뽑는 일입니다. 한 도구로 모든 형식을 열 수 없어서 형식마다 도구를 고릅니다. 아래 도구는 모두 파이썬 라이브러리이고, 3일차 "실습 환경 준비"의 명령으로 설치합니다.

  • PDF는 인쇄를 위한 형식입니다. 파일에는 글자와 그 위치만 있고 "이 줄이 제목"이라는 표시가 없습니다. 머리말과 바닥글이 본문과 같은 줄로 섞여 나오고, 표는 칸마다 줄이 바뀝니다. pypdf로 엽니다.
  • DOCX는 편집을 위한 형식입니다. 문단마다 스타일(Heading 1, Normal)이 있어서, 작성자가 제목 스타일을 썼다면 제목과 본문을 구분할 수 있습니다. 굵은 글씨만 쓰고 스타일이 Normal뿐인 DOCX는 PDF처럼 제목을 추측해야 합니다. python-docx로 엽니다. 원본이 DOCX로 남아 있으면 같은 문서의 PDF 대신 DOCX를 파싱합니다.
  • XLSX는 표 자체가 본문입니다. 사람이 보라고 만든 엑셀은 열 이름 위에 제목, 출력일, 빈 줄이 붙어 있어서, 첫 줄을 열 이름으로 읽으면 틀립니다. pandas의 read_excel로 열고, 병합된 제목처럼 셀의 정보를 보려면 openpyxl을 씁니다.

스캔한 PDF는 글자가 아니라 이미지여서 글을 뽑으면 0자가 나옵니다. 이런 파일에는 글자를 인식하는 단계(OCR, optical character recognition)가 앞에 하나 더 필요하고, 이 교재에서는 다루지 않습니다. 0자로 나온 파일은 실패 목록에 남깁니다. 이 파트의 process()(예제 2-7)는 글자가 없는 파일을 ValueError로 처리합니다.

머리말, 바닥글, 쪽번호는 본문이 아닌데 문서마다 되풀이되는 노이즈입니다. 문서 대부분에 나오는 줄을 세어 후보를 찾을 수 있지만, 같은 양식의 문서에서는 제목과 정형 문장도 후보에 들어오므로 사람이 읽고 지울 줄을 정합니다.

노이즈는 본문이 아닌데 문서마다 되풀이되는 줄입니다. 머리말, 바닥글, 쪽번호가 여기에 해당합니다. 노이즈가 들어간 청크는 그 글까지 벡터에 반영됩니다. 노이즈는 문서마다 같은 글이므로 청크를 구별하는 정보가 아닙니다.

노이즈를 지우는 규칙은 낱말 목록으로 만듭니다. 줄에 목록의 낱말이 들어 있거나 줄 전체가 - 1 - 꼴의 쪽번호이면 노이즈로 봅니다. 쪽번호 꼴은 정규식(regular expression, 문자열의 패턴을 기호로 적는 표기법)으로 적습니다. 낱말이 들어 있는 줄은 모두 지우므로, 본문 줄에 같은 낱말이 있으면 규칙이 본문 줄도 지웁니다("파이프라인으로 묶기" 절의 엑셀 사례).

DROP_WORDS = ['무단 반출 금지', '문서관리시스템', '문서번호']
PAGE_NUMBER = re.compile(r'-\s*\d+\s*-')


def is_noise(line, words=DROP_WORDS):
    """줄에 노이즈 낱말이 들어 있거나 쪽번호 줄이면 True. 공백을 뺀 글로 비교합니다."""
    squeezed = ''.join(line.split())
    return (any(''.join(word.split()) in squeezed for word in words)
            or bool(PAGE_NUMBER.fullmatch(line.strip())))

표를 통째로 임베딩하면 최대 입력 길이를 넘는 뒷부분의 행이 벡터에 반영되지 않습니다. 한 행을 한 문장으로 풀면 행마다 벡터가 생겨, 질문이 각 행과 직접 비교됩니다.

표는 RAG에서 다루기 어려운 문서 요소입니다. 사람은 열 이름을 보고 값의 뜻을 알지만, 글로 뽑은 표에서는 열 이름이 값 옆에 없어서 2026-07-11이 점검일인지 알 수 없습니다.

표를 다루는 방법은 세 가지입니다.

  • 표를 글 그대로 통째로 임베딩합니다.
  • 열의 위치를 살려 행마다 한 줄로 뽑습니다(PDF의 layout 모드).
  • 행마다 열 이름을 붙여 한 문장으로 풉니다.

청크 분할 원본 p.143–152

문서를 청크로 자르는 기준은 글자 수, 문장, 문서 구조입니다. 글자 수로 자르면 문장 한가운데가 끊기고, 문서 구조로 자르면 청크가 어느 문서의 어느 절인지 알 수 있습니다. 중첩을 주면 이웃한 청크가 겹치고, 문서가 청크보다 여러 배 길면 청크 수가 늘어납니다.

임베딩 모델은 최대 입력 길이를 넘는 부분을 잘라 내고, 검색은 답이 있는 대목을 찾아야 합니다. 그래서 긴 문서는 청크로 잘라 청크마다 벡터를 만듭니다. 청크 크기에는 상충 관계가 있습니다. 너무 작으면 문맥이 끊겨 청크만 봐서는 무엇에 대한 글인지 알 수 없고, 너무 크면 한 벡터에 여러 주제가 섞여 질문과 관련된 부분의 비중이 줄어 유사도가 낮아지고 프롬프트에 넣는 토큰도 늘어납니다. 이 교재의 문서는 짧아서(127~603자, 중앙값 272자) 길이 때문에 자를 필요는 거의 없습니다. 그래도 자르는 방법이 검색 결과를 바꾸는지 보기 위해 여러 방법을 비교합니다.

자르는 방법은 세 가지입니다.

  • 글자 수(fixed-size chunking): 정한 글자 수마다 자릅니다. 가장 단순하고, 문장 한가운데에서 끊길 수 있습니다.
  • 문장(sentence-based chunking): 마침표나 줄바꿈에서 끊고, 정한 길이에 가깝게 문장을 이어 붙입니다.
  • 문서 구조(structure-based chunking): ##로 시작하는 절 단위로 자르고, 청크 앞에 문서 제목을 붙입니다. 청크만 봐도 어느 문서의 어느 절인지 알 수 있습니다.

문서 구조로 자르려면 문서에 구조가 있어야 합니다. Markdown의 ##와 DOCX의 Heading 2는 구조이고, PDF는 구조가 없어 글자 수나 문장으로 자릅니다.

중첩(overlap)은 앞 청크의 끝부분을 다음 청크의 앞에도 넣어 이웃한 청크가 겹치게 하는 것입니다. 경계에 걸친 문장이 두 청크 어느 쪽에도 온전히 들어가지 않는 문제를 줄입니다. 중첩에는 비용이 있습니다. 청크 수가 늘고 그만큼 인덱스가 커지며 검색할 벡터가 늘어납니다.

def chunk_fixed(text, size=300, overlap=0):
    """size 글자씩 자릅니다. overlap 글자는 다음 청크의 앞에도 넣습니다."""
    step = size - overlap
    # 시작 위치는 len(text) - overlap 앞까지만 둡니다. 남은 글이 모두 앞 청크의 중첩 부분이면 새 청크를 만들지 않습니다
    return [text[start:start + size] for start in range(0, max(len(text) - overlap, 1), step)
            if text[start:start + size].strip()]


def chunk_sentences(text, size=300):
    """마침표나 줄바꿈에서 끊고, 길이가 size에 가깝게 문장을 이어 붙입니다."""
    pieces = re.split(r'(?<=[.!?])\s+|\n+', text)
    chunks, current = [], ''
    for piece in pieces:
        if current and len(current) + len(piece) > size:
            chunks.append(current.strip())
            current = ''
        current += piece + ' '
    if current.strip():
        chunks.append(current.strip())
    return chunks


def chunk_sections(text):
    """## 절 단위로 자르고, 청크 앞에 문서 제목을 붙입니다."""
    title = text.split('\n', 1)[0].lstrip('# ').strip()
    parts, current, heading = [], [], None
    for line in text.split('\n'):
        if line.startswith('## '):
            if current:
                parts.append((heading, '\n'.join(current)))
            heading, current = line[3:].strip(), []
        else:
            current.append(line)
    if current:
        parts.append((heading, '\n'.join(current)))
    return [f'[{title}] {heading or ""}\n{body}'.strip() for heading, body in parts if body.strip()]

청크 크기는 블로그의 권장값이 아니라 질문 세트로 측정해 정합니다. 질문 세트가 달라지면 크기의 순서가 달라지므로, 이 코퍼스에서는 청크 크기에 따른 차이를 말할 수 없습니다.

"청크는 500토큰, 중첩 50토큰" 같은 권장값은 누군가의 문서에서 나온 결과입니다. 내 문서에도 맞는지는 알 수 없습니다. 청크 크기와 중첩은 바꿀 수 있는 설정이고, 바꾼 설정이 좋아졌는지는 같은 질문 세트로 측정해야 알 수 있습니다. 질문 세트는 질문마다 정답 문서를 사람이 정해 둔 것입니다. 질문은 실제로 받은 문의나 인수인계 문서의 Q&A에서 모읍니다.

청크로 자르면 검색 결과도 청크 단위가 되므로, 측정 방법도 청크 단위로 바꿉니다. 점수가 높은 청크 순서로 정렬해 다음 두 값을 구합니다. 2일차 파트 3의 recall@k를 청크 단위로 센 것입니다. 정답 문서의 청크가 상위 k개 안에 있으면 맞힌 것으로 셉니다.

  • recall@1: 1위 청크가 정답 문서의 청크인 질문의 비율입니다.
  • recall@3: 상위 3개 청크 가운데 정답 문서의 청크가 있는 질문의 비율입니다.

측정에는 질문 세트 두 가지를 씁니다. 청크 크기 측정용으로 만든 질문 10개(청크_질문_10.csv)와 2일차 파트 3의 질문 20개(검색_질문_20.csv)입니다.

def index_chunks(split, texts=docs):
    """문서마다 split으로 자르고 (청크의 벡터 배열, 청크의 문서 번호 목록)을 돌려줍니다."""
    chunks, owners = [], []
    for name, text in zip(names, texts):
        for chunk in split(text):
            chunks.append(chunk)
            owners.append(name)
    return embed.passages(chunks), owners


def measure(vectors, owners, questions):
    """(recall@1 %, recall@3 %, 1위와 4위 청크의 점수 차 평균)을 돌려줍니다."""
    recall1 = recall3 = gap = 0
    for question, gold in zip(questions['질문'], questions['정답']):
        scores = vectors @ embed.query(question)
        order = np.argsort(-scores, kind='stable')
        found = [owners[position] for position in order[:3]]
        recall1 += found[0] == gold
        recall3 += gold in found
        gap += scores[order[0]] - scores[order[3]]
    count = len(questions)
    return recall1 / count * 100, recall3 / count * 100, gap / count

def front_matter(text):
    """문서 맨 앞의 --- 로 둘러싼 부분을 (dict, 나머지 본문)으로 나눕니다. 없으면 ({}, 전체)."""

    return {key: value for key, value in pairs}, body

지금까지 만든 부분을 함수 하나로 묶습니다. 파서는 형식별로 따로 있고, 청킹과 메타데이터는 형식과 관계없이 같은 코드를 씁니다. 정리의 노이즈 규칙은 엑셀을 뺀 형식에 적용합니다. 엑셀의 행 문장은 표의 데이터이기 때문입니다. 이 함수의 청킹은 글자 수(400자)로만 자르고, DOCX의 Heading 2 같은 구조 정보는 쓰지 않습니다.

  • 열린 파일 수: 파이프라인이 실제로 처리한 파일의 수입니다.
  • 지운 줄 수: 정리 단계가 지운 줄의 수입니다. 갑자기 늘거나 줄면 문서 양식이나 노이즈 규칙이 바뀐 것일 수 있습니다.
  • 열리지 않은 파일: 파일 이름과 오류의 이름입니다. 파일 한 건이 열리지 않아도 나머지는 계속 처리합니다.

def read_xlsx(path):
    """엑셀의 각 행을 '열 이름 값, 열 이름 값' 한 줄로 만들어 줄바꿈으로 이어 돌려줍니다."""
    table = pd.read_excel(path, skiprows=SKIP_ROWS[Path(path).stem])
    return '\n'.join(', '.join(f'{column} {value}' for column, value in row.items() if pd.notna(value))
                     for _, row in table.iterrows())


def read_file(path):
    """형식에 맞는 도구로 파일을 열어 글을 돌려줍니다. 열리지 않거나 글자가 없으면 오류를 발생시킵니다."""
    suffix = Path(path).suffix.lower()
    if suffix == '.pdf':
        text = '\n'.join(page.extract_text() for page in PdfReader(path).pages)
    elif suffix == '.docx':
        text = '\n'.join(paragraph.text for paragraph in Document(path).paragraphs)
    elif suffix == '.xlsx':
        text = read_xlsx(path)
    else:
        _, text = front_matter(open(path, encoding='utf-8').read())   # front matter는 본문이 아니므로 뺍니다(예제 2-6)
    if not text.strip():
        raise ValueError('글자 없음')                    # 스캔한 PDF처럼 글자가 0자인 파일도 실패 목록에 남깁니다
    return text


def process(root, size=400):
    """폴더 아래의 모든 파일을 열어 (청크 목록, 처리 보고)를 돌려줍니다."""
    chunks, report = [], {'열린 파일': 0, '지운 줄': 0, '실패': []}
    for path in sorted(Path(root).rglob('*')):
        if not path.is_file():
            continue
        try:
            text = read_file(path)
        except Exception as error:                       # 열리지 않은 파일은 목록에 남기고 계속합니다
            report['실패'].append((path.name, type(error).__name__))
            continue
        lines = [CONTROL.sub('', line).strip() for line in text.split('\n') if line.strip()]
        if path.suffix.lower() != '.xlsx':                # 엑셀의 행 문장은 표의 데이터이므로 노이즈 규칙을 적용하지 않습니다
            kept = [line for line in lines if not is_noise(line)]
        else:
            kept = lines
        report['열린 파일'] += 1
        report['지운 줄'] += len(lines) - len(kept)
        for piece in chunk_fixed('\n'.join(kept), size):
            chunks.append({'doc_id': path.stem, 'type': type_of(path.stem), 'version': version_of(path.stem),
                           'dept': dept_of('\n'.join(kept)), 'source': path.name, 'text': piece})
    return chunks, report

핵심 정리

  • 문서 처리는 파싱, 정리, 청킹, 메타데이터 붙이기의 네 단계이고, 임베딩 모델은 그 결과인 청크의 글만 봅니다. 검색이 이상하면 이 단계의 결과를 먼저 읽습니다.
  • PDF는 구조 정보가 없고 머리말과 표가 섞입니다. 제목 스타일을 쓴 DOCX는 구조를 그대로 쓸 수 있고, XLSX는 건너뛸 장식 줄의 수가 파일마다 다릅니다. 원본이 DOCX로 남아 있으면 PDF 대신 DOCX를 씁니다.
  • 반복 줄 탐지는 후보를 찾는 도구입니다. 같은 양식의 문서에서는 제목과 정형 문장도 후보에 들어오므로 지우기 전에 사람이 읽습니다.
  • 표를 통째로 임베딩하면 최대 입력 길이를 넘는 뒷부분이 벡터에 반영되지 않습니다. 행을 열 이름이 붙은 한 문장으로 풀어 넣습니다.
  • 청크 크기는 권장값이 아니라 질문 세트로 측정해 정하고, 질문이 적으면 크기의 순서가 바뀔 수 있습니다. 중첩은 문서가 청크보다 여러 배 길 때 청크 수를 늘립니다.
  • 메타데이터는 청크를 만들 때 붙이고, 같은 뜻의 값은 하나로 정리합니다. 열리지 않은 파일은 처리 보고의 실패 목록에 남깁니다.

자가점검

1. 같은 회의록이 PDF와 DOCX로 모두 남아 있습니다. 어느 쪽을 파싱해야 하고, 그 이유는 무엇입니까?

정답 보기

DOCX를 파싱합니다. 작성자가 제목 스타일(Heading 1, Heading 2)을 썼다면 제목과 본문이 구분되어, 제목을 추측하는 규칙 없이 절 단위로 자를 수 있습니다. 스타일이 Normal뿐이면 DOCX도 제목을 추측해야 합니다. PDF에는 글자와 위치만 있어서 제목을 규칙으로 추측해야 합니다.

2. 전체 문서의 80%를 넘는 문서에 나오는 줄을 세어 반복 줄을 찾았더니 회의록 10건에서 "논의 사항", "결정 사항"이 후보로 나왔습니다. 후보를 모두 지워도 됩니까?

  • A. 지워도 된다. 80%를 넘는 문서에 나오는 줄은 확실히 머리말이나 바닥글이다
  • B. 지우면 안 된다. 같은 양식의 문서에서는 절 제목과 정형 문장도 반복되므로 사람이 후보를 읽고 지울 줄을 정한다
  • C. 80%를 90%로 올리면 후보가 정확해지므로 그때는 지워도 된다
정답 보기

B. 회의록은 양식이 같아서 절 제목과 정형 문장이 문서마다 똑같이 나옵니다. 반복 줄 탐지는 후보를 찾는 도구이고, 지울 줄은 사람이 읽고 정합니다(예제 2-2).

3. 모든 문서에 같은 머리말과 바닥글이 남아 있는 채로 임베딩하면 검색에 어떤 일이 생깁니까?

정답 보기

청크끼리의 유사도 평균이 올라갑니다(분할 없음 0.865에서 0.892). 글자 수로 자른 경우에는 청크 수도 늘어납니다(글자 100은 825건에서 990건). 이 코퍼스에서 질문 20개의 recall@3은 달라지지 않았고, 점수 차도 눈에 띄게 줄지 않았습니다(분할 없음 0.0226에서 0.0210). 순위를 해치지는 않았지만, 문서마다 같은 글은 청크를 구별하는 정보가 아니고 청크 수와 입력 토큰만 늘어나므로 지웁니다(예제 2-5).

4. 30행짜리 표를 통째로 임베딩했더니 마지막 행을 묻는 질문에서 그 행이 검색되지 않습니다. 원인과 해결 방법은 무엇입니까?

정답 보기

표 전체가 722토큰이어서 임베딩 모델의 최대 입력 길이 512토큰을 넘기 때문입니다. 넘는 뒷부분은 벡터에 반영되지 않았고, 임베딩 결과에는 오류도 경고도 나타나지 않았습니다. 행마다 열 이름을 붙여 한 문장으로 풀면 행마다 벡터가 생겨, 질문이 각 행과 직접 비교됩니다(예제 2-3).

5. 질문 10개로 측정했더니 100자 청크의 recall@3이 60%, 400자 청크가 80%였습니다. 이 결과만으로 "청크는 클수록 좋다"고 결론 내려도 됩니까?

정답 보기

안 됩니다. 같은 인덱스를 질문 20개로 측정하면 글자 100의 recall@3이 95%로 가장 높아 순서가 달라집니다(예제 2-5). 두 질문 세트 모두 가장 높은 값과 낮은 값의 차이가 질문 두 개 수준이어서, 질문 세트가 달라지면 크기의 순서가 바뀝니다. 이 코퍼스는 문서가 짧아(중앙값 272자) 크기를 바꿔도 청크가 크게 달라지지 않습니다. 청크 크기는 내 문서와 질문 세트로 측정해 정하고, 질문이 열 개 안팎이면 결론을 내리지 않습니다.

6. 청크에 중첩을 주면 어떤 일이 일어나고 어떤 비용이 듭니까?

  • A. 경계에 걸친 문장이 잘리는 문제를 줄이지만 청크 수와 인덱스 크기가 늘어난다
  • B. 청크 수와 인덱스 크기는 그대로이고 검색 점수만 올라간다
  • C. 문서가 짧아 청크가 한두 개뿐일 때 효과가 가장 크다
정답 보기

A. 앞 청크의 끝부분을 다음 청크의 앞에도 넣으므로, 문서가 청크보다 여러 배 길면 청크 수가 늘어납니다. 200자 청크에 중첩 60자를 주면 청크가 469건에서 526건(1.12배)이 됩니다(예제 2-5). 문서가 짧아 청크가 한두 개뿐이면 경계가 적어 효과가 작고, 400자 청크에서는 청크 수도 282건 그대로였습니다(예제 2-4).

7. 청크에 문서 유형, 버전, 날짜, 부서 같은 메타데이터를 붙이는 이유는 무엇입니까? 부서 값이 총무팀/설비기술팀처럼 적힌 문서가 있을 때 주의할 점은 무엇입니까?

정답 보기

임베딩 점수로는 알 수 없는 조건(유형, 최신 여부, 부서)으로 검색 범위를 필터링하고, 응답에 출처를 붙이기 위해서입니다. 총무팀/설비기술팀을 그대로 비교하면 "설비기술팀" 필터에서 그 문서의 청크가 빠지므로, 필터링 전에 /로 나눠 값을 정리해야 합니다(예제 2-6).

8. 문서 묶음에서 한 파일이 열리지 않았는데 오류 메시지가 나오지 않았고, 한 달 뒤 "그 문서는 왜 검색이 안 되느냐"는 문의가 왔습니다. 파이프라인을 어떻게 고쳐야 합니까?

정답 보기

파일이 열리지 않아도 나머지를 계속 처리하되, 열리지 않은 파일의 이름과 오류의 이름을 처리 보고의 실패 목록에 남깁니다. 열린 파일 수와 지운 줄 수도 함께 기록하면 어떤 문서가 인덱스에 들어가지 못했는지 바로 알 수 있습니다(예제 2-7).

파트 3. 첫 RAG 완성

파트 1에서는 벡터 인덱스를 파일로 저장하고 고치는 방법을 다뤘고, 파트 2에서는 문서를 청크로 자르고 메타데이터를 붙이는 함수를 만들었습니다. 이 파트에서는 그것들을 모아 RAG를 완성합니다. 질문을 검색하고, 찾은 문서를 프롬프트에 넣고, 출처가 붙은 응답을 받습니다. 그리고 RAG가 오류 없이 틀리는 경우를 일부러 만들어 보고, 응답이 이상할 때 어디부터 확인하는지 정합니다.

이 파트를 마치면 다음을 할 수 있습니다.

  1. 검색 결과를 프롬프트에 넣어 응답과 출처를 받고, 문서 없이 물었을 때의 응답과 비교해 달라진 점을 말합니다.
  2. RAG 프롬프트를 역할 지정, 검색 결과, 출력 규칙, 근거 없음 규칙(예제 3-3에서 설명합니다)으로 구성하고, 근거 없음 규칙을 뺐을 때 생기는 일을 보여 줍니다.
  3. 출처가 안정적으로 붙으려면 검색 결과의 청크마다 문서 번호를 붙이는 것과 출력 규칙에서 요구하는 것이 모두 필요하다는 점을 실행해 확인합니다.
  4. RAG가 오류 없이 틀리는 세 경우(관련 없는 문서가 상위를 채움, 버전 충돌, 절이 문서의 맥락을 잃음)를 증상으로 알아보고 각각의 대책을 적용해 효과를 확인합니다.
  5. 응답이 이상할 때 검색 결과부터 확인하는 진단 함수를 작성하고, 점수만으로는 답이 있는 질문과 없는 질문을 구분할 수 없다는 점을 설명합니다.
  6. 새 문서 묶음으로 RAG를 구성해 질문을 진단하고, 구판이 섞였을 때 고칩니다.

예제의 실행 결과는 2026-11-26에 실행한 값이고, 학습 노트북을 실행한 출력을 그대로 실었습니다. 모델의 응답은 실행할 때마다 조금씩 다릅니다. 검색 결과(점수, 문서, 절)는 인덱스가 같으면 거의 같은 값이 나옵니다. 이 파트의 예제는 LLM API를 약 40회 호출하므로 API 요금이 듭니다. 응답이 실행마다 다른 예제는 같은 요청을 세 번씩 보내 결과를 셉니다.

def read_manifest(path):
    """문서 목록 파일을 {파일 이름: 메타데이터}로 읽습니다."""
    with open(path, encoding='utf-8-sig') as file:
        return {unicodedata.normalize('NFC', row['file']): row for row in csv.DictReader(file)}


def build_chunks(folder, manifest):
    """문서를 '## ' 절 단위로 잘라 메타데이터를 붙인 Chunk 목록을 돌려줍니다."""
    chunks = []
    for raw in sorted(os.listdir(folder)):
        file = unicodedata.normalize('NFC', raw)         # 한글 파일 이름을 목록 파일의 이름과 같은 형태로 맞춥니다
        if not file.endswith('.md'):
            continue
        meta = manifest[file]
        head, *sections = re.split(r'\n(?=## )', open(f'{folder}/{raw}', encoding='utf-8').read())
        for part in [head] + sections:
            part = part.strip()
            if not part:
                continue
            if sections and part == head.strip():
                part = '\n'.join(part.splitlines()[:8])      # 첫 조각은 제목과 문서 정보 줄까지만 둡니다
            title = part.splitlines()[0].lstrip('# ').strip()
            chunks.append(Chunk(meta['doc_id'], meta['version'], meta['type'], meta['date'], title, part[:1200]))
    return chunks


def build_index(folder, manifest):
    chunks = build_chunks(folder, manifest)
    return ChunkIndex(chunks, embed.passages([chunk.text for chunk in chunks]))


def search(index, question, k=4, exclude_types=()):
    """질문과 가까운 청크를 점수가 높은 순으로 k건 찾습니다. exclude_types에 든 유형의 문서는 뺍니다."""
    allowed = [row for row, chunk in enumerate(index.chunks) if chunk.type not in exclude_types]
    scores = index.vectors[allowed] @ embed.query(question)
    return [Hit(round(float(scores[row]), 3), *index.chunks[allowed[row]])
            for row in np.argsort(-scores, kind='stable')[:k]]

출처 표기 원본 p.236–237

출처가 안정적으로 붙게 하려면 검색 결과의 청크마다 문서 번호를 앞에 붙이고, 출력 규칙에서도 문장마다 그 번호를 붙이라고 요구합니다. 이 예제에서는 한쪽만 했을 때 대괄호 출처가 붙지 않거나(청크 표시만), 붙어도 인용한 번호가 모두 한 문서의 번호였습니다(규칙만).

출처 표기가 없는 응답은 사람이 원문과 대조할 수 없어서 쓰기 어렵습니다. 최소한 문서 번호가 있어야 하고, 개정본이 있는 문서에는 버전도 필요합니다. 버전이 없으면 구판과 개정판 가운데 어느 쪽을 인용했는지 알 수 없습니다.

출처를 붙이게 하는 방법이 두 가지 있습니다. 청크마다 문서 번호를 앞에 붙여 프롬프트에 넣는 방법과, 출력 규칙으로 요구하는 방법입니다. 청크에 문서 번호가 없으면 모델이 번호를 알 수 있는 곳은 본문에 적힌 번호뿐이고, 규칙이 없으면 모델이 번호를 알아도 응답에 적지 않을 수 있습니다. 세 가지 조합을 각각 세 번씩 보내, 대괄호로 표기한 출처의 개수를 세고 인용한 문서 번호를 모읍니다.

RAG가 오류 없이 틀리는 세 경우 원본 p.238–273

RAG는 오류 없이 그럴듯하게 틀립니다. 틀리는 경우는 관련 없는 문서가 상위를 채움, 버전 충돌, 절이 문서의 맥락을 잃음의 세 가지입니다. 모두 검색 결과에서 원인이 드러나므로 응답이 이상하면 검색 결과부터 확인합니다.

RAG는 틀려도 오류가 나지 않습니다. 2일차 파트 1의 조용한 실패에 해당합니다. 응답은 그럴듯하게 나오고 출처까지 붙을 수 있습니다. 틀린 응답을 고치려면 원인이 검색에 있는지 생성에 있는지부터 판단해야 합니다. 먼저 검색 결과가 질문에 맞는지 봅니다. 여기서 "맞다"는 필요한 청크가 있고, 관련 없는 청크와 구판이 없다는 뜻입니다. 검색 결과가 맞는데 응답이 틀렸으면 프롬프트(생성)를 고칩니다. 검색 결과가 맞지 않으면 프롬프트를 고쳐도 근거가 늘지 않으므로 검색이나 인덱싱을 고칩니다. 코퍼스에 답이 없는 질문은 검색을 고쳐도 답할 수 없습니다. 이때는 근거 없음 규칙으로 찾지 못했다고 답하게 합니다. 아래 그림은 이 판단과 세 경우를 한 장에 정리한 것입니다.

def rank_of_section(index, question, doc_id, section):
    """문서 번호와 절 제목으로 청크를 찾아 (순위, 점수)를 돌려줍니다."""
    scores = index.vectors @ embed.query(question)
    for rank, row in enumerate(np.argsort(-scores, kind='stable'), 1):
        chunk = index.chunks[row]
        if chunk.doc_id == doc_id and chunk.section == section:

NO_EVIDENCE = '근거를 찾지 못했습니다'


def diagnose(question, k=4, index=None):
    """질문 하나를 RAG로 처리하고 (검색과 응답의 상태를 적은 딕셔너리, 응답 글)을 돌려줍니다."""
    text, found = ask(question, k, index=index or titled)
    shown = {f'{hit.doc_id}_{hit.version}' for hit in found} | {hit.doc_id for hit in found}
    cited = set(re.findall(r'\[([A-Z]+-[^\]\s]+)\]', text))
    versions = {(hit.doc_id, hit.version) for hit in found}
    row = {'질문': question[:20],
           '최고 점수': found[0].score,
           '1위-4위 차': round(found[0].score - found[min(3, len(found) - 1)].score, 3),
           '유형': '/'.join(hit.type for hit in found),
           '여러 판': '있음' if len(versions) > len({hit.doc_id for hit in found}) else '없음',
           '출처 표기': len(cited),
           '검색 결과에 없는 인용': len(cited - shown),
           '근거 없음': '예' if NO_EVIDENCE in text else '아니오'}
    return row, text

"구판과 개정판" 질문의 응답은 8.0 Torr, 허용 편차 ±0.4 Torr를 [SOP-ETCH-012_v2.0] 출처와 함께 답했습니다. 이 진단 함수는 문자열 비교로 출처와 근거 없음을 셉니다. 모델이 규칙의 문구와 다르게 "찾지 못했다"고 쓰면 "근거 없음"을 놓칠 수 있습니다. 반대로 응답의 일부에만 근거 없음 문구가 있어도 "예"로 셉니다. 예제 3-5의 구체적인 질문처럼 조치는 답하고 원인만 근거를 찾지 못했다고 한 응답도 "예"가 됩니다. 출처는 대괄호 하나에 번호 하나를 적은 것만 셉니다. [QIR-2026-0712, SOP-ETCH-007]처럼 대괄호 하나에 번호를 여러 개 적은 출처는 세지 않습니다. 같은 문서를 SOP-ETCH-012와 SOP-ETCH-012_v2.0으로 다르게 적으면 둘로 셉니다.

응답을 받았을 때는 다음 네 가지를 같은 순서로 확인합니다.

  1. 출처가 있습니까? 근거 없음 응답이 아닌데 출처가 없으면 지어낸 응답일 수 있습니다.
  2. 그 문서가 현행입니까? 버전과 날짜를 봅니다. 구판이면 인덱스에서 구판을 빼도록 문서 관리 담당자에게 요청합니다.
  3. 인용한 내용이 검색 결과에 실제로 있습니까? 인용한 문장을 검색 결과에서 찾습니다.
  4. 빠진 답은 없습니까? 질문이 둘인데 하나에만 답하지는 않았는지 봅니다.

RAG를 업무에 적용할 때는 코드 밖에서 정할 일이 네 가지 있습니다.

  1. 어떤 문서를 인덱스에 넣고 뺄지 정합니다. 구판과 초안은 빼는 것이 기본입니다.
  2. 문서가 개정되면 언제 인덱스에 반영할지와 누가 반영할지 정합니다.
  3. 누가 어느 문서를 검색할 수 있는지 정합니다.
  4. 틀린 응답을 받았을 때 어디에 알릴지 정합니다. 알리는 경로가 없으면 개선이 멈춥니다.

  • 구판을 넣었을 때와 뺐을 때 검색 결과 네 건의 판 구성과 응답의 값
  • 응답이 맞아도 구판을 인덱스에 남기면 안 되는 이유

핵심 정리

  • 검색 결과를 문서 번호와 함께 프롬프트에 넣으면 사내 기준의 값과 출처가 있는 응답이 나옵니다. 검색 결과를 많이 넣는다고 나아지지 않고, 필요한 청크가 들어 있어야 나아집니다.
  • RAG 프롬프트는 역할 지정, 검색 결과(재료), 출력 규칙(형식), 근거 없음 규칙(제약)으로 이루어집니다. 근거 없음 규칙이 없으면 없는 대상의 질문에 비슷한 다른 대상의 기준이 덧붙은 응답이 나올 수 있습니다.
  • 출처는 청크마다 문서 번호를 붙이는 것과 출력 규칙의 요구가 모두 있어야 안정적으로 붙습니다.
  • RAG는 오류 없이 틀립니다. 관련 없는 문서가 상위를 채움, 버전 충돌, 절이 문서의 맥락을 잃음의 세 경우는 모두 검색 결과에서 원인이 드러납니다.
  • 응답이 이상할 때는 검색 결과가 질문에 맞는지부터 봅니다. 필요한 청크가 있고 관련 없는 청크와 구판이 없으면 검색 결과가 맞는 것입니다. 검색 결과가 맞지 않으면 청킹, 메타데이터, 인덱스를 고칩니다. 검색 결과가 맞는데 응답이 틀렸을 때만 프롬프트를 고칩니다.
  • 점수만으로는 답이 있는 질문과 없는 질문을 구분할 수 없습니다. 점수 차, 유형, 여러 판, 출처, 근거 없음 응답을 함께 봅니다.

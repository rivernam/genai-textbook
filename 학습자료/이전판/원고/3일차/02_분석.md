## 3. 학습 목표 (제안)

이 파트를 마치면 다음을 할 수 있다.

1. 문서 처리를 파싱, 정리, 청크 분할, 메타데이터의 네 단계로 나누고, 각 단계에서 검색 품질이 나빠지는 원인을 말한다.
2. PDF, DOCX, XLSX를 각각 알맞은 도구로 열고, 형식마다 생기는 문제(PDF의 머리말과 표, XLSX의 장식 줄)를 실행해 확인한다.
3. 여러 문서에 반복되는 줄을 찾아 지우는 규칙을 만들고, 이 방법이 틀리는 경우를 설명한다.
4. 표를 통째로 임베딩하면 최대 입력 길이를 넘는 뒷부분이 벡터에 반영되지 않는다는 것을 확인하고, 행을 한 문장으로 풀어 해결한다.
5. 청크를 글자 수, 문서 구조로 자르고 중첩을 줘서 청크 수가 어떻게 변하는지 보이며, 청크 크기를 질문 세트로 측정해 고른다. 질문 수가 적으면 결론이 뒤집힐 수 있다는 점을 설명한다.
6. 청크에 메타데이터를 붙여 검색 범위를 줄이고, 열리지 않는 파일을 실패 목록으로 남기는 파이프라인 함수를 작성한다.

## 4. 고칠 내용

1. **"잘게 자를수록 나빠졌다" (p.158, 165).** 질문 10개로는 100자 top-3 60%, 400자 80%라서 원본은 "작게 자를수록 정확하다는 권장과 반대"라고 결론 내린다. 같은 코퍼스에 질문 20개를 쓰면 100자 95%, 400자 90%이고, top-1은 통문서가 85%로 가장 높다. 차이는 질문 한두 개 수준이고 크기의 순서가 질문 세트에 따라 뒤집힌다. 원본의 결론은 질문 10개에서만 성립한다. 두 결과를 나란히 보이고 "이 코퍼스에서는 청크 크기에 따른 차이를 말할 수 없다. 표본이 작으면 한두 건으로 순서가 바뀐다"로 고친다. 원본 p.159의 "코퍼스가 짧기 때문"이라는 설명도 문서 길이(127~603자, 중앙값 272자)를 숫자로 보이며 이어 쓴다. 이 결론은 2일차 파트 1의 "20건은 작은 표본"과 같은 이야기다.
2. **"반복되는 줄은 80%가 넘는 문서에 나오는 줄" (p.123).** 원본은 "거의 확실히 머리말·바닥글"이라고 하며 코드 조각만 보이고 실행하지 않는다. 실행해 보니 PDF 8건에서는 머리말, 바닥글, 쪽번호, 등급 줄이 정확히 잡힌다. DOCX 10건에서는 "논의 사항", "결정 사항"(회의록의 제목)과 "안건별 담당자는 회의 종료 후 파트장이 개별 통지했습니다."(본문 문장)도 80%를 넘어 반복 줄로 잡힌다. 같은 양식의 회의록은 제목과 정형 문장이 반복되기 때문이다. 이 규칙은 후보를 찾는 데 쓰고, 지우기 전에 사람이 후보를 읽어 확인한다고 고쳐 쓴다. 이 대비를 실행 결과로 보인다.
3. **노이즈가 검색을 망친다는 설명 (p.119, 퀴즈 7번).** 원본은 "유사도가 한곳에 몰려 변별이 사라집니다"라고 한다. 코퍼스 253건에 같은 바닥글을 모두 붙여 측정하니 문서끼리 유사도 평균이 0.865에서 0.892로, 최솟값이 0.791에서 0.825로 올랐다. 질문 20개의 1위와 4위의 점수 차는 평균 0.0226에서 0.0210으로 조금 줄었고, 정답 순위는 바뀌지 않았다(recall@1 85% → 90%, recall@3 90%). 점수가 올라가고 차이가 조금 줄어드는 것은 맞지만, 이 코퍼스에서는 순위를 해칠 정도는 아니었다. 청크가 작을수록 반복 줄이 차지하는 비율이 커진다는 가설은 100자 청크에서 같은 실험을 해 보고 본문에 싣는다. 원본의 단정("변별이 사라집니다")은 싣지 않는다.
4. **PDF 숫자와 도구 (p.113–115, 118).** 같은 PDF를 뽑은 결과가 도구와 버전에 따라 다르다(953자 / 933자 / 915자, 101줄 / 54줄 / 57줄). 노이즈 비율도 7.0%와 13.3%로 다르다. 원본의 숫자를 쓰지 않고 실행한 값을 싣고, 숫자가 도구에 따라 달라진다는 점을 한 줄로 적는다. `pdftotext`(poppler)는 사내 PC에 없을 수 있으므로(Windows에는 기본으로 없다) 설치가 필요 없는 `pypdf`를 기본으로 하고 `pdftotext`는 보충으로 둔다(8절 1번). `pypdf`의 layout 모드가 표의 행을 살리는 것은 확인했다.
5. **노이즈 낱말이 도구에 따라 안 걸린다.** 실습 미션 2의 `NEW_NOISE = ['기밀', '계속', 'Printed']`에서 "기밀"이 든 줄은 `pdftotext`로는 걸리지만 `pypdf`로 뽑으면 글자 사이가 벌어진 "기 밀 · 내 부 검 토 용 …"으로 나와 걸리지 않는다. 같은 원본도 추출 도구에 따라 규칙이 맞지 않을 수 있다. 실습의 재료가 이 사실을 보일 수 있다. 어느 도구로 뽑든 규칙은 추출 결과를 읽어 만든다고 적는다.
6. **표를 문장으로 푸는 템플릿 (p.134, 137).** 원본의 출력은 "SPEC-002 은 ETCH-06 호기에 적용되는 RCP-ETCH-693 관리 한계 이고, …"로 조사가 어색하다. 열 이름을 그대로 쓴 문장("SPEC-002: ETCH-06 적용, 문서명 RCP-ETCH-693 관리 한계, 개정일 2026-07-17, 버전 v1.0")으로 고쳐 쓴다. `df.itertuples()`의 `r._3`(열 이름에 공백이 있을 때 pandas가 붙이는 위치 이름)는 쓰지 않고 열 이름으로 접근한다.
7. **문장 경계 청크 분할 (p.147).** 정규식 `(?<=[.!?다])\s+`는 "다" 뒤의 공백에서 무조건 나눠서, 문장 중간의 "~하다 보면" 같은 곳도 자른다. 이 한계를 적고, 세 방법(글자 수, 문장 경계, 문서 구조)을 모두 같은 질문 세트로 측정한다. 원본은 문장 경계를 보이기만 하고 측정하지 않았다.
8. **부서 메타데이터 (p.176–177).** "총무팀/설비기술팀"처럼 두 부서가 `/`로 붙은 값이 30건(공지)이어서, 부서가 "설비기술팀"인 문서를 필터링하면 이 30건이 빠진다. 부서 값을 분리해 정규화하는 코드를 한 줄 더하고, 이 사례를 메타데이터 정규화의 이유로 쓴다. 날짜를 문자열로 비교하는 것(`>= '2026-01-01'`)은 ISO 형식(YYYY-MM-DD)일 때만 맞다는 점도 적는다.
9. **"경고 없이 뒤가 잘린다" (p.143).** `SentenceTransformer.encode()`는 최대 입력 길이를 넘는 부분을 조용히 자른다. 토크나이저를 직접 부르면 "722 > 512" 경고가 출력된다. 어느 경우에 경고가 나오는지 구분해서 쓰고, 최대 입력 길이는 `model.max_seq_length`로 읽는다.
10. **용어.** 꼬리표 → 메타데이터. 노이즈(본문이 아닌 반복 줄)는 파트 3의 "실패 1"의 이름과 겹친다. 파트 3에서 그 실패를 다르게 부른다(`03_분석.md` 4절 9번). 정제본 → 정제한 Markdown 문서. "적중률" → top-1, top-3(또는 recall@1, recall@3). "재다" 계열 구어체는 "측정"으로 바꾼다.

## 5. 추가할 내용

1. **이 파트에서 만드는 것.** 입력(PDF, DOCX, XLSX, MD)과 출력(청크 목록 한 줄에 본문과 메타데이터, 처리 보고)의 예를 첫 절에 보인다. 처리 보고는 처리한 파일 수, 걷어낸 줄 수, 실패한 파일 목록이다.
2. **파이프라인 그림.** 입구는 형식별 파서 넷, 출구는 하나(같은 모양의 청크)이고, 정리와 청크 분할은 공통이며, 실패와 처리 보고가 따로 남는다는 것을 시간 순서로 보인다.
3. **실패 목록 예제.** `docs_raw_m2_ext/`의 깨진 파일 두 건으로, 파이프라인 함수가 열지 못한 파일을 오류와 함께 목록으로 남기고 나머지를 계속 처리하는 것을 보인다. 열지 못한 파일이 목록에 없으면 "왜 이 문서는 검색이 안 되지"의 이유를 찾을 수 없다(p.140, 179).
4. **표본 크기 실험.** 같은 코드를 질문 10개와 20개로 돌려 결과가 뒤집히는 것을 보인다(4절 1번).
5. **반복 줄을 자동으로 찾기.** 4절 2번의 실행 결과(PDF에서 맞고 DOCX에서 틀린 것)를 예제로 싣는다.

- 확장 미션, 제출물, 체크포인트(p.190–194): 운영 안내다.
- 오류 모음(p.178): `UnicodeDecodeError`, `pdftotext not found`, 추출 결과 0자는 본문의 해당 위치에 한 문장씩 흩어 쓴다.

## 8. 확인해 주실 것

1. **PDF를 여는 도구.** `pypdf`(pip만으로 설치, 이 PC에 있음)를 기본으로 하고 `pdftotext`를 보충으로 두는 것을 제안한다. `pdftotext`는 별도로 설치해야 하고(poppler), 원본 강의는 코랩에서 `apt-get`으로 설치했다. 사내 PC에서 poppler를 쓸 수 있다면 알려 주시면 `pdftotext`를 기본으로 바꿀 수 있다.
2. **`python-docx` 설치.** DOCX 예제를 실제로 실행하려면 `python-docx`(PyPI의 작은 패키지)를 이 PC에 설치해야 한다. 설치해도 되는지 묻는다. 설치하지 않으면 DOCX 예제를 실행하지 못한 채로 "미실행"으로 표시한다.
3. **질문 세트를 2일차의 20개로 쓰는 것(4절 1번)과 실습 2를 함수 작성으로 바꾸는 것(7.3절).** 원본의 결론("잘게 자를수록 나빠졌다")이 사라진다.

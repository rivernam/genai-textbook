## 3. 학습 목표 (제안)

이 파트를 마치면 다음을 할 수 있다.

1. RAG를 인덱싱, 검색, 생성의 세 단계로 나누고, 각 단계가 언제 실행되는지와 응답이 틀렸을 때 어느 단계부터 확인하는지 설명한다.
2. 벡터 인덱스를 파일로 저장하고 불러오며, 문서 이름 목록과 임베딩 모델 이름을 함께 저장하는 이유를 설명한다.
3. 문서의 개정, 추가, 폐기를 바뀐 행만 고쳐 반영하고, 벡터와 문서 이름 목록의 순서가 어긋나면 어떤 일이 생기는지 보인다.
4. 임베딩 모델을 고르는 기준(언어, 차원, 최대 입력 길이, 실행 위치)을 말하고, 후보 모델을 같은 질문 세트로 측정해 비교한다.
5. 임베딩 모델을 바꾸면 인덱스 전체를 다시 만들어야 하는 이유를 실행 결과로 설명한다.
6. 과제가 RAG에 맞는지 판단한다. 판단에 쓰는 기준은 문서의 분량, 문서가 바뀌는 빈도, 출처의 필요 여부다.

## 4. 고칠 내용

1. **갱신을 확인하는 질문 (p.47–48).** 원본은 "온도 초과 판정을 몇 분으로 단축했나요"라는 질문의 순위가 4위에서 1위로 오르는 것을 보인다. 이 질문은 추가한 문장("상한 초과 판정 시간을 5분에서 3분으로 단축합니다")과 같은 낱말을 쓴다. 같은 문서를 다르게 물은 질문("ESC 온도가 높을 때 챔버가 멈추기까지 얼마나 걸리나요")은 반영 전에도 1위였다. 이 대비를 그대로 싣고, 갱신이 검색에 반영됐는지는 개정으로 새로 생긴 내용을 묻는 질문으로 확인한다는 기준을 적는다.
2. **예제 1-1의 (a), (b), (c) (p.37–43).** 2일차 파트 3에서 이미 만든 인덱스와 recall@k를 같은 질문 5개로 다시 측정한다. 질문 5개에서 80%와 100%는 한 문제 차이라서 2일차에서 "표본이 작다"고 고친 바로 그 측정이다. 이 파트에서는 `embed.passages()`로 인덱스를 만들고 2일차의 질문 20개로 한 번만 확인하는 정도로 줄이고, 시간을 저장·갱신에 쓴다.
3. **"벡터 DB"라는 이름 (p.37, 51).** 원본은 numpy 배열과 이름 목록을 "벡터 DB"라고 부른다. 벡터 DB는 보통 벡터의 저장, 갱신, 검색, 메타데이터 필터링을 제공하는 시스템을 가리킨다. 이 파트에서 만드는 것은 그 핵심 기능만 가진 최소 구현이라는 점, 문서가 수만 건 이하일 때는 이것으로 충분하다는 점을 먼저 밝힌다. "수십만 건이면 FAISS·hnswlib 같은 근사 검색으로 바꾼다"(p.321)는 원본의 말은 공식 문서를 확인한 뒤 이름과 역할만 한 문장으로 싣는다.
4. **지나친 단정 두 곳.**
   - "영어 전용 모델은 성능이 크게 떨어집니다"(p.56). 비교 예제로 보이기 전까지는 근거가 없는 문장이다. 예제 1-2의 실행 결과(질문 20개)를 근거로 쓴다.
   - "파인튜닝으로 말투를 바꾼다, RAG를 붙여도 말투는 안 바뀐다"(p.76, 퀴즈 6번). 말투와 형식은 프롬프트의 지시와 예시로도 대부분 바뀐다. 파인튜닝은 그렇게 해서 안정되지 않거나, 매 요청에 긴 지시를 넣는 비용이 클 때 고려한다. 공식 문서로 확인한 뒤 고치고, 퀴즈 6번의 정답 문장도 같이 고친다.
5. **업무 여섯 개의 판정 (p.74).** "신입 교육 자료 15건 → RAG", "QIR 59건 → RAG"라고 판정한다. 이 코퍼스에서 교육자료 15건은 3,449자, 품질이슈 59건은 16,064자다. 253건 전체가 70,937자이고 2일차에서 전부 넣어도 컨텍스트 윈도우에 들어갔다. 문서가 많아서 RAG가 필요하다는 근거는 숫자로 성립하지 않는다. 이 업무들이 RAG에 맞는 이유는 "매년 개정되고 답마다 출처가 필요하다"이다. 판정 근거를 분량, 개정 빈도, 출처의 세 기준으로 다시 쓰고, 분량은 유형별 글자 수를 직접 세어 보이는 예제를 추가한다.
6. **용어.** 이름표(names) → 문서 이름 목록. 꼬리표 → 메타데이터(파트 2에서 정의). 검색 적중률 → recall@k. 색인 → 인덱스(만드는 일은 인덱싱). "재다"(측정하다)와 "잽니다" 같은 구어체는 작성규칙의 검사 패턴에 걸리므로 모두 "측정"으로 바꾼다. 모델 이름은 코드에서 `embed` 모듈이 읽으므로 본문에 쓰지 않는다.

## 5. 추가할 내용

1. **이 파트에서 만드는 것.** 입력(문서 253건과 변경 목록)과 출력(파일로 저장되고 바뀐 행만 고쳐지는 벡터 인덱스, 검색 결과)의 예를 첫 절에 보인다.
2. **RAG의 세 단계를 시간 순서로 보인 그림.** 인덱싱은 문서가 바뀔 때, 검색과 생성은 질문마다 실행된다. 2일차 파트 3의 "검색, 생성" 그림을 인덱싱까지 넓히고, 이 교재의 파트 1~3이 각각 어느 칸을 만드는지 표시한다.
3. **인덱스에 모델 정보를 함께 저장.** 인덱스를 만든 임베딩 모델의 이름과 접두어 규칙을 파일에 같이 남긴다. 다른 모델로 질문을 임베딩해 검색하면 어떻게 되는지를 예제 1-3에서 보인다.
4. **벡터와 문서 이름 목록을 한 곳에 두는 최소 구현.** 원본은 배열 `E`, 목록 `names`, `docs`를 따로 고치고 "같은 자리를 함께 고쳐야 한다"고 말로 당부한다. 이 방식으로 어긋나는 사례를 먼저 보이고(2절 마지막 행), 세 가지를 한 객체(`VectorIndex`, 40줄 안팎)에 묶어 교체·추가·삭제가 항상 같이 일어나게 만든다. 모든 예제 코드는 원고에 전부 적는다.
5. **업무의 분량 세기.** 문서 유형별 글자 수와 건수를 세어, 전부 넣어도 되는 분량인지 판단하는 예제(2절의 유형별 글자 수는 이미 확인했다).

## 6. 삭제할 내용

- 오리엔테이션 p.1–16, 코랩을 여는 순서와 환경 준비 셀(p.31–34): 강의 운영과 코랩 안내다. 환경 준비는 `3일차/00_환경준비.md`로 새로 쓴다(`2일차/00_환경준비.md`와 같은 방식).
- 임베딩이 느릴 때의 배치 크기(p.38), recall@k를 반복하는 슬라이드(p.41–43), 점수 벌어짐 미리 보기(p.44, 본문이 없는 슬라이드): 같은 내용이 2일차 파트 3과 이 교재의 파트 3에 있다.
- 사내 구축과 API 사용을 비교한 표(p.58–59): 칸의 값이 이미지로만 남아 추출되지 않고, 주장에 근거가 없다. 임베딩 모델을 어디서 실행하는지는 "사내 문서를 외부 API로 보낼 수 있는가"라는 하나의 기준으로 줄인다.
- 제출물, 확장 미션 안내, 체크포인트, "실습 미션 1까지 하신 것"(p.92–98): 운영 안내다. 확장 미션의 `apply_changes` 함수 작성은 실습의 본 과제로 올린다(7.3절).

## 8. 확인해 주실 것

1. **영어 전용 임베딩 모델 내려받기.** 예제 1-3의 비교에는 `sentence-transformers/all-MiniLM-L6-v2`(약 90MB, Hugging Face)가 필요하고, 이 PC에는 없다. 내려받아도 되는지 묻는다. 허락이 없으면 이 비교를 싣지 않거나, 원본 슬라이드의 수치(질문 10개로 측정, 직접 실행하지 않은 값)를 "원본 강의의 결과"로 표시해 싣는다. 후자는 규칙(실행한 결과만 싣는다)에 어긋나서 권하지 않는다.
2. **`VectorIndex` 최소 구현을 추가하는 것(5절 4번).** 원본의 방식(배열과 목록을 따로 고침)을 먼저 보이고 어긋나는 사례를 거친 뒤 객체로 묶는다. 4일차에도 이 객체를 쓸 수 있다.
3. **갱신 확인 질문을 고치는 것(4절 1번)과 업무 판정을 분량 기준으로 고치는 것(4절 5번).** 강의에서 들은 판정("교육 자료 15건 → RAG")이 달라진다.

# 2일차 파트 2 "구조화 출력과 시스템 연동" 분석

대상: 원본 강의안 p.176–292(117쪽), 예제·실습 노트북의 파트 2 구간, 미션 2 재료(`2일차_미션2_재료.csv` 80건), 퀴즈 중 파트 2 문항(3, 4, 8, 9번).
이 문서는 교재 본문을 쓰기 전에 방향을 확인받기 위한 것이다. 확인 후에는 교재에 넣지 않는다.

**작성 후 달라진 점 (2026-11-19).** 사용자가 학습 목표와 순서를 작성자 판단에 맡기고 원본 재료를 그대로 쓸 필요가 없다고 했다. 실제 원고는 아래 구성안과 세 가지가 다르다. (1) 저장을 검증 뒤로 옮겼다. 순서는 배치 처리, 검증, 재실행 비교, 상태, 저장, 실행 기록이다. 학습 목표는 여섯 개가 됐다. (2) 실습 재료는 원본 80건을 다듬지 않고 새로 썼다. (3) 예제 번호 2-7 이후가 6.2절의 표와 다르다. 최종 대응표는 원고 끝의 "원본과 달라진 점"에 있다.

원본의 흐름은 유지할 만하다. "형식이 맞는 것과 값이 맞는 것은 다르다"는 결론, 그리고 허용값에서 `IT`를 빼 보는 실험은 구조화 출력의 한계를 잘 드러낸다.
문제는 네 가지다.

1. **구조화 출력이 왜 형식을 보장하는지 설명이 없다.** "스키마 모양의 JSON만 돌아옵니다"라는 결과만 있다. 원리(모델이 다음 토큰을 고를 때 스키마에 맞는 토큰만 허용한다)를 모르면 보장되는 것과 보장되지 않는 것을 구분하지 못한다.
2. **보장 범위를 실제보다 넓게 말한다.** 4절 1번.
3. **검증의 층이 섞여 있다.** "형식 검증"이라는 이름 아래 호출 실패, 응답 잘림, id 불일치, 분류값 이상이 한데 들어 있다. id 불일치는 형식이 아니라 값의 문제다. 무엇을 확인하면 무엇을 알 수 있는지가 흐려진다.
4. **실습이 "그대로 실행"이다.** 미션 2는 코드와 값이 모두 채워져 있고, 정답 라벨은 80건 중 10건뿐이라 정확도를 제대로 말할 수 없다.

## 2. 학습 목표 (제안)

이 파트를 마치면 다음을 할 수 있다.

1. 프롬프트로 JSON을 요청하는 방식과 구조화 출력의 차이를 설명하고, 구조화 출력이 보장하는 것과 보장하지 않는 것을 구분한다.
2. 저장할 표의 열에서 출발해 스키마를 설계한다(자료형, 허용값, 값이 없을 때의 처리, 필드 이름).
3. 한 건을 처리하는 함수를 배치 처리로 확장하고, 결과를 원본 표와 결합해 엑셀과 DB에 저장한다. 같은 배치를 다시 실행해도 행이 중복되지 않게 한다.
4. 형식 검증, 업무 규칙 검증, 재실행 비교, 정답 라벨 비교가 각각 무엇을 확인하는지 구분하고 코드로 구현한다.
5. 결과를 자동 처리, 사람 확인, 실패로 나누고, 사람이 확인할 범위와 남는 오류를 숫자로 말한다.

## 4. 고칠 내용

1. **"구조화 출력은 스키마 모양만 돌아옵니다" (p.192, 196).** 조건이 빠져 있다. 응답이 정상 종료했을 때만 성립한다. 2026-11-19에 직접 호출해 확인했다. `max_tokens`를 20으로 두면 종료 이유가 `max_tokens`이고 응답은 `{"분류": "긴급", "equipment": "3호기 `에서 끊겨 `json.loads`가 실패한다. 공식 문서도 거절(`refusal`)일 때는 스키마와 다를 수 있다고 적는다. 교재에는 "정상 종료한 응답에 한해 형식을 보장한다. 그래서 파트 1의 응답 검사를 그대로 둔다"로 쓴다.
2. **스키마에 쓸 수 없는 키워드가 있다는 설명이 없다.** `minimum`을 넣어 보내면 400 오류가 난다(같은 날 확인. 오류 문구는 `property 'minimum' is not supported`). 숫자 범위, 문자열 길이 같은 제약은 API가 받지 않으므로 코드에서 검사해야 한다. 이것이 "형식 검증을 통과해도 값 검증이 필요한 이유" 가운데 하나다.
3. **`safe()`가 모든 예외를 잡는다 (p.213).** `except Exception`은 호출 실패뿐 아니라 내 코드의 버그(`KeyError` 등)도 "호출 실패"로 기록한다. 오류 이름만 남겨 재시도할 수 있는 실패인지도 알 수 없다. 호출 오류(`CallError`)와 파싱·검증 오류만 잡고, 실패 종류를 함께 기록하게 고친다.
4. **`INSERT OR REPLACE`의 부작용 (p.225, p.256).** 원본은 "사람이 본 결과를 status 열에 다시 적어 둡니다"라고 하면서 같은 id를 `INSERT OR REPLACE`로 덮어쓴다. 이 문은 행 전체를 지우고 새로 넣으므로, 다시 실행하면 사람이 적어 둔 값이 사라진다. 덮어쓸 열을 지정하는 방법(`ON CONFLICT ... DO UPDATE`)과 이미 처리한 id를 건너뛰는 방법을 구분해 쓴다.
5. **상위 모델 재확인에 판정 기준이 없다 (p.247–249).** 소형 모델 1차, 2차, 중형 모델의 분류를 나란히 출력하고 끝난다. 어느 것이 맞는지 알 수 없어 "비싼 모델은 걸린 건에만 씁니다"라는 결론을 뒷받침하지 못한다. 예제 재료에는 정답 라벨이 있으므로(파트 1에서 작성) 재확인이 실제로 정확도를 올리는지 측정한다. 결과가 실행마다 달라질 수 있어, 본문의 결론은 특정 숫자에 묶지 않는다.
6. **두 실행의 비교가 행 순서에 기댄다 (p.244).** `first_run['category'].values != second_run['category'].values`는 한쪽에 실패한 행이 있으면 어긋난다. id로 결합해 비교한다.
7. **`stop != 'end_turn'`을 모두 "응답 잘림"으로 적는다 (p.238).** 거절도 잘림으로 기록된다. `llm.py`의 종료 이유(`end`, `max_tokens`, `refusal`, `other`)를 그대로 사유로 남긴다.
8. **`status()`가 전역 변수에 기댄다 (p.251).** 함수 밖의 `recheck`를 읽는다. 인자로 받게 고친다.
9. **깨진 실행 결과와 모델 이름.** 슬라이드 변환 과정에서 줄이 뒤섞인 코드와 결과(p.198, 241, 259 등)는 새로 실행한 결과로 대체한다. 모델은 파트 1과 같이 현행 모델을 쓴다.

참고로 확인한 것: "예상해 보세요"의 한글 키 문제(p.197)는 원본에 답이 없다. 직접 호출해 보니 한글 키 그대로 온다(`{"분류": "긴급", ...}`). 교재에는 "한글 키도 되지만 열 이름으로 쓸 것이므로 영문으로 쓴다"는 한 문장으로 넣는다.

### 6.5 `llm.py`와 사내 API 경로

구조화 출력은 두 API의 요청 방법이 다르고, OpenAI 호환 서버는 지원 범위가 서버마다 다르다. 이 파트에서 사내 API 독자가 막힐 가능성이 가장 큰 곳이다.

- `llm.send()`와 `llm.ask()`에 `schema` 인자를 더한다. Anthropic은 `output_config={'format': {'type': 'json_schema', 'schema': ...}}`로, OpenAI 호환은 `response_format={'type': 'json_schema', 'json_schema': {'name': ..., 'schema': ..., 'strict': True}}`로 보낸다(설치된 SDK의 타입 정의에서 확인).
- 사내 서버가 `json_schema`를 받지 않을 때를 위해 환경 변수 하나로 방식을 고른다: 스키마 강제(기본), JSON 형식만 강제(`json_object`), 프롬프트로만 요청. 뒤의 두 방식에서는 스키마를 프롬프트에 넣어 보낸다.
- 어느 방식이든 받은 JSON은 pydantic으로 검증한다. 서버가 형식을 강제하지 않는 환경에서는 이 검증이 형식을 지키는 유일한 수단이다. 그래서 pydantic을 심화가 아니라 본문 5절로 올린다. Claude의 `messages.parse()`는 "SDK가 같은 일을 대신 해 준다"는 보충으로 싣는다.
- 본문 3절에 "내 서버가 무엇을 지원하는지 확인하는 방법"을 넣는다. 예제 2-2를 실행해 오류가 나면 방식을 바꾸는 순서다.

`llm.py`를 바꾸므로 `tests/test_llm.py`에 두 API의 요청 본문을 확인하는 테스트를 더한다(로컬 가짜 HTTP 서버 사용).

### 6.6 용어집에 더할 용어

JSON 스키마, 구조화 출력, enum(허용값), 필수 필드, 파싱, 스키마 검증, 멱등성, 기본 키, upsert, 업무 규칙, 재현성, 정답 라벨, 정확도, 사람 확인. 원본의 "정답률"은 "정확도"로, "갈린 건"은 "결과가 달라진 건"으로 쓴다.

## 7. 확인하지 못하는 것과 추가 설치

- 사내 API가 `response_format`의 `json_schema`를 지원하는지는 여기서 확인할 수 없다. 세 방식을 모두 구현하고 로컬 가짜 서버로 요청 형식만 검증한다.
- 엑셀 저장에는 `openpyxl` 패키지가 필요하다. 환경 준비의 설치 명령에 `openpyxl`과 `pydantic`을 더한다.
- 예상 API 요금: 예제와 풀이를 한 번 실행하는 데 약 0.1–0.2달러(대부분 소형 모델, 100건을 서너 번).

## 8. 확인해 주실 것

1. 학습 목표 다섯 개와 본문 순서(6.1)가 원하시는 방향과 맞는지.
2. pydantic을 심화가 아니라 본문으로 올리는 것(6.5). 사내 API에서는 필수에 가깝다고 판단했다.
3. 엑셀과 SQLite 저장을 원본 분량대로 유지하는 것. 생성형 AI 개념은 아니지만 "다시 실행해도 중복되지 않게", "실행 조건을 남긴다"는 실무에서 자주 빠뜨리는 내용이라 유지하되, pandas와 SQL 문법 설명은 줄일 생각이다.
4. 실습 재료를 원본 80건을 다듬어 쓰고 정답 라벨을 80건 모두에 붙이는 것(6.4).
5. 사내 서버가 `json_schema` 방식의 구조화 출력을 지원하는지 아신다면 알려 주시면 좋다. 모르셔도 세 방식을 모두 넣으므로 진행에는 지장이 없다.

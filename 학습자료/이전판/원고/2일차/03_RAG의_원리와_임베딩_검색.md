# 파트 3. RAG의 원리와 임베딩 검색

파트 1과 2에서는 모델이 이미 아는 지식만으로 할 수 있는 일을 했습니다. 문의를 분류하는 데에는 사내 문서가 필요하지 않았습니다. 사내 규정이나 설비 기준을 묻는 질문은 다릅니다. 모델은 사내 문서를 학습하지 않았기 때문에 답할 근거가 없습니다. 이 파트에서는 질문에 맞는 문서를 찾아 프롬프트에 넣는 방법을 다룹니다. 문서 253건에서 질문에 맞는 문서를 찾는 검색을 만들고, 그 검색이 얼마나 맞는지 측정합니다.

이 파트를 마치면 다음을 할 수 있습니다.

1. 모델이 사내 문서를 모른다는 점을 확인하고, 문서를 모두 넣는 방식과 찾아서 넣는 방식의 입력 토큰과 요금을 비교해 검색이 필요한 이유를 숫자로 설명합니다.
2. 키워드 검색이 문서에 점수를 매기는 방법을 설명하고, 한국어에서 글을 나누는 단위가 결과를 어떻게 바꾸는지 실행해 보입니다.
3. 임베딩과 코사인 유사도를 설명하고, 문서를 벡터 인덱스로 만들어 질문과 가까운 문서를 찾는 `search()`를 작성합니다.
4. 정답 문서를 아는 질문 세트로 recall@k를 측정해 검색 방법을 비교합니다.
5. 검색 1위 문서를 열어 질문에 답하는 문서인지 판정하고, 점수만으로 판정하면 안 되는 이유를 설명합니다.
6. 찾은 문서를 프롬프트에 넣어 답하게 하고, RAG가 검색과 생성의 두 단계로 이루어진다는 점을 설명합니다.

예제의 실행 결과는 2026-11-26에 실행한 값이고, 학습 노트북을 실행한 출력을 그대로 실었습니다. 모델의 응답과 토큰 수는 실행할 때마다 조금씩 다릅니다. 검색 점수와 순위는 같은 임베딩 모델을 쓰면 거의 같은 값이 나옵니다.

문서 한 건은 다음과 같이 생겼습니다.

```
# SOP-ETCH-007 에치 장비 ESC 온도 관리 기준

- 적용 장비: ETCH-01 ~ ETCH-06 전 호기
- 개정일: 2026-02-17 (v2.1) · 작성: 설비기술팀 김성호 · 승인: 공정기술그룹장

## 관리 기준
- ESC(정전척) 온도의 정상 운전 범위는 **58.0 ~ 62.0°C** 입니다.
- **상한 62.0°C 를 5분 이상 지속 초과하면 챔버 인터락이 자동 작동**하여 신규 로트
  투입이 차단됩니다.
```

이 파트에서 만드는 것은 검색 함수입니다. 질문을 넣으면 문서의 순위와 점수가 나옵니다.

| 질문 | 1위 | 2위 | 3위 |
| --- | --- | --- | --- |
| 칠러가 안 도는 것 같은데 챔버가 멈추는 기준이 뭔가요 | `SOP-ETCH-007_v2.1` (0.861) | `QIR-2026-0703` (0.852) | `MTG-2026-W47` (0.843) |

질문에는 "ESC"나 "인터락"이라는 낱말이 없지만 검색은 ESC 온도 관리 기준 문서를 1위로 찾았습니다. 이 파트는 다음 순서로 진행합니다.

1. 모델이 사내 문서를 모른다는 것을 확인하고, 문서를 모두 넣으면 요금이 얼마나 드는지 계산합니다.
2. 낱말이 같은 문서를 찾는 키워드 검색을 만듭니다.
3. 글을 벡터로 바꿔 의미가 비슷한 문서를 찾는 임베딩 검색을 만듭니다.
4. 정답 문서를 아는 질문 20개로 두 검색을 측정합니다.
5. 1위 문서를 직접 열어 판정하고, 찾은 문서를 프롬프트에 넣어 응답을 받습니다.

## 모델은 사내 문서를 모른다 {원본 p.301-318}

:::요점
사내 규정을 근거 없이 물으면 모델은 답하지 못합니다. 해당 문서를 프롬프트에 넣으면 답합니다. 문서를 모두 넣어도 답하지만 질문마다 문서 전체의 토큰만큼 요금이 듭니다.
:::

모델은 학습한 글에 없는 내용을 알지 못합니다. 사내 규정, 설비 기준, 회의록은 공개된 적이 없으므로 학습한 글에 없습니다. 이런 질문에 답하게 하려면 근거가 되는 문서를 프롬프트에 넣어야 합니다. 1일차에서 이것을 [[그라운딩]]이라고 했습니다.

같은 질문을 세 가지 방법으로 보냅니다. 근거 없이 보내고, 해당 문서 한 건을 넣어 보내고, 문서 253건을 모두 넣어 보냅니다. 근거 없이 보내는 요청은 응답이 실행마다 다를 수 있으므로 세 번 보냅니다. 요청은 `llm.ask()`로 소형 모델에 보냅니다.

:::예제 3-1 근거 없이, 한 건을 넣어, 모두 넣어 보내기
```python
# 예제 3-1
QUESTION = '우리 공장 에치 장비의 ESC 온도 정상 운전 범위가 몇 도인가요? 숫자로 짧게 답해 주세요.'

for number in [1, 2, 3]:
    reply = llm.ask(QUESTION, model='소형', max_tokens=600)
    print(number, reply.text[:90].replace('\n', ' '))
```

해당 문서 한 건을 프롬프트에 넣어 다시 보냅니다.

```python
# 예제 3-1 (문서 한 건을 넣습니다)
CORPUS = f'{DATA}/corpus'
document = open(f'{CORPUS}/SOP-ETCH-007_v2.1.md', encoding='utf-8').read()

reply_one = llm.ask(f'다음 문서를 근거로 답해 주세요.\n\n{document}\n\n질문: {QUESTION}',
                    model='소형', max_tokens=600)
print(reply_one.text)
print('입력 토큰:', reply_one.input_tokens)
```

문서 253건을 모두 넣어 보냅니다.

```python
# 예제 3-1 (문서를 모두 넣습니다)
names = sorted(file[:-3] for file in os.listdir(CORPUS) if file.endswith('.md'))   # 문서 번호
docs = [open(f'{CORPUS}/{name}.md', encoding='utf-8').read() for name in names]    # names와 같은 순서의 본문
print(f'{len(docs)}건, 글자 수 {sum(len(doc) for doc in docs):,}')

everything = '\n\n'.join(docs)
reply_all = llm.ask(f'다음 문서들을 근거로 답해 주세요.\n\n{everything}\n\n질문: {QUESTION}',
                    model='소형', max_tokens=600, timeout=180)
print(reply_all.text[:200])
print(f'입력 토큰: {reply_all.input_tokens:,}')
```

두 방식의 입력 요금을 계산합니다.

```python
# 예제 3-1 (입력 요금을 비교합니다)
for label, tokens in [('한 건 넣기', reply_one.input_tokens), ('모두 넣기', reply_all.input_tokens)]:
    for alias in ['소형', '기본']:
        once = cost_usd(tokens, 0, alias)
        print(f'{label}, {alias} 모델, 입력 {tokens:,}토큰, 한 번 ${once:.4f}, 하루 1,000번 ${once * 1000:.2f}')
print(f'입력 토큰은 {reply_all.input_tokens / reply_one.input_tokens:.0f}배입니다')
```
:::

이번 실행에서 근거 없이 보낸 세 번은 모두 이 공장의 값은 알 수 없다고 답했습니다. 세 번째 응답에는 일반적인 범위(약 20~60°C)가 덧붙어 있었습니다. 이 범위는 이 공장의 기준과 다릅니다. 모델이 덧붙인 일반론을 사내 기준으로 옮겨 적으면 안 됩니다. 문서 한 건을 넣자 58.0~62.0°C라고 답했습니다. 문서를 모두 넣어도 같은 답이 나왔습니다. 달라진 것은 입력 토큰입니다. 문서를 모두 넣으면 질문 한 번에 문서 253건의 토큰을 모두 보냅니다.

문서를 모두 넣는 방식에는 세 가지 한계가 있습니다.

- **질문마다 문서 전체의 요금이 듭니다.** 위 결과의 요금은 입력만 계산한 값입니다. 질문 수가 늘면 그대로 곱해집니다.
- **문서 전체의 토큰 수가 컨텍스트 윈도우를 넘으면 보낼 수 없습니다.** 이 코퍼스는 입력 약 68,000토큰(예제 3-1)이라 컨텍스트 윈도우(현행 Claude 모델은 100만 토큰) 안에 들어갔지만, 실제 사내 문서는 이보다 훨씬 많습니다.
- **답과 관계없는 문서가 대부분입니다.** 질문 하나에 필요한 문서는 한두 건인데 나머지 250여 건도 입력 토큰으로 보냅니다. 첫 번째 한계에서 계산한 요금은 대부분 답과 관계없는 문서의 토큰에 드는 요금입니다.

문서가 몇 건뿐이고 질문이 드물다면 모두 넣는 방식이 더 간단합니다. 문서가 많아지면 질문에 필요한 문서만 찾아 넣어야 하고, 그 방식이 RAG입니다.

## RAG의 구조 {원본 p.319-320}

:::요점
RAG는 질문에 맞는 문서를 찾는 검색과, 찾은 문서를 넣어 응답을 만드는 생성의 두 단계입니다. 검색이 맞는 문서를 찾지 못하면 생성 단계에서 고칠 수 없습니다.
:::

[[RAG]](retrieval-augmented generation)는 질문과 관련된 문서를 검색해 프롬프트에 넣고 응답을 생성하는 방식입니다. 두 단계로 이루어집니다.

모델에 지식을 더하는 방법은 RAG만이 아닙니다. 세 가지를 비교하면 다음과 같습니다.

| 방법 | 지식을 모델에 주는 방법 | 미리 해 둘 일 | 문서가 바뀌면 할 일 |
| --- | --- | --- | --- |
| 프롬프트에 직접 넣기 | 필요한 문서를 사람이 골라 넣거나 모두 넣음 | 없음 | 넣는 문서를 바꿈 |
| RAG | 질문마다 관련 문서를 검색해 넣음 | 검색할 문서를 미리 처리해 둠 | 바뀐 문서만 다시 처리함 |
| [[파인튜닝]] | 모델을 추가로 학습시킴 | 학습 데이터를 만들고 학습시킴 | 다시 학습시킴 |

사내 문서처럼 자주 바뀌고 출처를 밝혀야 하는 지식에는 RAG를 씁니다. 응답의 형식과 말투는 먼저 프롬프트의 지시와 예시로 맞춥니다. 그래도 같은 지시에 형식이나 말투가 요청마다 달라지면 파인튜닝을 고려합니다. 파인튜닝은 6일차에서 다룹니다.

검색 방법은 두 가지를 차례로 만듭니다. 질문과 같은 낱말이 든 문서를 찾는 키워드 검색과, 의미가 비슷한 문서를 찾는 임베딩 검색입니다.

## 키워드 검색 {원본 p.323-340}

:::요점
키워드 검색은 낱말이 겹치는 문서를 찾습니다. 한국어는 낱말에 조사가 붙습니다. 공백으로만 나누면 "칠러가"와 "칠러"가 다른 낱말이 되므로, 글자 단위로 나누거나 조사를 떼어 냅니다. 같은 것을 다른 낱말로 부르는 질문은 찾지 못합니다.
:::

[[키워드 검색]]은 질문과 문서에 같은 낱말이 얼마나 들어 있는지로 점수를 매기는 검색입니다. 점수를 계산하는 방법으로 [[TF-IDF]]를 많이 씁니다. TF-IDF는 두 값을 곱합니다.

- TF(term frequency)는 그 낱말이 한 문서 안에 얼마나 자주 나오는지입니다. 자주 나올수록 큽니다.
- IDF(inverse document frequency)는 그 낱말이 얼마나 드문지입니다. 적은 수의 문서에만 나오는 낱말일수록 큽니다. "장비"처럼 거의 모든 문서에 나오는 낱말은 점수가 낮습니다.

`scikit-learn`의 `TfidfVectorizer`가 이 계산을 합니다. `token_pattern`은 글을 낱말로 나누는 규칙이고, `vocabulary_`는 문서에서 찾은 낱말의 목록(어휘)입니다. `fit_transform(문서 목록)`은 문서마다 어휘의 낱말별 TF-IDF 점수를 계산해 행렬로 돌려줍니다. 행 하나가 문서 하나의 점수를 나열한 TF-IDF 벡터입니다. `transform([질문])`은 같은 어휘로 질문의 TF-IDF 벡터를 계산합니다. `TfidfVectorizer`는 기본값(`norm='l2'`)으로 벡터의 길이를 1로 맞추므로, 두 결과를 곱한 값은 질문과 문서의 코사인 유사도입니다. 벡터와 코사인 유사도는 "임베딩과 유사도" 절에서 설명합니다.

검색이 맞았는지 판정하려면 정답을 먼저 정해 두어야 합니다. 질문에 답하는 내용이 들어 있다고 사람이 미리 정해 둔 문서를 [[정답 문서]]라고 합니다. 아래 질문의 정답 문서는 ESC 온도 관리 기준인 `SOP-ETCH-007_v2.1`입니다. 칠러 유량과 챔버 인터락의 기준이 이 문서에 있습니다.

:::예제 3-2 키워드 검색과 글을 나누는 단위
```python

from sklearn.feature_extraction.text import TfidfVectorizer

Q = '칠러가 안 도는 것 같은데 챔버가 멈추는 기준이 뭔가요'
GOLD = 'SOP-ETCH-007_v2.1'                                       # 정답 문서

word_tfidf = TfidfVectorizer(token_pattern=r'(?u)\b\w+\b')       # 공백과 문장 부호에서 나눈 낱말 단위. 한국어는 1글자 낱말도 많아 기본값(2글자 이상)과 달리 남깁니다
word_matrix = word_tfidf.fit_transform(docs)                     # 문서 × 낱말 점수 행렬
scores = (word_matrix @ word_tfidf.transform([Q]).T).toarray().ravel()
print(f'최고 점수 {scores.max()}, 0점인 문서 {int((scores == 0).sum())}건')
for word in ['칠러', '챔버', '기준', '칠러가', '챔버가', '기준이']:
    print(word, '→', '어휘에 있음' if word in word_tfidf.vocabulary_ else '어휘에 없음')
```

글자 2~3개 단위로 나누어 다시 검색합니다.

```python
# 예제 3-2 (글자 2~3개 단위로 나눕니다)
char_tfidf = TfidfVectorizer(analyzer='char_wb', ngram_range=(2, 3))
char_matrix = char_tfidf.fit_transform(docs)


def keyword_search(question, k=3):
    """글자 단위 TF-IDF 점수가 높은 순으로 상위 k건의 (문서 번호, 점수)를 돌려줍니다."""
    scores = (char_matrix @ char_tfidf.transform([question]).T).toarray().ravel()
    # argsort는 작은 값부터 정렬하므로 부호를 뒤집어 점수가 높은 순으로 정렬합니다
    return [(names[position], round(float(scores[position]), 3)) for position in np.argsort(-scores)[:k]]


print(keyword_search(Q))
```

낱말 단위로 나눈 첫 번째 검색에서는 문서 253건이 모두 0점입니다. 질문의 "칠러가", "챔버가", "기준이"가 문서의 "칠러", "챔버", "기준"과 다른 낱말로 계산됐기 때문입니다. 한국어는 낱말에 조사가 붙으므로 공백으로만 나누면 같은 낱말이 서로 다른 낱말이 됩니다.

글자 2~3개 단위로 나누자 정답 문서가 1위로 나왔습니다. "칠러가"를 "칠러", "러가"처럼 나누면 "칠러"가 문서와 겹칩니다. 글을 나누는 단위를 바꾼 것뿐이고 점수를 계산하는 방법은 같습니다. 한국어 키워드 검색에서는 이렇게 글자 단위로 나누거나, 형태소 분석기로 조사를 떼어 낸 뒤 낱말로 나눕니다. 형태소 분석기는 문장을 뜻을 가진 가장 작은 단위(형태소)로 나누고 조사와 어미를 구분하는 도구입니다. 예: Kiwi, MeCab-ko.

세 번째 코드는 키워드 검색이 놓치는 경우입니다. 문서는 "가스라인 퍼지", "ESC(정전척) 교체"라고 쓰는데 질문은 "가스 배관을 비울 때", "척을 갈 때"라고 물었습니다. 두 질문 모두 정답 문서가 1위가 아닙니다. 같은 것을 다른 낱말로 부르면 겹치는 글자가 줄어들고, 장비 이름만 같은 다른 문서가 앞에 옵니다.

키워드 검색이 잘 찾는 질문과 놓치는 질문은 다음과 같이 나뉩니다.

- 레시피 번호, 문서 번호, 알람 코드처럼 글자가 정확히 같아야 하는 말로 물으면 잘 찾습니다.
- 현장에서 쓰는 말과 문서에 적힌 말이 다르면 놓칩니다. 약어와 풀어 쓴 말(PM과 예방정비)도 같은 경우입니다.

## 임베딩과 유사도 {원본 p.341-352}

:::요점
임베딩 모델은 글을 벡터로 바꿉니다. 의미가 비슷한 글은 벡터의 방향이 비슷하고, 그 정도를 코사인 유사도로 계산합니다.
:::

[[임베딩]](embedding)은 글의 의미를 나타내도록 글을 고정된 길이의 [[벡터]]로 바꾼 것입니다. 벡터는 숫자를 순서대로 나열한 것이고, 숫자의 개수를 차원이라고 합니다. 의미가 비슷한 글은 벡터도 가깝습니다. 그래서 낱말이 하나도 겹치지 않아도 의미가 비슷한 문서를 찾을 수 있습니다.

글을 임베딩으로 바꾸는 모델을 [[임베딩 모델]]이라고 합니다. 지금까지 쓴 LLM과 다른 모델입니다.

- LLM은 글을 입력받아 글을 생성합니다. 임베딩 모델은 글을 입력받아 벡터 하나를 출력하고, 글을 생성하지 않습니다.
- 이 교재가 쓰는 `intfloat/multilingual-e5-small`은 약 470MB로 작아 PC에서 실행할 수 있고, 글 하나를 384차원 벡터로 바꿉니다. 임베딩 모델을 API로 쓸 수도 있습니다. Anthropic API는 임베딩 모델을 제공하지 않으므로 다른 제공자(예: Voyage AI)의 API를 씁니다. OpenAI 호환 API는 서버에 따라 임베딩 엔드포인트(`/v1/embeddings`)를 제공하기도 합니다.
- 문서와 질문은 같은 임베딩 모델로 바꿔야 비교할 수 있습니다. 모델이 다르면 벡터의 차원도, 각 숫자의 뜻도 다릅니다.

두 벡터가 얼마나 가까운지는 [[코사인 유사도]](cosine similarity)로 계산합니다. 코사인 유사도는 두 벡터의 방향이 얼마나 같은지 나타내는 값입니다. 같은 방향이면 1, 직각이면 0, 반대 방향이면 -1입니다. 벡터의 길이를 1로 맞춰 두면 계산이 간단해집니다. 같은 자리의 숫자끼리 곱해 모두 더한 값(내적)이 곧 코사인 유사도입니다. 파이썬에서는 `a @ b`로 계산합니다. 예제 3-2의 키워드 검색이 계산한 점수도 길이를 1로 맞춘 TF-IDF 벡터끼리의 코사인 유사도입니다.

임베딩 모델은 `embed.py`로 불러옵니다. `embed.load()`는 PC에 저장된 모델이 있으면 그것을 쓰고, 없으면 내려받습니다. 모델은 처음 한 번만 내려받습니다.

:::주의
사내에서는 모델을 사내 Hugging Face 프록시에서 내려받습니다. 프록시 주소는 환경 변수 `HF_ENDPOINT`에 넣고, Jupyter를 시작하기 전에 설정합니다. 설정하지 않았다면 `embed.load()`가 주소를 물어봅니다. 입력한 주소는 화면에 보이지 않고 노트북 파일에도 저장되지 않습니다. 설정 방법은 "실습 환경 준비"의 "임베딩 모델 준비" 절에 있습니다.
:::

이 모델에는 사용 규칙이 하나 있습니다. 문서로 쓸 글 앞에는 `passage: `를, 질문 앞에는 `query: `를 붙입니다(콜론 뒤에 공백 한 칸). 이렇게 글 앞에 붙이는 글자를 접두어(prefix)라고 합니다. 모델이 접두어를 붙인 글로 학습됐기 때문이고, 모델 카드에 적혀 있는 규칙입니다. 모델 카드는 Hugging Face에서 모델마다 사용법과 한계를 적어 둔 설명 문서입니다. 접두어를 빼도 오류는 나지 않지만, 모델 카드에 따르면 검색 성능이 떨어집니다. `normalize_embeddings=True`는 벡터의 길이를 1로 맞추라는 뜻입니다.

```python
# 예제 3-3 (문장 다섯 개와 질문 두 개의 유사도)
sentences = ['챔버 온도가 상한을 넘으면 즉시 공정을 중지하고 인터락을 건다',
             '클린룸 방진복은 모자, 마스크, 상의, 하의, 장갑 순서로 입는다',
             '연차는 분기마다 사용 계획을 제출한다',
             '웨이퍼 반송 로봇은 2주마다 그리스를 바른다',
             '구내식당 저녁 배식은 18시에 시작한다']
sentence_vectors = model.encode(['passage: ' + sentence for sentence in sentences], normalize_embeddings=True)

for question in ['설비가 과열되면 어떻게 하나요', '휴가 신청은 어떻게 하나요']:
    question_vector = model.encode(['query: ' + question], normalize_embeddings=True)[0]
    scores = sentence_vectors @ question_vector          # 길이가 1인 벡터끼리의 내적 = 코사인 유사도
    print('질문:', question)
    for position in np.argsort(-scores):
        print(f'   {scores[position]:.3f} {sentences[position]}')
```

:::예제 3-4 문서 253건의 벡터 인덱스와 search()

```python
# 예제 3-4
started = time.time()
index = embed.passages(docs)                 # 문서 253건의 임베딩. 행이 문서, 열이 차원입니다
print(f'{index.shape}, {round(index.nbytes / 1e6, 3)}MB, {time.time() - started:.0f}초')


def search(question, k=3):
    """질문과 유사도가 높은 순으로 상위 k건의 (문서 번호, 점수)를 돌려줍니다."""
    scores = index @ embed.query(question)   # 문서마다 질문과의 코사인 유사도
    return [(names[position], round(float(scores[position]), 3)) for position in np.argsort(-scores)[:k]]


print(search(Q, k=4))
```

## 검색을 측정하기 {원본 p.361-366}

:::요점
정답 문서를 아는 질문 세트를 만들고, 정답 문서가 상위 k건 안에 든 질문의 비율인 recall@k를 계산합니다. 검색 방법마다 놓치는 질문의 종류가 다릅니다.
:::

질문 한두 개로는 검색이 잘 되는지 말할 수 없습니다. 파트 1에서 모델을 고를 때와 같습니다. 정답을 아는 표본을 만들어 측정합니다.

[[recall@k]]는 정답 문서가 검색 결과의 상위 k건 안에 들어 있는 질문의 비율입니다. recall@1은 정답 문서가 1위인 질문의 비율이고, recall@3은 3위 안에 든 질문의 비율입니다. RAG에서는 상위 몇 건을 프롬프트에 넣으므로, 넣는 건수에 맞는 k로 측정합니다.

질문 세트는 `검색_질문_20.csv`입니다. 질문 20개마다 정답 문서 번호가 붙어 있고, 유형이 네 가지입니다.

| 유형 | 건수 | 예 |
| --- | --- | --- |
| 현장 말투 | 10 | 에치 장비 척을 갈 때 무엇부터 하나요 |
| 문서 말투 | 4 | CVD 가스라인 퍼지 절차 |
| 식별자 | 5 | RCP-ETCH-693 관리 한계 |
| 구판과 신판 | 1 | He 배면압 설정 기준이 어떻게 되나요 |

:::예제 3-5 질문 세트로 세 가지 검색을 측정하기
```python
# 예제 3-5
questions = pd.read_csv(f'{DATA}/검색_질문_20.csv')


def rank_of(scores, gold):
    """점수가 높은 순으로 정렬했을 때 정답 문서가 몇 위인지 돌려줍니다."""
    order = list(np.argsort(-scores, kind='stable'))
    return order.index(names.index(gold)) + 1


def recall_at(ranks, k):
    """정답 문서가 상위 k위 안에 든 질문의 비율(%)을 돌려줍니다."""
    return sum(rank <= k for rank in ranks) / len(ranks) * 100


methods = {
    '낱말 단위': lambda question: (word_matrix @ word_tfidf.transform([question]).T).toarray().ravel(),
    '글자 단위': lambda question: (char_matrix @ char_tfidf.transform([question]).T).toarray().ravel(),
    '임베딩': lambda question: index @ embed.query(question),
}
ranks = questions[['질문', '정답', '유형']].copy()
for label, scores_of in methods.items():
    ranks[label] = [rank_of(scores_of(question), gold) for question, gold in zip(questions['질문'], questions['정답'])]
    print(f'{label}: recall@1 {recall_at(ranks[label], 1):.0f}%, recall@3 {recall_at(ranks[label], 3):.0f}%')
```

글자 단위 키워드 검색이나 임베딩 검색에서 정답 문서가 1위가 아닌 질문을 출력합니다.

```python
# 예제 3-5 (정답 문서가 1위가 아닌 질문)
missed = ranks[(ranks['글자 단위'] > 1) | (ranks['임베딩'] > 1)]
print(missed[['질문', '유형', '낱말 단위', '글자 단위', '임베딩']].to_string(index=False))
```
:::

recall@1은 낱말 단위 키워드 검색이 55%, 글자 단위 키워드 검색이 75%, 임베딩 검색이 85%입니다. recall@3은 글자 단위 키워드 검색(95%)이 임베딩 검색(90%)보다 높습니다. 이 결과에서 읽을 것은 네 가지입니다.

- **글을 나누는 단위만 바꿔도 키워드 검색의 결과가 크게 달라집니다.** 낱말 단위와 글자 단위는 점수 계산 방법이 같습니다.
- **두 방법이 놓치는 질문이 다릅니다.** 두 번째 출력에서 "가스 배관을 비울 때", "척을 갈 때"는 글자 단위 키워드 검색에서 2위이고 임베딩 검색에서 1위입니다. 문서와 다른 낱말로 물은 질문입니다. 반대로 "새는 곳이 없는지 확인하는 방법"은 글자 단위 키워드 검색에서 2위인데 임베딩 검색에서는 9위입니다. "정기 정비"라고 물은 질문은 두 방법 모두 놓쳤습니다. 문서는 "예방정비(PM)"라고 씁니다. 한 방법이 다른 방법보다 모든 질문에서 나은 것은 아닙니다. 두 검색의 결과를 합치는 방법(하이브리드 검색)은 4일차에서 다룹니다.
- **식별자로 물은 질문은 세 방법 모두 대부분 찾았습니다.** 이 코퍼스에서는 레시피 번호가 문서 제목에 그대로 있기 때문입니다. 낱말 단위 키워드 검색은 번호(`693`)가 정확히 같은 문서에만 점수를 줍니다. 번호가 비슷한 문서가 많아지면 이런 방식이 임베딩 검색보다 유리할 수 있습니다.
- **구판과 신판이 함께 있는 문서는 세 방법 모두 구판을 먼저 찾았습니다.** 이 문제는 다음 절에서 다룹니다.

질문 20개는 작은 표본입니다. recall@1에서 5%포인트는 질문 한 개입니다. 한두 개 차이로 방법의 우열을 정하지 않고, 어떤 유형의 질문을 놓쳤는지를 읽습니다.

:::주의
모든 문서가 0점인 검색에서는 순위에 뜻이 없습니다. 낱말 단위 키워드 검색은 질문 세트의 첫 질문에서 모든 문서가 0점이었고, 정답 문서의 순위는 문서 번호의 정렬 순서대로 214위로 계산됐습니다.
:::

## 1위 문서를 열어 판정하기 {원본 p.373-383}

:::요점
검색은 답이 없는 질문에도 1위 문서를 내놓고, 그 점수는 답이 있는 질문과 비슷합니다. 1위 문서가 질문에 답하는지는 문서를 열어 읽고 판정합니다.
:::

검색 결과는 문서 번호와 점수입니다. 그 문서가 질문에 답하는 문서인지는 검색이 알려 주지 않습니다. 세 가지 경우를 검색해 봅니다. 구판과 신판이 함께 있는 질문, 코퍼스에 답이 없는 질문 두 개입니다.

:::예제 3-6 검색 결과를 읽고 1위 문서 열어 보기
```python
# 예제 3-6
def show(question, k=3):
    """질문의 상위 k건을 점수, 문서 번호, 제목과 함께 출력합니다."""
    print(question)
    for name, score in search(question, k):
        print(f'   {score} {name}, {docs[names.index(name)].splitlines()[0][2:]}')


show('He 배면압 설정 기준이 어떻게 되나요')
show('구내 헬스장은 몇 시까지 여나요')
show('세정 장비 약액 교체 주기가 어떻게 되나요')
```

답이 없는 질문의 1위 문서를 열어 봅니다.

```python
# 예제 3-6 (1위 문서를 엽니다)
top_name = search('세정 장비 약액 교체 주기가 어떻게 되나요', k=1)[0][0]
print(docs[names.index(top_name)])
```

같은 내용을 세 가지 말로 묻습니다.

```python
# 예제 3-6 (현장 말, 문서 말, 약어로 묻습니다)
for question in ['칠러가 안 도는 것 같은데 챔버가 멈추는 기준이 뭔가요',     # 현장 말
                 '챔버 인터락이 자동 작동하는 온도 조건',                      # 문서 말
                 'ESC 과열 시 인터락 기준']:                                   # 약어
    print(question, '→', search(question, k=2))
```
:::

첫 번째 결과에서 읽을 것은 두 가지입니다.

- **구판이 신판보다 앞에 왔습니다.** "He 배면압" 질문의 1위는 `SOP-ETCH-012_v1.2`이고 2위가 `SOP-ETCH-012_v2.0`입니다. 두 문서는 제목이 같고, 설정값(6.0 Torr와 8.0 Torr), 허용 편차(±0.5 Torr와 ±0.4 Torr), 적용 장비 표기, 개정일과 승인 줄만 다릅니다. 본문에 개정일과 버전이 적혀 있어도 임베딩은 어느 문서가 최신인지 판단하지 않습니다. 두 점수의 차이도 0.001 정도입니다. 최신 문서만 검색되게 하는 방법은 3일차에서 다룹니다.
- **답이 없는 질문에도 1위 문서가 나옵니다.** 코퍼스에는 헬스장 운영 시간도, 세정 장비의 약액 교체 주기도 없습니다. 그래도 검색은 가장 가까운 문서를 1위로 내놓고, 그 점수는 0.8이 넘습니다. 답이 있는 질문의 1위 점수와 크게 다르지 않습니다. 그래서 "점수가 얼마 이상이면 맞는 문서"라는 기준을 세우기 어렵습니다.

두 번째 결과는 답이 없는 질문의 1위 문서입니다. 문서를 열어 보면 질문이 물은 내용이 없습니다. 1위 문서를 판정하는 방법은 다음과 같습니다.

- 질문이 묻는 수치나 절차가 본문에 그대로 있으면 질문에 답하는 문서입니다. 그 문장을 근거로 적어 둡니다.
- 같은 설비나 같은 낱말은 나오지만 묻는 내용이 없으면 답하는 문서가 아닙니다. 회의록과 품질 이슈 보고서가 이런 식으로 1위에 오는 경우가 많습니다.
- 정답 문서가 1위가 아니면 2위와 3위도 열어 봅니다.

세 번째 결과에서는 같은 내용을 현장 말, 문서 말, 약어로 물었습니다. 세 질문 모두 1위가 `SOP-ETCH-007_v2.1`입니다. 1위 점수는 현장 말로 물은 질문이 0.861이고, 문서 말과 약어로 물은 질문이 0.885와 0.889입니다. 질문 앞부분에 붙은 사례 이야기 때문에 1위 문서가 바뀌는 경우는 실습 9에서 직접 확인합니다.

## 찾은 문서를 넣어 답하기 {원본 p.370-372}

:::요점
검색한 문서를 프롬프트에 넣어 보내면 RAG의 두 단계가 이어집니다. 검색이 틀린 문서를 찾으면 모델은 그 문서를 근거로 틀린 답을 합니다.
:::

검색과 생성을 잇습니다. 질문을 검색해 1위 문서를 찾고, 그 문서를 프롬프트에 넣어 모델에 보냅니다. 예제 3-1에서는 사람이 문서를 골라 넣었고, 이번에는 검색이 고릅니다.

:::예제 3-7 검색한 문서를 넣어 답하게 하기
```python
# 예제 3-7
def answer(question, k=1):
    """질문을 검색해 상위 k건을 프롬프트에 넣어 보내고 (넣은 문서 번호 목록, Reply)를 돌려줍니다."""
    found = [name for name, _ in search(question, k)]
    context = '\n\n'.join(docs[names.index(name)] for name in found)
    prompt = ('다음 문서를 근거로 답해 주세요. 문서에 없는 내용이면 "문서에 없습니다"라고 답합니다.\n\n'
              f'{context}\n\n질문: {question}')
    return found, llm.ask(prompt, model='소형', max_tokens=600)


for question in [QUESTION, 'He 배면압 설정 기준이 어떻게 되나요', '구내 헬스장은 몇 시까지 여나요']:
    found, reply = answer(question)
    print(question)
    print(f'   넣은 문서 {found}, 입력 토큰 {reply.input_tokens}')
    print('  ', reply.text.replace('\n', ' ')[:160])
```
:::

첫 질문은 검색이 `SOP-ETCH-007_v2.1`을 찾았고, 모델은 그 문서를 근거로 58.0~62.0°C라고 답했습니다. 입력 토큰은 문서 한 건을 넣었을 때와 같은 수준입니다.

두 번째 질문은 검색이 구판(`SOP-ETCH-012_v1.2`)을 1위로 찾았습니다. 모델은 구판에 적힌 6.0 Torr를 답했습니다. 현재 기준은 신판의 8.0 Torr입니다. 모델은 받은 문서를 근거로 정확히 답했고, 틀린 것은 검색입니다. 응답만 읽어서는 이 오류를 알 수 없습니다. 어느 문서를 넣었는지를 응답과 함께 남겨야 하는 이유입니다.

세 번째 질문은 코퍼스에 답이 없습니다. 프롬프트에 "문서에 없는 내용이면 문서에 없습니다라고 답합니다"라는 문장을 넣었고, 모델은 그렇게 답했습니다. 이 문장이 없으면 모델이 받은 회의록에 없는 운영 시간을 지어내거나, 관계없는 내용을 답으로 내놓을 수 있습니다.

RAG의 품질은 검색에서 먼저 정해집니다. 검색이 맞는 문서를 찾지 못하면 모델은 답할 근거가 없고, 틀린 문서를 찾으면 그 문서대로 답합니다. 3일차에서는 문서를 작은 조각으로 나누고, 최신 문서만 검색되게 하고, 응답에 출처를 붙여 RAG를 완성합니다.

:::보충
`intfloat/multilingual-e5-small`의 차원(384), 접두어 규칙(`query: `, `passage: `), 접두어를 빼면 성능이 떨어진다는 점, 유사도가 0.7~1.0에 분포한다는 점은 모델 카드에서 확인했습니다(2026-11-26 확인). Anthropic이 임베딩 모델을 제공하지 않는다는 점은 Anthropic의 Embeddings 문서에서 확인했습니다(2026-11-26 확인). 예제는 sentence-transformers 6.1.0, scikit-learn 1.9.1로 실행했습니다.
:::

## 핵심 정리

- 모델은 학습하지 않은 사내 문서를 모릅니다. 문서를 프롬프트에 넣으면 답하고, 문서가 많으면 질문에 맞는 문서만 찾아 넣습니다. 이 방식이 RAG이고 검색과 생성의 두 단계입니다.
- 키워드 검색은 같은 낱말이 든 문서를 찾습니다. 한국어에서는 글을 나누는 단위를 글자나 형태소로 해야 조사 때문에 놓치지 않습니다. 같은 것을 다른 낱말로 물으면 놓칩니다.
- 임베딩 모델은 글을 벡터로 바꿉니다. 의미가 비슷한 글은 코사인 유사도가 높습니다. 문서의 임베딩을 미리 계산해 둔 것이 벡터 인덱스입니다.
- 검색은 정답 문서를 아는 질문 세트와 recall@k로 측정합니다. 방법마다 놓치는 질문의 종류가 다릅니다.
- 검색은 답이 없는 질문에도 1위 문서를 내놓고, 최신 문서와 구판을 구분하지 못합니다. 1위 문서는 열어 읽고 판정합니다.
- 검색이 틀린 문서를 찾으면 모델은 그 문서를 근거로 답합니다. 어느 문서를 넣었는지를 응답과 함께 남깁니다.

## 자가점검

**1.** 사내 규정을 근거 문서 없이 물었을 때 모델이 정확한 수치를 답하지 못하는 이유는 무엇입니까?

:::정답
사내 규정은 공개된 적이 없어 모델이 학습한 글에 없기 때문입니다. 답할 근거가 되는 문서를 프롬프트에 넣어야 합니다.
:::

**2.** 문서 253건을 모두 프롬프트에 넣어도 정답이 나왔습니다. 그런데도 질문에 맞는 문서만 찾아 넣는 이유를 두 가지 써 보세요.

:::정답
질문마다 문서 전체의 입력 토큰만큼 요금이 듭니다. 문서 전체의 토큰 수가 컨텍스트 윈도우를 넘으면 보낼 수 없습니다. 답과 관계없는 문서까지 모두 입력으로 보낸다는 점도 이유입니다.
:::

**3.** 낱말 단위 TF-IDF로 "칠러가 안 도는 것 같은데 챔버가 멈추는 기준이 뭔가요"를 검색했더니 모든 문서가 0점이었습니다. 원인과 고치는 방법은 무엇입니까?

- A. 키워드 검색은 한국어를 지원하지 않으므로 임베딩 검색으로 바꿔야 한다
- B. 조사가 붙은 "칠러가"와 문서의 "칠러"가 다른 낱말로 계산됐다. 글자 단위로 나누거나 형태소 분석기로 조사를 떼어 낸다
- C. 문서 수가 너무 적어서 점수가 계산되지 않았다

:::정답
**B.** 글을 나누는 단위의 문제입니다. 글자 2~3개 단위로 나누자 같은 질문의 정답 문서가 1위로 나왔습니다(예제 3-2).
:::

**4.** 임베딩 모델과 LLM은 무엇이 다릅니까?

:::정답
LLM은 글을 입력받아 글을 생성합니다. 임베딩 모델은 글을 입력받아 벡터 하나를 출력하고 글을 생성하지 않습니다. 이 교재가 쓰는 임베딩 모델(약 470MB)은 PC에서 실행할 수 있습니다.
:::

**5.** 문서의 임베딩은 A 모델로 만들고 질문의 임베딩은 B 모델로 만들었습니다. 어떤 문제가 생깁니까?

:::정답
두 벡터를 비교할 수 없습니다. 모델이 다르면 차원이 다를 수 있고, 차원이 같더라도 각 숫자가 나타내는 것이 다릅니다. 문서와 질문은 같은 임베딩 모델로 바꿔야 합니다.
:::

**6.** 질문 20개 가운데 정답 문서가 1위인 질문이 16개, 3위 안에 든 질문이 19개입니다. recall@1과 recall@3은 각각 얼마입니까? 상위 3건을 프롬프트에 넣는 RAG라면 어느 값을 봅니까?

:::정답
recall@1은 80%, recall@3은 95%입니다. 상위 3건을 넣는다면 정답 문서가 3위 안에만 있어도 모델이 근거를 받으므로 recall@3을 봅니다.
:::

**7.** 검색 1위 문서의 유사도가 0.85입니다. 이 문서를 응답의 근거로 써도 되는지 어떻게 판정합니까?

- A. 0.8보다 높으므로 써도 된다
- B. 문서를 열어 질문이 묻는 수치나 절차가 본문에 있는지 읽고 판정한다
- C. 2위와의 점수 차이가 0.01보다 크면 써도 된다

:::정답
**B.** 코퍼스에 답이 없는 질문에도 1위 문서는 나오고 그 점수가 0.8을 넘었습니다(예제 3-6). 점수는 같은 질문 안에서 순위를 정하는 데 쓰고, 맞는 문서인지는 본문을 읽고 판정합니다.
:::

**8.** "He 배면압 설정 기준"을 물었더니 모델이 6.0 Torr라고 답했는데, 현재 기준은 8.0 Torr입니다. 모델이 틀린 것입니까? 무엇을 확인해야 합니까?

:::정답
모델은 받은 문서대로 답했습니다. 검색이 구판 문서를 1위로 찾아 프롬프트에 넣었기 때문입니다(예제 3-7). 어느 문서를 넣었는지 확인해야 하고, 그러려면 넣은 문서의 번호를 응답과 함께 남겨야 합니다. 임베딩 검색은 어느 문서가 최신인지 구분하지 못합니다.
:::

- 글을 나누는 단위에 따라 키워드 검색의 결과가 달라진다는 점과 글자 단위 TF-IDF.
- 임베딩 모델이 LLM과 어떻게 다른지, 문서와 질문을 같은 모델로 바꿔야 한다는 점.
- 벡터 인덱스를 파일로 저장하는 방법과, 문서의 순서를 함께 보관해야 한다는 점.
- 벡터 인덱스를 미리 만드는 일과 질문마다 하는 일을 나눠 보인 그림.
- 질문 20개의 세트와 유형별 분석, 표본이 작다는 주의.
- 코퍼스에 답이 없는 질문의 검색 결과.
- 검색이 구판을 찾았을 때 모델이 구판대로 답하는 사례.
- 문서를 모두 넣는 방식의 한계 두 가지(컨텍스트 윈도우, 관계없는 문서).
- 사내 Hugging Face 프록시 설정 안내와 `embed.py`.
- Anthropic API는 임베딩 모델을 제공하지 않는다는 점과, 이 모델의 유사도가 0.7~1.0에 분포한다는 모델 카드의 설명.
- 구판과 신판의 차이(설정값, 허용 편차, 개정일)와, 개정일이 본문에 있어도 임베딩이 최신 문서를 판단하지 않는다는 점.

### 고친 내용

- "키워드 검색은 253건 전부 0점"(p.330-335, 357) → 0점의 원인은 글을 공백으로 나눈 것이고, 글자 단위로 나누면 같은 질문의 정답 문서가 1위로 나온다고 고침. 키워드 검색이 놓치는 경우는 문서와 다른 낱말로 묻는 질문으로 따로 보임. 직접 실행해 확인함.
- "1일차 실습에서 경량 모델이 조항을 통째로 지어냄"(p.303) → 삭제. 1일차 교재를 만들 때 재현되지 않았음. 예제 3-1의 실제 응답으로 설명.
- 입력 토큰과 요금의 숫자(p.313-318, 380-382) → 다시 실행한 값으로 바꿈.
- "문서 253건 임베딩 0.3초"(p.353) → PC에 따라 다르다고 고치고, 2026-11-26 실행에서 걸린 시간(23초)을 적음.
- "파인튜닝은 형식과 말투 고정"(p.320) → 형식과 말투는 먼저 프롬프트의 지시와 예시로 맞추고, 요청마다 달라질 때 파인튜닝을 고려한다고 고침(3일차 파트 1과 같은 설명).
- recall@k를 질문 5개로 측정(p.361-366) → 20개로 늘리고 표본이 작다는 점을 적음.
- "숫자 384개", "머리말", "검색 적중률", "낱말 목록" → 384차원, 접두어, recall@k, 어휘.
- "임베딩 점수와 검색 순위는 같은 값이 나옵니다"(p.424) → "거의 같은 값"으로 고침.

# GenAI 강의 복습 교재 설계서

작성일: 2026-11-18

## 1. 목적

생성형 AI 교육(GenAI Intensive)의 일자별 강의자료를 **강의 후 복습용 학습 교재**로 다시 만든다.
원본 강의안은 문장과 용어가 어색하고 일관성이 떨어져, 읽을 때마다 문장을 한 번 더 해석해야 한다.
교재는 그 수고 없이 읽히고, 수강하지 않은 동료에게 공유해도 혼자 학습할 수 있어야 한다.
강의가 진행 중이므로 남은 일자의 자료도 같은 기준으로 계속 추가한다.

## 2. 목표 / 하지 않는 것 / 실패로 보는 것

**가장 중요한 기준 (사용자 결정)**
생성형 AI를 학습하는 데 필요한 개념이 잘 설명되어야 한다. 원본은 출발점이지 기준이 아니다.
- 원본에 없더라도 개념을 이해하는 데 필요한 내용은 추가한다.
- 원본 내용이 틀렸으면 고친다.
- 어색한 한국어 문장과 용어는 고친다.
- 학습에 필요 없는 내용은 삭제한다.

**목표**
- 각 개념을 "무엇인지, 왜 필요한지, 어떻게 동작하는지, 언제 쓰는지"가 드러나게 설명한다.
- 불필요한 문장을 걷어내고, 자연스러운 문장과 일관된 용어로 다시 쓴다.
- 개념 설명, 예제 코드, 실행 결과, 실습 미션, 자가점검 문제가 한 교재 안에서 연결된다.
- 동료가 사내 LLM API(OpenAI 호환)로 파이썬 실습을 직접 실행할 수 있다.
- 새 일자 폴더가 추가되면 한 번의 요청으로 같은 규칙에 따라 교재에 붙는다.

**하지 않는 것**
- 원본 파일(`GenAI_N일차_배포용/`)은 수정하지 않는다.
- 교재 페이지 안에서 파이썬을 실행하는 기능은 만들지 않는다(실습이 LLM API와 임베딩 모델에 의존).
- 외부 서비스에 올려 링크로 공유하지 않는다. 파일로 만들어 사내 채널로 전달한다.
- 원본 예제·실습을 그대로 옮기지 않는다. 학습에 필요한 것을 기준으로 다시 만든다(5.4절).
- 강의 주제와 무관한 내용으로 범위를 넓히지 않는다. 추가는 해당 일자의 주제를 이해하는 데 필요한 것에 한정한다.

**실패로 보는 것**
- 개념 설명이 부정확하거나, 읽어도 왜 필요한지와 어떻게 동작하는지 알 수 없는 것.
- 추가하거나 고친 내용이 틀린 것. 확신할 수 없는 사실은 공식 문서로 확인하고, 확인하지 못하면 싣지 않는다.
- 실행해 보지 않은 코드의 결과를 지어내 싣는 것.
- 원본이 다루던 핵심 개념을 이유 없이 빠뜨리는 것.
- 일자마다 용어나 문체가 달라지는 것.

- Claude 고유 기능 사용: `messages.count_tokens`, `messages.parse`(구조화 출력), `output_config={'effort': ...}`, thinking 블록.
- 임베딩은 `sentence-transformers`의 `intfloat/multilingual-e5-small`을 쓴다. 4일차는 `rank_bm25`도 쓴다.
- 폴더 구조와 파일 이름 규칙이 일자마다 조금씩 다르다(예: `2일차_예제.ipynb` / `day03-examples.ipynb`).

## 4. 검토한 방식

| 방식 | 내용 | 판단 |
| --- | --- | --- |
| A. 웹 교재(HTML) | 목차·검색·용어집 연결·도식·구문 강조 코드·자가점검을 갖춘 브라우저용 교재 | **채택(작성자 제안).** 300쪽 분량과 계속 늘어나는 구조를 감당하고, 파일만 전달하면 열린다 |
| B. 문서형 교재(Word/PDF) | 장·절로 구성한 책 형태 | 인쇄·첨부는 쉽지만 분량이 커지면 찾아보기 어렵고 코드 가독성이 낮다 |
| C. 해설 노트북 | 노트북에 설명을 합친 형태 | 실습 복습에는 좋지만 이론 비중이 큰 강의안 전체를 담기 어렵다 |

A를 본체로 하고, 실습은 C의 일부를 가져와 "정리된 노트북"으로 짝짓는다.
사용자는 복습용, 동료 공유용, 파이썬 실습 병행, 사내 API가 OpenAI 호환이라는 점을 정했다.
A 방식과 파일 전달은 작성자가 제안한 것으로, 이 설계서 승인으로 확정한다.

## 5. 결과물 구성

모든 결과물은 `학습자료/` 아래에 둔다.

```
학습자료/
  설계서.md
  작성규칙.md          문체·삭제 기준·표기 원칙
  용어집.md            일자 공통 용어 (누적)
  원고/
    2일차/01_LLM_API_기초.md ...   교재 내용의 원본(Markdown)
  교재/                build.py가 만든 HTML (공유 대상)
    index.html, 1일차.html, 2일차.html ...
  노트북/              정리된 노트북 (공유 대상)
    llm.py             공통 호출 함수
    2일차_예제.ipynb, 2일차_실습.ipynb ...
  build.py             원고 → 교재 변환
```

작업 폴더 최상위에 `CLAUDE.md`를 두어, 이후 세션에서 "N일차 정리해줘"라고 하면 이 구조와 규칙을 따르게 한다.

### 5.1 원고 (Markdown)

- 슬라이드 순서가 아니라 **파트 → 개념 단위**로 재구성한다. 여러 장에 걸쳐 "(계속)"으로 끊긴 슬라이드는 하나의 설명으로 합친다.
- 각 절에 원본 쪽수를 표기한다(예: `원본 2일차 p.60–62`). 원본에 없이 추가한 절은 "추가"로 표시한다.
- **개념 설명 쓰는 법(작성자 제안)**: 개념마다 한 문장 정의 → 왜 필요한지(없으면 생기는 문제) → 동작 원리 → 짧은 예 → 흔한 오해나 주의점 순으로 쓴다. 앞에서 설명하지 않은 용어를 쓰지 않고, 선행 개념이 원본에 빠져 있으면 먼저 설명을 추가한다.
- **변경 기록(작성자 제안)**: 파트 끝에 원본 대비 변경 기록을 둔다. "추가한 내용 / 고친 내용(원본 표현 → 고친 표현, 이유) / 삭제한 내용(이유)" 세 가지를 적는다. 문장 다듬기는 적지 않고, 내용이 달라진 것만 적는다. 수강한 동료가 강의와 다른 점을 알 수 있고, 사용자가 수정이 맞는지 검토할 수 있다.
- **변하는 사실(작성자 제안)**: 모델 이름, 요금, API 파라미터처럼 시간이 지나면 바뀌는 내용은 공식 문서로 확인하고 확인한 날짜를 적는다.
- 한 파트의 구성: 이 파트에서 배우는 것 → 개념 설명 → 예제(코드 + 실행 결과 + 해설) → 실습 미션 안내 → 핵심 정리 → 자가점검.
- 예제와 실습은 5.4절의 기준으로 다시 만든 것을 싣는다.
- 실행 결과는 실제로 실행해 얻은 값만 싣는다(7절). 실행마다 달라질 수 있는 값은 그렇게 표시한다.
- 자가점검 문제는 일자별 퀴즈 txt에서 가져온다. 정답과 해설은 접어 둔다.
- 도식은 원본 이미지를 넣지 않고 내용을 파악해 새로 그린다(인라인 SVG 또는 표).

### 5.2 작성규칙과 용어집

- 작성규칙: 문체(합니다체, 한 문장에 한 내용), 삭제 대상(반복되는 안내 문구, 내용 없는 연결 문장, 슬라이드 머리말·꼬리말), 영문 용어 표기(첫 등장 시 한글(영문) 병기), 코드·수치는 원문 그대로.
- 용어집: 용어, 채택한 표기, 원본에 나온 다른 표기, 한 줄 정의, 처음 나온 일자. 새 일자를 정리할 때마다 먼저 용어집을 갱신한 뒤 원고를 쓴다.
- 두 파일의 초안은 샘플 작업에서 만들고, 사용자 검토로 확정한다.

### 5.2a 학습 노트북 (2026-11-19 추가)

사용자 결정: 원본처럼 교재와 노트북이 따로 있으면 오가며 보기 불편하다. 학습과 실행을 한 곳에서 한다.

- 예제의 실행 가능한 전체 코드를 원고의 `:::예제` 상자 안에 쓴다. 코드는 원고 한 곳에만 있다.
- `build.py`가 원고에서 학습 노트북(`노트북/N일차_NN_제목.ipynb`)을 만든다. 설명, 그림, 예제 코드가 순서대로 들어간다. 예전의 `N일차_예제.ipynb`를 대체한다.
- 실행 결과는 원고에 적지 않는다. `tools/run_nb.py`로 학습 노트북을 실행한 사본에서 가져와 HTML 교재와 학습 노트북에 넣는다.
- 원고의 코드를 고치고 다시 실행하지 않으면 빌드가 알려 주고 테스트가 실패한다.
- 노트북에서는 찾기, 용어 풍선, 탭 전환이 없다. 그림은 이미지로 바꿔 넣는다.
- 실습 노트북과 풀이 노트북은 그대로 따로 둔다.
- 아래 5.3, 5.4절과 "원고에 실행 결과를 싣는다"는 앞의 서술 가운데 이 절과 다른 부분은 이 절을 따른다.

### 5.3 교재 (HTML)

- `build.py`가 원고를 읽어 일자별 HTML 한 파일과 `index.html`을 만든다. Python의 `markdown`, `pygments` 패키지를 쓴다.
- CSS·JS·SVG를 파일 안에 모두 넣는다. 외부 CDN·폰트를 쓰지 않아 사내망과 오프라인에서 그대로 열린다.
- 기능: 왼쪽 목차, 페이지 내 검색, 용어에 마우스를 올리면 정의 표시, 코드 구문 강조와 복사 버튼, 접히는 정답, 밝은/어두운 화면.
- 각 예제·미션에 "노트북 `2일차_예제.ipynb`의 `예제 1-1` 셀"처럼 실행 위치를 표시한다.
- 화면 디자인은 샘플 단계에서 사용자에게 보여 주고 확정한다.
- **파일 크기(작성자 판단)**: 일자별 한 파일을 기본으로 한다. 원본 이미지를 넣지 않으므로 수 MB 이내로 예상하며, 샘플에서 크기를 재 보고 첨부가 어려운 수준이면 파트별 파일로 나눈다.
- **출처 표기(작성자 판단)**: 슬라이드마다 반복되는 꼬리말은 지우되, 교재 첫 화면과 각 페이지 하단에 출처(GenAI Intensive 강의자료를 재구성했다는 사실과 원 표기)를 한 번씩 남긴다. 보안 등급 문구가 필요하면 `build.py`의 공통 꼬리말 설정값으로 넣는다.

### 5.4 다시 만드는 예제·실습 노트북

사용자 결정: 예제와 실습은 원본을 토대로 하되, 학습에 실제로 필요한 내용이 무엇인지 판단해 다시 만든다.

아래 방법은 작성자 제안이다.

- **학습 목표 먼저**: 파트마다 원본 강의안·예제·미션·퀴즈를 읽고 "이 파트를 마치면 할 수 있어야 하는 것"을 3~6개로 정리한다. 이 목록을 원고 맨 앞에 싣고, 예제와 실습은 모두 이 목표 중 하나에 대응시킨다.
- **예제**: 목표 하나에 예제 하나를 기본으로 한다. 한 번에 한 가지만 보여 주는 짧은 코드로 쓰고, 같은 내용을 반복하는 원본 예제는 합치거나 뺀다. 원본에 없더라도 목표에 꼭 필요한 예제는 새로 쓴다.
- **실습**: 따라 치기가 아니라 스스로 판단해야 풀리는 과제로 만든다. 각 실습은 목적, 주어진 재료, 완료 기준, 단계별 힌트(접힘), 풀이와 해설(접힘)로 구성한다.
- **재료**(사용자 결정: 필요하면 다시 만든다). 아래 기준은 작성자 제안이다.
  - 원본 재료(csv, corpus, 평가셋, 프롬프트 txt 등)가 학습 목표에 맞으면 그대로 쓴다.
  - 다시 만드는 경우: 목표를 드러내기에 재료가 부족하거나 지나치게 클 때, 정답을 확인할 수 없게 되어 있을 때, 문장이 어색해 재료를 읽는 데 힘이 들 때, 새로 쓴 예제·실습과 맞지 않을 때.
  - 새 재료는 모두 지어낸 가상 데이터로 만든다. 실제 사내 문서나 업무 데이터를 쓰지 않는다. 주제와 형식은 원본 재료(문의 분류, 사내 문서 검색 등)를 따른다.
  - 검색·평가처럼 재료와 정답이 묶인 실습은 문서, 질문, 정답 문서 번호를 한 묶음으로 만들고, 정답이 실제로 맞는지 실행해 확인한다.
  - 대응표에 "원본 재료 → 그대로 사용 / 수정 / 새로 작성"과 그 이유를 함께 적는다.
  - 재료는 `노트북/data/N일차/`에 두고, 만드는 데 쓴 스크립트가 있으면 같이 둔다.
- **대응표**: 파트마다 "원본 예제·미션 → 새 예제·실습" 대응표를 원고 끝에 둔다. 뺀 것은 뺀 이유를 적는다. 원본이 가르치려던 내용이 빠지지 않았는지 이 표로 확인한다.
- **풀이**: 실습 풀이는 새로 쓴다. 실행해 확인한 풀이만 싣는다.
- 노트북은 원본을 고치지 않고 새 파일로 만든다(일자별 `N일차_예제.ipynb`, `N일차_실습.ipynb`).
- 모델 호출은 `llm.py`의 공통 함수로 모은다. 환경 변수 `LLM_PROVIDER`로 `anthropic`(수강생) / `openai`(사내, OpenAI 호환)를 고른다. 사내용은 `openai` 패키지에 `base_url`, 키, 모델명을 환경 변수로 넣는다. 실제 주소·키·모델명은 파일에 적지 않는다.
- Claude 고유 기능의 사내 API 대응:

| 원본 | 사내(OpenAI 호환) 경로 |
| --- | --- |
| `messages.create` | `chat.completions.create` |
| `messages.parse`(구조화 출력) | JSON 응답을 요청하고 `pydantic`으로 검증 |
| `messages.count_tokens` | 응답의 `usage` 값 사용. 호출 전 계산이 필요한 대목은 근사치임을 표시 |
| `effort`, thinking 블록 | Claude 전용 예제로 표시하고 사내 경로에서는 건너뜀. 교재에는 슬라이드의 실행 결과로 설명 |

- Colab 전용 코드(`google.colab.userdata`)는 환경 변수 또는 `getpass` 입력으로 바꿔 Colab과 로컬 Jupyter 양쪽에서 돈다.
- 임베딩 모델 이름과 경로를 설정값으로 빼서, 사내망에서 내려받기가 막혀 있으면 미리 받은 모델 폴더를 지정할 수 있게 한다.
- 1일차는 노트북이 없으므로 교재만 만든다. (2026-11-19 변경: 원본 1일차는 채팅 화면에 프롬프트를 붙여 넣는 방식이라 동료가 따라 할 수 없다. 파트 1, 2의 예제를 학습 노트북으로 옮기고 `llm.Chat`으로 프롬프트를 보낸다. Gemma 대신 소형과 기본 등급을 비교한다. 근거는 `원고/1일차/00_분석.md`)
- **실습 데이터 전달(작성자 판단)**: 원본 노트북의 "환경 준비" 셀은 외부 학습 사이트에서 zip을 내려받는다. 사내망에서 막힐 수 있으므로, 실습에 쓰는 재료(원본이든 새로 만든 것이든)를 `노트북/data/N일차/`에 넣어 함께 전달하고, 노트북은 이 폴더에서 바로 읽는다. 외부 내려받기는 쓰지 않는다.
- **모델 비교 예제(작성자 판단)**: 원본은 Claude 모델 여러 종을 바꿔 호출한다. `llm.py`에 소형/기본/대형 세 별칭을 두고 환경 변수로 실제 모델명을 연결한다. 사내 모델이 하나뿐이면 세 별칭이 같은 모델을 가리키고, 비교 예제에는 "모델이 하나면 차이가 나지 않는다"는 안내를 붙인다.
- **퀴즈(작성자 판단)**: 일자별 퀴즈 txt의 문제와 정답은 자가점검으로 싣되, 문장은 작성규칙에 맞게 다듬는다.
- **샘플 단계의 노트북(작성자 판단)**: 2일차 파트 1에 해당하는 예제와 실습만 담은 노트북을 새로 만든다. 나머지 파트는 확장 단계에서 같은 파일에 이어 붙인다.

## 6. 진행 순서

1. **샘플**: 2일차 파트 1 "LLM API 기초"만으로 작성규칙·용어집 초안, 원고, HTML, 해당 노트북 구간을 만든다.
2. **검토**: 사용자가 문장 수준, 구성, 화면을 보고 수정 의견을 준다. 규칙과 디자인을 확정한다.
3. **확장**: 2일차 나머지 → 1일차 → 3일차 → 4일차 순으로 파트 단위로 작업한다.
4. **이후 일자**: 새 폴더가 들어오면 같은 절차(용어집 갱신 → 원고 → 빌드 → 노트북)를 반복한다.

## 7. 확인 방법과 한계

- 확인하는 것: `build.py`가 오류 없이 끝나는지, 교재의 목차·검색·내부 링크가 동작하는지(브라우저로 확인), 노트북이 올바른 형식이고 코드 셀이 문법 오류 없이 컴파일되는지, 원고의 코드·수치가 원본과 일치하는지(파트별 대조).
- **실행 검증**: 예제와 실습을 새로 쓰므로 슬라이드의 실행 결과를 가져다 쓸 수 없다. 모든 코드를 실제로 실행해 결과를 얻어야 한다.
  - LLM을 부르지 않는 코드(데이터 처리, 임베딩, 검색 등)는 작성 환경에서 직접 실행한다.
  - LLM을 부르는 코드는 작성 환경에 API 키가 있어야 실행할 수 있다. 키가 없으면 사용자가 노트북을 실행해 결과가 저장된 파일을 돌려주고, 그 결과를 교재에 싣는다.
  - 실행하지 못한 예제는 결과 칸을 비우고 "미실행"으로 표시한다. 결과를 지어내지 않는다.
- 확인하지 못하는 것: 사내 API 경로의 실행. 사용자가 사내에서 실행해 확인하고, 오류가 나면 메시지를 받아 고친다.
- PDF 쪽을 이미지로 보려면 도구 설치가 필요하다(`pypdfium2` 등). 도식 재작성에 필요하므로 샘플 단계에서 설치한다.

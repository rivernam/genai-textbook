14장 코딩 에이전트와 멀티 에이전트

강의 1일차 파트 3, 8일차 파트 1~3에 해당합니다.

채팅 화면의 모델은 내 PC의 폴더를 보지 못하므로, 답을 파일로 옮기고 실행해 보는 일은 사람이 합니다. 코딩 에이전트는 그 일까지 직접 합니다. 이 장은 코딩 에이전트가 어떻게 동작하는지 설명하고, 규칙 파일, Skill, 서브에이전트, 권한과 훅이 각각 모델의 컨텍스트에 무엇을 넣거나 빼는지, 모델이 하는 일 가운데 무엇을 막는지 설명합니다. 모델이 도구를 요청하는 형식과 에이전트 루프의 원리는 13장 "AI 에이전트"에서 다룹니다. 기능 이름은 Claude Code의 것을 쓰고, opencode에서 같은 일을 하는 기능은 "권한과 훅" 절 끝의 대응 표에 모았습니다.

학습 목표

  1. 코딩 에이전트가 채팅과 무엇이 다른지 작업 폴더, 도구, 하네스로 설명하고, 질문 한 줄에도 입력 토큰이 10만 개 안팎 드는 이유를 설명할 수 있습니다.
  2. 코딩 에이전트가 보내는 요청 하나가 무엇으로 채워지는지 설명하고, 컨텍스트 엔지니어링이 무엇을 정하는 일인지 설명할 수 있습니다.
  3. 규칙 파일과 Skill이 컨텍스트에 들어가는 시점이 어떻게 다른지 설명하고, 어떤 지시를 어디에 둘지 고를 수 있습니다.
  4. 서브에이전트가 메인 에이전트의 컨텍스트를 줄이는 원리를 설명하고, 일을 나누면 전체 토큰이 늘어날 수도 줄어들 수도 있다는 것을 계산으로 보일 수 있습니다.
  5. 규칙 파일의 지시, 권한 규칙, 훅이 각각 무엇을 막고 무엇을 막지 못하는지 설명할 수 있습니다.

예제 14-1은 Claude Code가 설치되어 있고 로그인된 PC에서만 실행되며, 없으면 셀이 안내문만 출력합니다. 예제 14-2와 두 실습은 API(application programming interface)를 호출하지 않고, 예제 14-2는 1장의 토크나이저로 토큰을 셉니다. 예제 14-3과 14-4는 API로 모델을 호출합니다. 모델의 응답과 토큰 수는 실행할 때마다 교재와 다를 수 있고, 예제 14-1의 숫자는 Claude Code의 버전과 PC의 설정(사용자 폴더의 규칙 파일, 설치한 Skill과 플러그인)에 따라서도 다릅니다.

코딩 에이전트

코딩 에이전트는 모델과 하네스로 이루어집니다. 모델은 다음에 할 행동만 정하고, 하네스가 도구를 실행해 그 결과를 붙인 다음 요청을 보내는 일을 작업이 끝날 때까지 되풀이합니다. 그래서 질문 한 줄도 모델 요청 여러 번이 되고, 요청마다 앞 내용 전체를 다시 보냅니다.

모델과 하네스

코딩 에이전트(coding agent)는 작업 폴더(working directory)에서 파일을 읽고 만들고 고치며 명령을 실행하는 에이전트입니다. 작업 폴더는 코딩 에이전트를 시작한 폴더로, 코딩 에이전트는 기본으로 이 폴더 안에서 일합니다. 파일 읽기, 파일 쓰기, 명령 실행처럼 글을 생성하는 것 말고 에이전트가 하는 일을 도구(tool)라고 합니다. Claude Code와 opencode가 코딩 에이전트입니다.

모델은 글을 받아 다음 토큰을 이어 쓸 뿐이고(1장), 파일을 직접 열 수 없습니다. 모델이 "이 파일을 읽겠다"는 요청을 정해진 형식으로 출력하면, 모델 밖의 프로그램이 실제로 파일을 읽고 그 내용을 다음 요청에 붙여 보냅니다. 이 프로그램을 하네스(agent harness)라고 합니다. Claude Code 문서도 Claude Code를 하네스라고 부릅니다. 모델에 도구를 주고, 모델이 보는 컨텍스트를 관리하는 프로그램이라는 뜻입니다. 하네스가 도구를 실행하고 결과를 붙여 다시 요청하는 반복을 에이전트 루프(agent loop)라고 합니다(13장에서 다룹니다).

모델은 무상태이므로(3장 "컨텍스트"), 하네스는 요청할 때마다 시스템 프롬프트, 도구 정의, 지금까지의 대화와 도구 결과를 모두 다시 보냅니다. 도구 정의는 모델에게 어떤 도구가 있고 각 도구에 무엇을 넣어야 하는지 알려 주는 글입니다.

세션과 되돌리기

세션(session)은 코딩 에이전트와 나누는 대화 하나입니다. 하네스가 세션의 대화를 모아 두었다가 요청마다 보내므로, 새 세션의 모델은 앞 세션에서 무엇을 했는지 모릅니다. 파일은 작업 폴더에 남으므로, 다음 세션에서 이어 갈 내용은 파일로 남겨 둡니다.

Claude Code는 사용자가 메시지를 보낼 때마다 파일 상태를 저장해 두므로, 고른 메시지를 보내기 전의 상태로 대화와 파일을 되돌릴 수 있습니다. 이 기능을 되돌리기(rewind)라고 하고 /rewind로 엽니다. 저장하는 것은 파일 편집 도구로 바꾼 파일이고, 셸 명령으로만 바뀐 파일은 되돌리지 않습니다. 명령이 DB나 다른 시스템에 남긴 변경도 되돌릴 수 없으므로, 되돌릴 수 없는 명령은 실행 전에 막아야 합니다("권한과 훅" 절에서 다룹니다).

헤드리스 모드

Claude Code는 보통 터미널의 대화 화면에서 쓰지만, claude -p "요청"으로 실행하면 대화 화면 없이 요청 하나를 끝까지 처리하고 결과를 출력한 뒤 끝납니다. 이 실행 방식을 헤드리스 모드(headless mode)라고 하고, 스크립트나 예약 작업에서 코딩 에이전트를 부를 때 씁니다. --output-format json을 붙이면 응답과 함께 사용량을 JSON(JavaScript Object Notation)으로 돌려주므로, 질문 한 줄에 에이전트 턴이 몇 번 있었고 토큰이 얼마나 들었는지 확인할 수 있습니다. 에이전트 턴은 위 그림의 고리 한 바퀴, 곧 모델이 출력하고 그 출력의 도구 요청을 하네스가 실행하는 한 번입니다.

예제 14-1질문 한 줄의 비용노트북 14_코딩_에이전트와_멀티_에이전트.ipynb의 예제 14-1

임시 폴더에 가상의 설비팀 작업 폴더를 만들고, 그 폴더에서 Claude Code를 헤드리스 모드로 한 번 실행합니다. 작업 폴더에는 규칙 파일과 Skill 세 개("규칙 파일", "Skill과 점진적 공개" 절에서 설명합니다), 기록 파일이 있습니다. 에이전트 턴 수, 보낸 입력 토큰의 합과 그중 캐시에서 읽은 토큰, 응답이 규칙 파일의 "출처 파일 이름을 괄호로 붙인다" 규칙을 지켰는지 봅니다. Claude Code의 소형 모델로 실행하며 요금이 듭니다.

코딩 에이전트의 컨텍스트

코딩 에이전트의 요청 하나에는 하네스가 늘 넣는 앞부분(시스템 프롬프트, 도구 정의, 규칙 파일, Skill 목록)과 작업하면서 쌓이는 뒷부분(대화, 읽은 파일, 명령 출력)이 함께 들어갑니다. 컨텍스트 엔지니어링은 그 안에 무엇을 늘 넣고, 무엇을 필요할 때만 넣고, 무엇을 요약하거나 다른 에이전트에 맡길지 정하는 일입니다.

요청 하나의 구성

같은 앞부분을 서버가 캐시해 두고 다음 요청에서 낮은 단가로 다시 읽는 것을 프롬프트 캐싱(prompt caching)이라고 합니다(5장 "LLM API"). 예제 14-1에서 보낸 입력의 대부분이 캐시에서 읽은 토큰이었던 이유입니다. 캐시에서 읽은 토큰도 컨텍스트 윈도우를 차지하므로, 앞부분이 길면 작업에 쓸 수 있는 윈도우가 그만큼 줄어듭니다.

뒷부분은 파일을 읽고 명령을 실행할 때마다 늘어납니다. 윈도우가 차 가면 Claude Code는 그때까지의 대화를 요약으로 바꾸고 그 요약으로 대화를 이어 가는데, 이것을 컨텍스트 압축(compaction)이라고 합니다. 요약은 사용자의 요청과 주요 코드를 남기지만, 대화 앞부분에서 준 자세한 지시는 빠질 수 있습니다. 그래서 늘 지켜야 하는 규칙은 대화가 아니라 규칙 파일에 적습니다. 작업 폴더의 규칙 파일은 압축한 뒤 디스크에서 다시 읽어 넣습니다(2026-11 확인).

Claude Code에서 지금 컨텍스트를 무엇이 얼마나 차지하는지는 /context로 보고, 직접 압축할 때는 /compact, 대화를 비우고 새 세션을 시작할 때는 /clear를 입력합니다.

컨텍스트 엔지니어링

컨텍스트가 길면 비용만 커지는 것이 아닙니다. Anthropic(2025b)은 컨텍스트 윈도우의 토큰이 늘어날수록 모델이 그 안의 정보를 정확히 꺼내 쓰는 능력이 떨어지는 현상을 context rot이라고 부르고, 토큰마다 모델의 주의를 나눠 쓰므로 토큰이 하나 늘 때마다 그만큼 덜 집중한다고 설명합니다. 3장의 "긴 문서" 절에서 다룬 lost in the middle도 긴 컨텍스트에서 정보를 덜 정확히 쓰는 현상입니다.

Anthropic(2025b)은 요청마다 모델에 보낼 토큰을 고르고 관리하는 일을 컨텍스트 엔지니어링(context engineering)이라고 부릅니다. 4장의 프롬프트 설계가 지시문 하나를 잘 쓰는 일이라면, 컨텍스트 엔지니어링은 에이전트가 요청을 보낼 때마다 무엇을 넣을지를 되풀이해 정하는 일입니다. 코딩 에이전트에는 이것을 정하는 수단이 기능으로 들어 있습니다.

수단 컨텍스트에 들어가는 시점 쓸지 정하는 쪽 두는 내용
규칙 파일 세션을 시작할 때 전체 늘 들어감 모든 작업에 필요한 짧은 사실과 규칙
Skill 시작할 때 이름과 설명, 고르면 본문 모델(설명을 보고) 또는 사용자(/이름) 가끔 쓰는 절차, 양식, 참고 자료
서브에이전트 메인에는 맡길 일을 적은 메시지(위임 메시지)와 요약만 모델 또는 사용자 읽을 것이 많고 결과는 짧은 일
권한 규칙, 훅 들어가지 않음(막혔을 때 이유만) 하네스가 매번 적용 반드시 막거나 매번 실행해야 하는 일

규칙 파일

규칙 파일은 세션을 시작할 때마다 전체가 컨텍스트에 들어가는 지시입니다. 모든 작업에 필요한 짧은 사실과 규칙만 두고, 가끔 쓰는 절차는 Skill로 옮깁니다. 모델이 읽는 글일 뿐이므로, 반드시 막아야 하는 일은 권한 규칙이나 훅으로 막습니다.

규칙 파일(rule file)은 코딩 에이전트가 세션을 시작할 때마다 읽어 컨텍스트에 넣는 지시 파일입니다. Claude Code에서는 CLAUDE.md, opencode에서는 AGENTS.md라는 이름을 씁니다. 새 세션의 모델은 앞 세션을 모르므로, 규칙 파일이 없으면 빌드 명령, 폴더 구조, 사내 약어, 늘 지킬 규칙을 세션마다 다시 설명해야 합니다. Claude Code 문서는 같은 실수를 두 번째로 보거나, 지난 세션에 입력한 정정을 또 입력해야 하면 그 내용을 CLAUDE.md에 더하라고 권합니다.

읽히는 곳과 시점

Claude Code는 CLAUDE.md를 다음 위치에서 찾습니다(2026-11 확인).

  • 조직 관리 정책: IT 부서가 배포하는 파일. Windows에서는 C:\Program Files\ClaudeCode\CLAUDE.md이고, 조직의 모든 사용자에게 적용됩니다.
  • 사용자: ~/.claude/CLAUDE.md. 내 모든 프로젝트에 적용됩니다.
  • 프로젝트: 작업 폴더의 CLAUDE.md 또는 .claude/CLAUDE.md. 저장소에 커밋해 팀이 함께 씁니다.
  • 로컬: 작업 폴더의 CLAUDE.local.md. 나만 쓰는 프로젝트 설정이므로 .gitignore에 넣습니다.

세션을 시작할 때 Claude Code는 작업 폴더와 그 위의 모든 폴더에 있는 CLAUDE.md를 덮어쓰지 않고, 범위가 넓은 것부터 모두 이어 붙입니다. 하위 폴더의 CLAUDE.md는 시작할 때 읽지 않고, 모델이 그 하위 폴더의 파일을 읽거나 고칠 때 들어갑니다.

CLAUDE.md 안에 @경로로 다른 파일을 불러올 수도 있지만, 불러온 파일도 함께 들어가므로 정리에 도움이 될 뿐 토큰은 줄지 않습니다.

무엇을 쓰는가

규칙 파일 전체가 세션의 모든 요청에 들어가므로, 한 줄을 더하면 그 줄이 모든 요청에 붙습니다. Claude Code 문서는 파일 하나를 200줄 이하로 두라고 권하고, 길수록 컨텍스트를 더 쓰고 지시를 지키는 정도가 떨어진다고 설명합니다. 여러 단계로 된 절차나 일부 작업에만 필요한 내용은 Skill로 옮깁니다.

지시는 확인할 수 있게 구체적으로 씁니다. 문서의 예로는 "변경을 테스트한다" 대신 "커밋 전에 npm test를 실행한다"처럼 씁니다. 두 지시가 서로 어긋나면 모델이 그중 하나를 임의로 따를 수 있으므로, 여러 위치의 규칙 파일을 함께 점검합니다. 이 장의 예제에 쓰는 규칙 파일(data/14장/규칙파일.md)은 폴더 구조, 늘 지킬 규칙 다섯 줄, 사내 약어로 되어 있습니다.

규칙 파일은 모델이 읽는 지시이지 강제 설정이 아닙니다. Claude Code 문서도 CLAUDE.md를 컨텍스트로 다룰 뿐 강제하지 않는다고 적고, 모델의 판단과 관계없이 막아야 하는 일은 훅으로 막으라고 안내합니다. "기록/은 읽기만 한다"를 적어 두어도, 모델이 지시를 어기거나 읽은 문서 속 지시에 속으면(15장 "보안과 거버넌스") 파일이 바뀔 수 있습니다.

Skill과 점진적 공개

Skill은 업무 하나의 절차, 양식, 참고 파일을 묶은 폴더입니다. 세션에는 이름과 설명만 들어가고, 모델이 설명을 보고 필요하다고 판단하면 본문을, 본문이 가리키면 딸린 파일을 읽습니다. 그래서 이름과 설명이 모델이 Skill을 고르는 단서의 전부입니다.

Skill의 구조

Skill은 업무 하나의 절차, 양식, 참고 파일을 SKILL.md와 함께 폴더 하나에 묶은 것입니다. 프로젝트의 Skill은 .claude/skills/<이름>/SKILL.md에, 내 모든 프로젝트에서 쓰는 Skill은 ~/.claude/skills/<이름>/SKILL.md에 둡니다. SKILL.md는 맨 앞의 front matter와 그 아래의 본문으로 되어 있습니다.

---
name: writing-alarm-report
description: 설비 한 대의 주간 알람 보고서 초안을 설비팀 양식으로 작성한다. 설비 번호와 주차(예 2026-W47)가 주어지고 알람 현황, 알람 보고서, 주간 알람 정리를 요청받았을 때 쓴다.
---

# 주간 알람 보고서 작성
(절차, 검증, 하지 않는 일. 양식은 같은 폴더의 양식.md를 읽는다)

name은 Skill의 이름이고, 사용자가 /writing-alarm-report처럼 이름을 입력해 직접 부를 때도 씁니다. description은 이 Skill이 무엇을 하고 언제 쓰는지 적은 설명입니다. 같은 폴더의 양식.md 같은 딸린 파일에는 양식, 규정, 예시를 둡니다. 딸린 스크립트는 모델이 내용을 읽지 않고 명령으로 실행하므로, 스크립트의 코드는 컨텍스트에 들어가지 않고 실행 결과만 들어갑니다.

가끔 쓰는 절차를 규칙 파일에 넣으면 그 절차와 관계없는 요청에도 매번 들어가 토큰을 쓰고, 다른 지시와 섞입니다. 매번 요청에 양식을 붙여 넣으면 사람마다, 회차마다 조금씩 다른 양식이 들어갑니다. Skill은 절차를 파일 하나로 고정하면서, 쓰지 않는 동안에는 컨텍스트를 거의 차지하지 않습니다.

세 단계로 들어간다

Skill은 필요한 만큼만 차례로 컨텍스트에 들어갑니다. 정보를 처음부터 모두 넣지 않고 목록, 본문, 딸린 파일의 순서로 필요할 때 넣는 방식을 점진적 공개(progressive disclosure)라고 합니다(Anthropic, 2025c).

1단계에서 하네스는 설치된 모든 Skill의 이름과 설명을 컨텍스트의 Skill 목록에 넣습니다. 모델은 요청을 읽고 목록의 설명과 비교해 쓸 Skill을 고르고, 고르면 도구로 SKILL.md를 읽습니다(2단계). 읽은 본문은 대화의 메시지 하나가 되어 그 뒤의 요청에 모두 들어갑니다. 본문이 "같은 폴더의 양식.md를 읽고"처럼 가리키는 파일은 모델이 그 단계에 이르렀을 때 읽습니다(3단계).

예제 14-2Skill의 세 단계 토큰 수노트북 14_코딩_에이전트와_멀티_에이전트.ipynb의 예제 14-2

재료의 규칙 파일과 Skill 세 개를 1장의 토크나이저로 셉니다. 규칙 파일은 모든 요청에 전체가 들어가고, Skill은 1단계(목록의 한 줄)만 늘 들어갑니다. 1단계와 2단계, 3단계의 토큰 수가 몇 배 차이 나는지 봅니다.

def tokens(text):
    return len(tokenizer.encode(text))


rules = (MATERIAL / '규칙파일.md').read_text(encoding='utf-8')
print(f'규칙 파일: {tokens(rules):,}토큰. 세션의 모든 요청에 들어갑니다\n')
for folder in sorted((MATERIAL / 'skills').iterdir()):
    meta = front_matter(folder / 'SKILL.md')                       # 준비 셀의 함수: name, description
    listing = f"- {meta['name']}: {meta['description']}"          # 1단계: Skill 목록의 한 줄
    body = (folder / 'SKILL.md').read_text(encoding='utf-8')       # 2단계: SKILL.md 전체
    files = sum(tokens(path.read_text(encoding='utf-8'))           # 3단계: 딸린 파일
                for path in folder.glob('*.md') if path.name != 'SKILL.md')
    print(f'{folder.name}\n  1단계 {tokens(listing):,}토큰, 2단계 {tokens(body):,}토큰, 3단계 {files:,}토큰')

summarizing-shift-handover

writing-alarm-report

세 Skill의 1단계는 68~80토큰으로 규칙 파일(395토큰)의 5분의 1 정도이고, 2단계는 1단계의 4~7배입니다. writing-alarm-report는 딸린 파일까지 읽으면 1단계의 약 12배(582 + 391토큰)가 됩니다. 세 Skill의 본문과 딸린 파일을 모두 규칙 파일에 넣었다면 약 1,900토큰이 보고서와 관계없는 요청에도 매번 붙었을 것입니다. Skill로 두면 평소에는 목록 세 줄만 들어가고, 본문과 양식은 그 Skill을 쓰는 요청에서만 들어갑니다.

설명이 고르는 단서다

모델은 2단계에 들어가기 전에 본문을 보지 못하므로, Skill을 쓸지는 이름과 설명만 보고 정합니다. 본문이 아무리 잘 쓰여 있어도 설명에 언제 쓰는지가 없으면 모델이 그 Skill을 고르지 못할 수 있습니다. 설명에는 무엇을 하는지와 언제 쓰는지를 함께 쓰고, 사용자가 요청할 때 쓸 법한 낱말(알람 현황, 주간 알람 정리)을 넣습니다. Claude Code는 목록에서 설명을 1,536자에서 자르므로 핵심을 앞에 씁니다(2026-11 확인).

예제 14-3설명만 보고 Skill 고르기노트북 14_코딩_에이전트와_멀티_에이전트.ipynb의 예제 14-3

Skill 목록을 시스템 프롬프트에 넣어 모델에게 요청마다 읽을 Skill을 고르게 합니다. Claude Code에서 모델이 Skill을 고르는 과정을 단순하게 흉내 낸 것입니다. 같은 요청 네 개를 이름과 설명이 모호한 목록과, 무엇과 언제를 적은 재료의 목록에 각각 보냅니다. 마지막 요청은 어느 Skill도 필요 없는 일반 질문입니다. 이 셀은 API를 8번 호출합니다.

vague = {'helper': '업무를 돕는 양식 모음입니다.', 'checker': '문서를 확인합니다.', 'notes': '메모를 다룹니다.'}
clear = {meta['name']: meta['description']
         for meta in (front_matter(path) for path in sorted((MATERIAL / 'skills').glob('*/SKILL.md')))}
requests = ['W-07의 이번 주 알람 현황을 정리해 주세요.',
            '내일 게시할 안전 공지 초안인데 규정에 맞는지 봐 주세요.',
            '야간조가 남긴 인수인계 메모를 표로 바꿔 주세요.',
            '와이어 본딩에서 캐필러리는 어떤 역할을 하나요?']
for label, skills in [('모호한 설명', vague), ('무엇과 언제를 적은 설명', clear)]:
    listing = '\n'.join(f'- {name}: {description}' for name, description in skills.items())
    system = (f'너는 코딩 에이전트다. 쓸 수 있는 Skill은 다음과 같다.\n{listing}\n'
              '요청을 처리하기 전에 읽을 Skill이 있으면 그 이름만, 없으면 "없음"이라고만 답한다.')
    print(f'[{label}]')
    for request in requests:
        reply = llm.ask(request, system=system, model='소형', max_tokens=1000)   # thinking에도 출력 토큰을 쓰므로 넉넉히 둡니다
        print(f'  {request[:22]}… → {reply.text.strip()}')

교재의 실행에서 무엇과 언제를 적은 설명을 주자 소형 모델은 세 요청에 맞는 Skill을 고르고, 일반 질문에는 "없음"이라고 답했습니다. 모호한 설명으로는 요청과 뜻이 가까운 checker와 notes는 골랐지만, 알람 현황 요청에는 "없음"이라고 답해 helper를 고르지 않았습니다. 실제 코딩 에이전트에서 Skill을 고르지 않으면 본문이 컨텍스트에 들어가지 않으므로, 모델은 양식과 검증 절차를 모른 채 보고서를 씁니다.

설명이 모호해 모델이 스스로 고르지 못해도, 사용자가 /이름으로 부르면 그 Skill의 본문이 들어갑니다. 반대로 front matter에 disable-model-invocation: true를 적으면 모델은 그 Skill을 스스로 고르지 않고, 설명도 목록에 들어가지 않습니다. 배포나 메일 발송처럼 사람이 시점을 정해야 하는 절차에 씁니다.

Claude Code 문서는 SKILL.md를 500줄 이하로 두고 자세한 참고 자료는 별도 파일로 옮기라고 권합니다. 딸린 파일은 SKILL.md에서 직접 가리키게 둡니다. Anthropic의 Skill 작성 지침은 딸린 파일이 다시 다른 파일을 가리키면 모델이 그 파일의 앞부분만 읽어 정보를 놓칠 수 있다고 설명합니다. Skill, 서브에이전트, 훅을 묶어 다른 사람에게 한 번에 설치해 주는 단위를 Claude Code에서는 플러그인이라고 부릅니다(2026-11 확인).

서브에이전트와 멀티 에이전트

서브에이전트는 메인 에이전트가 맡긴 일을 자기 컨텍스트에서 처리하고 요약만 돌려줍니다. 메인의 컨텍스트는 가벼워지지만, 서브에이전트마다 시스템 프롬프트와 도구 정의를 다시 보내므로 짧은 일은 나눌수록 전체 토큰이 늘어납니다.

서브에이전트

서브에이전트(subagent)는 메인 에이전트가 작업의 일부를 맡기려고 따로 실행하는 에이전트입니다. 로그 수백 행을 읽고 결론 몇 줄을 얻는 일을 메인이 직접 하면, 읽은 로그가 메인의 대화에 남아 그 뒤의 모든 요청에 들어갑니다. 서브에이전트에 맡기면 로그는 서브에이전트의 컨텍스트에서만 읽히고, 메인에는 결론만 남습니다.

Claude Code의 서브에이전트는 새 컨텍스트에서 시작하고, 메인의 대화, 메인이 이미 읽은 파일, 메인이 쓴 Skill을 보지 못합니다. 메인의 모델이 맡길 일을 정리한 위임 메시지를 쓰고, 서브에이전트는 자기 시스템 프롬프트, 규칙 파일, 위임 메시지로 시작합니다. 내장 서브에이전트 Explore와 Plan은 규칙 파일도 읽지 않습니다(2026-11 확인). 그래서 위임 메시지에는 목표, 돌려받을 형식, 쓸 도구와 자료, 하지 않을 일을 모두 적어야 합니다. 메인의 대화에서 정한 것이라도 위임 메시지에 없으면 서브에이전트는 모릅니다.

서브에이전트는 .claude/agents/<이름>.md 파일 하나로 정의합니다. front matter의 name과 description은 반드시 적고, tools로 쓸 수 있는 도구를, model로 모델을, maxTurns로 서브에이전트가 멈추기 전까지의 에이전트 턴 상한을 정합니다. 본문은 그 서브에이전트의 시스템 프롬프트가 됩니다. 메인의 모델은 Skill과 마찬가지로 description을 보고 어느 서브에이전트에 맡길지 고릅니다. Claude Code에는 읽기 전용으로 파일을 찾고 분석하는 Explore, plan 모드에서 계획에 필요한 자료를 모으는 Plan 같은 서브에이전트가 들어 있습니다.

---
name: report-reviewer
description: 보고서 초안이 규칙 파일과 양식을 지키는지 검토하고 위반 항목만 돌려준다. 보고서 초안을 쓴 뒤 검토가 필요할 때 쓴다.
tools: Read, Grep, Glob
maxTurns: 8
---

너는 설비팀 보고서 검토 담당이다. 초안을 고치지 않고, 위반 항목과 근거 줄만 돌려준다.

이 정의의 tools에는 읽기 도구만 있으므로, 검토 담당은 초안을 고칠 수 없고 판정만 돌려줍니다.

예제 14-4서브에이전트가 메인에 남기는 것노트북 14_코딩_에이전트와_멀티_에이전트.ipynb의 예제 14-4

알람 로그 400행에서 부품 교체 기록을 찾는 일을 두 방법으로 처리하고, 메인이 이어서 질문할 때 그 요청의 입력 토큰을 비교합니다. 직접 읽기는 메인의 대화에 로그가 남습니다. 서브에이전트 방식은 별도 요청에 로그를 넣고, 메인의 대화에는 위임 메시지와 요약만 남깁니다. 메인의 다음 응답은 종료 이유(5장 "LLM API")도 출력합니다. 서브에이전트를 llm.ask() 요청 하나로 단순하게 흉내 낸 것입니다. 이 셀은 API를 4번 호출합니다.

log = (MATERIAL / '기록' / '알람로그.csv').read_text(encoding='utf-8')
task = '알람 로그에서 조치가 "부품 교체"로 시작하는 행을 모두 찾아 일시, 설비, 부품을 알려 주세요.'
follow = '그 가운데 와이어 본더에 대해, 다음 PM 때 확인할 것을 한 문장으로 제안해 주세요.'  # PM: 예방 정비(재료 규칙 파일의 사내 약어)
# 직접 읽기: 로그 전체가 메인의 대화에 남습니다
direct = llm.ask(f'{task}\n\n{log}', model='소형', max_tokens=1000)   # thinking에도 출력 토큰을 쓰므로 넉넉히 둡니다
main_direct = [{'role': 'user', 'content': f'{task}\n\n{log}'}, {'role': 'assistant', 'content': direct.text}]
# 서브에이전트에 맡기기: 로그는 별도 요청에만 넣고, 메인에는 위임 메시지와 요약만 남깁니다
sub = llm.ask(f'{task} 결과만 세 줄 이내로 답해 주세요.\n\n{log}', model='소형', max_tokens=1000)
main_sub = [{'role': 'user', 'content': task}, {'role': 'assistant', 'content': sub.text}]
print(f'서브에이전트: 입력 {sub.input_tokens:,}토큰, 출력 {sub.output_tokens:,}토큰(thinking 포함). 메인에 돌려준 요약:\n{sub.text.strip()}\n')
for label, history in [('직접 읽기', main_direct), ('서브에이전트', main_sub)]:
    reply = llm.ask(follow, history=history, model='소형', max_tokens=1000)
    print(f'[{label}] 메인의 다음 요청 입력 {reply.input_tokens:,}토큰, 종료 이유 {reply.stop_reason} → {reply.text.strip()}')

서브에이전트: 입력 15,418토큰, 출력 395토큰(thinking 포함). 메인에 돌려준 요약:
2026-11-18 02:37, W-07, 캐필러리
2026-11-20 00:51, B-04, 흡착 노즐
2026-11-21 10:13, M-03, 히터 카트리지

[직접 읽기] 메인의 다음 요청 입력 15,589토큰, 종료 이유 end → 다음 PM에서는 W-07의 캐필러리 교체(2026-11-18) 이후에도 와이어 끊김(E-214)이 계속 발생하므로, 캐필러리 장착 상태와 와이어 장력 및 공급 경로를 함께 점검하고 교체 효과를 재평가해야 합니다.
[서브에이전트] 메인의 다음 요청 입력 184토큰, 종료 이유 end → 다음 PM에서는 W-07 캐필러리 교체 후 본딩 강도(풀 테스트)와 1st/2nd 본드 형상을 확인하고, 캐필러리 팁의 마모와 오염 여부를 점검하세요.

교재의 실행에서 서브에이전트 쪽 요청은 로그를 읽느라 입력 15,418토큰을 썼지만, 메인에 돌아온 것은 세 줄입니다. 메인의 다음 요청 입력은 로그를 직접 읽었을 때 15,589토큰, 서브에이전트에 맡겼을 때 184토큰이었습니다. 직접 읽으면 이 대화가 이어지는 동안 모든 요청에 로그 약 1만 5천 토큰이 들어갑니다.

대신 요약에 없는 정보는 메인이 알 수 없습니다. 교재의 실행에서 로그를 직접 읽은 메인은 캐필러리를 교체한 뒤에도 와이어 끊김(E-214)이 이어진다는 로그 내용을 근거로 제안했지만, 서브에이전트에 맡긴 메인은 요약 세 줄에 그 내용이 없어 일반적인 점검 항목을 제안했습니다. 위임 메시지에 돌려받을 항목을 정해 두는 이유입니다.

일을 나누는 방식

에이전트 여럿이 일을 나눠 맡고 결과를 주고받는 구성을 멀티 에이전트(multi-agent system)라고 합니다. 코딩 에이전트에서는 메인 에이전트가 서브에이전트에 일을 맡기는 형태가 대부분입니다. Anthropic(2024)은 LLM(large language model) 호출과 도구를 미리 정한 코드 경로로 엮는 워크플로(workflow)를 몇 가지로 정리하고, 모델이 다음 행동을 스스로 정하는 에이전트와 구분했습니다. 그중 일을 나눌 때 쓰는 네 가지는 코딩 에이전트가 서브에이전트에 일을 맡기는 구성에도 그대로 나타납니다.

  • 프롬프트 체인(prompt chaining): 앞 단계의 출력을 다음 단계가 받습니다(4장). 단계 사이에 코드로 확인하는 검사를 두어, 실패하면 다음 단계로 가지 않게 합니다.
  • parallelization: 서로 독립인 일을 여러 에이전트가 동시에 처리하고 결과를 합칩니다. 설비 다섯 대의 로그를 한 대씩 맡기는 경우입니다.
  • orchestrator-workers: 메인 에이전트가 일을 어떻게 나눌지 실행 중에 정하고, 워커에게 맡긴 뒤 결과를 합칩니다. parallelization과 달리 나눌 방법을 미리 정하지 않습니다.
  • evaluator-optimizer: 작성 담당의 결과를 검토 담당이 판정하고, 반려하면 피드백과 함께 다시 쓰게 합니다. 검토 담당은 작성 과정의 대화를 보지 않고 결과물과 기준만 받아 판정합니다. 통과하지 못하는 경우에 대비해 반려 횟수에 상한을 두고, 상한에 이르면 멈추고 사람에게 넘깁니다.

나누는 데는 비용이 듭니다. 서브에이전트마다 자기 시스템 프롬프트와 도구 정의를 처음부터 보내고, 위임 메시지와 요약을 주고받는 요청이 더해집니다. Anthropic(2025a)은 자사 리서치 시스템에서 에이전트 하나가 채팅보다 토큰을 약 4배, 멀티 에이전트가 약 15배 썼다고 보고했습니다. 같은 글은 모든 에이전트가 같은 컨텍스트를 공유해야 하는 일은 지금의 멀티 에이전트에 맞지 않는다고 적었습니다. 한 번의 조회로 끝나는 짧은 일, 에이전트끼리 중간 결과를 계속 주고받아야 하는 일은 한 에이전트로 처리합니다. 일의 길이에 따라 나눌 때와 나누지 않을 때의 토큰이 어떻게 바뀌는지는 실습 14-2에서 계산합니다.

권한과 훅

규칙 파일의 지시는 모델이 따르지 않을 수도 있는 글입니다. 권한 규칙과 훅은 하네스가 도구 실행마다 적용하는 설정과 코드이므로 모델의 판단과 관계없이 적용됩니다. 다만 둘 다 도구 요청에 적힌 내용만 검사하므로, 스크립트 안에서 일어나는 일까지 막으려면 샌드박스가 필요합니다.

권한 요청과 권한 모드

권한 요청(permission prompt)은 모델이 파일 수정이나 명령 실행을 요청했을 때, 하네스가 그 요청을 실행하기 전에 사용자에게 허용할지 묻는 확인입니다. 모델이 요청한 명령은 잘못 판단했거나 문서 속 지시에 속은 결과일 수 있으므로, 사용자가 실행 전에 멈출 기회가 필요합니다. 요청마다 물으면 사용자가 모든 수정과 명령을 확인할 수 있습니다. 대신 사용자가 답할 때까지 작업이 멈춥니다. 묻지 않으면 작업이 빨리 끝납니다. 대신 잘못된 명령을 멈출 사람이 없습니다.

하네스는 도구 요청마다 "바로 실행", "사용자에게 물음", "실행하지 않음" 가운데 하나로 처리합니다. 권한 모드(permission mode)는 어떤 요청을 이 셋 가운데 무엇으로 처리할지 정하는 세션 설정입니다. 아래 표는 권한 규칙과 훅(다음 두 소절)에 해당하지 않는 요청을 모드마다 어떻게 처리하는지 보여 줍니다. 작업 폴더 안의 파일 읽기와 검색은 어느 모드에서나 바로 실행하므로 표에서 뺐습니다(2026-11 확인).

모드 바로 실행 사용자에게 물음 실행하지 않음
default 읽기 전용 셸 명령 파일 수정, 그 밖의 셸 명령, 웹 접근 없음
acceptEdits 작업 폴더 안의 파일 수정, 작업 폴더 안의 경로에 대한 mkdir, rm, mv 같은 파일 명령 그 밖의 셸 명령, 웹 접근 없음
plan 읽기 전용 셸 명령 그 밖의 셸 명령 파일 수정(계획을 승인하기 전까지)
auto 분류 모델이 안전하다고 판정한 요청 분류 모델이 잇달아 막은 뒤의 요청 분류 모델이 위험하다고 판정한 요청
dontAsk 읽기 전용 셸 명령 없음 그 밖의 모든 요청
bypassPermissions 모든 요청 없음 없음

auto 모드에서는 하네스가 요청을 실행하기 전에 별도의 분류 모델에 보내 위험한지 판정하게 합니다. 분류 모델이 연속 3번 또는 세션 전체에서 20번 막으면, 하네스는 자동 판정을 멈추고 다시 사용자에게 묻습니다. 표의 plan 행은 auto 모드를 쓸 수 없는 세션의 처리이고, auto 모드를 쓸 수 있으면 plan 모드에서도 셸 명령을 분류 모델이 판정합니다(2026-11 확인).

모드는 작업에 따라 다음처럼 고릅니다.

  • 처음 다루는 코드이거나 중요한 작업이면 default를 씁니다.
  • 파일 수정은 맡기고 바뀐 내용을 diff로 검토하려면 acceptEdits를 씁니다.
  • 고치기 전에 계획부터 확인하려면 plan을 씁니다.
  • 긴 작업에서 사용자가 확인하는 횟수를 줄이려면 auto를 씁니다.
  • CI처럼 답할 사용자가 없는 실행에는 dontAsk를 씁니다. 예제 14-1이 이 모드로 실행했으므로, default라면 사용자에게 물었을 파일 수정과 셸 명령은 실행하지 않았습니다.
  • bypassPermissions는 격리된 컨테이너나 가상 머신에서만 씁니다. 이 모드에서는 deny와 ask 규칙, 훅 말고는 확인 없이 실행하므로, 모델이 잘못된 명령을 요청해도 회사 파일과 네트워크에 닿지 않는 환경이어야 합니다.

plan 모드(plan mode)는 사용자가 계획을 승인하기 전까지 하네스가 파일 수정 도구를 실행하지 않는 권한 모드입니다. 프롬프트에 "고치지 말고 계획만 세워 달라"고 적으면 모델이 이 지시를 어길 수 있지만, 권한 모드는 하네스가 적용하므로 모델이 수정 도구를 요청해도 실행되지 않습니다. 다만 사용자가 허용한 셸 명령은 실행되므로, sed -i나 리다이렉션(>)으로 파일이 바뀔 수는 있습니다. 대화 화면에서는 Shift+Tab으로 모드를 바꾸고, dontAsk는 claude를 실행할 때 --permission-mode dontAsk로 지정합니다.

권한 규칙

권한 규칙(permission rule)은 어떤 도구 실행을 묻지 않고 허용할지(allow), 물을지(ask), 막을지(deny) 설정 파일에 적은 규칙입니다. 설정 파일은 ~/.claude/settings.json(내 모든 프로젝트), .claude/settings.json(팀이 공유하는 프로젝트 설정), .claude/settings.local.json(나만 쓰는 프로젝트 설정), 조직이 배포하는 관리 설정이 있습니다.

{
  "permissions": {
    "allow": ["Bash(python tools/count_alarms.py *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Edit(./기록/**)", "Bash(rm *)", "Read(./.env)"]
  }
}

규칙은 도구 이름과 괄호 안의 패턴으로 씁니다. Claude Code는 deny, ask, allow 순서로 규칙을 보고 처음 맞는 규칙을 따르며, 규칙이 얼마나 구체적인지는 순서를 바꾸지 않습니다. 그래서 Bash(aws *)를 deny에 두면 allow에 Bash(aws s3 ls)가 있어도 막힙니다. 어느 설정 파일의 deny든 다른 설정 파일이나 명령줄 옵션의 allow로 풀 수 없습니다(2026-11 확인).

훅

훅(hook)은 도구 실행 전후처럼 정해진 시점에 하네스가 자동으로 실행하는 명령입니다. 모델이 정하지 않고 하네스가 시점마다 실행하므로, 훅에 넣은 검사와 기록은 매번 일어납니다. 도구를 실행하기 전의 PreToolUse, 실행한 뒤의 PostToolUse, 사용자가 메시지를 보낼 때의 UserPromptSubmit, 세션을 시작할 때의 SessionStart 같은 시점이 있습니다.

PreToolUse 훅이 실행되면 Claude Code는 실행하려는 도구의 이름(tool_name)과 입력(tool_input)을 JSON으로 훅의 표준 입력에 넘깁니다. 훅의 종료 코드에 따라 다음과 같이 처리합니다(2026-11 확인).

  • 0: 도구 요청이 평소의 권한 확인으로 넘어갑니다. 훅이 아무것도 출력하지 않으면 허용한 것이 아니라 판단하지 않은 것입니다. 훅이 JSON으로 permissionDecision에 "allow"를 출력해도 deny와 ask 규칙은 그대로 적용됩니다.
  • 2: 도구 실행을 막고, 훅이 표준 오류에 쓴 글을 모델에게 막힌 이유로 알립니다.
  • 그 밖의 코드: 훅의 오류로 보고 도구는 실행합니다. 파이썬 훅이 예외로 끝나도 종료 코드가 1이므로 도구가 실행됩니다. 정책을 강제하려는 훅은 막을 때 2로 끝내고, 훅 자체가 실패할 때도 막으려면 훅 설정에 "onFailure": "block"을 적습니다(v2.1.295 이상).

훅은 설정 파일의 hooks에 적고, matcher로 어떤 도구에 실행할지 고릅니다. 훅은 출력이 없으면 컨텍스트를 차지하지 않습니다. 막는 일 말고도 PostToolUse 훅으로 도구 실행마다 로그를 남기거나, 파일을 고칠 때마다 형식 검사를 실행하는 데 씁니다.

13장 AI 에이전트

강의 1일차 파트 1과 3, 7일차 파트 1과 2, 8일차 파트 2와 3에 해당합니다.

LLM(large language model)은 글을 받아 다음 토큰을 이어 쓸 뿐이고, 사내 문서를 열거나 계산기를 누르거나 작업 요청을 등록하지 못합니다. 그런데도 에이전트는 문서를 찾아 읽고 답합니다. 이 장은 모델이 글만 생성하면서 어떻게 도구를 쓰는지, 도구를 쓰는 반복이 언제 끝나고 비용이 왜 늘어나는지, 도구 연결을 표준으로 정한 MCP(Model Context Protocol)가 무엇을 정하는지 설명합니다. 끝으로 에이전트가 틀리는 방식과 그것을 코드와 사람의 승인으로 막는 방법을 다룹니다. 코딩 에이전트의 규칙 파일, Skill, 서브에이전트, 훅은 14장 "코딩 에이전트와 멀티 에이전트"에서 다룹니다.

학습 목표

  1. 챗봇, 워크플로, 에이전트를 다음 행동을 누가 정하는지로 구분할 수 있습니다.
  2. 모델이 도구를 직접 실행하지 못하는데도 도구를 쓸 수 있는 이유를, 도구 정의와 도구 호출과 도구 결과가 모두 모델이 읽고 쓰는 토큰이라는 원리로 설명할 수 있습니다.
  3. 에이전트 루프가 언제 끝나는지, 단계마다 입력 토큰이 왜 늘어나는지 설명하고, 검색을 코드가 정하는 RAG(retrieval-augmented generation)와 모델이 정하는 에이전트를 비교할 수 있습니다.
  4. MCP가 표준으로 정하는 것과 그대로 두는 것을 설명할 수 있습니다.
  5. 에이전트가 틀리는 유형마다 단계 상한, 오류 결과, 최소 권한, human-in-the-loop 가운데 무엇으로 막을지 고르고, 어떤 일에 에이전트를 쓸지 판단할 수 있습니다.

예제 13-1은 1장의 공개 모델 토크나이저만 쓰고 API(application programming interface)를 호출하지 않습니다. 예제 13-2, 13-3은 API로 모델을 호출합니다. 예제가 쓰는 사내 문서 120건의 검색 함수 search_docs(), 읽기 함수 read_doc(), 두 함수의 도구 정의 TOOLS는 노트북 폴더의 doc_tools.py에 있고 장 노트북의 준비 코드가 불러옵니다. search_docs()는 7장의 키워드 검색 BM25(Best Matching 25)를 단순하게 구현한 것입니다. 관통 프로젝트 5단계는 평가셋(data/evalset.json)의 질문을 씁니다. 평가셋은 질문마다 정답 문서(답이 든다고 미리 정해 둔 문서)와 맞는 답에 들어 있어야 할 핵심어를 붙여 둔 질문 묶음입니다(9장). 모델의 응답과 고르는 도구는 실행할 때마다 교재와 다를 수 있습니다.

챗봇, 워크플로, 에이전트

LLM을 쓰는 시스템은 다음 행동을 누가 정하는지로 나눕니다. 워크플로에서는 개발자가 작성한 코드가 순서를 정하고, 에이전트에서는 모델이 도구 결과를 읽고 다음 행동을 정합니다.

LLM을 시스템에 연결하는 네 가지 방식을 다음 행동을 정하는 쪽으로 비교하면 다음과 같습니다.

방식 다음 행동을 정하는 쪽 모델에 연결하는 것 사람이 하는 일
챗봇 사람 대화 이력 답을 읽고 다음 질문을 정한다
코파일럿 사람 편집기, 문서 화면 모델의 제안을 반영할지 정한다
워크플로 개발자가 작성한 코드 사내 시스템과 데이터 코드 경로를 설계하고 결과를 확인한다
에이전트 모델 여러 도구 목표를 주고 결과를 확인한다

워크플로는 LLM과 도구를 미리 정해 둔 코드 경로로 연결한 시스템입니다. 8장의 RAG가 대표적인 예입니다. 질문이 오면 코드가 언제나 한 번 검색하고, 검색 결과를 프롬프트에 넣어 모델을 한 번 부릅니다. 모델은 검색할지, 무엇으로 검색할지 정하지 않습니다. 에이전트는 다음 행동과 도구 사용을 LLM이 스스로 정하며, 목표를 이룰 때까지 반복하는 시스템입니다. 검색할지, 어떤 검색어로 몇 번 검색할지, 어느 문서를 열어 읽을지, 언제 멈추고 답할지를 모델이 정합니다. Anthropic의 "Building effective agents"(2024)도 이 기준으로 둘을 나누고, 단계를 미리 정할 수 있는 일에는 워크플로를, 단계를 미리 알 수 없는 일에만 에이전트를 쓰라고 권합니다.

에이전트에 붙이는 도구가 달라도 구조는 같습니다. 14장의 코딩 에이전트는 파일 읽기, 파일 쓰기, 명령 실행을 도구로 받은 에이전트이고, 컴퓨터 사용 에이전트는 화면 캡처와 마우스, 키보드 조작을 도구로 받은 에이전트입니다.

도구 호출

모델은 글만 생성하므로 도구를 직접 실행하지 못합니다. 모델이 도구 이름과 인자를 정해진 형식으로 출력하면, 그 출력을 받은 코드가 도구를 실행하고 결과를 다음 요청에 넣어 보냅니다.

모델에 도구(tool)를 붙이는 이유는 두 가지입니다.

  • 모델이 볼 수 없는 데이터가 있습니다. 사내 문서, 생산 DB, 설비 이력은 학습 데이터에 없고, 지식 기준일(2장) 뒤의 일도 모델은 알지 못합니다.
  • 정확해야 하는 일이 있습니다. 토크나이저는 긴 숫자를 몇 자리씩 묶어 토큰으로 나누고, 모델은 계산 결과의 숫자도 다음 토큰을 예측해 씁니다(1장). 큰 수의 곱셈이나 날짜 계산을 맞혀도 그 답이 맞는지는 다시 계산해 봐야 알 수 있습니다. 조회와 계산처럼 코드로 하면 틀리지 않는 일은 코드에 맡깁니다.

도구 호출(tool use)은 모델이 도구의 이름과 인자를 정해진 형식으로 출력해 실행을 요청하고, 그 요청을 받은 코드가 도구를 실행하는 방식입니다. OpenAI는 같은 기능을 function calling이라고 부릅니다. 도구를 실행하는 것은 모델이 아니라 요청을 받은 코드입니다. 모델은 도구 결과를 다음 요청의 입력으로 받아 읽고, 답을 쓰거나 다른 도구를 다시 요청합니다.

도구 정의는 입력에 들어가는 글이다

도구 정의(tool definition)는 도구의 이름, 설명, 인자의 JSON(JavaScript Object Notation) 스키마를 적어 요청에 함께 보내는 것입니다. 이 장의 예제가 쓰는 search_docs의 정의는 다음과 같습니다(Anthropic API 형식).

{'name': 'search_docs',
 'description': '후공정 회사의 사내 문서 120건(작업 표준, 설비 매뉴얼, 품질 이슈 보고서, 회의록, 공지, 교육 자료, '
                '안전 규정)을 키워드로 검색한다. 관련이 높은 순서로 5건의 문서 번호, 제목, 종류, 부서, 개정, 날짜, '

OpenAI 호환 API에서는 같은 내용을 {'type': 'function', 'function': {'name': ..., 'description': ..., 'parameters': ...}}로 감싸 보냅니다. 인자의 스키마를 적는 키가 Anthropic은 input_schema, OpenAI는 parameters이고 내용은 같습니다.

모델은 이 정의를 어떻게 읽을까요? 모델이 받는 것은 채팅 템플릿이 메시지 목록을 이어 붙인 토큰 열 하나입니다(3장). 도구 정의도 따로 전달되는 것이 아니라 채팅 템플릿이 이 토큰 열 안에 글로 넣습니다. API로 제공되는 Claude 모델의 템플릿은 공개되지 않습니다. 다만 Anthropic의 문서에 따르면 도구를 주면 API가 도구 사용을 위한 시스템 프롬프트를 자동으로 더하고, 그 토큰(Claude Haiku 5.5는 tool_choice가 auto일 때 286토큰)과 도구 정의의 토큰이 입력 토큰으로 계산됩니다(2026-11 확인). 공개 모델의 템플릿으로는 실제로 어떤 글이 되는지 볼 수 있습니다.

예제 13-1도구 정의는 입력에 들어가는 글이다노트북 13_AI_에이전트.ipynb의 예제 13-1

1장의 공개 모델 Qwen2.5의 채팅 템플릿에 같은 질문을 도구 없이, 도구 두 개와 함께 넣어 입력 토큰 수를 비교하고, 도구 정의가 들어간 입력 전체를 출력합니다. 이어서 모델이 도구를 요청하고 코드가 결과를 돌려준 뒤의 입력에서 새로 붙은 부분만 출력합니다. 도구 정의, 도구 호출, 도구 결과가 각각 어떤 글로 들어가는지 봅니다. API를 호출하지 않습니다.

# Qwen의 템플릿은 OpenAI 형식의 도구 정의를 받으므로 TOOLS(Anthropic 형식)를 바꿔 넣습니다
qwen_tools = [{'type': 'function', 'function': {'name': tool['name'], 'description': tool['description'],
                                                'parameters': tool['input_schema']}} for tool in TOOLS]
question = [{'role': 'user', 'content': 'SSC가 뭔가요?'}]
plain = tokenizer.apply_chat_template(question, tokenize=False, add_generation_prompt=True)
with_tools = tokenizer.apply_chat_template(question, tools=qwen_tools, tokenize=False, add_generation_prompt=True)
print(f'입력 토큰: 도구 없이 {len(tokenizer(plain).input_ids)}개, 도구 두 개와 함께 {len(tokenizer(with_tools).input_ids)}개\n')
print(with_tools)

# 모델이 search_docs를 요청했고, 코드가 실행한 결과(앞 200자)를 돌려준 뒤의 입력입니다
turns = question + [{'role': 'assistant', 'content': '', 'tool_calls': [
                        {'type': 'function', 'function': {'name': 'search_docs', 'arguments': {'query': 'SSC'}}}]},
                    {'role': 'tool', 'content': search_docs('SSC')[:200]}]
after = tokenizer.apply_chat_template(turns, tools=qwen_tools, tokenize=False, add_generation_prompt=True)
print('---- 도구 호출과 결과가 붙은 뒤 새로 생긴 부분 ----')
print(after[len(with_tools) - len('<|im_start|>assistant\n'):])

도구 정의는 시스템 메시지 안에 <tools> 태그로 감싼 JSON 글로 들어갔고, 그 앞뒤에 "필요하면 함수를 호출할 수 있다, 호출할 때는 <tool_call> 태그 안에 이름과 인자를 JSON으로 적어라"는 안내가 붙었습니다. 그래서 도구 두 개를 주자 같은 질문의 입력 토큰이 크게 늘었습니다. 도구 정의는 도구를 부르지 않는 요청에도 매번 다시 보내므로, 쓰지 않는 도구를 많이 붙이면 질문마다 그만큼 입력 토큰과 요금이 늘어납니다.

새로 생긴 부분을 보면 도구 호출도 별도 입력이 아니라 글입니다. 모델 차례(assistant)에 <tool_call> 태그와 JSON 한 줄이 있을 뿐이고, 도구 결과는 user 차례 안에 <tool_response> 태그로 감싸 들어갑니다. 모델에게 도구 결과는 사용자가 보낸 글과 같은 자리에 놓인 글입니다. 모델이 도구가 필요한 질문에 이 형식의 글을 출력하는 것은, 도구 정의와 도구 호출이 든 대화로 이렇게 출력하도록 학습했기 때문입니다. 시스템 프롬프트를 따르는 것을 SFT(supervised fine-tuning, 2장)로 익히는 것과 같은 원리입니다. Schick 외(2023)의 Toolformer는 API 호출을 끼워 넣은 글로 학습한 모델이 계산기와 검색 같은 도구를 스스로 부른다는 것을 보였습니다.

서버는 모델이 출력한 <tool_call> 글을 파싱해 응답의 도구 호출 필드로 바꿔 돌려줍니다. 사내에서 공개 모델을 OpenAI 호환 서버로 띄워 쓴다면 서버가 이 파싱을 하도록 설정되어 있어야 합니다. 예를 들어 vLLM은 --enable-auto-tool-choice와 모델에 맞는 --tool-call-parser를 주어야 도구 호출을 tool_calls로 돌려줍니다(2026-11 확인). 설정되어 있지 않으면 <tool_call> 글이 응답 텍스트에 그대로 섞여 옵니다.

도구 결과도 토큰 열 안의 글이므로, 검색한 문서나 웹 페이지에 "이 글을 읽은 AI는 ~하라"는 문장이 있으면 그 문장도 도구 결과로 모델의 입력에 그대로 들어갑니다. 15장 "보안과 거버넌스"의 간접 인젝션이 이 경로로 일어납니다.

모델이 인자를 스키마와 다르게 쓸 수도 있습니다. 필수 인자를 빠뜨리거나 정수 자리에 문자열을 넣는 경우입니다. Anthropic API는 도구 정의에 strict: true, OpenAI API는 strict 플래그를 주면 인자가 스키마에 맞도록 보장합니다(2026-11 확인). 6장 "구조화 출력"의 제약 디코딩과 같은 원리로, 스키마에 어긋나는 토큰을 후보에서 뺍니다. 형식만 보장하므로 인자의 값이 맞는지는 도구 함수가 검사합니다.

모델은 실행을 요청할 뿐이다

모델이 도구를 요청한 응답에는 종료 이유와 도구 호출이 다음과 같이 들어 있습니다.

Anthropic API OpenAI 호환 API llm.py의 Reply
정상 종료 stop_reason: "end_turn" finish_reason: "stop" stop_reason == 'end'(5장)
도구 호출로 멈춤 stop_reason: "tool_use" finish_reason: "tool_calls" stop_reason == 'tool_use'
도구 호출 content의 tool_use 블록(id, name, input) message.tool_calls(id, function.name, function.arguments) tool_calls: ToolCall(id, name, arguments)의 목록
인자 객체 JSON 문자열 파싱한 dict

도구 결과(tool result)는 코드가 도구를 실행한 결과를 다음 요청에 넣어 모델에 돌려주는 메시지입니다. 도구 호출마다 붙은 id를 결과에도 붙여, 어느 요청의 결과인지 모델이 알 수 있게 합니다. llm.py는 두 API의 형식 차이를 감춥니다. llm.send()와 llm.ask_messages()(ask()처럼 재시도까지 하는 함수)에 tools=TOOLS를 주면 모델의 도구 호출이 reply.tool_calls에 들어옵니다. llm.assistant_turn(reply)는 그 응답을, llm.tool_result(call, 글)은 실행 결과를 대화 이력에 넣을 메시지로 만듭니다.

모델이 도구를 부를지는 요청의 tool_choice로 정합니다. 기본값 auto는 부를지 말지를 모델이 정합니다. Anthropic의 any와 OpenAI의 required는 반드시 도구 하나 이상을 부르게 하고, 도구 이름을 지정하면 그 도구만 부르게 하며, none은 부르지 못하게 합니다(2026-11 확인). 이 장의 예제는 모두 auto로 보냅니다.

QUESTIONS = ['SSC가 뭔가요?',                                    # 사내 약어: 문서를 찾아야 답할 수 있음
             '와이어 본딩이 어떤 공정인지 한 문장으로 설명해 주세요.',   # 널리 알려진 일반 지식

        print(f'  도구 호출: {call.name}({call.arguments}), id {call.id}')
    if reply.text:
        print('  응답 텍스트:', reply.text.strip().replace('\n', ' ')[:150])

도구 정의 작성

모델은 함수의 코드를 보지 못하고 도구 정의의 이름, 설명, 스키마만 보고 도구를 고르고 인자를 만듭니다. 그래서 도구 정의는 함수의 주석이 아니라 모델에게 주는 프롬프트로 작성합니다. Anthropic의 "Building effective agents"도 도구 정의에 프롬프트만큼 공을 들이라고 권합니다. 설명에는 다음을 적습니다.

  • 무엇을 하는지와 언제 쓰는지: "사내 문서를 키워드로 검색한다"처럼 동작을 적고, 비슷한 도구가 있으면 둘을 나누는 기준을 적습니다.
  • 무엇을 돌려주는지: search_docs는 본문 전체가 아니라 한 줄만 돌려준다고 적어, 모델이 본문이 필요하면 read_doc을 부르게 합니다.
  • 하지 않는 일과 한계: "문서 수를 세지 않는다", "폐기된 문서도 결과에 나온다"처럼 모델이 잘못 기대할 만한 것을 적습니다.
  • 인자의 형식과 예: '예: SOP-WB-001'처럼 예를 하나 적으면 모델이 형식에 맞는 인자를 만듭니다.

도구가 많을수록 좋은 것은 아닙니다. 설명이 비슷한 도구가 여럿이면 모델이 목적과 다른 도구를 고르기 쉽습니다. 이름과 설명이 도구 선택을 얼마나 바꾸는지는 실습 13-1에서 측정합니다.

에이전트 루프

에이전트는 모델에 요청하고, 모델이 요청한 도구를 실행해 결과를 붙이고, 다시 요청하는 일을 모델이 도구를 더 요청하지 않을 때까지 반복합니다. 요청할 때마다 앞의 대화 전체를 다시 보내므로 단계가 늘수록 요청 하나의 입력 토큰이 커집니다.

에이전트 루프(agent loop)는 에이전트가 자료를 읽고, 도구를 실행하고, 결과를 확인하는 일을 작업이 끝날 때까지 되풀이하는 방식입니다. 코드로는 반복문 하나입니다. 모델에 요청을 보내고, 종료 이유가 tool_use이면 요청받은 도구를 실행해 결과를 대화 이력에 붙인 뒤 다시 보냅니다. 종료 이유가 다른 값이면 응답 텍스트를 답으로 돌려주고 끝냅니다. 모델이 끝내지 않을 때를 대비해 반복 횟수에도 상한을 둡니다. 이 상한을 단계 상한(step limit)이라고 하고, 에이전트 루프의 다른 종료 조건과 함께 그림에 나타냈습니다.

반복할 때마다 모델은 다음에 할 일을 정하고(어느 문서를 찾을지), 도구로 행동하고, 결과를 읽습니다. Yao 외(2022)의 ReAct는 다음 행동의 이유를 적는 글(thought)과 도구를 부르는 행동을 번갈아 생성하게 하는 방법을 제안했고, 지금의 에이전트 루프는 대부분 이 구조를 따릅니다.

루프에서 눈여겨볼 성질이 두 가지 있습니다.

  • 모델은 응답 하나에서 도구 호출을 여러 개 요청할 수 있습니다. 이를 병렬 도구 호출(parallel tool use)이라고 합니다. 서로 기다릴 필요가 없는 검색 두 개를 한 번에 요청하는 경우입니다. 코드는 요청받은 호출을 모두 실행하고 결과를 모두 붙인 뒤에 다음 요청을 보냅니다. Anthropic API는 결과를 user 메시지 하나에 모아 보내야 합니다(llm.py가 이렇게 묶습니다). 두 API 모두 기본으로 허용하고, Anthropic은 tool_choice의 disable_parallel_tool_use, OpenAI는 parallel_tool_calls: false로 끌 수 있습니다(2026-11 확인).
  • API 서버는 무상태이므로(3장) 단계마다 질문, 앞 단계의 도구 호출, 도구 결과를 모두 다시 보냅니다. 질문 하나의 요금은 단계마다 보낸 입력 토큰을 모두 더해 계산하므로, 단계 수가 두 배가 되면 요금은 두 배보다 더 늘어납니다. 문서 본문처럼 긴 도구 결과는 그 뒤의 모든 단계에 다시 들어갑니다.

에이전트가 단계마다 부른 도구, 인자, 결과를 차례로 남긴 것을 실행 기록(trace)이라고 합니다. 답에 적힌 값이 어느 도구 결과에서 왔는지, 어디서 틀렸는지는 실행 기록을 읽어야 알 수 있습니다.

예제 13-3에이전트 루프노트북 13_AI_에이전트.ipynb의 예제 13-3

run_agent()는 종료 이유가 tool_use인 동안 도구를 실행해 결과를 붙이고 다시 요청하는 반복문입니다. 두 문서를 이어야 답할 수 있는 평가셋 질문 E40을 묻고, 단계마다 입력 토큰과 모델이 요청한 도구를 출력합니다. 모델이 정한 검색어, 한 응답에 든 도구 호출의 수, 단계마다 늘어나는 입력 토큰을 봅니다. 이 셀은 API를 3~5번 호출합니다.

TOOL_FUNCTIONS = {'search_docs': search_docs, 'read_doc': read_doc}     # 도구 이름 → 실제로 실행할 함수
SYSTEM = '너는 후공정 회사의 사내 문서 도우미다. 도구로 사내 문서를 찾아 근거가 있는 것만 답하고, 답 끝에 근거 문서 번호를 적는다.'


def run_agent(question, max_steps=8):
    messages = [{'role': 'user', 'content': question}]
    for step in range(1, max_steps + 1):
        reply = llm.ask_messages(messages, system=SYSTEM, tools=TOOLS, model='소형', max_tokens=2000)
        print(f'{step}단계 입력 {reply.input_tokens:,}토큰:', [f'{call.name}({call.arguments})' for call in reply.tool_calls] or '최종 답')
        if reply.stop_reason != 'tool_use':                # 도구를 더 요청하지 않으면 응답 텍스트가 답입니다
            return reply.text
        if step == max_steps:                              # 결과를 돌려줄 다음 요청이 없으므로 도구도 실행하지 않습니다
            break
        messages.append(llm.assistant_turn(reply))
        for call in reply.tool_calls:                      # 요청받은 도구를 모두 실행하고, 결과에 같은 id를 붙입니다
            messages.append(llm.tool_result(call, TOOL_FUNCTIONS[call.name](**call.arguments)))
    return '(단계 상한에 닿아 멈췄습니다)'


print(run_agent('고객사 B의 요구로 강화된 기준 두 가지는 무엇이고 각각 얼마인가요?'))

1단계 입력 851토큰: ["search_docs({'query': '고객사 B 강화 기준'})", "search_docs({'query': '고객사 B 요구 기준'})"]
2단계 입력 2,193토큰: ["read_doc({'doc_id': 'SOP-WB-001'})", "read_doc({'doc_id': 'SOP-VI-001'})"]
3단계 입력 4,175토큰: 최종 답
고객사 B의 요구로 강화된 기준은 두 가지입니다.

1. **와이어 풀 강도 하한(금선 25μm): 5.0gf → 6.0gf**
   - 2026-03-16 개정 3에서 상향되었습니다(구리선은 6.0gf → 7.0gf).
   - 풀 테스트는 로트마다 5와이어를 측정하며, 한 와이어라도 하한에 못 미치면 로트를 홀드합니다.

2. **리드 코플래너리티: 0.10mm → 0.08mm 초과 시 불량**
   - 2026-10-05 개정 4에서 강화되었습니다.
   - 적용 제품은 QX48, SP8입니다.

근거 문서: SOP-WB-001(와이어 본딩 작업 표준, 개정 3), SOP-VI-001(외관 검사 기준, 개정 4)

검색을 도구로 쓰는 에이전트

검색을 도구로 주면 8장 "RAG"와 같은 검색 엔진을 쓰면서 검색어와 검색 횟수를 모델이 정합니다.

모델이 검색어를 정하면 질문의 낱말이 문서의 낱말과 다를 때 다른 낱말로 다시 검색할 수 있고, 두 문서를 이어야 하는 질문에서 첫 검색 결과를 읽고 빠진 것을 찾아 한 번 더 검색할 수 있습니다. 대신 질문 하나에 모델을 여러 번 부르므로 시간과 요금이 늘고, 같은 질문에도 실행마다 검색 경로가 다를 수 있습니다. 모델이 첫 결과만 보고 일찍 답하거나, 읽지 않은 문서의 번호를 근거로 적을 수도 있습니다. 질문 대부분이 한 번의 검색으로 답할 수 있는 것이면 RAG가 빠르고 싸며 결과도 일정합니다. 여러 문서를 잇거나 검색어를 바꿔 가며 찾아야 하는 질문이 많으면 에이전트가 낫습니다. 관통 프로젝트 5단계에서 두 방식이 정답 문서를 찾았는지 비교합니다.

MCP

MCP는 AI 응용과 도구를 제공하는 서버 사이의 연결 방식을 표준으로 정합니다. 모델이 도구를 고르고 요청하는 방식은 그대로이고, 도구 목록을 누가 알려 주고 누가 실행하는지만 바뀝니다.

도구를 붙일 때마다 응용마다 연결 코드를 따로 작성하면, 응용 N개와 도구 M개를 잇는 코드가 N×M개 필요합니다. MCP(Model Context Protocol)는 AI 응용이 도구와 자료를 제공하는 서버에 연결하는 표준 프로토콜입니다. Anthropic이 2024년에 공개했고, 도구를 MCP 서버로 한 번 만들면 MCP를 지원하는 응용 어디서나 쓸 수 있습니다. 명세는 참여자를 셋으로 나눕니다.

  • MCP 호스트(MCP host): MCP 서버에 연결해 그 도구를 모델에 넘기는 AI 응용입니다. Claude Code, Claude Desktop, VS Code가 여기에 해당합니다.
  • MCP 클라이언트: 호스트 안에서 서버 하나와의 연결을 맡는 부분입니다. 호스트는 연결하는 서버마다 클라이언트를 하나씩 만듭니다.
  • MCP 서버(MCP server): MCP로 도구, 리소스(읽을 자료), 프롬프트(미리 작성한 프롬프트 템플릿)를 제공하는 프로그램입니다. 사내 DB, 문서 저장소, 업무 시스템을 감쌉니다.

메시지는 JSON-RPC 2.0 형식입니다. 클라이언트가 tools/list를 요청하면 서버는 도구마다 name, description, inputSchema(인자의 JSON 스키마)를 돌려주고, tools/call에 도구 이름과 인자를 보내면 실행 결과를 content에, 실행 중 오류 여부를 isError에 담아 돌려줍니다. 서버가 같은 PC에서 실행되면 호스트가 서버를 하위 프로세스로 띄워 표준 입출력(stdio)으로 주고받고, 원격 서버와는 Streamable HTTP로 주고받습니다(명세 2026-07-28판, 2026-11 확인).

모델은 MCP를 알지 못합니다. 호스트가 tools/list로 받은 목록을 API 요청의 도구 정의로 바꿔 넣고, 모델이 도구 호출을 요청하면 그 요청을 tools/call로 서버에 보내고 결과를 도구 결과로 모델에 돌려줍니다. 모델 쪽에서 보면 도구 정의를 받고 도구 호출을 출력하는 일은 MCP가 없을 때와 같습니다.

MCP 서버를 붙이면 서버가 보내는 글이 모델의 입력에 들어갑니다. 도구의 설명과 도구 결과에 지시문이 들어 있으면 간접 인젝션(15장)이 됩니다. MCP 명세도 도구 실행을 사용자가 거부할 수 있도록 사람이 확인하는 단계를 두고, 서버가 알려 주는 도구의 동작 정보(annotations: 읽기 전용인지, 되돌릴 수 없는 변경을 하는지 등)는 신뢰하는 서버의 것이 아니면 믿지 말라고 권고합니다. 회사가 확인한 서버만 연결하고, 서버에 주는 계정에는 그 도구에 필요한 권한만 줍니다.

실패 패턴과 가드레일

에이전트는 틀려도 오류 없이 그럴듯한 답을 냅니다. 프롬프트에 하지 말라고 적는 것은 모델이 그렇게 할 확률을 낮출 뿐이므로, 반드시 막아야 하는 것은 루프의 상한, 도구 함수의 검사, 권한, 사람의 승인으로 코드에서 막습니다.

가드레일(guardrail)은 모델이 잘못 판단해도 피해가 생기지 않도록 코드, 권한, 사람 확인으로 두는 제한입니다. 에이전트가 틀리는 방식은 크게 네 가지이고, 유형마다 막는 방법이 있습니다.

실패 유형 예 막는 방법
잘못된 도구나 인자 문서 수를 세는 질문에 검색 도구를 부른다. 폐기된 구판을 읽고 그 값을 쓴다 도구 정의를 구체적으로 쓴다. 도구 결과에 문서 상태를 함께 돌려준다
근거 없는 값 도구 결과에 없는 값이나 읽지 않은 문서 번호를 답에 적는다 답에 적힌 문서 번호를 도구 결과에 나온 문서 번호와 대조한다(관통 프로젝트 5단계). 중요한 값은 사람이 원문을 확인한다
끝나지 않는 반복 문서에 답이 없는 질문에 검색어를 바꿔 가며 계속 검색한다 단계 상한과 질문당 토큰 예산을 둔다
과한 행동 조회만 시켰는데 작업 요청을 등록하거나 메일을 보낸다 도구에 최소 권한만 주고, 되돌릴 수 없는 도구는 사람이 승인한 뒤 실행한다

코드로 두는 가드레일은 다음과 같습니다.

  • 단계 상한과 토큰 예산: 루프를 정해 둔 횟수에서 멈추고, 질문 하나나 하루에 쓴 토큰이 예산을 넘으면 남은 일을 실행하지 않고 사람에게 알립니다.
  • 결과 길이 상한: 도구 결과는 그 뒤의 모든 요청에 다시 들어가므로 길이를 제한합니다. read_doc()은 본문을 4,000자에서 자릅니다.
  • 오류를 결과로 돌려주기: 도구 함수에서 예외가 발생하면 루프를 멈추지 않고 오류 내용을 도구 결과로 돌려줍니다. Anthropic API는 is_error를 True로 설정해 오류임을 알리고, OpenAI 호환 API에는 이 필드가 없어 오류 문구만 전달됩니다. 모델은 "없는 문서 번호입니다" 같은 오류를 읽고 인자를 고쳐 다시 요청할 수 있습니다. MCP 명세도 같은 이유로 인자 검사 실패 같은 실행 오류는 isError로 모델에 돌려주라고 권합니다.
  • 도구 함수 안의 검사: 인자의 값이 허용 범위인지, 사용자에게 권한이 있는지는 도구 함수가 실행 전에 검사합니다. 조회 도구는 읽기 전용 계정으로 연결합니다. 15장의 최소 권한(least privilege)입니다.

human-in-the-loop

human-in-the-loop은 에이전트가 정해 둔 행동을 실행하기 전에 사람이 승인하거나 거절하게 하는 설계입니다. 도구를 읽기 도구와 쓰기 도구로 나누는 기준은 바깥 상태를 바꾸는지입니다. 문서 검색과 조회는 잘못 불러도 결과를 버리면 되지만, 작업 요청 등록, 메일 발송, 결재는 실행하는 순간 다른 사람의 일정과 기록이 바뀝니다.

사람이 확인하는 지점은 세 가지이고, 되돌릴 수 있는지와 틀렸을 때의 피해를 기준으로 고릅니다.

  • 실행 전 승인: 쓰기 도구와 되돌릴 수 없는 도구는 코드가 실행을 멈추고 사람에게 묻습니다. 거절하면 "사람이 승인하지 않아 실행하지 않았다"는 도구 결과를 모델에 돌려줍니다.
  • 결과 확인: 에이전트의 답을 그대로 쓰지 않고, 사람이 확인한 뒤 보고서나 결정에 씁니다. 6장의 사람 확인과 같습니다.
  • 계획 승인: 일을 시작하기 전에 에이전트가 세운 계획을 사람이 확인합니다. 14장의 plan 모드가 이 방식입니다.

세 지점을 모두 두면 사람이 모든 일을 다시 해야 하고, 승인 요청이 너무 잦으면 사람이 읽지 않고 승인합니다.

에이전트를 쓸 일인가

여러 단계가 이어지고, 코드가 확실히 할 수 있는 조회나 계산이 섞여 있고, 결과를 검증할 방법이 있는 일에 에이전트를 씁니다. 검증할 방법이 없는 일은 초안까지만 맡기고, 단계가 하나뿐인 일은 더 단순한 방식으로 처리합니다.

다음과 같은 일은 도구를 붙여도 에이전트가 끝까지 처리하게 하지 않습니다.

  • 되돌릴 수 없는 일: 발송, 결재, 이체는 실행한 뒤에는 되돌릴 수 없으므로 사람이 승인합니다.
  • 검증할 방법이 없는 일: 맞았는지 대조할 원본이 없으면 틀려도 알 수 없습니다.
  • 틀리면 사람이 다치는 일: 안전, 의료, 법률 판단은 사람이 내립니다.

에이전트가 틀렸을 때 모델 탓으로 돌리면 무엇을 고칠지 찾을 수 없습니다. 실행 기록에서 틀린 단계를 찾고, 고치는 비용이 낮은 곳부터 고칩니다. 도구 정의의 설명, 시스템 프롬프트(코딩 에이전트라면 규칙 파일), 답을 검사하는 코드, 모델 등급, 사람이 확인하는 단계의 순서입니다. 하나를 고칠 때마다 같은 질문 묶음으로 다시 측정해 다른 질문이 새로 틀리지 않았는지 확인합니다(9장).

                    result, failed = f'오류: {error}', True
            messages.append(llm.tool_result(call, result, is_error=failed))
    return '(단계 상한에 닿아 멈췄습니다)', max_steps

RAG를 고릅니다. 한 번의 검색으로 답할 수 있으면 모델을 한 번만 부르는 RAG가 빠르고 싸며, 같은 질문에 검색 결과가 일정합니다. 에이전트는 질문의 낱말이 문서와 달라 검색어를 바꿔야 하는 질문, 첫 검색 결과를 읽고 다른 문서를 더 찾아야 하는 질문(두 문서를 이어야 답할 수 있는 질문)에 낫습니다.

5. 팀에서 만든 문서 검색 도구를 MCP 서버로 바꿔 Claude Code와 사내 채팅 도구에서 함께 쓰려고 합니다. 모델에 보내는 API 요청에서 바뀌는 것과 바뀌지 않는 것은 무엇입니까? 서버를 연결할 때 무엇을 확인합니까?

정답 보기

모델에 보내는 요청은 바뀌지 않습니다. 호스트가 tools/list로 받은 도구 목록을 도구 정의로 바꿔 요청에 넣고, 모델의 도구 호출을 tools/call로 서버에 보내 결과를 도구 결과로 돌려줍니다. 바뀌는 것은 도구 정의를 누가 알려 주고 도구를 누가 실행하는지입니다. 서버의 도구 설명과 도구 결과가 모델 입력에 들어가므로 회사가 확인한 서버만 연결하고, 서버에 주는 계정에는 필요한 권한만 줍니다.

6. 다음 세 가지 실패를 막으려면 각각 어떤 가드레일을 두겠습니까? (가) 문서에 답이 없는 질문에 검색어를 바꿔 가며 20번 검색했다. (나) 알람 원인만 찾아 달라고 했는데 메일 발송 도구를 불러 협력사에 메일을 보냈다. (다) 답에 읽지 않은 문서 번호를 근거로 적었다.

정답 보기

(가)는 단계 상한과 질문당 토큰 예산을 코드로 둡니다. 시스템 프롬프트에 "답이 없으면 찾지 못했다고 답하라"고 적는 것도 도움이 되지만 멈추는 것을 보장하지 않습니다. (나)는 메일 발송처럼 되돌릴 수 없는 도구를 실행 전에 사람이 승인하게 하고, 이 일에 필요 없는 도구는 아예 주지 않습니다(최소 권한). (다)는 답에 적힌 문서 번호를 실행 기록의 도구 결과와 대조해, 결과에 없던 번호가 있으면 사람이 확인할 대상으로 표시합니다.

7. "매주 월요일에 정해진 SQL로 지난주 알람 건수를 집계해 같은 양식의 표로 만든다"는 일에 에이전트를 쓰는 것이 맞습니까?

정답 보기

맞지 않습니다. 단계가 미리 정해져 있고 모델이 다음 행동을 정할 일이 없으므로, 정해진 SQL과 스크립트로 처리하는 것이 빠르고 싸며 결과도 일정합니다. 집계 결과를 읽고 원인을 찾아 다른 자료를 조회하는 것처럼 다음 단계가 결과에 따라 바뀌는 일이 더해질 때 에이전트를 고려합니다.

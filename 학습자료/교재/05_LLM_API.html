5장 LLM API

강의 2일차 파트 1에 해당합니다.

채팅 화면에서는 질문을 한 건씩 붙여 넣고 응답을 눈으로 읽습니다. 같은 일을 문의 1만 건에 하려면 프로그램이 LLM(large language model)에 요청을 보내고 응답을 받아야 합니다. 이 장은 요청과 응답에 무엇이 들어 있는지, 요금이 어떻게 계산되는지, 어떤 모델 등급을 고를지, 요청이 어떻게 실패하는지를 설명합니다.

학습 목표

  1. API(application programming interface) 요청에 넣는 값과 응답으로 돌아오는 값(응답 텍스트, 토큰 사용량, 종료 이유)을 설명하고, Anthropic SDK(software development kit)와 OpenAI SDK로 같은 요청을 보낼 수 있습니다.
  2. 요금이 입력 토큰과 출력 토큰으로 계산되고 thinking 토큰도 출력 토큰에 들어간다는 것을 설명하고, 대량 작업의 요금을 보내기 전에 어림할 수 있습니다.
  3. 같은 문의를 모델 등급별로 보내 정확도, 시간, 요금을 측정하고 그 결과로 등급을 고를 수 있습니다.
  4. 실패를 기다리면 풀리는 오류, 요청을 고쳐야 풀리는 오류, 예외 없이 끝난 실패로 나누고, 각각을 어떻게 처리할지 설명할 수 있습니다.
  5. effort와 프롬프트 캐싱이 각각 어떤 토큰을 줄여 요금을 낮추는지 설명할 수 있습니다.

예제 5-1~5-3은 API로 Claude 모델이나 사내 API의 모델을 호출합니다. 예제 5-1의 effort 비교는 Anthropic API에서만 실행됩니다. 모델의 응답, 토큰 수, 걸린 시간은 실행할 때마다 교재와 다를 수 있습니다.

요청과 응답

프로그램은 모델 이름, 최대 출력 토큰, 메시지 목록을 담은 요청을 보내고, 응답 텍스트, 토큰 사용량, 종료 이유를 담은 응답을 받습니다. 응답 텍스트만 읽지 않고 종료 이유를 먼저 확인합니다.

API(application programming interface)는 프로그램이 다른 프로그램의 기능을 정해진 형식으로 요청하고 결과를 받는 인터페이스입니다. LLM API에서 프로그램이 보내는 한 번의 요청(request)에는 어느 모델에 보낼지, 출력을 최대 몇 토큰까지 허용할지, 무엇을 물을지가 들어 있습니다. 서버는 모델이 생성한 글과 그 과정의 기록을 응답(response)으로 돌려줍니다. 요청과 응답은 HTTP로 주고받지만, 이를 직접 조립하지 않고 SDK(software development kit)를 씁니다. SDK는 요청을 조립하고, 응답을 파이썬 객체로 바꾸고, 실패를 파이썬 예외로 바꿔 주는 라이브러리입니다. 이 교재는 두 가지 API로 실행합니다. Anthropic API는 Claude 모델을 제공하는 Anthropic의 API이고, OpenAI 호환 API는 OpenAI의 Chat Completions 요청 형식을 그대로 따르는 API입니다. 사내 API가 이 형식을 따르므로 OpenAI SDK(openai 패키지)에 사내 주소를 넣어 씁니다.

Anthropic API에서 요청에 꼭 넣는 값은 세 가지입니다. model은 모델 이름, max_tokens는 최대 출력 토큰, messages는 대화의 메시지 목록입니다. OpenAI 호환 API는 max_tokens를 넣지 않아도 되지만, 이 교재는 두 API 모두 넣습니다. 시스템 프롬프트(3장)는 Anthropic API에서는 system 파라미터로, OpenAI 호환 API에서는 messages 맨 앞의 system 메시지로 보냅니다.

응답에서는 세 가지를 읽습니다. 응답 텍스트는 Anthropic API에서는 content 목록의 text 블록에 있고(그 앞에 thinking 블록이 올 수 있습니다, 2장), OpenAI 호환 API에서는 choices[0].message.content에 있습니다. usage는 이 요청에 쓴 토큰 수이고, 요금은 이 값으로 계산합니다. 종료 이유(stop reason)는 모델이 생성을 멈춘 이유입니다. 종료 이유가 정상 종료가 아니면 응답 텍스트가 있어도 그대로 쓰지 않습니다. 조건은 "정상 종료일 때만 쓴다"로 작성합니다. "잘림이면 버린다"로 작성하면 새로 생긴 종료 이유가 왔을 때 잘못된 응답을 저장합니다.

뜻 Anthropic stop_reason OpenAI 호환 finish_reason llm.py의 Reply.stop_reason
정상 종료 end_turn stop end
최대 출력 토큰이나 컨텍스트 윈도우에 닿아 잘림 max_tokens, model_context_window_exceeded length max_tokens
안전 기준에 따른 거절 refusal content_filter refusal
그 밖의 종료 이유 위에 없는 값 위에 없는 값 other

이 교재의 예제는 공통 호출 함수 llm.py로 요청을 보냅니다. llm.send()는 요청을 한 번 보내고, llm.ask()는 여기에 재시도("실패 유형" 절)를 더합니다. 두 함수 모두 어느 SDK를 쓰든 같은 Reply(응답 텍스트 text, input_tokens, output_tokens, stop_reason, 답한 모델 이름 model, seconds)를 돌려줍니다. 두 SDK를 직접 부르는 코드는 예제 5-1에서 한 번만 나란히 보여 줍니다.

토큰과 요금

요금은 입력 토큰 수와 출력 토큰 수에 각각의 단가를 곱해 더한 값이고, 출력 단가가 입력의 5배입니다. thinking 토큰은 응답에 보이지 않아도 출력 토큰으로 계산되므로, 요금을 어림할 때 출력을 응답 텍스트 길이만으로 잡으면 적게 나옵니다.

LLM API의 요금은 토큰 수로 계산합니다. 단가(price)는 토큰 100만 개당 요금이고, 입력 토큰과 출력 토큰의 단가가 다릅니다. Anthropic API의 현행 모델은 세 등급 모두 출력 단가가 입력 단가의 5배입니다(아래 표, 2026-11 확인). 제공사가 단가를 정한 이유를 밝히지는 않지만, 생성 방식의 차이가 있습니다. 입력은 모든 토큰을 한 번에 계산하지만, 출력은 토큰 하나를 생성할 때마다 계산을 한 번씩 하고 그 토큰을 입력에 붙여 다시 계산합니다(1장).

교재의 등급 llm.py가 쓰는 Anthropic 모델 입력 단가 출력 단가 캐시 읽기 단가
소형 Claude Haiku 5.5 0.10달러 0.50달러 0.01달러
기본 Claude Sonnet 5.5 2달러 10달러 0.10달러
대형 Claude Opus 5.5 4달러 20달러 0.20달러

Haiku 5.5의 단가는 프롬프트가 10만 토큰 이하일 때의 값이고, 넘으면 입력 0.50달러, 출력 2.50달러입니다. 캐시 읽기 단가는 "프롬프트 캐싱" 절에서 설명합니다. 사내 API의 단가는 사내 안내를 따릅니다. 노트북 준비 셀의 PRICES에 이 표의 단가와 캐시 쓰기 단가(입력 단가의 1.25배)가 들어 있고, cost(reply, tier)가 응답 하나의 요금을 계산합니다.

출력 토큰에는 응답 텍스트뿐 아니라 thinking 토큰도 들어갑니다(2장). 현행 Claude 모델은 thinking 내용을 기본으로 보여 주지 않지만, 생성한 thinking 토큰은 모두 출력 토큰으로 요금이 붙습니다. 그래서 짧게 답한 응답도 출력 토큰이 수백 개일 수 있습니다.

thinking에 쓴 토큰 수는 응답에서 따로 확인할 수 있습니다. Anthropic API는 usage.output_tokens_details.thinking_tokens에 출력 토큰 가운데 thinking에 쓴 수를 적어 줍니다. 이 값은 요약해서 돌려준 thinking 글이 아니라 모델이 실제로 생성한 thinking 토큰의 수이고, output_tokens에 이미 포함되어 있습니다(2026-11 확인). OpenAI 호환 API는 usage.completion_tokens_details.reasoning_tokens라는 같은 뜻의 필드가 있지만, 서버가 이 값을 채우지 않으면 비어 있습니다.

보내기 전에 토큰 세기

요금을 미리 어림하려면 입력 토큰 수를 알아야 합니다. Claude의 토크나이저는 공개되어 있지 않으므로, Anthropic API가 제공하는 토큰 세기(token counting) 기능으로 셉니다. 요청과 같은 모델, 시스템 프롬프트, 메시지를 보내면 생성 없이 입력 토큰 수만 돌려줍니다. 요금은 들지 않고, 분당 요청 수의 상한만 따로 있습니다. 돌려주는 값은 추정값이라 실제 요청의 입력 토큰과 조금 다를 수 있습니다(2026-11 확인). llm.count_tokens()가 이 기능을 부르고, OpenAI 호환 API에는 표준 기능이 없어 None을 돌려줍니다. 그때는 몇 건을 실제로 보내 Reply.input_tokens로 어림합니다.

출력 토큰은 보내기 전에 셀 수 없습니다. 몇 건을 실제로 보내 출력 토큰의 평균을 측정하고, 그 값으로 전체를 어림합니다. 이때 출력에 thinking 토큰이 들어 있다는 점을 빼놓지 않습니다.

출력 토큰의 양을 정하는 effort

effort는 모델이 응답 하나에 토큰을 얼마나 쓸지 정하는 Anthropic API의 설정입니다. 낮추면 thinking과 응답 텍스트 모두 짧아져 출력 토큰과 시간이 줄고, 어려운 문제에서는 정확도도 함께 낮아질 수 있습니다.

effort는 output_config의 effort 값으로, low, medium, high, xhigh, max 가운데 하나를 넣습니다. 값을 넣지 않으면 모델마다 정해진 기본값을 씁니다. Claude Haiku 5.5와 Claude Opus 5.5는 medium, Claude Sonnet 5.5는 high가 기본값입니다(2026-11 확인). effort는 thinking뿐 아니라 응답 텍스트와 도구 호출을 포함한 모든 출력 토큰에 작용합니다.

effort는 정해진 토큰 수의 상한이 아닙니다. 낮은 effort에서도 어려운 문제에는 thinking을 하고, 같은 문제에서 높은 effort일 때보다 적게 할 뿐입니다. 최대 출력 토큰은 thinking과 응답 텍스트를 합친 길이를 자르는 상한이므로, effort를 높일 때는 max_tokens도 넉넉하게 둡니다. 분류처럼 답이 정해진 일은 낮은 effort부터 시험하고, 정확도가 떨어지는지 표본으로 확인한 뒤 정합니다.

OpenAI API에는 비슷한 파라미터 reasoning_effort가 있지만, OpenAI 호환 서버가 이 값을 지원하는지는 서버와 모델마다 다르고, llm.py의 함수도 effort를 받지 않습니다. 아래 예제는 Anthropic SDK를 직접 불러 effort를 바꿔 봅니다.

예제 5-1SDK로 직접 보내기노트북 05_LLM_API.ipynb의 예제 5-1

같은 계산 문제를 SDK로 직접 보내고, 응답의 블록 종류, 종료 이유, 입력 토큰, 출력 토큰과 그중 thinking 토큰을 봅니다. Anthropic 쪽은 effort를 low와 high로 바꿔 두 번 보내고 출력 토큰이 어떻게 다른지 봅니다. 두 코드 가운데 지금 쓰는 API에 해당하는 쪽만 실행되고, 이 셀은 API를 2번(OpenAI 호환은 1번) 호출합니다.

question = 'UPH 1,200인 와이어 본더 3대가 하루 22시간, 가동률 87%로 돌면 하루 생산량은 몇 개입니까? 숫자만 답하세요.'
if llm.provider() == 'anthropic':
    import anthropic
    client = anthropic.Anthropic()                    # 환경 변수 ANTHROPIC_API_KEY를 읽습니다
    for effort in ['low', 'high']:
        response = client.messages.create(
            model=llm.model_name('소형'), max_tokens=4000,   # max_tokens에는 thinking 토큰도 들어갑니다
            system='너는 후공정 라인의 생산 계산을 돕는 도우미다.',
            messages=[{'role': 'user', 'content': question}],
            output_config={'effort': effort})        # Anthropic API에만 있는 설정입니다
        usage, text = response.usage, ''.join(block.text for block in response.content if block.type == 'text')
        thinking = usage.output_tokens_details.thinking_tokens if usage.output_tokens_details else '알 수 없음'
        print(f'effort={effort}: 블록 {[block.type for block in response.content]}, 종료 이유 {response.stop_reason}')
        print(f'  입력 {usage.input_tokens}토큰, 출력 {usage.output_tokens}토큰(그중 thinking {thinking}) → {text.strip()}')
else:
    print('Anthropic을 쓰지 않으므로 건너뜁니다.')

effort=low: 블록 ['thinking', 'text'], 종료 이유 end_turn
  입력 103토큰, 출력 66토큰(그중 thinking 62) → 68904
effort=high: 블록 ['thinking', 'text'], 종료 이유 end_turn
  입력 103토큰, 출력 85토큰(그중 thinking 81) → 68904

question = 'UPH 1,200인 와이어 본더 3대가 하루 22시간, 가동률 87%로 돌면 하루 생산량은 몇 개입니까? 숫자만 답하세요.'
if llm.provider() == 'openai':
    from openai import OpenAI
    client = OpenAI(base_url=os.environ['OPENAI_BASE_URL'], api_key=os.environ['OPENAI_API_KEY'])
    response = client.chat.completions.create(
        model=llm.model_name('소형'), max_tokens=4000,
        messages=[{'role': 'system', 'content': '너는 후공정 라인의 생산 계산을 돕는 도우미다.'},
                  {'role': 'user', 'content': question}])      # 시스템 프롬프트는 맨 앞의 system 메시지입니다
    choice, usage = response.choices[0], response.usage
    details = usage.completion_tokens_details
    thinking = details.reasoning_tokens if details and details.reasoning_tokens is not None else '알 수 없음'
    print(f'종료 이유 {choice.finish_reason}, 입력 {usage.prompt_tokens}토큰, '
          f'출력 {usage.completion_tokens}토큰(그중 thinking {thinking}) → {choice.message.content.strip()}')
else:
    print('OpenAI 호환 API를 쓰지 않으므로 건너뜁니다.')

교재의 실행에서 effort가 low일 때 출력 66토큰 가운데 thinking이 62토큰, high일 때 85토큰 가운데 81토큰이었고, 두 번 모두 답은 68,904로 맞았습니다. 응답 텍스트는 숫자 하나뿐이어서 출력 토큰의 대부분이 응답에 보이지 않는 thinking이었습니다. 이 정도의 계산에서는 effort를 낮춰도 답이 같았고 출력 토큰은 줄었습니다. 줄어드는 폭은 실행마다 다릅니다. 두 SDK 코드의 차이는 시스템 프롬프트를 넣는 곳과, 응답 텍스트, 토큰 수, 종료 이유를 읽는 이름입니다.

모델 등급 고르기

등급이 높은 모델은 단가가 높습니다. thinking의 길이와 응답 시간은 등급 순서를 따르지 않을 수 있으므로, 등급은 정답 라벨이 있는 표본으로 정확도, 시간, 요금을 측정해, 필요한 정확도를 내는 가장 낮은 등급으로 고릅니다.

같은 제공사의 모델은 능력과 가격에 따라 여러 등급으로 나뉩니다. 이 교재는 이를 모델 등급(model tier)이라 하고 소형, 기본, 대형으로 부릅니다. 응답 전체에 걸리는 시간은 출력 토큰 수에도 달려 있어, 높은 등급이 늘 느리지는 않습니다(예제 5-2). 그 대신 판단이 까다로운 입력에서 더 정확할 수 있습니다.

어느 등급이 충분한지는 일마다 다르고, 모델 설명만 읽어서는 알 수 없습니다. 정답 라벨이 있는 표본을 등급마다 보내 정확도, 시간, 요금을 나란히 놓고 봅니다. 쉬운 입력만 고르면 등급 사이의 차이가 드러나지 않으므로, 표본에는 판단이 어려운 입력을 넣습니다. 등급을 올려도 정확도가 그대로라면 남은 오류는 모델의 능력보다 분류 기준이 모호한 데서 오는 경우가 많으므로, 기준을 먼저 고칩니다(4장 "프롬프트 설계").

예제 5-2등급별 정확도, 시간, 요금노트북 05_LLM_API.ipynb의 예제 5-2

4장의 문의 데이터에서 두 라벨에 걸쳐 판단하기 어려운 문의 15건(Q41~Q55)을 한 요청에 담아 소형, 기본, 대형 모델에 보냅니다. 준비 셀의 numbered(), parse_labels(), accuracy()는 4장과 같습니다. 보내기 전에 센 입력 토큰과 실제 입력 토큰, 정확도, 출력 토큰, 걸린 시간, 요금을 비교합니다. 이 셀은 API를 3번 호출하고, 토큰 세기를 3번 부릅니다(요금 없음).

hard = inquiries[40:55]                                # Q41~Q55, 두 라벨에 걸쳐 헷갈리는 문의
system = ('문의를 다음 판정 기준을 위에서부터 차례로 적용해 하나의 라벨로 분류한다. '
          '1. 사람이 다치거나 다칠 위험이 있으면 안전 2. 원하는 것이 문서나 기록의 전달이면 문서와 데이터 요청 '
          '3. 원인 설비가 특정되고 조치 대상이 설비이면 설비 이상 4. 제품 결과에 이상이 있고 원인 설비가 특정되지 않으면 품질. '
          '답은 "번호: 라벨" 형식으로 한 줄에 한 건씩만 쓴다.')
messages = [{'role': 'user', 'content': numbered(hard)}]
for tier in ['소형', '기본', '대형']:
    counted = llm.count_tokens(messages, system=system, model=tier)       # 보내기 전에 셉니다. OpenAI 호환이면 None
    reply = llm.send(messages, system=system, model=tier, max_tokens=16000, timeout=300)  # thinking이 길 수 있어 출력과 대기 시간(초)을 넉넉히 둡니다
    print(f'{tier}: 정확도 {accuracy(parse_labels(reply.text), hard):.0%}, 입력 {counted}→{reply.input_tokens}토큰, '
          f'출력 {reply.output_tokens:,}토큰, {reply.seconds:.1f}초, {cost(reply, tier):.4f}달러')

소형: 정확도 100%, 입력 914→914토큰, 출력 1,521토큰, 7.0초, 0.0009달러
기본: 정확도 93%, 입력 914→914토큰, 출력 1,013토큰, 8.2초, 0.0120달러
대형: 정확도 100%, 입력 914→914토큰, 출력 884토큰, 8.3초, 0.0213달러

교재의 실행에서 정확도는 소형과 대형이 15건 모두, 기본이 14건(93%)이었습니다. 등급이 높다고 더 맞히지는 않았습니다. 요금은 대형이 0.0213달러로 소형(0.0009달러)의 약 24배였고, 시간은 소형 7.0초, 기본 8.2초, 대형 8.3초였습니다. 응답은 15줄인데 출력은 884~1,521토큰으로 대부분이 thinking이었고, thinking이 가장 긴 것은 소형이었습니다. 토큰 세기로 미리 센 입력 914토큰은 실제 입력 토큰과 같았습니다. 판정 기준을 프롬프트에 적어 준 이 일에서는 소형으로 충분했습니다. 15건은 작은 표본이므로, 실제로 등급을 정할 때는 표본을 늘리고 여러 번 실행해 정확도의 변동도 확인합니다.

실패 유형

API 요청의 실패는 세 가지입니다. 기다렸다 다시 보내면 풀리는 오류는 재시도하고, 요청을 고쳐야 풀리는 오류는 바로 멈추고, 예외 없이 끝났지만 쓸 수 없는 응답은 응답 검사로 찾아냅니다.

서버는 요청이 실패하면 상태 코드(status code)로 이유를 알립니다. 4xx는 요청 쪽의 문제, 5xx는 서버 쪽의 문제입니다. 다만 429(레이트 리밋)는 4xx이지만 기다리면 풀립니다. SDK는 이 상태 코드를 예외로 바꿔 발생시키고, llm.py는 다시 llm.CallError 하나로 바꿉니다. CallError의 kind는 오류의 종류이고, retryable은 기다렸다 다시 보내면 풀릴 수 있는 오류인지를 알려 줍니다.

기다리면 풀리는 오류

레이트 리밋(rate limit)은 일정 시간에 보낼 수 있는 요청 수와 토큰 수의 상한입니다. Anthropic API는 모델마다 분당 요청 수, 분당 입력 토큰 수, 분당 출력 토큰 수의 상한을 두고, 어느 하나라도 넘으면 429 오류가 납니다. 남은 허용량은 정해진 시각에 한꺼번에 초기화되지 않고 시간이 지나는 만큼 조금씩 다시 채워지므로(token bucket 방식), 잠시 기다리면 다시 보낼 수 있습니다. 응답에 retry-after 헤더가 있으면 그 초만큼 기다립니다. 같은 429라도 월 사용 한도에 닿은 경우에는 다음 달까지 풀리지 않고 retry-after 헤더도 없습니다(2026-11 확인).

타임아웃(timeout)은 응답 대기 시간의 상한입니다. 상한 안에 응답이 오지 않으면 SDK가 요청을 포기하고 예외를 발생시킵니다. 출력이 길거나 thinking이 길면 응답이 늦으므로, 타임아웃은 측정한 응답 시간보다 넉넉하게 둡니다. 타임아웃으로 포기한 요청도 서버에서는 이미 처리되어 요금이 붙었을 수 있습니다.

이런 오류는 같은 요청을 다시 보내는 재시도(retry)로 풀립니다. 재시도할 때는 대기 시간을 1초, 2초, 4초처럼 늘려 가는 백오프(backoff)를 씁니다. 레이트 리밋에 걸린 요청 여러 개를 같은 간격으로 재시도하면 재시도 시각이 다시 겹치므로, 대기 시간에 작은 무작위 값인 지터(jitter)를 더합니다.

SDK에도 자동 재시도가 있습니다. Anthropic SDK는 연결 실패, 타임아웃, 408, 409, 429, 500 이상을 기본 2번 재시도하고, 기본 타임아웃은 10분입니다(2026-11 확인). SDK의 재시도와 직접 작성한 재시도를 함께 쓰면 전체 시도 횟수는 두 횟수의 곱이 됩니다. SDK가 3번, 직접 작성한 재시도가 3번이면 최대 9번 보냅니다. 그래서 llm.py는 SDK의 재시도를 끄고(max_retries=0) llm.ask() 한 곳에서만 재시도합니다.

요청을 고쳐야 풀리는 오류

400(요청 형식이 잘못됨), 401(키가 틀림), 403(권한 없음), 404(없는 모델이나 주소)는 같은 요청을 몇 번 다시 보내도 똑같이 실패합니다. 재시도하면 시간만 쓰므로, 바로 멈추고 요청이나 설정을 고칩니다. 400은 입력이 컨텍스트 윈도우를 넘을 때(3장)도 납니다.

예외 없이 끝난 실패

예외 없이 응답을 받았어도 쓸 수 없는 응답이 있습니다. 종료 이유가 max_tokens이면 응답이 중간에 끊겼고, refusal이면 모델이 답하지 않았습니다. 정상 종료했더라도 요구한 형식이 아니거나 응답 텍스트가 비어 있을 수 있습니다. 이처럼 오류나 예외 없이 끝났지만 결과를 쓸 수 없는 실패를 조용한 실패(silent failure)라고 합니다. 이런 실패는 try와 except로 잡히지 않으므로, 받은 응답을 코드로 확인하는 응답 검사(response validation)로 찾아냅니다.

예제 5-3세 가지 실패노트북 05_LLM_API.ipynb의 예제 5-3

없는 모델 이름, 0.5초 타임아웃, 20토큰의 최대 출력 토큰으로 같은 요청을 보냅니다. 없는 모델 이름과 타임아웃 요청이 실패할 때 어떤 예외가 발생하는지, 셋째 요청은 예외 없이 무엇을 돌려주는지 봅니다. 이 셀은 API를 최대 3번 호출합니다. 재시도가 섞이지 않도록 llm.send()로 한 번씩만 보냅니다.

messages = [{'role': 'user', 'content': '와이어 본딩 공정을 세 문장으로 설명해 주세요.'}]
cases = {'없는 모델 이름': dict(model='claude-no-such-model'),
         '타임아웃 0.5초': dict(model='소형', timeout=0.5),        # 0.5초 안에 응답이 오지 않으면 포기합니다
         '최대 출력 토큰 20': dict(model='소형', max_tokens=20)}    # thinking 토큰도 이 20토큰 안에 들어갑니다
for name, options in cases.items():
    try:
        reply = llm.send(messages, **options)
        print(f'{name}: 예외 없음, 종료 이유 {reply.stop_reason}, 출력 {reply.output_tokens}토큰, 응답 텍스트 {reply.text!r}')
    except llm.CallError as error:
        print(f'{name}: 예외 {error.kind}, 상태 코드 {error.status}, 재시도할 오류인지 {error.retryable}')

없는 모델 이름: 예외 not_found, 상태 코드 404, 재시도할 오류인지 False
타임아웃 0.5초: 예외 timeout, 상태 코드 None, 재시도할 오류인지 True
최대 출력 토큰 20: 예외 없음, 종료 이유 max_tokens, 출력 20토큰, 응답 텍스트 '와이어 본딩은 반도체 칩의 본딩'

없는 모델 이름은 404로 실패했고 재시도할 오류가 아니었습니다. 0.5초 타임아웃은 서버 응답을 받기 전에 포기했으므로 상태 코드 없이 timeout이 되었고, 재시도할 오류였습니다. 최대 출력 토큰 20은 예외 없이 끝났지만 종료 이유가 max_tokens이고, 응답 텍스트는 문장 중간에서 끊겼습니다. 이 응답은 try와 except로는 찾을 수 없고, 종료 이유를 확인해야 찾을 수 있습니다.

이 세 가지 처리를 문의 여러 건에 적용하면 배치 처리(batch processing) 코드가 됩니다. 재시도를 끝까지 실패한 건과 응답 검사에 걸린 건은 버리지 않고, 식별자와 사유를 실패 목록(failure list)에 남겨 사람이 다시 처리하게 합니다. 실습 P1에서는 재시도를 끝까지 실패한 건을 "실패", 응답 검사에 걸린 건을 "확인 필요"로 표시하고 둘 다 목록에 남깁니다. 이 구현은 관통 프로젝트 1단계(실습 P1)에서 작성합니다.

프롬프트 캐싱

요청마다 같은 앞부분(시스템 프롬프트, 긴 문서, 대화 이력)을 보내면, 프롬프트 캐싱으로 그 앞부분을 서버에 저장해 두고 다음 요청에서 입력 단가의 0.1배 이하로 다시 읽을 수 있습니다. 앞부분이 한 글자라도 다르면 캐시를 읽지 못합니다.

3장의 대화 이력, 4장의 긴 시스템 프롬프트와 few-shot 예시처럼 요청마다 같은 앞부분을 다시 보내는 경우가 많습니다. 모델은 요청마다 입력 전체를 처음부터 계산하므로, 같은 앞부분이라도 매번 입력 단가를 냅니다. 프롬프트 캐싱(prompt caching)은 서버가 앞부분의 계산 결과를 저장해 두었다가, 다음 요청의 앞부분이 똑같으면 그 결과를 다시 읽는 기능입니다. 다시 계산하지 않으므로 단가가 낮고 응답도 빨라집니다.

캐시는 요청의 맨 앞부터 같은 부분까지만 적용됩니다. 그래서 바뀌지 않는 내용(시스템 프롬프트, 고정된 문서)을 앞에 두고, 요청마다 바뀌는 내용(질문, 현재 시각)을 뒤에 둡니다. 시스템 프롬프트 맨 앞에 현재 시각을 넣으면 요청마다 앞부분이 달라져 캐시를 한 번도 읽지 못합니다.

Anthropic API의 수치는 다음과 같습니다(2026-11 확인).

  • 요청에 cache_control을 넣어야 캐싱합니다. 캐시를 처음 쓸 때는 입력 단가의 1.25배를 내고, 캐시를 읽을 때는 0.1배(Sonnet 5.5와 Opus 5.5는 0.05배)를 냅니다. 그래서 같은 앞부분을 두 번만 보내도 캐싱하지 않을 때보다 저렴합니다.
  • 캐시는 기본으로 5분 동안 유지되고, 읽을 때마다 5분이 다시 시작됩니다. 1시간 동안 유지하는 설정은 캐시 쓰기 단가가 입력 단가의 2배입니다.
  • 앞부분이 512토큰(현행 모델 기준)보다 짧으면 표시를 해도 캐싱하지 않습니다.
  • 응답의 usage.cache_creation_input_tokens는 캐시에 쓴 토큰 수, usage.cache_read_input_tokens는 캐시에서 읽은 토큰 수입니다. 이 둘은 input_tokens와 따로 집계됩니다.

llm.py는 캐싱을 요청하지 않으므로 이 교재의 예제에서는 캐시를 쓰지 않습니다. OpenAI 호환 서버의 캐싱 지원과 단가는 서버마다 다르므로 사내 안내를 확인합니다.

실습은 장 노트북의 빈칸을 채워 실행합니다. 코드를 실행하기 전에 결과를 먼저 예측해 적고, 실행한 뒤 예측과 다른 부분을 이 장의 원리로 설명해 봅니다.

실습 5-1한 달 요금 어림하기노트북 05_LLM_API.ipynb의 실습 5-1

def monthly_cost(tier, requests=10_000, system_tokens=800, inquiry_tokens=60, output_tokens=40, cached=False):
    """한 달 요금(달러). PRICES의 단가를 씁니다. cached=True면 시스템 프롬프트를 캐싱합니다"""
    price = PRICES[tier]
    if cached:
        system_cost = system_tokens * (price['cache_write'] + (requests - 1) * price['cache_read'])
    else:
        system_cost = requests * system_tokens * price['input']
    rest = requests * (inquiry_tokens * price['input'] + output_tokens * price['output'])
    return (system_cost + rest) / 1_000_000

def answer(question, tier='소형', tries=3, send=llm.send, sleep=time.sleep):
    """질문 하나에 답합니다. 돌려주는 dict의 키: question, status('완료', '확인 필요', '실패'),
    answer, input_tokens, output_tokens, cost, reason"""
    result = {'question': question, 'status': '실패', 'answer': '', 'input_tokens': 0,
              'output_tokens': 0, 'cost': 0.0, 'reason': ''}
    for attempt in range(tries):
        try:
            reply = send([{'role': 'user', 'content': question}], system=SYSTEM, model=tier, max_tokens=2000)
        except llm.CallError as error:
            result['reason'] = str(error)
            if not error.retryable:
                return result                         # 요청을 고쳐야 풀리는 오류는 다시 보내지 않습니다
            if attempt < tries - 1:
                sleep(2 ** attempt + random.random())  # 1초, 2초 … 백오프에 지터를 더합니다
            continue
        result.update(answer=reply.text, input_tokens=reply.input_tokens, output_tokens=reply.output_tokens,
                      cost=cost(reply, tier), reason=reply.stop_reason,
                      status='완료' if reply.stop_reason == 'end' else '확인 필요')
        return result
    return result

SDK는 요청 하나를 처음 1번과 재시도 2번으로 최대 3번 보내고, 직접 작성한 재시도가 이것을 3번 부르므로 최대 9번입니다. 대기 시간도 함께 늘어납니다. 재시도 횟수는 한 곳에서만 정하도록 SDK의 재시도를 끕니다(max_retries=0).

6. 요청마다 같은 3,000토큰짜리 시스템 프롬프트를 보내고 있습니다. effort를 낮추는 것과 프롬프트 캐싱을 쓰는 것은 각각 어떤 토큰의 요금을 줄입니까? 캐싱이 효과를 내려면 시스템 프롬프트를 어떻게 작성해야 합니까?

정답 보기

effort는 출력 토큰(thinking과 응답 텍스트)을 줄이고, 프롬프트 캐싱은 반복해서 보내는 입력 토큰의 단가를 낮춥니다. 캐싱은 요청의 앞부분이 똑같을 때만 적용되므로, 시스템 프롬프트에 요청마다 바뀌는 내용(현재 시각, 질문)을 넣지 않고 바뀌는 내용은 뒤에 둡니다.

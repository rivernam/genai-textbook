3장 컨텍스트

강의 1일차 파트 1과 파트 2, 2일차 파트 1, 6일차 파트 1에 해당합니다.

모델은 요청 하나를 받을 때마다 그 안에 든 글만 보고 응답합니다. 이 장은 그 "요청 하나에 든 글", 곧 컨텍스트가 무엇으로 채워지고 어디까지 들어가는지를 설명합니다. 대화가 이어지는 것처럼 보이는 이유, 대화가 길어질수록 비용이 늘어나는 이유도 이 장에서 설명합니다.

학습 목표

  1. 컨텍스트 윈도우가 무엇으로 채워지는지(시스템 프롬프트, 대화 이력, 넣은 문서, 질문, 출력) 설명하고, 상한을 넘으면 어떤 일이 생기는지 설명할 수 있습니다.
  2. 시스템 프롬프트와 역할(system, user, assistant)이 채팅 템플릿을 거쳐 하나의 토큰 열이 되는 과정을 설명할 수 있습니다.
  3. 모델이 대화를 기억하지 않는다(무상태)는 것과, 대화를 이어 가려면 이력 전체를 매번 다시 보내야 해서 입력 토큰이 쌓인다는 것을 계산으로 보일 수 있습니다.
  4. 긴 문서를 한 번에 넣을 때와 나눠 넣을 때 각각 무엇을 얻고 잃는지 설명할 수 있습니다.

예제 3-1과 실습 3-1은 1장의 토크나이저만 PC에서 씁니다. 예제 3-2와 3-3은 API(application programming interface)로 서비스 모델을 호출합니다. 모델의 응답, 토큰 수, 걸린 시간은 실행할 때마다 교재와 다를 수 있습니다.

컨텍스트 윈도우

모델이 요청 하나에서 다룰 수 있는 토큰 수에는 상한이 있고, 입력과 출력이 이 상한을 나눠 씁니다. 입력에는 이번 질문뿐 아니라 시스템 프롬프트, 대화 이력, 넣은 문서가 모두 들어갑니다.

컨텍스트 윈도우(context window)는 모델이 요청 한 번에 다룰 수 있는 토큰 수의 상한입니다. 모델은 다음 토큰을 정할 때마다 입력과 지금까지 생성한 토큰 전체를 다시 보므로(1장), 상한은 입력과 출력을 합친 길이에 걸립니다.

현행 Claude 모델의 컨텍스트 윈도우는 100만 토큰이고, 1장과 2장에서 PC로 실행한 Qwen2.5-0.5B-Instruct는 32,768토큰입니다. 입력만으로 윈도우를 넘으면 API가 요청을 오류(400, prompt is too long)로 거절합니다. 생성 중에 윈도우가 차면 응답이 끊기고, Claude 4.5 이후 모델은 종료 이유 model_context_window_exceeded를 돌려줍니다(llm.py는 max_tokens로 바꿔 줍니다). 채팅 서비스는 대화가 아주 길어지면 앞부분을 빼고 보내기도 하므로, 긴 대화의 앞부분은 응답에 반영되지 않을 수 있습니다(2026-11 확인).

역할과 채팅 템플릿

요청에 담은 시스템 프롬프트와 메시지들은 모델에 따로따로 전달되지 않습니다. 채팅 템플릿이 역할 표시 토큰으로 감싸 글 한 덩어리로 이어 붙이고, 모델은 그 끝에 이어질 토큰을 생성할 뿐입니다.

API로 요청할 때는 메시지(message)의 목록을 보냅니다. 메시지마다 누가 말했는지를 나타내는 역할(role)이 붙습니다. user는 사용자, assistant는 모델이고, system은 대화 전체에 적용할 지시로 이 글을 시스템 프롬프트(system prompt)라고 합니다. OpenAI 호환 API는 system 역할의 메시지로, Anthropic API는 system 파라미터로 받습니다. 무엇을 적을지는 4장 "프롬프트 설계"에서 다룹니다.

그런데 1장에서 본 모델의 입력은 토큰 ID의 나열 하나뿐입니다. 메시지 목록은 채팅 템플릿(chat template)이라는 규칙을 거쳐 글 한 덩어리가 됩니다. 채팅 템플릿은 메시지마다 역할을 나타내는 표시 토큰을 앞뒤에 붙이고, 마지막에 모델의 답 차례를 여는 표시를 붙입니다. 2장의 SFT(supervised fine-tuning)에서 모델은 바로 이 형식의 글로 학습했으므로, 답 차례가 열리면 답을 이어 씁니다.

예제 3-1채팅 템플릿 보기노트북 03_컨텍스트.ipynb의 예제 3-1

시스템 프롬프트, 질문, 이전 답, 새 질문으로 된 메시지 네 개를 1장의 토크나이저로 채팅 템플릿에 넣고, 만들어진 글과 그 토큰 수를 봅니다. 역할 이름 앞뒤에 어떤 표시 토큰이 붙는지, 마지막 줄이 무엇인지 봅니다.

시스템 프롬프트도 별도 입력이 아니라 이 글의 맨 앞부분입니다. 모델이 시스템 프롬프트를 잘 따르는 것은 SFT와 RLHF(reinforcement learning from human feedback)에서 system 표시 토큰 안의 지시를 따르도록 학습했기 때문입니다. 표시 토큰의 형태는 모델마다 다르고, 서비스 모델의 템플릿은 공개되지 않은 경우가 많습니다. 그래도 API에 보낸 메시지가 한 덩어리의 글로 바뀌어 모델에 들어간다는 점은 같습니다.

모델은 대화를 기억하지 않는다

모델과 이 교재가 쓰는 API(Anthropic Messages, OpenAI 호환 Chat Completions)는 이전 요청을 기억하지 않습니다. 대화를 이어 가려면 앞의 질문과 답을 매번 다시 보내야 하므로, 대화가 길어질수록 요청 하나의 입력 토큰과 전체 비용이 함께 늘어납니다.

모델은 요청에 든 글만 보고 응답하며, 요청이 끝나면 그 내용을 다음 요청으로 이어 주지 않습니다. 이처럼 이전 요청을 기억하지 않는 성질을 무상태(stateless)라고 합니다. 채팅 화면에서 대화가 이어지는 것처럼 보이는 것은, 화면 쪽 프로그램이 지금까지 주고받은 메시지인 대화 이력(conversation history)을 요청마다 함께 보내기 때문입니다. API를 직접 쓸 때는 이 일을 우리 코드가 합니다.

예제 3-2기억하지 않는 모델노트북 03_컨텍스트.ipynb의 예제 3-2

이름을 알려 준 뒤, 이력 없이 새 요청으로 이름을 물어봅니다. 이어서 이력을 함께 보내며 두 번 묻고, 요청마다 입력 토큰이 어떻게 늘어나는지 봅니다. llm.ask()는 공통 호출 함수 llm.py의 함수로, history에 이력을 주면 이력 뒤에 질문을 붙여 보냅니다(5장 "LLM API"). 이 셀은 API를 4번 호출합니다.

intro = '제 이름은 김후공입니다. 기억해 주세요.'
first = llm.ask(intro, model='소형', max_tokens=500)
alone = llm.ask('제 이름이 뭐였죠?', model='소형', max_tokens=500)   # 이력 없이 새 요청
print(f'[이력 없이] 입력 토큰 {alone.input_tokens}개: {alone.text.strip()}\n')

history = [{'role': 'user', 'content': intro}, {'role': 'assistant', 'content': first.text}]
for question in ['제 이름이 뭐였죠?', '제가 처음에 한 말을 그대로 적어 주세요.']:
    reply = llm.ask(question, history=history, model='소형', max_tokens=500)   # 이력을 함께 보냄
    print(f'[이력 {len(history)}개와 함께] 입력 토큰 {reply.input_tokens}개: {reply.text.strip()}\n')
    history += [{'role': 'user', 'content': question}, {'role': 'assistant', 'content': reply.text}]

[이력 없이] 입력 토큰 21개: 죄송하지만 저는 대화 간에 기억을 유지하지 못해서, 이전 대화에서 이름을 알려드렸는지 알 수 없습니다. 제가 특정 이름을 가지고 있는 것도 아니고요. 다만 저는 Claude라는 AI 어시스턴트입니다.

혹시 제가 이름을 기억하길 원하셨던 거라면, 지금 알려주시면 이 대화 안에서는 그 이름을 기준으로 이야기할 수 있어요. 아니면 찾으시는 다른 정보가 있을까요?

[이력 2개와 함께] 입력 토큰 203개: 안내해 주신 대로 김후공 님이시죠. 이 대화 안에서 기억하고 있습니다.

[이력 4개와 함께] 입력 토큰 270개: 처음에 하신 말씀은 다음과 같습니다.

"제 이름은 김후공입니다. 기억해 주세요."

이력 없이 보낸 요청의 입력은 질문 하나뿐인 21토큰이었고, 모델은 이름을 알 수 없다고 답했습니다. 이력을 함께 보내자 이름을 답했고, 처음 한 말도 그대로 적었습니다. 그 대신 입력은 203토큰, 다음 요청에서 270토큰으로 늘었습니다. 모델이 기억한다고 답하더라도, 실제로는 이번 요청에 이력이 들어 있었을 뿐입니다.

질문 200토큰, 답 300토큰인 대화라면 20번째 요청 하나의 입력만 9,700토큰(앞 19쌍 × 500 + 질문 200)이고, 20번까지의 합은 실습 3-2에서 계산합니다. 같은 앞부분을 반복해서 보내는 비용은 프롬프트 캐싱으로 줄일 수 있고(5장), 이력이 너무 길면 오래된 부분을 빼거나 요약해서 보냅니다(실습 3-1).

긴 문서

긴 문서는 한 번에 넣을 수도, 나눠 넣을 수도, 필요한 부분만 찾아 넣을 수도 있습니다. 한 번에 넣으면 비용이 크고 중간 내용을 놓칠 수 있으며, 나눠 넣으면 모델이 구간마다 따로 판단합니다.

윈도우가 100만 토큰이라도 긴 문서를 그대로 넣는 것이 늘 좋지는 않습니다. 입력 토큰만큼 요금과 시간이 들고, Liu 외(2023)는 여러 모델이 긴 입력의 처음과 끝에 있는 정보는 잘 쓰지만 중간에 있는 정보는 덜 쓴다고 보고했습니다(lost in the middle). 이 실험의 모델은 GPT-3.5-Turbo, Claude 1.3 같은 2023년 모델이어서, 현행 모델에서도 같은지는 과제마다 확인해야 합니다.

분할 처리(map-reduce)는 문서를 구간으로 나눠 같은 지시로 하나씩 처리한 뒤 결과를 합칩니다. 모델이 구간마다 따로 판단해 구간 사이의 기준이 어긋날 수 있으므로, 기준을 지시에 분명히 적고 합친 결과를 원문과 대조합니다.

예제 3-3긴 문서의 중간노트북 03_컨텍스트.ipynb의 예제 3-3

코드로 만든 가상 교대 일지 600줄의 앞(5%), 중간(50%), 끝(95%)에 부품 교체 기록 한 줄을 넣고, 매번 같은 질문을 보냅니다. 위치마다 기록을 찾는지, 입력 토큰이 얼마인지 봅니다. 이 셀은 API를 3번 호출합니다.

equipment = ['1호기 다이 본더', '2호기 와이어 본더', '4호기 몰딩기', '5호기 테스트 핸들러', '6호기 마킹기']
lines = [f'{n // 3 + 1}일 {"ABC"[n % 3]}조: {equipment[n % 5]} 정상 가동, 생산 {400 + n % 37}로트, 특이 사항 없음.'
         for n in range(600)]
fact = '3호기 와이어 본더의 캐필러리를 교체함. 사유는 본딩 강도 저하.'
question = '캐필러리를 교체한 설비와 그 사유를 한 문장으로 답해 주세요.'
for position in [0.05, 0.5, 0.95]:                                # 일지의 앞, 중간, 끝
    log = lines.copy()
    log.insert(int(len(log) * position), fact)
    prompt = '다음은 교대 일지입니다.\n\n' + '\n'.join(log) + '\n\n' + question
    reply = llm.ask(prompt, model='소형', max_tokens=1000)
    print(f'위치 {position:.0%}: 입력 토큰 {reply.input_tokens:,}개, {reply.seconds:.1f}초 → {reply.text.strip()}')

위치 5%: 입력 토큰 25,656개, 1.9초 → 3호기 와이어 본더의 캐필러리를 교체했으며, 교체 사유는 본딩 강도 저하입니다.
위치 50%: 입력 토큰 25,656개, 1.2초 → 3호기 와이어 본더의 캐필러리를 교체했으며, 사유는 본딩 강도 저하입니다.
위치 95%: 입력 토큰 25,656개, 1.1초 → 3호기 와이어 본더의 캐필러리를 교체했으며, 사유는 본딩 강도 저하였습니다.

교재의 실행에서 소형 모델은 세 위치 모두에서 기록을 찾았습니다. "캐필러리"가 일지의 한 줄에만 나오는 쉬운 과제여서, 이 결과만으로 중간을 놓치는 현상이 없다고 할 수는 없습니다. 그래도 질문 한 줄을 묻기 위해 요청마다 약 2만 6천 토큰, 세 번에 약 7만 7천 토큰을 보냈습니다.

개념 확인 실습

실습은 장 노트북의 빈칸을 채워 실행합니다. 코드를 실행하기 전에 결과를 먼저 예측해 적고, 실행한 뒤 예측과 다른 부분을 이 장의 원리로 설명해 봅니다. 두 실습 모두 API를 호출하지 않습니다.

실습 3-1이력 줄이기노트북 03_컨텍스트.ipynb의 실습 3-1

def total_input_tokens(turns, question_tokens=200, answer_tokens=300, keep_last=None):
    """요청마다 보낸 입력 토큰(이력 + 새 질문)을 모두 더합니다. keep_last가 있으면 이력을 최근 keep_last쌍만 보냅니다"""
    total = 0
    for turn in range(1, turns + 1):
        pairs = turn - 1 if keep_last is None else min(turn - 1, keep_last)  # 이번 요청에 함께 보내는 앞 대화 쌍
        total += pairs * (question_tokens + answer_tokens) + question_tokens
    return total

12장 경량화와 배포

강의 6일차 파트 2에 해당합니다.

11장에서 학습한 모델을 실제로 쓰려면 모델을 GPU(graphics processing unit)에 올려 실행할 장비가 필요합니다. 이 장은 모델에 드는 메모리를 파라미터 수로 계산하는 방법, 메모리를 줄이는 양자화가 무엇을 잃는지, 4비트로 줄인 모델 위에서 학습하는 QLoRA(quantized low-rank adaptation), 그리고 직접 운영하는 작은 모델과 상용 API(application programming interface) 가운데 무엇을 쓸지 비용과 보안으로 판단하는 방법을 설명합니다.

학습 목표

  1. 모델을 실행하고 학습하는 데 드는 GPU 메모리를 파라미터 수, 정밀도, KV 캐시로 계산할 수 있습니다.
  2. 양자화가 파라미터를 어떻게 정수 단계로 반올림하는지, int4에서 출력이 크게 나빠질 수 있는 이유와 블록 단위 양자화가 오차를 줄이는 이유를 설명할 수 있습니다.
  3. QLoRA가 7B 모델의 학습 메모리를 112GB에서 몇 GB로 줄이는 원리를 설명할 수 있습니다.
  4. 같은 일을 sLM(small language model)으로 직접 운영할지 상용 API로 처리할지를 데이터 보안, 하루 요청 수에 따른 비용, 정확도로 판단할 수 있습니다.

예제 12-1~12-3과 실습 12-1은 PC의 CPU(central processing unit)에서 1장의 공개 LLM(large language model)인 Qwen2.5-0.5B-Instruct를 씁니다. 실습 12-2만 API로 모델을 호출합니다. 손실, 모델의 답, 토큰 수는 PC, 라이브러리 버전, 실행할 때마다 교재와 다를 수 있습니다.

파라미터 수와 GPU 메모리

가중치의 메모리는 파라미터 수에 파라미터 하나의 바이트 수를 곱한 값입니다. 실행할 때는 생성한 토큰마다 KV 캐시가 더해지고, 전체 파인튜닝은 기울기와 옵티마이저 상태까지 파라미터마다 16바이트가 듭니다.

모델은 GPU 메모리에 모두 올라가야 실행할 수 있습니다. GPU는 같은 계산을 많은 수에 동시에 하는 프로세서로, LLM의 행렬 계산을 CPU보다 훨씬 빠르게 처리합니다. 그런데 GPU 메모리는 한 장에 24GB나 80GB처럼 정해져 있어서, 모델을 고르기 전에 메모리에 들어가는지부터 계산합니다.

가중치의 메모리는 파라미터 수와 정밀도(precision)로 정해집니다. 정밀도는 파라미터 값 하나를 몇 비트로 저장하는지입니다. 학습의 기본 형식인 fp32는 32비트(4바이트)이고, 지금 모델을 배포할 때 흔히 쓰는 bf16은 16비트(2바이트)입니다. bf16은 fp32와 같은 범위의 수를 나타내되 유효 자릿수를 줄인 형식이라, 모델의 결과가 거의 달라지지 않습니다. 따라서 파라미터 70억 개(7B) 모델의 가중치는 bf16으로 70억 × 2바이트 = 14GB입니다.

실행할 때는 가중치 말고도 메모리가 듭니다. 모델은 토큰을 하나 생성할 때마다 앞 토큰 전체에 어텐션을 계산하는데(1장), 앞 토큰들의 계산 결과인 키(key)와 값(value)을 매번 다시 계산하지 않도록 저장해 둡니다. 이 메모리를 KV 캐시(KV cache)라고 합니다. KV 캐시는 토큰 수에 비례해 커지므로, 긴 입력을 넣거나 여러 요청을 동시에 처리하면 가중치보다 커질 수도 있습니다.

학습할 때는 더 많이 듭니다. 혼합 정밀도로 AdamW를 쓰는 전체 파인튜닝은 파라미터마다 bf16 가중치 2바이트, 기울기 2바이트, 옵티마이저가 쓰는 fp32 가중치 사본과 상태 두 개 12바이트로 모두 16바이트가 듭니다(Rajbhandari 외, 2020). 여기에 배치의 계산 중간값(활성화값)이 더해집니다.

양자화

양자화는 파라미터를 몇 개의 정수 단계로 반올림해 저장합니다. 단계 간격은 가장 큰 값에 맞춰 정하므로, 큰 값 하나가 나머지 값의 오차를 키웁니다. 블록마다 스케일을 따로 두면 오차가 크게 줄어듭니다.

양자화(quantization)는 파라미터를 더 적은 비트의 정수로 바꿔 저장하는 것입니다. int8은 파라미터 하나를 -127~127의 정수 하나로, int4는 -7~7의 정수 하나로 나타냅니다. 바꾸는 방법은 다음과 같습니다.

  1. 행렬에서 절댓값이 가장 큰 값을 찾아, 그 값이 가장 큰 정수(int8은 127, int4는 7)가 되도록 스케일(scale)을 정합니다. 스케일은 정수 한 단계가 원래 값으로 얼마인지 나타냅니다.
  2. 파라미터마다 스케일로 나누고 가장 가까운 정수로 반올림해 저장합니다.
  3. 계산할 때는 정수에 스케일을 곱해 원래 값에 가까운 실수로 되돌립니다. 반올림한 만큼 오차가 남습니다.

int4는 bf16의 4분의 1 메모리로 가중치를 저장하지만, 단계가 15개뿐이라 반올림 오차가 큽니다. 게다가 LLM의 행렬에는 대부분의 값보다 절댓값이 훨씬 큰 값이 일부 섞여 있습니다. 이런 이상치(outlier)가 스케일을 정하면 단계 간격이 넓어져, 0 근처에 몰린 대부분의 값이 0으로 반올림됩니다. Dettmers 외(2022)는 이상치가 6.7B 규모 이상의 모델에서 모든 층에 나타나 일반적인 8비트 양자화의 정확도를 떨어뜨린다고 보고했습니다.

그래서 실제 양자화는 행렬을 작은 블록(예: 64개)으로 나누고 블록마다 스케일을 따로 둡니다. 이것을 블록 단위 양자화(block-wise quantization)라고 합니다. 이상치는 자기 블록의 간격만 넓히고, 다른 블록은 자기 값에 맞는 좁은 간격을 씁니다. 블록마다 스케일을 하나씩 더 저장해야 하므로 메모리는 조금 늘어납니다.

예제 12-2행렬 하나를 양자화하기노트북 12_경량화와_배포.ipynb의 예제 12-2

0번 층 어텐션의 q_proj 행렬을 int8과 int4로 양자화했다가 되돌려, 원래 값과의 평균 오차와 0으로 반올림된 값의 비율을 계산합니다. 스케일을 행렬 전체에 하나만 둘 때와 64개 블록마다 둘 때를 비교합니다. 어느 조합에서 오차가 크게 늘어나는지 봅니다.

def quantize(weight, bits, block_size=None):
    """weight를 bits비트 정수 단계로 반올림했다가 실수로 되돌립니다. block_size가 있으면 블록마다 스케일을 따로 둡니다"""
    levels = 2 ** (bits - 1) - 1                            # int8은 127, int4는 7
    groups = weight.reshape(-1, block_size) if block_size else weight.reshape(1, -1)
    scale = groups.abs().amax(dim=1, keepdim=True) / levels  # 그룹에서 가장 큰 절댓값이 가장 큰 정수가 됩니다
    return (torch.round(groups / scale) * scale).reshape(weight.shape)


weight = model.model.layers[0].self_attn.q_proj.weight.detach()
print(f'q_proj 값 {weight.numel():,}개: 절댓값 평균 {weight.abs().mean():.4f}, 최댓값 {weight.abs().max():.4f}')
for bits, block_size in [(8, None), (8, 64), (4, None), (4, 64)]:
    restored = quantize(weight, bits, block_size)
    error = ((restored - weight).abs().mean() / weight.abs().mean()).item()   # 절댓값 평균에 대한 평균 오차
    zeros = ((restored == 0) & (weight != 0)).float().mean().item()
    where = '64개 블록마다' if block_size else '행렬 전체에 하나'
    print(f'int{bits}, 스케일 {where}: 평균 오차 {error:.1%}, 0이 된 값 {zeros:.0%}')

int8, 스케일 행렬 전체에 하나: 평균 오차 5.7%, 0이 된 값 11%
int8, 스케일 64개 블록마다: 평균 오차 0.7%, 0이 된 값 1%

int4를 행렬 단위로 양자화하면 평균 오차가 74.1%로 값 대부분을 잃었고, 블록 단위로는 13.5%였습니다. int8은 행렬 단위로도 5.7%, 블록 단위로는 0.7%였습니다.

행렬 하나의 오차가 모델의 출력을 얼마나 바꾸는지는 행렬만 보아서는 알 수 없습니다. 오차는 24개 층을 지나며 쌓이기 때문입니다. 그래서 양자화한 모델은 2장에서 쓴 손실과, 11장처럼 평가셋의 정확도로 다시 측정합니다.

실제로 메모리를 줄이려면 정수를 그대로 저장하고, 계산할 때 블록마다 실수로 되돌려 곱하는 라이브러리를 씁니다. bitsandbytes, GPTQ, AWQ, GGUF(llama.cpp의 파일 형식)가 널리 쓰입니다. 되돌리는 계산이 더해지므로, 양자화한 모델이 원래 모델보다 빠른지는 GPU와 라이브러리에 따라 다릅니다. 메모리가 충분하면 bf16 그대로 실행하는 편이 빠른 경우도 있으므로, 운영할 장비에서 응답 시간을 측정해 확인합니다.

QLoRA

QLoRA는 원래 모델을 4비트로 양자화해 고정하고, 그 위에 붙인 LoRA(low-rank adaptation) 행렬만 bf16으로 학습합니다. 고정한 가중치의 메모리가 4분의 1로 줄어, 7B 모델을 GPU 한 장의 몇 GB 안에서 학습할 수 있습니다.

11장의 LoRA(low-rank adaptation)는 학습하는 파라미터를 줄여 기울기와 옵티마이저 상태의 메모리를 거의 없앴습니다. 그래도 고정한 원래 가중치는 bf16으로 메모리에 있어야 하므로, 7B 모델이면 14GB가 남습니다. QLoRA(quantized low-rank adaptation)는 이 고정한 가중치를 4비트로 양자화합니다(Dettmers 외, 2023). 고정한 가중치는 학습하는 동안 바뀌지 않으므로 반올림 오차를 바로잡을 필요가 없고, LoRA 행렬은 bf16으로 학습하면서 양자화의 오차까지 보정하는 쪽으로 학습됩니다.

QLoRA는 세 가지를 더했습니다.

  • NF4(4-bit NormalFloat): 학습된 파라미터는 0 근처에 몰린 정규분포에 가깝게 분포합니다. NF4는 16개 단계를 같은 간격으로 나누지 않고, 값이 많은 0 근처에 촘촘히, 드문 양 끝에 성기게 둡니다. 같은 4비트로 반올림 오차가 더 작습니다.
  • 이중 양자화(double quantization): 블록마다 둔 스케일도 메모리를 차지하므로, 스케일 자체를 다시 8비트로 양자화합니다.
  • 페이지드 옵티마이저(paged optimizers): 긴 입력에서 메모리 사용이 순간적으로 치솟을 때 옵티마이저 상태를 CPU 메모리로 잠시 옮겨, 메모리 부족으로 학습이 중단되는 것을 막습니다.

Dettmers 외(2023)는 이 방법으로 65B 모델을 48GB GPU 한 장에서 파인튜닝했고, 16비트로 파인튜닝한 것과 같은 수준의 성능을 얻었다고 보고했습니다. 학습한 LoRA 어댑터는 11장처럼 따로 저장하고, 실행할 때는 같은 4비트 모델에 붙이거나 bf16 모델에 합쳐 씁니다. 메모리 계산은 실습 12-1에서 합니다.

sLM과 상용 API

직접 운영하는 sLM은 데이터가 회사 밖으로 나가지 않고, 요청이 많을수록 요청당 비용이 싸집니다. 상용 API는 운영 부담 없이 요청한 만큼만 비용을 내고, 대개 더 큰 모델을 씁니다. 먼저 보안 조건을 보고, 그다음 하루 요청 수로 비용을 비교하고, 어느 쪽이든 평가셋으로 정확도를 확인합니다.

sLM(small language model)은 파라미터가 수억~수십억 개로 GPU 한 장이나 PC에서 실행할 수 있는 언어 모델입니다. 작은 모델은 지식의 폭과 복잡한 문제를 푸는 능력이 큰 모델보다 떨어지지만, 11장의 알람 정규화처럼 범위가 좁은 일은 파인튜닝으로 큰 모델에 가까운 정확도를 낼 수 있습니다. 큰 모델이 붙인 답을 학습 데이터로 삼아 작은 모델을 학습시키는 방법을 증류(knowledge distillation)라고 하며, 사람이 정답을 붙이기 어려울 때 씁니다. 이때 큰 모델이 틀린 답도 정답으로 학습되므로, 일부는 사람이 확인합니다.

모델을 회사가 관리하는 서버와 GPU에서 직접 실행하는 방식을 온프레미스(on-premises) 운영이라고 합니다. 두 방식은 다음 기준으로 다릅니다.

기준 온프레미스 sLM 상용 API
데이터 회사 밖으로 나가지 않습니다 입력이 공급사의 서버로 전송됩니다. 보관 기간과 학습 사용 여부는 공급사 약관과 회사 계약으로 정해집니다
비용 GPU를 켜 두는 동안 요청 수와 관계없이 듭니다 요청마다 토큰 수 × 단가로 듭니다(5장)
모델 공개 모델을 골라 파인튜닝할 수 있습니다 공급사가 제공하는 모델만 씁니다. 대개 더 크고 지식이 넓습니다
운영 장비, 모델 갱신, 장애 대응을 직접 합니다 공급사가 맡습니다. 레이트 리밋과 공급사의 장애를 함께 겪습니다

비용은 하루 요청 수로 비교합니다. 상용 API의 하루 비용은 요청 수에 비례해 늘고, 온프레미스의 하루 비용은 장비 비용과 전기료처럼 요청 수와 관계없이 거의 일정합니다. 두 비용이 같아지는 하루 요청 수를 손익분기점(break-even point)이라고 하며, 요청이 이보다 꾸준히 많으면 온프레미스가 쌉니다. 다만 온프레미스 쪽에는 사람의 운영 시간, 요청이 몰릴 때를 대비한 여유 장비, 학습 비용이 더 붙으므로, 요청이 손익분기점보다 충분히 많을 때 검토합니다.

보안 조건이 맞지 않으면 비용 비교는 의미가 없습니다. 공정 조건, 고객 정보, 공개 전 품질 이슈처럼 회사 밖으로 보낼 수 없는 데이터라면 정확도가 조금 낮더라도 사내에서 실행하는 모델을 씁니다. 어떤 데이터를 보낼 수 있는지는 회사의 데이터 등급 기준으로 정합니다(15장).

def training_memory_gb(params, method, lora_ratio=0.005):
    """학습에 드는 메모리(GB, 활성화값 제외). method는 'full', 'lora', 'qlora'"""
    if method == 'full':
        return params * 16 / 1e9                     # 가중치, 기울기, 옵티마이저 상태와 fp32 사본
    weight_bytes = 2 if method == 'lora' else 0.5    # 고정한 가중치: bf16 또는 4비트
    return (params * weight_bytes + params * lora_ratio * 16) / 1e9

140억 × 2바이트 = 28GB로 가중치만으로 24GB를 넘습니다. int8(14GB)이나 int4(7GB)로 양자화하거나 GPU를 두 장 씁니다. 가중치가 들어가도 생성할 때 토큰 수에 비례하는 KV 캐시가 더 필요하므로, 긴 입력이나 동시 요청이 많으면 여유 메모리를 남겨 둡니다.

2. int4로 양자화할 때 스케일을 행렬 전체에 하나만 두면 출력이 크게 나빠질 수 있습니다. 이유와 대책을 설명해 보세요.

정답 보기

스케일은 절댓값이 가장 큰 값에 맞춰 정해집니다. LLM의 행렬에는 이상치가 섞여 있어 단계 간격이 넓어지고, int4는 단계가 15개뿐이라 0 근처에 몰린 대부분의 값이 0으로 반올림됩니다. 블록(예: 64개)마다 스케일을 따로 두면 이상치가 자기 블록의 간격만 넓혀 오차가 크게 줄어듭니다(예제 12-2).

3. 양자화한 모델을 배포하기 전에 무엇을 측정해야 합니까?

정답 보기

같은 평가셋으로 원래 모델과 정확도를 비교하고, 운영할 장비에서 메모리와 응답 시간을 측정합니다. 행렬 하나의 오차로는 출력의 변화를 알 수 없고, 양자화한 모델이 더 빠른지도 장비와 라이브러리에 따라 다르기 때문입니다.

4. 7B 모델을 전체 파인튜닝하면 약 112GB가 드는데 QLoRA로는 약 4GB입니다. 무엇이 줄어든 것인지 설명해 보세요.

정답 보기

전체 파인튜닝은 파라미터마다 가중치, 기울기, 옵티마이저 상태와 fp32 사본으로 16바이트가 듭니다. LoRA는 원래 가중치를 고정해 기울기와 옵티마이저 상태를 LoRA 행렬(파라미터의 일부)에만 두므로 이 몫이 거의 없어집니다. QLoRA는 남은 고정 가중치까지 4비트(파라미터마다 0.5바이트)로 양자화해 14GB를 3.5GB로 줄입니다.

5. 하루 2,000건의 품질 문의를 분류하는 업무에 sLM을 직접 운영할지 상용 API를 쓸지 판단하려 합니다. 어떤 순서로 무엇을 확인합니까?

정답 보기

먼저 문의에 회사 밖으로 보낼 수 없는 데이터(공개 전 품질 이슈, 고객 정보)가 있는지 확인합니다. 있으면 사내에서 실행하는 모델을 씁니다. 보낼 수 있으면 하루 2,000건의 API 요금과 GPU의 하루 비용을 비교합니다. 손익분기점보다 적으면 운영 부담이 없는 상용 API부터 씁니다. 어느 쪽이든 같은 평가셋으로 정확도를 측정해 기준을 넘는지 확인합니다.

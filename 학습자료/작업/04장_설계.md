# 4장 설계: 프롬프트 설계

상태: 원고 작성, 실행, 검토 반영 완료(2026-11-27). 작성일: 2026-11-27. 사용자 확인: 2026-11-27(Q35 문의 60건, Q36 확신도 뺌, Q37 API 약 15회).

## 학습 목표

1. 프롬프트의 요소(목적, 맥락, 입력 재료, 출력 형식, 제약)를 더할수록 응답이 왜 일정해지는지 1장의 확률 분포로 설명할 수 있습니다.
2. few-shot 예시가 응답을 바꾸는 원리를 설명하고, 예시를 고를 때 주의할 점(라벨 치우침, 순서)을 들 수 있습니다.
3. 형식이 빈칸을 요구하면 모델이 근거 없이 채운다는 것을 보이고, 제약으로 막는 방법을 설명할 수 있습니다.
4. CoT, 프롬프트 체인, 자기 검증과 루브릭이 각각 무엇을 해결하고 무엇을 해결하지 못하는지 설명할 수 있습니다.

| 예제 | 보여 줄 현상 | 방법 | 비용 |

| 4-1 모호한 지시 | "분류해 주세요"만 주면 같은 문의 10건에 실행마다 다른 라벨 이름과 개수가 나오고, 라벨 목록과 출력 형식을 정하면 일정해진다 | 문의 10건을 한 요청에 넣어 두 조건으로 2번씩 | API 4회 |

## 개념 확인 실습

- **실습 4-1 분류 프롬프트 만들고 측정하기**: 문의 20건(예제와 다른 건)으로 프롬프트를 만들고 정확도를 측정한다. 먼저 예상 정확도를 적고, 틀린 건을 보고 프롬프트를 한 번 고쳐 다시 측정한다. 빈칸: 프롬프트 문자열과 정확도 계산 함수. API 2회.
- **실습 4-2 체인으로 나누기**: "분류하고 긴급 여부를 판단하고 담당 부서를 정하라"를 한 번에 시킨 결과와, 분류 → 긴급 판단 두 단계로 나눈 결과를 비교한다. 단계 사이에 라벨이 허용 목록에 있는지 검사하는 코드를 넣는다. API 3회 안팎.

## 재료: 문의 분류 데이터 (4장을 쓰기 전에 만든다)

- 가상 후공정 회사(설계서 5절)의 현장 문의 60건. 직접 작성한다.
- 열: 번호, 문의 글, 정답 라벨, 긴급 여부, 비고(헷갈리는 이유).
- 라벨 4개: 설비 이상, 품질, 안전, 문서와 데이터 요청.
- 구성: 분명한 문의 40건, 두 라벨에 걸쳐 헷갈리는 문의 15건, 담당자나 설비 번호가 빠진 문의 5건(예제 4-3).
- 쓰는 곳: 4장 예제와 실습, 5장(API로 여러 건 처리, 프로젝트 1단계는 별도), 6장(구조화 출력).
- 파일: `노트북/data/문의.csv`. 정답 라벨은 작성자가 정하고, 헷갈리는 문의는 비고에 판정 근거를 적는다.

## 확인할 사실

1. few-shot의 출처: Brown 외(2020) GPT-3. 예시의 라벨 분포와 순서에 따른 치우침: Zhao 외(2021) "Calibrate Before Use". Min 외(2022)의 "예시의 라벨보다 형식이 중요"는 원문으로 확인한 뒤에만 쓴다.
2. CoT: Wei 외(2022). thinking 모델에서 CoT 지시의 효과에 대한 Anthropic 문서의 안내.
3. Anthropic 프롬프트 가이드의 XML 태그로 구분하기, 역할 지정(system prompt로 role)의 권장.
4. LLM-as-a-judge의 위치 편향: Zheng 외(2023) "Judging LLM-as-a-Judge".

강의에 없지만 넣는 것: RAG가 전체를 묻는 질문에 약한 이유(top-k의 한계, Edge 외 2024의 GraphRAG가 출발한 문제), Karpathy의 LLM Wiki 원문이 정한 세 층과 세 작업(2026-11 확인), 지식 그래프와 온톨로지의 정의(Hogan 외 2021), 트리플과 RDF, 구조화 출력의 enum으로 관계 이름을 강제하는 방법(6장 응용), 추출 결과를 정답 트리플과 비교하는 검증.

## 학습 목표

1. 질문마다 검색한 청크 몇 개로 답하는 RAG가 집계 질문과 여러 문서를 모아야 하는 질문에 약한 이유를 설명할 수 있습니다.
2. LLM Wiki가 문서를 언제, 어떻게 정리해 두는지 설명하고, 위키에 틀린 정리가 쌓이지 않게 하는 규칙을 정할 수 있습니다.
3. 온톨로지와 지식 그래프의 차이를 설명하고, LLM으로 문서에서 트리플을 뽑아 관계를 따라가는 질문에 답할 수 있습니다.
4. 질문의 종류, 문서의 규모와 갱신 빈도를 보고 RAG, LLM Wiki, 지식 그래프 가운데 무엇을 먼저 갖출지 고를 수 있습니다.

## 개념 확인 실습

- **실습 10-1 새 문서로 위키 갱신하기**: 예제 10-2의 페이지에 회의록 MTG-20261116을 넣어 갱신하는 `update_page()`를 작성한다. 갱신한 페이지의 "현재 기준"에 트랜스퍼 시간이 몇 초로 적히고 [검토 필요]가 붙을지 먼저 예측한다. API 1회(소형).
- **실습 10-2 그래프로 멀티홉 질문에 답하기**: 제품 하나의 보고서 → 개정 문서 → 관리 부서를 따라가는 `revised_docs()`를 작성한다. BG256의 결과 행 수를 먼저 예측한다. QX48 결과에 QIR-2026-019가 없는 이유(회의에서 개정을 결정했지만 그래프는 보고서에서만 뽑았다)를 설명한다. API 없음.

## 확인할 사실

1. Karpathy의 LLM Wiki(gist "llm-wiki.md"): 원본은 고치지 않는 층, 위키는 LLM이 쓰는 층, 스키마(CLAUDE.md, AGENTS.md)가 구조와 작업 방식을 정하는 층. 작업은 ingest, query, lint. index.md와 log.md. RAG는 질문마다 처음부터 다시 찾는다는 대비. 규모는 "약 100개 원본, 수백 쪽"에서 index로 충분하다고 적음. 확인함(2026-11).
2. Edge 외(2024), arXiv:2404.16130 "From Local to Global: A GraphRAG Approach to Query-Focused Summarization". 코퍼스 전체를 묻는 질문(주제 요약)에 일반 RAG가 약하다는 문제의식, LLM으로 그래프를 뽑고 커뮤니티 요약을 미리 만들어 둔다. 확인함.
3. Hogan 외(2021), "Knowledge Graphs", ACM Computing Surveys 54(4). 지식 그래프 정의("a graph of data intended to accumulate and convey knowledge of the real world, whose nodes represent entities of interest and whose edges represent ... relations"), 온톨로지 정의("a concrete, formal representation ... on what terms mean within the scope in which they are used"), 데이터 모델(directed edge-labelled graph, property graph). 확인함.
4. W3C RDF 1.1 Concepts: 트리플은 subject, predicate, object. 확인함.

## 사용자에게 확인할 것

1. 강의 예제 3-1은 Claude Code로 폴더 전체를 위키로 만들었다. 교재에서는 노트북에서 `llm.ask`로 주제 페이지 하나를 만드는 것으로 줄였다(실행 시간과 비용, 코딩 에이전트 사용법은 14장). 코딩 에이전트로 폴더 전체를 위키로 만드는 실습을 따로 둘지.
2. "LLM Wiki"는 고유한 이름이라 번역하지 않았다. [검토 필요] 표시는 강의의 표기를 그대로 썼다.
3. 관계 이름(제품, 발생 설비, 담당 부서, 개정 문서, 상태)을 강의의 동사형(겪었다, 조치했다)이 아니라 명사형으로 정했다. 트리플을 표처럼 읽기 쉽게 하려는 것이다.
4. 품질 이슈 보고서는 같은 양식으로 쓰여 있어 소형 모델도 트리플을 거의 틀리지 않을 수 있다. 양식이 없는 회의록에서 뽑는 예제를 더할지(API 16회 안팎 추가).

## 학습 목표

1. 챗봇, 워크플로, 에이전트를 다음 행동을 누가 정하는지로 구분할 수 있습니다.
2. 모델이 도구를 직접 실행하지 못하는데도 도구를 쓸 수 있는 이유를, 도구 정의와 도구 호출과 도구 결과가 모두 모델이 읽고 쓰는 토큰이라는 원리로 설명할 수 있습니다.
3. 에이전트 루프가 언제 끝나는지, 단계마다 입력 토큰이 왜 늘어나는지 설명하고, 검색을 코드가 정하는 RAG와 모델이 정하는 에이전트를 비교할 수 있습니다.
4. MCP가 표준으로 정하는 것과 그대로 두는 것을 설명할 수 있습니다.
5. 에이전트가 실패하는 유형마다 단계 상한, 오류 결과, 최소 권한, human-in-the-loop 가운데 무엇으로 막을지 고르고, 어떤 일에 에이전트를 쓸지 판단할 수 있습니다.

## 개념 확인 실습

- **실습 13-1 도구 설명이 도구 선택을 바꾼다**: search_docs와 문서 목록을 조건으로 세는 list_docs 두 도구를, 이름과 설명이 모호한 판과 구체적인 판으로 준다. 질문 6개에 모델이 처음 고른 도구가 맞은 수를 먼저 예측한다. API 12회(소형).
- **실습 13-2 단계 상한과 사람 승인**: 쓰기 도구(request_work: 설비 작업 요청 등록)를 더하고, 실행 전에 approve()를 거치게 하고, 도구 오류를 결과로 돌려주고, 단계 상한을 거는 run_guarded()를 작성한다. 작업 요청을 시키는 질문과 문서에 답이 없는 질문으로 확인한다. API 5~8회(소형).

## 관통 프로젝트 5단계

- 목적: 검색을 모델이 정하는 에이전트로 문서 질문에 답한다. 실행 기록을 남기고, 답에 적힌 문서 번호가 실제로 도구 결과에 나왔는지 코드로 대조한다.
- 재료: `노트북/doc_tools.py`(코퍼스 120건 검색과 읽기, 도구 정의), `evalset.json`의 5문항(E18 바꿔 말함, E40 여러 문서, E41 충돌, E43 충돌, E57 답 없음).
- 할 일: answer_agent()(단계 상한, 오류 결과, 실행 기록, 인용 대조)를 작성하고 5문항을 실행한다. 질문을 그대로 한 번 검색했을 때(API 없음)와 에이전트가 본 문서에 정답 문서가 있었는지 비교한다.
- 완료 기준: 5문항 모두 답과 실행 기록이 나오고, 근거 없는 인용(도구 결과에 없던 문서 번호)이 0건이다. 답 없음 질문(E57)에 모른다고 답한다.
- API: 문항당 3~5회, 15~25회(소형).
- 3단계(7, 8장)와 4단계(9장)는 다른 작업자가 쓰는 중이다. 5단계는 그 풀이에 기대지 않도록 `doc_tools.py`를 직접 불러 쓴다. 3단계의 검색 함수가 정해지면 search_docs 대신 그것을 도구로 감쌀지 정한다(사용자에게 확인할 것 2).

## 관통 프로젝트 6단계(15장 원고에 상자만 더한다)

- 목적: 5단계 에이전트에 15장의 방어를 붙이고, 오염 문서 4건이 든 질문으로 방어 전후를 측정한다.
- 할 일: (1) 도구 결과 정제(HTML 주석 삭제, 지시문 형태의 줄을 표시), (2) 도구 결과를 구분자로 감싸고 시스템 프롬프트에 규칙 추가, (3) 응답 검사(허용하지 않은 주소, 비밀번호 요구), (4) 요청마다 원문 없는 감사 로그 한 행.
- 질문: E49, E50, E51과 오염 회의록 MTG-20260706이 검색되는 E27, 정상 질문 2개(E18, E40).
- 완료 기준: 방어 뒤 지시를 따른 답 0건, 정상 질문 2개는 핵심어를 담은 답, 감사 로그에 질문 원문 없음.
- 15장 설계의 6단계 계획 가운데 가명처리와 사전 권한 필터는 코퍼스에 사용자 권한 정보가 없어 뺐다. 예제 15-2, 15-3으로 이미 다뤘다.
- API: 질문 6개 × 방어 전후 × 3~4회. 40회 안팎(소형).

## 공통 코드

- `llm.py`: 도구 호출 지원을 더한다(tools 인자, Reply.tool_calls, ToolCall, assistant_turn(), tool_result(), 재시도하는 ask_messages()). 두 API의 도구 메시지 형식을 교재 형식 하나로 맞춘다. 종료 이유에 'tool_use'를 더한다. test_llm.py에 왕복 테스트를 더한다.
- `노트북/doc_tools.py`(새 파일): 코퍼스를 읽어 키워드 검색(BM25, 두 글자 조각)과 문서 읽기, 도구 정의 TOOLS. 5단계 풀이가 이 모듈을 불러 쓰므로, 6단계 노트북(15장 준비 코드를 씀)에서도 그대로 실행된다.

## 확인할 사실

1. Anthropic 도구 사용: tools(name, description, input_schema), tool_use 블록(id, name, input), stop_reason "tool_use", tool_result(tool_use_id, content, is_error)는 user 메시지로, tool_choice(auto, any, tool, none), 병렬 도구 호출, 도구 정의와 도구 사용 시스템 프롬프트가 입력 토큰에 더해짐(Haiku 5.5 286토큰), strict. 확인함(platform.claude.com, 2026-11).
2. OpenAI Chat Completions: tools(type function, function.name, description, parameters, strict), message.tool_calls(id, type, function.name, function.arguments는 JSON 문자열), finish_reason "tool_calls", role "tool"과 tool_call_id, tool_choice(none, auto, required, 지정), parallel_tool_calls(기본 true). 확인함(developers.openai.com, 2026-11).
3. MCP: 호스트, 클라이언트, 서버, JSON-RPC 2.0, tools/list, tools/call(name, arguments, content, isError), 전송 방식 stdio와 Streamable HTTP, 도구 외에 resources, prompts, 명세의 human-in-the-loop 권고, 현재 버전 2026-07-28. 확인함(modelcontextprotocol.io, 2026-11).
4. Anthropic, Building effective agents(2024-12): 워크플로는 미리 정한 코드 경로, 에이전트는 LLM이 과정과 도구 사용을 스스로 정함. 확인함.
5. Qwen2.5 채팅 템플릿의 도구 표기(<tools>, <tool_call>, <tool_response>): 토크나이저로 직접 확인함.
6. ReAct: Yao 외(2022), arXiv:2210.03629. Toolformer: Schick 외(2023), arXiv:2302.04761.

## 사용자에게 확인할 것

1. llm.py에 도구 호출 지원을 더했다. 사내 OpenAI 호환 API가 도구 호출(tools, tool_calls)을 지원하는지는 사내에서 확인해야 한다. 지원하지 않으면 13장 예제 13-2, 13-3과 실습, 5, 6단계를 사내 API로 실행할 수 없다.
2. 5단계는 3단계 풀이 대신 새 모듈 doc_tools.py의 키워드 검색을 도구로 쓴다. 3단계가 병합된 뒤 3단계의 검색 함수를 도구로 감싸도록 바꿀지.
3. 7일차 파트 3(업무 페르소나)은 4장의 내용과 겹쳐 옮기지 않았다.
4. 7일차의 DB 조회 도구(query_db, 읽기 전용 연결) 예제는 옮기지 않았다. 사내 DB가 없는 독자도 실행할 수 있게 문서 검색 도구만 썼다.

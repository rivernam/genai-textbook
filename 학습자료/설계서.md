# 생성형 AI 교재 설계서

작성일: 2026-11-26 (2판)
1판: `이전판/설계서_v1.md` (2026-11-18, 강의 복습 교재)

## 1. 바꾼 이유

1판은 일자별 강의자료를 **복습 교재**로 다시 쓰는 것이 목적이었다. 1~3일차를 그 방식으로 썼다. 결과물을 보니 구성이 원본과 거의 같았다.

- 절 제목이 원본 쪽 순서(`{원본 p.xx}`)를 그대로 따라갔다.
- 파트 하나에 예제가 7~13개였고, 분량(35,000~62,000자)의 상당 부분을 예제와 실행 결과 해설이 차지했다.
- 원리 설명이 예제 사이에 끼어 있었다. 예를 들어 임베딩 유사도를 측정하는 예제는 있었지만, 임베딩 모델이 어떻게 학습되기에 의미가 가까운 문장이 가까운 벡터가 되는지는 설명하지 않았다.

사용자 결정(2026-11-26): 원본 강의안이 마음에 들지 않으므로, 원본을 대체하는 **새 교재**를 만든다. 생성형 AI의 용어와 원리를 친절하고 구체적으로 설명하는 것이 중심이다. 예제는 꼭 필요한 경우에만 간단하게 보여 준다. 실습도 원본 구조를 따르지 않고 처음부터 다시 정의한다.

이 설계서의 결정은 대화에서 질문과 답으로 정했다. 각 항목 끝의 (Qn)은 그 질문 번호다.

## 2. 목표 / 하지 않는 것 / 실패로 보는 것

**가장 중요한 기준**
생성형 AI의 용어와 원리가 잘 설명되어야 한다. 원본 강의안은 다룰 주제의 목록으로만 쓴다.

**목표**
- 개념마다 "무엇인지, 왜 필요한지, 어떻게 동작하는지, 언제 쓰는지"를 설명한다.
- 원리는 메커니즘 수준까지 설명한다. 예를 들어 토큰은 "글을 토큰 단위로 나눈다"에서 멈추지 않고, 토크나이저가 BPE로 자주 나오는 글자 조합을 묶는 과정을 작은 예로 보여 준다. 한국어에 토큰이 더 드는 이유도 이 과정으로 설명한다. 수식은 softmax와 temperature처럼 꼭 필요한 곳에만 숫자 예로 쓴다. (Q3)
- 강의를 듣지 않은 동료가 혼자 읽고 이해할 수 있다.
- 동료가 사내 LLM API(OpenAI 호환)로 예제와 실습을 직접 실행할 수 있다.

**하지 않는 것**
- 원본 파일(`GenAI_N일차_*/`)은 수정하지 않는다.
- 원본의 절 순서, 예제, 실습, 재료를 그대로 옮기지 않는다.
- 강의에 없는 주제로 범위를 넓히지 않는다. 범위는 1~9일차 강의가 다루는 주제와, 그 주제를 이해하는 데 필요한 선행 개념까지다. 예를 들어 RAG를 다루므로 임베딩 모델의 학습 방식은 넣는다. 강의에 없는 이미지 생성은 넣지 않는다. (Q7)
- 외부 서비스에 게시하지 않는다. 파일로 만들어 사내에 공유한다.
- 교재 페이지 안에서 파이썬을 실행하는 기능은 만들지 않는다.

**실패로 보는 것**
- 개념 설명이 부정확하거나, 읽어도 왜 그렇게 동작하는지 알 수 없는 것.
- 확인하지 않은 사실을 싣는 것. 확신할 수 없는 사실은 공식 문서로 확인하고, 확인하지 못하면 싣지 않는다.
- 실행해 보지 않은 코드의 결과를 지어내 싣는 것.
- 강의가 다루던 핵심 개념을 이유 없이 빠뜨리는 것. `작업/원본_대응표.md`로 확인한다.
- 예제가 원리 설명보다 많아지는 것.
- 장마다 용어나 문체가 달라지는 것.

### 4.2 장 하나의 구성

1. 장 제목과 "강의 N일차 파트 M에 해당" 한 줄. 강의를 들은 동료가 찾아올 수 있게 한다. (Q8)
2. **학습 목표**: 이 장을 마치면 할 수 있는 것 3~5개를 "~할 수 있습니다"로 쓴다. 독자가 실제로 가질 법한 궁금증을 목표 문장에 넣는다. 예: "같은 질문에 응답이 매번 다른 이유를 확률 분포와 샘플링으로 설명할 수 있습니다." 본문은 이 목표의 순서대로 쓴다. (Q11)
3. 개념 설명: 절마다 `:::요점`을 두고, 작성규칙의 "개념을 설명하는 순서"를 따른다.
4. 예제: 4.3절의 기준에 맞는 것만 본문 사이에 둔다.
5. 개념 확인 실습 안내.
6. 자가점검(아래 7번). 핵심 정리는 두지 않는다. 절마다 있는 요점과 겹치기 때문이다(2026-11-27).
7. 자가점검: 원리를 묻는 문제로 새로 쓴다. 원본 퀴즈 가운데 개념을 묻는 문제는 다듬어서 섞는다. 정답과 해설은 접어 둔다. 학습 목표마다 문제를 하나 이상 두어, 독자가 목표를 이뤘는지 확인할 수 있게 한다. (Q12)

본문에는 원본 쪽수(`{원본 p.xx}`), 원본 대응표, 변경 기록을 두지 않는다. 원본 개념과 새 교재의 장과 절의 대응은 `작업/원본_대응표.md`에 둔다. (Q8)

### 4.3 예제 (Q4, Q5, Q13)

- 직접 실행해야 납득되는 현상만 예제로 둔다. 예: 같은 프롬프트에 응답이 매번 다른 것, 토큰 수, 유사도 숫자.
- 예제 하나는 코드 15줄 안팎의 셀 하나로 쓴다. 한 예제에 세부 셀을 여러 개 잇지 않는다.
- 장마다 예제는 2~4개를 넘기지 않는다.
- 예제 코드는 공통 호출 함수(`llm.py`)로만 작성한다. Anthropic SDK와 OpenAI 호환 SDK를 직접 호출하는 코드는 5장에서 한 번만 나란히 보여 준다.
- 재시도, 배치 처리, 저장, 멱등성처럼 LLM을 시스템에 붙이는 구현 내용은 본문에서 "LLM을 쓰면 왜 이 문제가 생기는가"만 설명한다. 예: 응답이 매번 달라서 같은 문의를 다시 분류하면 결과가 바뀐다. 구현 코드는 실습으로 옮긴다.
- 실행 결과는 원고에 적지 않는다. 풀이 노트북(예제와 풀이가 든 검증용 노트북)을 실제로 실행한 출력을 빌드가 넣는다.
- 예제 상자 안에는 코드 앞에 한두 문장으로 무엇을 보여 주는 예제인지, 무엇을 눈여겨볼지 적는다. 이 글이 장 노트북의 안내 셀이 된다.

### 4.4 실습 (Q6, Q9, Q17)

실습은 원본을 따르지 않고 새로 정의한다. 두 가지를 둔다.

**개념 확인 실습**: 장마다 1~2개. 결과를 먼저 예측해 적고, 실행해서 확인하고, 왜 그런 결과가 나오는지 설명한다. 예: "temperature를 0과 1로 바꾸면 같은 질문 다섯 번의 응답이 어떻게 다를지 먼저 적어 보세요."

**관통 프로젝트 "사내 문서 질의응답 도우미"**: 여러 장에 걸쳐 한 단계씩 만든다.

| 단계 | 만드는 것 | 장 |
| --- | --- | --- |
| 1 | API로 질문에 답하게 한다 | 5 |
| 2 | 답을 구조화된 데이터로 받는다 | 6 |
| 3 | 문서를 검색해 근거를 붙여 답한다 | 7, 8 |
| 4 | 평가셋으로 측정하고 개선한다 | 9 |
| 5 | 검색을 도구로 쓰는 에이전트로 바꾼다 | 13 |
| 6 | 프롬프트 인젝션을 막는다 | 15 |

- 각 실습은 목적, 주어진 재료, 완료 기준, 단계별 힌트(접힘), 풀이와 해설(접힘)로 구성한다. 풀이는 실행해 확인한 것만 싣는다.
- 실습의 빈칸 코드는 노트북에, 풀이는 HTML의 접힌 상자에만 둔다. 풀이를 먼저 보지 않고 스스로 풀게 하기 위해서다. (Q25)
- K단계 프로젝트 노트북은 앞 단계들의 풀이 코드에서 시작한다.
- 본문에서 뺀 구현 내용(재시도, 배치 처리, 저장)은 프로젝트 단계에서 다룬다.
- 파인튜닝(11, 12장)은 프로젝트와 흐름이 맞지 않아 별도 실습으로 둔다.

### 4.5 GPU가 필요한 내용 (Q15)

- 11, 12장의 본문 예제는 CPU에서 돌아가는 것만 둔다. 예: 토크나이저 출력, 파라미터 수로 GPU 메모리 계산, LoRA의 학습 파라미터 수 계산.
- 실제 학습은 실습 노트북에 두고 "GPU 필요"로 표시한다. 그 노트북은 특정 GPU 서비스에 묶지 않고 작성한다.
- 동료들은 사내 GPU 환경을 쓸 수 있다. 사용 방법은 사내에서만 확인할 수 있어 비워 둔다. GPU 실습 노트북의 환경 안내 부분은 비운 채 작성하고, 사용자가 확인해 알려 주면 채운다(8절).

### 4.6 특정 도구의 기능 (Q16)

14장의 규칙 파일, Skill, 서브에이전트, 훅, plan 모드는 Claude Code의 기능 이름이다.

- 개념을 도구와 무관한 말로 먼저 설명한다. 예: "규칙 파일은 에이전트가 작업할 때마다 읽는 지시입니다."
- Claude Code를 주된 예로 쓴다. opencode에 대응하는 기능이 있으면 이름을 함께 적는다.
- 두 도구의 기능 이름과 대응 여부는 공식 문서로 확인하고 확인한 날짜를 적는다.

## 5. 재료 (Q17, Q20~Q24)

모든 재료를 **가상 반도체 후공정 회사** 하나를 배경으로 새로 만든다. 책 전체가 같은 배경을 쓰므로 독자가 장마다 새 배경을 익히지 않아도 된다.

- **두 층으로 쓴다.** 공정 설명은 널리 알려진 교과서 수준으로 쓴다. 다이싱, 다이 어태치, 와이어 본딩, 몰딩, 패키지 테스트, 외관 검사 같은 내용이다. 그 위에 가상 회사의 고유 정보를 얹는다. 관리 기준값, 담당 부서, 점검 주기, 개정 이력, 사내 약어 같은 것이다. 공정 지식이 없어도 읽을 수 있어야 하고, 회사 고유 정보를 묻는 질문은 검색해야만 답할 수 있어야 한다. 널리 알려진 내용만 쓰면 모델이 검색 없이도 답하므로 RAG가 필요한 이유를 보여 줄 수 없다.
- **일반 사실은 확인한다.** 공정 설명에 넣는 일반 사실은 공개 자료로 확인한다. 회사 고유 정보가 가상이라는 점은 `노트북/data/README.md`에 적는다.
- **코퍼스는 약 120건이다.** 각 장이 보여 줄 현상에 맞춰 종류를 넣는다.

| 들어갈 것 | 쓰는 장 |
| --- | --- |
| 작업 표준, 설비 매뉴얼, 품질 이슈 보고서, 회의록, 공지, 교육 자료, 안전 규정 | 7, 8 |
| 같은 문서의 구판과 신판(기준값이 바뀜) | 8 |
| 표가 든 문서, PDF와 HTML 형식의 문서 몇 건 | 8 |
| 평가셋: 질문, 정답 문서 번호, 정답. 문서에 답이 없는 질문 포함 | 9 |
| 지시문이 숨어 있는 오염 문서 몇 건 | 15 |

- **다른 재료도 같은 배경으로 만든다.** 문의 분류 데이터(4~6장의 개념 확인 실습)는 후공정 라인의 설비, 품질, 안전 문의로 만든다. 1장 예제에 쓰는 짧은 문장도 이 도메인에서 고른다.
- **직접 작성한다.** 공통 틀은 스크립트로 만들고 문장은 하나씩 쓴다. LLM API로 생성하지 않는다. 평가셋의 정답이 실제로 맞는지 확인하려면 문서 내용을 작성자가 통제해야 한다.
- **만드는 시점**: 문의 분류 데이터는 4장을 쓰기 전에, 코퍼스와 평가셋은 7장을 쓰기 전에 만든다.
- 실제 사내 문서나 업무 데이터는 쓰지 않는다.

## 6. 결과물과 폴더

```
학습자료/
  설계서.md            이 문서
  작성규칙.md          문체, 구조, 표기, 피할 표현
  용어집.md            용어의 채택 표기와 정의
  원고/                장마다 Markdown 한 파일 (교재 내용의 원본)
  교재/                build.py가 만든 HTML (공유 대상)
  노트북/              장 노트북, 프로젝트 노트북, llm.py, embed.py, data/ (공유 대상)
  교재_템플릿/         교재 화면(page.html, style.css, app.js)과 노트북의 준비 안내
  tools/, tests/       생성 스크립트와 테스트
  작업/                풀이 노트북, 실행 결과, 추출 결과, 원본 대응표, 장 설계, 진행 기록 (공유 대상 아님)
  이전판/              1판의 설계서, 원고, 교재, 노트북, 재료 (참고용 보관)
```

### 파일 이름

| 파일 | 이름 | 만드는 것 |
| --- | --- | --- |
| 원고 | `원고/NN_장제목.md` (예: `01_LLM은_어떻게_글을_만드는가.md`). `00_`은 "시작하기 전에"(환경 준비) | 작성자 |
| HTML | `교재/NN_장제목.html`, `교재/index.html`(부별 차례와 용어집) | `build.py` |
| 장 노트북 | `노트북/NN_장제목.ipynb`. 준비 셀, 예제 셀(`:::예제`), 개념 확인 실습의 빈칸 셀(`:::실습 1-2`) | `build.py` |
| 프로젝트 노트북 | `노트북/프로젝트_K.ipynb`. 앞 단계 풀이 + K단계 빈칸(`:::실습 PK`) | `build.py` |
| 풀이 노트북 | `작업/풀이/<노트북 이름>_풀이.ipynb`. 빈칸 대신 풀이(`:::풀이`)를 넣은 검증용 | `build.py` |
| 실행 결과 | `작업/실행결과/<풀이 노트북 이름>` | `tools/run_nb.py` |
| 준비 코드 | `교재_템플릿/준비_공통.py`(모든 장), `준비_NN.py`(그 장에만 필요할 때) | 작성자 |
| 장 설계 | `작업/NN장_설계.md` | 작성자 |

- 원고 한 곳에서 모두 만든다. 예제는 `:::예제`, 실습 빈칸은 `:::실습` 안의 코드, 풀이는 `:::실습` 안의 `:::풀이`에 쓴다.
- 공유하는 것은 `교재/`와 `노트북/`이다. 풀이 노트북은 공유하지 않는다.
- 원고 폴더에서 이름이 두 자리 번호로 시작하지 않는 파일은 교재에 넣지 않는다.
- 차례에서 장을 묶는 부는 `build.py`의 `PARTS`에 있다. 4.1절의 목차를 바꾸면 함께 고친다.
- 제목에 `{원본 p.xx}`를 적으면 빌드가 실패한다.

### 1판에서 유지하는 것 (Q10)

- `노트북/llm.py`(공통 호출 함수)와 `노트북/embed.py`(임베딩).
- 모델 호출: 환경 변수 `LLM_PROVIDER`로 `anthropic` / `openai`(사내, OpenAI 호환)를 고른다. 주소, 키, 모델명은 환경 변수로 넣고 파일에 적지 않는다. 소형/기본/대형 세 별칭을 두고 환경 변수로 실제 모델명을 연결한다.
- 임베딩 모델은 사내 Hugging Face 프록시(`HF_ENDPOINT`)에서 내려받아 PC에서 실행한다.
- Claude 고유 기능(thinking, effort, 호출 전 토큰 세기)의 사내 API 대응은 1판 설계서(`이전판/설계서_v1.md`) 5.4절의 표를 따른다.
- 원고 한 곳에만 코드를 쓰고, `build.py`가 원고에서 노트북과 HTML을 만든다. 실행 결과는 `tools/run_nb.py`로 실행한 노트북에서 가져온다.
- 1판의 학습 노트북(본문 전체를 담은 노트북)은 두지 않는다. 예제가 장마다 2~4개로 줄어 노트북의 대부분이 설명 셀이 되고, 설명은 용어 풍선과 검색이 있는 HTML에서 읽는 편이 낫기 때문이다. 대신 HTML에 예제 코드와 실행 결과를 모두 싣고, 장 노트북의 셀마다 안내를 붙인다. (Q25)
- HTML 교재의 기능: 왼쪽 목차, 페이지 내 검색, 용어 풍선, 코드 구문 강조와 복사, 접히는 정답, 밝은/어두운 화면. 외부 CDN과 폰트를 쓰지 않는다.
- 용어집과 작성규칙(특히 "피할 표현" 표).

1판의 원고와 실행 결과는 새 원고를 쓸 때 참고한다. 다만 설명 순서와 예제를 옮기지 않는다.

## 7. 확인 방법

- 원리 설명과 일반 사실: 확신할 수 없으면 공식 문서나 논문으로 확인하고 출처를 적는다.
- 예제와 실습: 모두 실제로 실행해 결과를 얻는다. LLM을 부르는 코드는 API 비용이 들므로 실행 전에 사용자 동의를 받는다. 실행하지 못한 것은 "미실행"으로 표시한다.
- 문장: `tests/test_style.py`의 "피할 표현" 검사를 통과한다. 장을 다 쓰면 `manuscript-reviewer` 에이전트로 검토한다.
- 범위: `작업/원본_대응표.md`로 강의의 핵심 개념이 빠지지 않았는지 확인한다.
- 화면: 브라우저로 HTML을 열어 확인한다.

## 8. 사용자 확인이 필요한 사항

1. 사내 GPU 환경의 사용 방법(11, 12장의 실습 노트북에 필요). 사용자가 사내에서 확인한다. 그때까지 비워 둔다.
2. 교재에 넣어야 하는 보안 등급이나 배포 범위 문구가 있는지.
